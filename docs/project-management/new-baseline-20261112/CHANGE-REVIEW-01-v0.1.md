## 3. 明确区分缺陷、架构设计与真正需求变更

- **不改 G1 的情况**：按钮或步骤操作不顺畅；执行器未支持注册步骤；按已有设计保存工程时卡住；测试包 Enabled 已有但不能执行；标准波形采集 UI 缺少入口；已批准的设备动作还没接线。这些首先是用户体验、设计/实现或验证缺口。
- **应修订 G2/G3 的情况**：项目级 Run/子包身份模型重新定义；设备会话或异常处理公共接口改变；波形 reference 校验结构需要新公共合同；烧录由独立工具复用到生产导致运行资源分配冲突。
- **应回 G1 作定点变更的情况**：新增不同于当前已批准能力的外部测试方式、要求某种新物理刺激或独立测量成为平台必需、取消已有系统要求，或新增/替代重大用户任务。
- **应更新工位/测试工程而非平台要求的情况**：某 ECU 的测试阈值、判定脚本、标准波形、CAN ID、DBC 或烧录参数发生变化，且平台已有配置机制可表达。

变化影响链：**现场事实/用户目标 → 需求条款 → G2 接口 → G3 合同 → 代码与硬件 → 指定验证 → 分期交付**。只检查受影响的关系，其他已批准工作继续有效。

## 4. G1 的交付期限并不等于每一版必须全功能

G1 是项目最终系统能力及验证边界；V1、V2 是本项目拟采用的逐步交付批次。因此 V1 可以先保证自动测试+扫码+按适用工序烧录的真实闭环，以及完整基础运行事实，却**不能**因为暂缓正式报告 UI/统计就宣称 REQ-46/47 已完全通过。

V2 需要使用 V1 的真实 Run 数据研究可用报告，不应将漂亮报表作为第一版可采集原始证据的替代品。V1 的正式对外范围、剩余限制及发布资格仍须根据实际证据另行批准。

## 5. 对当前 G2-01 v0.1 候审稿的建议改动

1. 在 §3 **突出 A 为第一优先链**；扫码连通是 A 之后的业务集成，并非与 A 完全同优先级的并行主线。
2. 在 §3 新增 **F：独立 CanTool 参考烧录**，明确先独立实测，再接回生产 TEST，不先要求完整烧录工具塞入主 WPF。
3. 在 §3/§8 明确**波形参考获取/自动判定属于 A，专门波形分析界面属于后续 X**；参考采集可借用现有波形服务与配置入口，UI 经试用决定。
4. 在 §5～§8 以 **A/F/V1/V2/X 的业务交付依赖**组织 Gate、实测反馈、版本验收和每周收敛，不将发布版号硬映射到 G2/G3/G4。
5. 将 G2-02～06 的研究顺序改为**优先测试项目/步骤/实际运行的公共契约与用户操作**，设备控制、波形及烧录按实际依赖同步研究；不平均推进全部领域。
6. 将 `local` 当前快照作为源码事实，不以本轮审查批准源码合并、真实烧录、固件修改或 G2 Gate。

上述为**新 G2-01 v0.2 候审稿的修订依据**；现有 v0.1 不自动获得批准或被隐式改写。

## 6. 对审批与实施权限的结论

- 本审查给出“暂不修改 G1”的技术建议，**不是**对未来需求变更的自动拒绝。
- 用户本轮说“继续”，表示继续开展项目管理研究、归类、形成候审成果；不能由此认定已批准具体 PM 计划、G2 新版本、源码实现或实体烧录。
- 后续每次实测反馈先保留原始事实，由研发侧分类，不要求用户自己填大型单据。仅需求/公共合同/高风险试验达到相应决策门槛时申请确定范围批准。
