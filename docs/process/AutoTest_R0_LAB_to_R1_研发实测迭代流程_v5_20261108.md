## 0. 纠偏与当前事实

此前 v4 最大缺陷：把 D0–D3 的一次详细设计、Mock/自动测试、INTEGRATION 和 R1 收敛视作主要路线，几乎没有安排 R1 前的现场试验、协议识别、专业工具用户试用与针对观测的反复修订。对 UDS、Flash、Wave、Bench 这样的硬件关联工具，这不成立。

本次上传的 HOST ZIP：本地分支 `g4/lab-gui-r0`、HEAD `0098b9f`，包含未提交的专业功能、专业 UI 和测试。它是**源码快照**，不代表这些新增文件已经构建通过或现场验收。

代码审查抽样确认：

- `src/AutoTest.Desktop/Tools/Uds/UdsToolViewModel.cs` 当前 UI 执行源限 Mock/Replay，Physical Tx 禁用；`src/AutoTest.Specialists/Uds/UdsClient.cs` 将物理修改状态类请求拒绝。没有依据宣称“完整现场 UDS 调试完成”。
- `src/AutoTest.Specialists/Flash/ProgrammingJobCoordinator.cs` 依赖 `MockProgrammingWorkflow` 且限定 MockOnly 授权。没有真实 ECU Bootloader 端到端烧录验证；不能把它定义为真实烧录完成。
- WAVE 已有捕获、参考、Replay、比较和多个 UI 方案候选；实际数据质量、时间戳语义、DBC/共享 CAN 联动和界面效率仍须按相应条件验证。
- DEVICE 已有 WinUSB Session/调试相关源码，不能把软件构建成功等同真实 USB、CAN、IGN、夹具等联机成功。硬件输出边界继续保持。
- `docs/engineering/KNOWN_LIMITATIONS.md` 包含 V0 时点的限制，不可不加日期地当成当前全部事实；新功能必须以最新代码和验证证据另行登记。

## 1. 产品工作目标与版本定义

- **UI 目标基线**：用户选定的 `AutoTest_Prototype.html` 为总体视觉、工作台布局与工具组织目标；不是直接复用其中的浏览器模拟业务代码。全局 Shell/交互语言先定；专业页设计按现场使用反馈修订。
- **R0-LAB**：允许工具在部分配置、部分服务、Mock、Replay、限权 Physical 等状态下交付**可试用的研发验证版本**。R0-LAB 不是出厂 R1，也不是一个必须全模块同时验收的单独大 Gate。
- **R0-SPECIALIST**：某项工具的局部可操作版本（如 UDS Console Mock+只读链、Flash 镜像预检及 Mock Job、Wave Replay/判定）。可以独立构建或接入 HOST，按真实依赖选择最小联合验证。
- **R0-INTEGRATED**：共享真实工程资源、会话、数据/日志上下文的可执行联合版本，要求相关链路测试通过，不要求全项目所有专业实测完成。
- **R1-CANDIDATE**：R1 范围内的专业功能、正式 UI、稳定性、共享合同、数据持久化以及**相关必需的现场证据**齐备。真实物理行为如果仍锁定/未验证，不得将相应能力标记 R1 完成。

**R1 可以是全局产品发布版本；研发工作始终按专业功能小版本持续迭代。** 不能按“G3 一次性设计 → G4 一次性写完 → R1 最后实测”的路线执行。

## 2. 每个功能的循环生命周期（不是全工程串行阶段）

| 状态 | 活动 | 负责人 | 输出与前进条件 |
|---|---|---|---|
| A. 设计假设 | 从 G3、现有软件、原型和已知设备事实拟定首版专业交互/协议/状态机 | 专业对话；主对话审核公共边界 | 可试验设计 v0.x，公开哪些尚待现场识别；不冒称最终设计 |
| B. 实验实现 | 制作模块/联合最小可执行能力、UI、Mock/Replay、必要诊断采集 | 专业对话设计及源码；Codex 本地机械构建 | 对应专项自动测试 PASS；权限保护完备 |
| C. 提前集成 | 接入已有工程、DBC/CAN/日志、Prism 入口的必要部分 | INTEGRATION；主对话裁决合同 | 相关链路可运行；无须等待其他专业所有页面 |
| D. 现场/体验试验 | 用户可在任何成熟时间点对单工具或联合工具测试并反馈 | **用户现场操作**；专业对话接收 | 真实观察日志、操作反馈、限制与差异；失败也是有效研发发现 |
| E. 观察驱动修订 | 用实测事实修订协议假设、参数、UI、时序、安全策略、代码 | 专业对话；主对话审核跨域影响 | 受控设计 v0.x+1、源码、回归测试、影响清单 |
| F. 必要复测 | 对受到变化影响的行为专项回归，并视风险复测真实设备 | 用户现场操作；专业对话整理证据 | 问题关闭/仍待处理；非相关功能不停工 |
| G. 稳定收敛 | 对已反复验证的能力冻结对应实施设计、接口版本及 UI 细节 | 主对话 + 用户批准 | 专业能力 R1-ready，含已知限制及证据 |
| H. 全局发布 | R1 范围完整度、软件质量、联合链路、离线部署、生产语义确认 | 主对话统筹；用户批准 | R1-CANDIDATE → R1；不能由 Mock/单元测试代替相关实测 |

A→B→C→D→E→F 可以循环多次。D 可早于 C（独立专项工具可直接现场试验）；C 可早于 D（先做软件联合验证）。必要硬件观察尚未到来时，受影响的风险功能保留“未冻结”，不阻断其他无关开发。

## 4. 开发并行组织：谁写什么，什么时候集成

- **主对话（系统负责人）**：G3/R1 追踪、版本状态、跨模块合同、确切源码审查、架构裁决、设计和发布归档。真实合同必须核对最新 HOST 类和签名。
- **总体 UI 设计专项**：用户选定原型之上的全局 Shell/导航/视觉/通用交互，13 页的产品完整性；专业局部反馈交回来后，负责兼容性与视觉修订。
- **PROJECT、DEVICE、WAVE、UDS/FLASH、TEST、RECORD、SCAN、UI/BENCH 八方向**：各自专业设计假设、可实验业务与 UI、专项测试、现场反馈修正。**UDS 与 Flash 在同对话但分开记录阶段和批准**。
- **INTEGRATION**：依据现有接口及已确定合同连续接线、最小跨模块验证、Prism、依赖注入、公共 Adapter；不等所有专项实测结束。
- **Codex 本地**：精确复制/修改、Restore/Build/Test、日志和 Git，**禁止任何自主错误定位和修复**。

切片交付的对象是 **可运行、可观察、可修订的能力**，不要求每次都交整套系统或等待其他功能完成。软件检查点必须关联 commit、设计版本和测试记录；“候选已写”与“实测已过”分别登记。

## 5. 阻断条件精确到依赖，不设总工等待

- UDS 真实会话时序仍待观察 ⇒ 不阻断 Flash 的镜像解析/Mock Job/UI，也不阻断 Wave Replay。
- Flash 的真实下载/校验/恢复未验证 ⇒ 真实 Flash 功能**不得标 R1-ready**；其他专业继续。
- Wave Live 不具备可信设备时间戳 ⇒ 不阻断离线 Replay/参考比较；Live 时间质量必须诚实标注。
- Controller 的五路电压缺少观察 ⇒ 不阻断 Controller 编辑器、Mock 台架；物理 PASS 不可自动生成。
- 生产扫码体验尚待用户反馈 ⇒ 不阻断 SQLite、Test、报告业务实现；R1 出厂放行仍须达到规定的真实验证证据。
- 只有公共合同发生实质更改时，分析所有消费者并在相关链路上设置局部停止和回归。

## 6. 设计冻结策略：先全局完整，再对未知行为保持开放

- **立即冻结设计目标的范围**：R1 要有什么、13 页总体产品 UI、共享状态语义、证据区分、权限边界。不要以此等同每个底层时序已确定。
- **先设计可修改的专业初版**：参数、请求、波形比较、烧录异常/恢复 UI 都应有原型；明确哪些是试验假设。
- **实测后才冻结具有经验依赖的详细行为**：UDS ECU 具体服务矩阵/时序、Flash Seed/Key 与恢复、Wave 数据质量与容差、台架真实观测。
- **可以提前冻结纯软件确定性部分**：工程资源 ID/版本、不可变 RunSnapshot、记录索引、基础导航、多文档、Mock/Replay 隔离、日志样式和多数 CRUD。
- **用户局部审批 = 对对应对象与版本的批准**，不是给全部 R1 下完成结论。

## 7. 实测反馈进入主线的最小材料

每条反馈由对应专业对话整理：`专业能力ID / 现有源码commit / UI设计版本 / 设备/ECU配置(可脱敏) / 实验数据来源和时间质量 / 目标操作 / 预期 / 实际 / 原始Trace/截图 / 初步问题分类 / 局部修正方案 / 涉及公共合同 / 必要复测范围 / 当前限制`。用户可以只发现场观察，专业对话补齐正式缺陷卡；不要让用户填写冗长表格。

主对话只处理**跨专业和版本影响**：局部 UI 问题由原专业改并回归；改 CAN、资源、RunId 等共享语义则必须统一裁决，安排受影响链路回归。

## 8. 代码与设计工作产品存放位置

- SAEF（应在独立且适当访问控制的仓库）：批准的 G3/G4、R0 试验计划/记录、专业详细设计 v0.x、用户批准、接口变更、R1 验证追踪。不把包含固件/原理图的整个 SAEF 资料公开上传。
- HOST Git：业务源码、专业 View/VM、工具/自动化测试、接线源码、可复现发布工程。保留本地真实提交历史，候选变更通过受控工作分支/PR 集成。
- 现场原始证据：含隐私/设备细节的 Trace/大文件放受控证据区；Git 中只放审批摘要、摘要 SHA、数据来源与证据引用。

分支建议：`main`=审核过的稳定软件；`lab/integration`=已通过自动回归的最新开发集成；`feature/<专业>/<能力>`=有明确边界的候选；`lab/<专项>`=必要时保留的可执行专项试验版本；`release/r1-rc`=仅 R1 收敛阶段。名称和实际 Git 保留情况以首次迁移结果为准，不擅自覆盖历史。

## 9. 从今天起的具体并行工作和收口条件

**A：当前 HOST 先保全真实历史**：先检查远程是否已有独立 Git 历史（本次远程 main 是仅 README 的提交），再创建独立源代码导入分支，禁止强推覆盖。GitHub 现为公开；固件与 SAEF 不直接公布。

**B：首批专项试用版本可立即设计与实现**：
- DEVICE 的 USB/Passive CAN 工具；
- UDS Mock/Replay/可诊断只读链与完整请求响应界面；
- Flash Image/Profile/Mock Job 与完整可操作进度/恢复界面；
- WAVE 从真实记录 Replay 到参考比较；
- Controller→BENCH、SCAN→TEST→RECORD 的最小联合操作链。

这些是**并行起步项目**，不是 R1 已具备真实烧录的保证。

**C：用户在任何一个专项可用时实测**：专项对话接收、修订、必要复测；不需要汇总到主对话后才可以开展下一轮局部研究。但影响公共合同必须及时汇总。

**D：INTEGRATION 不停止**：把准备好的专业 UI、正式资源、服务和证据链接进统一 WPF；软件自动回归与用户现场试用各自留下独立状态。

**E：R1 候选只在相应的真实与软件双侧证据满足时创建**：全功能追踪覆盖、关键工作流 WPF 可用、目标 ECU 上必要的诊断/烧录/波形/台架实际行为已观察且缺陷复测关闭、失败不放行、离线部署与数据完整性已验证。

## 10. 尚不能宣称关闭的事项

1. 真实 ECU 所支持的 UDS 服务及响应语义；
2. 真正烧录的编程会话/Seed-Key/HEX 分段/中断恢复；
3. Wave Live 的实际时间/采样质量及判定；
4. Bench 的真实映射和物理电压观测；
5. 当前 HOST 未提交候选增量的 Windows 全量 Build/Test 和统一 WPF 人工操作状态；
6. R1 全范围的现场验证证据与生产有效性。

**结论：R1 是试验学习与工程反复修正后的产品结果，不是一次性设计和编码的起点。**
