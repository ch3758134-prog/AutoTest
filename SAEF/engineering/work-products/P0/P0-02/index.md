# P0-02｜AutoTest 生命周期、研发组织与滚动计划（M2 集中修订候审）

> SAEF v2.0 · P0-02 · **M2 内容候审，未落档、未签发 Gate、未授权编码**。直接修订本地已接受的 P0-02 v001 属于受控基线变更。本文基于用户已经明确的项目目标与台架事实；具体系统接口、源码组织和 UI 实现由 G1/G2/G3 分别承担，不在 P0 虚构。

## 一、目标、产品与资产边界

AutoTest 是一套以 ECU 研发、自动出厂测试和维护为主要使用场景的完整软硬件系统。现役台架包括 Windows PC、主控 PCB、按键 PCB、对应的两套 MCU 固件、12V/24V 电源、ECU 工装夹具及电磁阀、外部扫码枪、线束及被测 DUT；真实连接、供电分配、电气安全和板级能力的事实以 G0 证据为准。现阶段一个 PC 与一个真实 DUT，其他 ECU 型号和未来工位扩展不阻塞近期目标。

主控和按键板 PCB 在当前研发批次视为固定设计输入；如果实测证明硬件能力缺口无法通过软件解决，则通过正式 CHG 评估改板。**主控 MCU 固件、按键 MCU 固件、Windows HOST 均为持续可开发的软件资产**。目前两套现场固件保持原版用于重新实测，只是当前实施策略，不是永久禁止修改。旧 HOST `src(20261030-022559).zip` 是经过长期研究形成的技术资产，必须做逐项设计复用评估，既不强制沿用旧架构，也不丢弃其中的实现成果。

近期首个工程目标是：在现役台架上形成能够稳定 USB 连接、管理工程/DBC、编辑与执行自动测试程序、观察真实 ECU 响应及记录结果的新 HOST。生产扫码、按 DUT 编号匹配型号和烧录/测试配置、CAN 烧录、统计与追溯属于已明确的整体产品范围，按条件分阶段验证与集成。具体编号方案、烧录机制、测试判定和 UI 细节需要在工程设计、参考程序核查与真实使用中演进，不由本计划预设为已实现功能。

## 二、两个持续运行的治理维度

**阶段基线链（P0—G5）**用于控制可依赖的工程决定：

| 阶段 | 负责确定或提供 | 不要求提前关闭的内容 | 准出所需证据 |
|---|---|---|---|
| P0 工程治理 | 生命周期、权限、版本、变更、进度与质量规则 | 具体测试逻辑和 UI 详细方案 | 八项工作产品接受、治理有效、独立 Gate 决定 |
| G0 现役事实 | PCB、工装、供电、实装/固件、当前能力、历史 `src` 资产和证据限制 | 尚需新 HOST 工具才能执行的所有台架复验 | 关键事实可追踪、未知与复验责任明确 |
| G1 系统需求 | 使用场景、稳定产品要求、首批目标、质量/接口/保护要求、待探索清单 | 未试用的详细匹配/判定/交互规则 | 需求来源与验证办法，未决项无隐性架构冲突 |
| G2 总体架构 | 全系统职责、跨板卡与 HOST 合同、自动测试模型、数据、UI 视觉/交互与扩展策略 | 每个未来模块的完整文件和函数清单 | 关键接口和依赖方向可供并行详细设计 |
| G3 详细设计 | **当前被授权开发批次**的工程/文件/类/接口/状态/错误/测试合同 | 以后尚未计划实施的全部专业服务 | 每个候选工作包可直接实施、验证与回退 |
| G4 实现与集成 | 受控编码、构建、模块/契约/实机验证、反馈修正 | 将所有未来能力一次实现 | 每条能力具备对应级别的真实执行证据 |
| G5 系统验证与发布 | 对明确范围的 H3/H4 等可用版本完成系统验证、配置和发布决议 | 全部产品长期设想 | 需求覆盖、实测、发布/回退与遗留风险结论 |

**项目运行链**从 P0 即启动，不属于某一单独 Gate：需求与问题发现 → 分类登记 → 影响分析 → 工作包排序 → 详细设计与授权 → 实施、构建及模块验证 → 集成与现场实测 → 更新需求/接口/风险/进度 → 下一轮。研究与方案比较可以提前进行，但未取得当前工作包授权不得将候选设计冒充已批准实施。

两条链相互约束而不是互相等待。G2 总体架构作为共用合同，G3 详细设计按工作包滚动。G4 的真实反馈可以触发 G1/G2/G3 的受控修订；不自动要求重走整个项目，也不允许绕过 Gate 修改已批准公共合同。每个阶段可有一次集中内容评审；与工作产品内容批准、Git 实际落档和 Gate PASS 必须严格区分。

## 三、并行开发与证据驱动迭代

### 3.1 当前执行策略

1. **先做 B0 安全、装配、供电、固件身份的现场核查**。非必要不改两套现场固件，首先取得可识别的配置和安全边界。
2. **统一设计新 HOST 的设备核心和小型台架诊断入口**，然后复验 USB、两路 CAN、IGN、夹具、按键和 ECU 闭环。B1～B6 使用真实设备、原始日志及必要的电气/物理观测；ACK 不等于动作到位。
3. 设备复验与 HOST 非硬件部分的详细设计可以并行：工程/资源/DBC、自动测试编辑与执行、UI 设计系统及组件、扫码烧录和数据记录设计共享 G2 合同。必要时使用虚拟设备或协议模拟先做独立验证。
4. 首个真实系统闭环 **H3**：工程创建和编辑、DBC、测试步骤编辑、现役硬件运行及结果记录。随后扩展为 **H4**：扫码—匹配—CAN 烧录—自动测试—追溯统计的生产流程。H3/H4 是候审里程碑，具体范围经 G1/G2/G3 进一步确认，不是已通过的验收结果。
5. 主控与按键固件若因实测需求必须修改，应建立独立工作包、板卡工程版本、烧录映像身份、接口兼容判断和硬件回归计划，然后与 HOST 验证。

### 3.2 并行工作流与同步点

- **A 设备/双固件**：USB、CAN、IGN、夹具与按键、现场诊断与驱动协议。
- **B 工程/资源/DBC**：工程文件、资源引用、配置、DBC、保存与版本迁移。
- **C 测试编辑/执行**：节点模型、流程控制、运行状态、判定、资源占用与执行记录。
- **D UI 视觉/交互**：设计 Token、控件与资源字典、布局、导航、编辑与状态反馈、研发/生产工作空间。
- **E 专业能力/追溯**：扫码输入、编号解析匹配、UDS、烧录、波形、结果与统计。

并发不等于各自发明接口。跨模块的数据类型、状态机、资源标识、USB 协议、测试节点语义及 ViewModel 命令接口在 G2/G3 的共同合同中取得一致。每批任务约定文件所有权、依赖版本、合并顺序、契约测试及冲突停止条件。Codex 只执行明确的文件和命令，不能独立选型或重构。

### 3.3 一次迭代的工作包合同

每项 `WPB-xxxx` 记录：产品目标/需求 ID、所依赖架构/接口版本、范围与不做项、允许修改的文件、输入资源、负责人、实施授权、独立测试/实测环境、预期输出和验收判据、风险、回退方式、实际状态和证据链接。

状态至少区分：`PROPOSED` → `DESIGNED` → `AUTHORIZED` → `IMPLEMENTED` → `BUILD_PASS` → `UNIT_OR_CONTRACT_PASS` → `BENCH_PASS` → `INTEGRATED` → `ACCEPTED`；不适用的验证要以 `N/A+依据` 明示，失败记 `FAILED`/`BLOCKED` 并关联问题，不以单一百分比冒充真实完成度。

## 四、持续需求、进度与基线变化

### 4.1 需求在三种成熟度下管理

- `CONFIRMED`：产品负责人已经明确的需求或有充分证据支撑的系统约束，纳入 G1 受控要求。
- `CANDIDATE`：可供比较的使用方式或技术方案，不可直接充当实现承诺。
- `TO_VALIDATE`：需要现场实测、交互试用、协议参考或数据取得后才有依据决定的问题；必须有验证方式和关闭时机，而不只是标注“以后再看”。

对于新增/修改已批准需求，先做影响分析：使用流程 → G1 要求 → G2 模块与 ICD → G3 文件和接口 → HOST/两套固件 → 测试、历史数据与发布配置。只修改受影响的合同，保留旧版本、原因、批准和回归证据。

### 4.2 单一项目总控，不重复建账

SAEF `engineering/control/` 保留 Gate、工作产品、审批和资产身份。新增的持续运行记录只保存**真实工作包、需求变动、问题和验证证据的索引**，引用原始证据文件及 Git commit，不复制整份报告或从聊天自动推定状态。总控展示同一底层数据，不另维护一张相互矛盾的完成率表。

最小视图：当前阶段/正式 Gate、当前工作包和负责人、实际构建/单测/契约/实机/集成状态、风险阻塞、需求候选/待实测、下一同步点与明确允许的执行范围。信息更新发生在实际变更或实测回传时，不把生成 HTML 当成项目进展。

### 4.3 已接受工作产品的受控修订

原工作产品的 `ACCEPTED` 字节和 `accepted_sha256` 是旧配置的真实证据，不允许直接覆盖。经负责人决定开启修订后，保存旧内容、旧登记状态、旧审批记录及 Git 身份，转入新草案；再使用 SAEF 原生 `apply → submit-review → accept-work-product` 完成新版候审和审批。若旧 Gate 已 PASS，则必须先单独批准进入 Gate 复审，保留原 Gate 决定历史；新版本不能沿用旧 Gate 的 PASS。M1 扩展候审工具只承担受控修订入口，不自动批准内容或 Gate。

## 六、M2 后续本地受控落档准则

- 上传的本地快照中 `P0-01…P0-08=ACCEPTED`，P0 Gate `NOT_REVIEWED`，`G0/G1=NOT_STARTED`。M1 工具只在隔离副本通过测试；用户电脑上是否安装并验证，尚无回执，不得视为完成。
- 一次集中**内容**评审可以覆盖 25 份候审工作产品；落档是另一类动作。P0 八项必须经 M1 的独立授权、备份、旧 SHA/Git 校验、受控开启新修订及正式 `apply/accept`。G0/G1 是新工作产品，按 SAEF 标准路径逐阶段归档。Gate 分别签审，不合并为一次伪 PASS。
- H3/H4 是可用能力目标，不是 Gate。B0～B6 重新实测是在有现场许可、可执行工具和具体测试合同之后展开的真实工作，不因为本文件规定了顺序就标记 `PASS`。
