# AutoTest｜九个专业对话统一沟通与交付指令 v1

## 发给每个专业对话的统一工作约定

请读取：
- `docs/delivery/README.md`
- `docs/delivery/01_交付协议与审批门禁.md`
- `docs/r0-lab/05_专项独立实测优先于统一集成_20261109.md`
- 自己专业在 `SAEF/engineering/` 的现行设计及已有源码/测试。

**从现在起 GitHub 是唯一正式交付中心**。你继续自主推进原本负责的专业研发，不因为 DEVICE 现场实测、其他分支未交付、用户暂未实测或 INTEGRATION 尚未集成而停工。每轮在自己专业负责的源码、WPF、日志、自动测试范围开发，将代码推到**自己负责的 GitHub 专业分支并创建/更新 Draft PR**。不要直接推 main、不要另发正式源码 ZIP、不要要求用户手工覆盖、不要要求用户在本地整合多个分支。

**各专业负责边界**：DEVICE（硬件传输/受控调试）、PROJECT（资源/DBC/Controller）、WAVE、UDS/FLASH、SCAN、TEST、RECORD、R1 UI（总体 IDE/Shell），BENCH（正式台架业务 UI）为独立 UI 子交付；INTEGRATION 仅后续负责共享 Shell/Prism 接线、项目引用、公共资源/Session/Trace 与跨模块回归。若 UI/BENCH 与 R1 UI 属于不同对话，要保持两个独立 PR，不交叉覆盖代码。

**交付 PR 应写**：CandidateId、BasedOnMainSha、当前 HeadSha、文件清单、用户能否独立运行/功能来源、启动入口、运行/错误日志和导出说明、构建/测试真实结果（未跑明确 NOT_RUN）、物理授权状态、共享依赖申请、下一项独立开发内容。主对话统一审查和审批，本地 Codex 只按主对话给的精确 commit 拉取/构建/启动并供用户操作；本地不审查 Git、代码差异或 PR，不进行人工实测，不允许自行研究或修复错误。

- 能独立实测的 DEVICE/WAVE/UDS/Flash/PROJECT/BENCH/SCAN 能力：专业先准备真实可操作的界面和适用的测试，再由用户自行集中安排时间实测，问题在原专业对话持续闭环；`USER_LAB_PENDING` 不是其他功能停工理由。
- TEST、RECORD/报告、R1 UI：现在继续正式功能、专业 UI、自动回归与候选 PR；完整用户操作验收后置到统一 HOST 集成。
- INTEGRATION：提前核对公共接口和模块依赖，建立最小受控适配候选，**不因一个物理专项未测就停止其它不依赖的工作**；未经主对话批准不合并或改写专业业务。
- 所有分支：若有跨专业/共享代码需求，提交精确最小依赖单（文件、合同、预期/实际、日志、修改建议、验证项），由主对话指定唯一负责方；不得擅自补第二套业务或修改公共 Contracts、底层设备权限等。

## 专业对话每轮给用户的最短汇报格式

```text
Specialist / CandidateId:
PR URL:
HeadSha:
ChangedPaths:
Implemented + test additions:
Windows Build/Test: PASS | FAIL | NOT_RUN (+ evidence)
Standalone/UserLab: PASS | PENDING | NOT_APPLICABLE (+ origin)
Cross-team blockers (only real blockers):
Next independent development item:
```

**沟通路径**：专业对话 → 自己的 GitHub Draft PR / Issues；主对话 → 集中审查、审批和给 Codex 验证指令；本地 Codex → 按主对话的精确 SHA 拉取并 Build/启动/保存日志；用户实测；用户 → 在自己选定时间测真实功能，反馈仍回专业对话。专业不必等主对话回复才继续自己不依赖此审批的下一项开发，但在取得审批前不得自行合并主线。
