# 个人研发工程生命周期管理平台｜产品需求候选 V0.3

> **候选需求，不是用户批准的设计基线。** 此文档描述一个通用软件产品，不是 AutoTest 需求或 SAEF 工作产品。AutoTest 只是第一个实测项目；同一个平台必须能够管理另一个独立产品，而无需在代码中出现 AutoTest、KEY_SIM、G0～G5 等固定业务规则。
>
> 2026-11-09 依据用户对 AI 辅助工程开发、企业级设计迭代、单人操作和 V0.2 UI 的直接反馈整理。仅记录当前需求理解与设计提案，未实施功能不得标记完成。

## 1. 要解决的问题

一个人负责真实产品定义、产品取舍、系统架构、实施准入、验证与发布；AI 可以辅助研究、撰写、分析、编写代码，但 AI 的高速度也使未经确认的架构漂移、过期上下文、重复设计和工作包冲突更容易发生。

现有工具的失效模式：
- 任务看板缺少产品全貌与跨层级设计；
- 文档库能存资料，却不让负责人看到一个能力的要求、分配、设计、实现与验证关系；
- 一次性 Gate 流水线不能自然支持开发后回到需求/系统架构；
- 为 AI 拼接历史上下文时混入不同版本、未批准想法和过时测试结论；
- UI 只有文件名、哈希和状态码，无法让人评价方案并作出决策；
- 特定硬件案例绑进产品模型，造成每新增一种项目就需要重新编码管理平台。

## 2. 使用者与责任

**主用户**：单人产品/系统负责人，负责浏览完整背景、提出和评审需求、技术取舍、变更、批准基线、控制实施和验证结论。单人不表示可以让所有审批自动通过。

**协作者**：AI 研究/设计/编码助手。AI 可提出结构化候选、分析变更影响、索引证据和生成工作包；不得自行把建议或代码提交提升为已批准产品需求或已验收能力。

**运行约束**：Windows 本地离线优先；无强制外部账号、多用户系统或云数据库；项目数据可在 Git 中独立版本化、备份和恢复；软件更新与具体项目数据隔离；保留可扩展空间但不强行复制企业人事、财务、工时系统。

## 3. 产品概念模型

采用 **Workspace → Product / Project → Product Version / Variant → System Element / Capability → Requirement / Architecture / Interface / Detailed Design → Work Package → Code / Verification → Release** 的结构化关系，外加全域的 Decision / Risk / Finding / Change / Experiment / Evidence / Baseline。

**区分概念而不混成一棵任务树：**
- **产品**：要交付什么，使用背景、角色、约束、配置/型号和发布版本；
- **项目**：为了交付某个产品版本开展的工程活动、范围、里程碑和资源约束；
- **系统层次结构（PBS）**：系统、子系统、硬件/固件/软件组件与外部接口；
- **功能/能力结构**：用户能做什么、场景与可验证行为，允许同一功能横跨多个系统元素；
- **需求分解**：来源需求 → 系统需求 → 分配后的子系统/软硬件要求；用明确链接管理，不机械以文件层级替代；
- **架构与设计**：总体架构、逻辑/物理分配、接口契约、运行行为、详细设计；必须能同时读叙述、结构字段与图；
- **实施活动（WBS）**：工作包、依赖、计划、实施记录；不等价于需求或架构；
- **验证与确认（V&V）**：需求与具体版本的测试规格、执行记录、原始证据、实物/软件等级与适用条件；
- **治理对象**：技术方案/ADR、问题、风险、变更、基线与审批，全生命周期可用。

## 5. 关键工作流与人机职责

### A. 人从产品需求展开设计
1. 打开一个产品版本，阅读其背景、目标用户、使用场景、范围与硬件/软件约束；
2. 在能力树定位一个能力，新增/修订需求并选择来源与验证标准；
3. 在系统架构视图分配责任与接口；逐层细化至子系统、详细设计；
4. 查看架构评审待办（接口冲突、设计缺口、风险和方案取舍）；
5. 人批准特定设计修订，形成可引用的基线；
6. 按批准设计生成实施工作包和 AI 上下文，代码与测试反馈至同一产品能力。

### B. 从 L6 反馈返回任意上层
1. 选择失败测试、源代码发现或实体实验记录，创建 Finding，记录适用产品/型号/源码/设备版本与证据；
2. 在需求—架构—设计—实现—验证关系图中追踪潜在影响，分别给 `review_required / affected / unaffected` 结论；
3. 负责人决定继续实验、修订要求、替换架构、局部设计改动或保持现状；
4. 系统保留旧批准版本和验证证据，生成新设计修订和针对受影响对象的工作包；
5. 新版接受测试通过后，更新当前基线；其余无关工作包不被无差别冻结。

### C. 项目经理/负责人日常管理
1. 打开研发驾驶舱：最近修改、待审批技术决定、需要验证的假设、严重风险、即将到期里程碑、实际阻塞；
2. 点击事项直接看到背景、证据、备选方案、影响和下一步动作，而不是孤立的状态码；
3. 选择版本/里程碑，查看系统能力地图，区分需求明确度、设计成熟度、实现、验证四条轴；
4. 审核单个工程对象的批准或退回操作，并查看影响范围；按风险、项目优先级安排下一轮探索与实施。

### D. AI 编码上下文
1. 人选择工作包和适用配置；
2. 系统沿已批准关系收集上游背景与确定设计，提示缺少的批准、陈旧依赖、接口冲突和未证实事实；
3. 生成给 AI 的可读说明与机器可读 manifest，均附对象修订、文件路径、哈希/ Git SHA、限制、验收合同；
4. AI 产生代码/测试与新的发现；系统导入结果并跟踪实施和验证，决策始终由负责人确认。

## 6. 信息架构（候选）

- **项目/产品选择器**：产品、项目、目标型号/版本、当前设计基线、源码基线。
- **项目驾驶舱**：产品全貌 / 关键决定 / 风险阻塞 / 研发进展 / 近期变更 / 下一动作。
- **产品定义**：背景、需求来源、CONOPS/场景、能力地图、范围与产品版本。
- **系统工程**：需求树、系统结构、逻辑/物理架构、详细设计、接口管理、设计评审。
- **计划与实施**：WBS/里程碑、工作包、依赖、编码准入、实际进展。
- **验证与质量**：验证计划、需求覆盖、测试用例、运行/实体实验记录、偏差与问题。
- **治理与配置**：变更、决策、风险、Gate/审批、基线对比、发布与配置身份。
- **知识档案与 AI**：资料阅读、来源索引、历史版本、跨层搜索、AI 上下文包/历史复用。

这些是人能理解的业务入口；P0/G0/G1 等流程阶段属于**可配置的项目治理模型**，不能代替产品/系统信息架构。

## 7. 页面布局：高密度、完整可读而非“指标看板”

### 驾驶舱
- 顶部：项目/产品/目标版本/设计基线，清晰说明数据截至何时；
- 首屏：产品目标与边界、功能/子系统地图及明确的“当前关键决定/阻塞/待复核”；
- 下半：最近活动、当前里程碑/工作包、验证覆盖与版本风险；
- 任意概览项点击可直接打开其详情、上下游关系和可执行操作。

### 需求与架构工作台
- 左：系统组成/能力树/需求层级导航（可切换）；
- 中：**完整而连续可读的内容**，可视化架构、设计文档、表格、关系及章节目录；
- 右：适用版本、状态、来源、上下游追踪、审查意见、影响、证据与批准动作；
- 顶：面包屑、当前配置/基线、与历史版差异；
- 编辑与查看使用同一信息结构，避免在表单中阅读数千字设计。

### 变更处理
- 左：发现/变更队列，按严重程度、产品版本、责任领域过滤；
- 中：问题描述、现场/代码证据、变更前后设计 diff 与候选方案；
- 右：影响对象及需采取的动作、审查结论和批准状态；
- 可从此一键回到任何受影响层级开始修订。

## 8. 第一版端到端验收（而非仅验证代码是否运行）

| ID | 现场可见的验收行为 |
|---|---|
| ACC-01 | 新建两个名称、对象不同的项目并独立配置流程；其中一个不存在 ECU/KEY_SIM，UI 及追踪引擎仍能工作 |
| ACC-02 | 从“产品全貌”进入一个能力，沿需求 → 总体架构 → 子系统 → 详细设计读到完整内容及来源 |
| ACC-03 | 人可在 UI 创建/修订系统要求，并看到上级来源、下级分配、待审查状态和版本 diff |
| ACC-04 | 在 UI 对一个接口/架构提出候选方案并批准其中一个修订；旧版和批准记录仍可按版本访问 |
| ACC-05 | 模拟实现后发现物理/软件局限，从 L6 形成 Finding 并回溯至 L1/L2；只标记实际受影响对象待复审 |
| ACC-06 | 工作包有明确审批与固定设计/源码版本后能生成 AI 编码说明；改变相关批准基线后，旧包收到可解释的复审提醒 |
| ACC-07 | 测试可回填至确切版本和产品配置；单测通过不能自动替代实体/用户验收 |
| ACC-08 | 在负责人驾驶舱中，能用自己的语言解释为什么某设计未准入、下一步该作什么决策、相关风险/计划影响 |
| ACC-09 | 从本地 Git/文件导入项目文档时，不把过期/未经批准的事实当作当前目标；哈希漂移可分类和逐项处理 |
| ACC-10 | 数据/软件备份、迁移、恢复后能重建对象及其审查与决策历史，且无需外部账号 |

## 9. 明确不应复制的企业负担

单人本地版不需财务、工时薪资、组织管理、多账号/角色授权、电子签章基础设施、定制 Scrum 教条。需要保留**工程纪律和决策可追溯性**，而不是复刻企业行政组织。

## 10. V0.2 试点的现实结论

现有工作台已经可以读取 55 项 SAEF 注册文档、显示一个 KEY_SIM 候选影响链并拒绝一个未批准工作包；**这只是技术可行性验证**。它没有实现 PR-01～PR-18 的通用模型、编辑、审批、项目驾驶舱和正式 AI 上下文管理。

后续产品开发不得继续把 KEY_SIM 示例数据写死为平台默认项目，也不得宣称“已读取所有文档”就等价于系统需求与架构已管理。先建立通用项目/产品/系统元素数据结构、可编辑对象和关系；AutoTest 才作为第一个数据集导入。
