# AutoTest R1｜全产品交互与界面统一约束

> 本文是产品界面设计和审查依据，不是 ECU 业务配置，也不参与运行时 AI 约束。真实设备协议、工程资源模型及测试执行条件均以对应已审批设计和源码门禁为准。

## 1. 产品交互基本原则

AutoTest 是 Windows 离线的通用 ECU 测试、工程编辑及诊断工具。用户的主要工作对象是**工程、TEST 用例与步骤、CAN 报文、DBC 报文和信号、按键动作、设备会话、ECU 实际响应、运行记录**，不是 UI 中的开发阶段代号或内部软件模块名。

- 操作入口应紧邻其作用对象。不要把“发送”藏在离发送表很远的底部，也不要让管理命令比真正的执行对象更抢眼。
- **主操作**：对象创建、执行、采集、发送、验证、查询等本场景核心任务；使用主按钮（AtPrimaryButton），每个操作组通常一个主操作。
- **次要操作**：停止、保存、复制、删除、修订、重新加载；优先使用上下文菜单、工具栏的二级组或对象右键，破坏性动作要明确，不静默清除草稿。
- **运行危险动作**：真实 CAN、KEY_SIM、IGN、夹具电磁阀、烧录必须保留现有 DEVICE/Station/工程许可、操作者授权和取消门禁。UI 不得把按钮变为默认自动执行。
- **反馈**：区分“编辑草稿”“请求已发送”“主控 ACK”“设备实际电压未知”“ECU 实际 CAN 报文”和“测试判定”，不把 ACK 说成 ECU 已响应/测试已通过。
- **默认空状态**：告诉用户此区域存放什么，以及完成目标所需的第一步；不要求先理解内部数据结构。
- **鼠标**：左键明确执行主行为或选中可编辑数据；对象右键操作必须针对鼠标所指的对象，不得错误地作用于上一次选中的对象。关键右键功能还应有可发现入口或提示。
- **键盘**：可见焦点、Ctrl+S/O/N、TEST 行操作和常用编辑快捷键保留；所有按钮允许 Tab 键访问。
- **长列表**：默认数据表支持滚动、合适列宽、更新频率与虚拟化；不会把一个对象拉伸占满可用高度。
- **多工具窗口**：保留统一工程和 Station 会话，不因为打开独立工具而新建 CAN、USB、运行上下文。独立工具窗口并非将十多个工具塞进主编辑区。

## 2. 统一组件与尺寸

统一基础定义在 `src/AutoTest.Desktop/Themes/StudioControls.xaml`。专业工具不得再各自复制一套隐式 Button/TextBox/DataGrid 控件模板。

| 组件 | 角色 | 约定 |
| --- | --- | --- |
| AtPrimaryButton | 本区域主要任务 | 适度强调；禁用与焦点清楚；禁止仅靠颜色区分行为 |
| 标准 Button | 次要/配套操作 | 同等高度/内边距；不与主操作抢注意力 |
| AtQuietButton | 管理/导航/低频 | 低对比、仍可访问 |
| AtDangerButton | 停止/清空/不可逆倾向 | 使用语义文字；真实硬件动作另有门禁 |
| AtPageTitle/AtSectionTitle | 标题体系 | 产品对象/用户任务命名，不用版本号、Gate 或临时 LAB 标识做主要标题 |
| AtHint/AtStatus | 帮助及结果 | 贴近对应任务，短句、不输出内部流水作为用户指导 |
| AtSurface/AtToolbar | 内容组织 | 面板负责分组而非平均分配空间 |
| DataGrid / TreeView | 数据对象 | 多列清楚、行高一致、可导航，不在空表格下面放跨屏远距离按钮 |

## 3. 模块任务、入口和反馈

| 位置 | 第一工作目标 | 核心交互 | 应观察的事实 |
| --- | --- | --- | --- |
| 主 Shell | 选工程与 TEST，进入任务工作区 | TEST 与工程树常驻；各专业工具独立窗口 | 当前工程 / Station / 扫码状态 |
| 工程树 | 找资源并打开对应编辑器 | 双击资源打开；重命名不影响设备 | 保存状态 / 资源修订 |
| TEST 编辑器 | 插入/修改/组织步骤 | 选择类型→插入；选中步骤右键复制/移动/删除 | 引用校验 / 草稿状态 |
| 自动测试 | 运行已确认程序 | 预检→执行→暂停/单步/停止 | StepFact / Actual / Verdict / 实物观测 |
| 手动台架左栏 | 发送真实 DUT CAN1 报文 | 从 DBC 选或创建原始帧→编辑→勾选周期发送/单发→停止 | ACK 与 ECU CAN1 广播分别显示 |
| 手动台架中栏 | 向 ECU 施加外部激励 | 左键执行工程按键动作；右键编辑、命名、复制、删除 | 当前动作/步骤/停止及实际状态未知 |
| 手动台架辅助 | 控制真实 IGN 与夹具 | 独立操作，不伪装为按键步骤 | 主控返回与物理状态区分 |
| 手动台架右栏 | 观察真实 ECU 广播 | 默认按 ID 更新；原始流水/筛选/暂停 | CAN1 实际帧与丢帧统计 |
| DBC | 建立并修改报文和信号 | 打开文件→编辑报文与信号→保存→纳入工程/发布修订 | 当前 DBC 与工程修订 |
| UDS | 诊断 ECU | 选服务→编辑请求→发送或回放→阅读响应 | NRC/响应/Trace，不能把请求构造当实机发送 |
| CAN 烧录 | 管理高风险物理编程 | 导入配置/镜像→预检→授权→实机烧录→核对 | 每阶段 ACK/UDS 结果和不确定状态 |
| 波形 | 从真实 CAN/档案采集、比较与判定 | 采集/回放→选 DBC 信号→参考/容差→比较 | 真实源、参考版本、数据质量 |
| Controller | 设置 ECU 对应的按键与五路模拟电压关系 | 控制器/状态/电压窗口分别编辑 | 逻辑开关与实际电压的区别 |
| 扫码生产 | 从编号进入实际 TEST | 连接扫码枪→识别→发布规则→执行/查看结果 | 真实条码、规则、测试事实 |
| 记录/审计 | 查事实而非执行设备 | 筛选→选择记录→查看详情→导出 | 记录来源、失败原因、Trace |

## 4. 交互评审门槛

每个可独立打开的界面在代码交付前回答：用户进来先看见什么；第一个合理操作是什么；左键/右键的动作及目标是什么；编辑草稿是否可能产生物理输出；失败后应看到什么；停止/取消后实际设备状态是否仍未知；是否要求先保存工程；用户需要的信息能否不靠内部术语解释。

自动化门禁负责 WPF 编译、可启动性、模型测试及资源结构；**真实鼠标位置、对齐、WPF 渲染和 ECU 电气响应必须由现场截图与硬件实测验收**。在这些证据缺失时，不能声明全产品 UI 已完成最终验收。

## 5. 改造范围及交付边界

本次统一设计涉及 Shell、Project Explorer、TEST 编辑与运行、手动台架、DBC、Controller、UDS、CAN Flash、Wave、Records、Operations 和 Scanner/Production，以及现有工作台/测试辅助视图。共用颜色、组件与交互词汇先落地；具体复杂界面的布局和鼠标任务流程按上述约束修改并持续接受实测反馈。候选保留 Draft PR，不擅自合并 main，不向主控自动发指令。
