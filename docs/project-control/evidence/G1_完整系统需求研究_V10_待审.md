# AutoTest｜G1 完整系统需求研究报告 V1.0（整体候审，未批准）

## 一、研究结论
依据获批准的 P0 V0.1，AutoTest 是面向不同 ECU 的可配置软硬件一体化自动测试系统。G1 研究对象是全系统应当提供的用户任务、可观察行为与验证效果，不是 CAN 单点功能方案、固定 EPB 场景、ECU 专用测试脚本或 WPF 模块清单。

**G1 研究内容已整理齐全，可提交负责人整体评审。G1 审批状态仍为未批准；本报告不批准 G2/G3 软件架构和任何编码/现场操作。**
本次范围包括真实台架与固件资产、工程资源、程序编排/调试、持续外部刺激、连续观测、DBC/波形、专业工具、执行状态、证据记录、扫码生产演进、质量与安全。近期优先实现真实 ECU 自动测试闭环，属于实现顺序，不缩减产品身份。

## 二、研究来源和可信度
- **负责人已确认**：P0 V0.1 整体批准；通用测试行为模型；软硬件系统而非只有上位机；主控两路 CAN 分别接 ECU 与 KEY_SIM、USB 接 PC、主控控制 IGN 和电磁阀，扫码枪接 PC、KEY_SIM 已连 DUT；两套 MCU 固件当前暂冻但属于系统源资产；CanTool、历史 src、板卡原理图是真实研究资产；持续周期 CAN 环境/运行中局部信号变化；波形（来自 ECU CAN 调试报文）是首个真实闭环的判定能力；不以静态/熄火驻车等 EPB 案例限定产品。
- **成熟产品证据**：ecu.test 2026.3 Project/Package/Parameters、TCF/TBC、Local/Global/Parameterized Mapping、Stimulus、Signal Recording/Trace Analysis、交互执行/Debugger、Report；Vector vTESTstudio 多种测试编辑方式与参数化、CANoe 剩余总线/仿真/测量协同；ASAM XIL 测试与台架解耦接口思路。可借鉴功能关系，不照搬配置文件、模块层数、授权模型或 UI。
- **历史设计与代码**：SAEF G1-01～08（旧 46 条候审要求）、G2-01/03/04/05/06/07、G3-03/04、main TEST 实现、TEST PR#10、UI PR#27。其事实层级分别是历史方案、存在的源码、软件候选，并不等于本次正式批准或完整实体执行成功。

## 三、完整工作活动（不是固定 8 步测试流程）
工程师在同一 HOST 中准备/编辑/保存工程，选择适用 ECU 的参数/资源、信号定义和台架能力；编排可复用测试程序（准备/测试/清理、条件/等待/循环/变量/子程序/异常）；根据程序运行背景刺激、实际动作并持续观察；使用原始报文、DBC 解码信号、时间序列与波形判定得到结果；调试、复测、保存 Run 的每次证据。CAN/DBC、UDS、烧录、Wave、手动台架作为独立可用的专业工具，也可按其条件服务统一测试流程。实际活动可持续、交叠或按事件触发，不要求全部依照固定页面顺序进行。

## 四、可审的 G1 系统需求基线候选
以下是**系统行为**，不是组件/类/配置文件方案。分为 C 已由负责人明确/已批准 P0 所支持的意图；R 基于旧研究和成熟实践建议在 G1 确认；V 条件/数值需下一阶段实测而不虚构。

### A. 完整系统与工程资源
G1-SYS-01 [C] 系统包含真实上位机、主控/按键板及 MCU 固件、夹具及必要外设；ECU 是 DUT，固件当前暂时冻结。
G1-SYS-02 [C] Windows 单 PC、单工位、当前单 DUT、完全离线为近期实物运行前提；多 DUT/新硬件作为后续扩展，不能束缚通用能力。
G1-ENG-01 [C] 用户能新建、打开、编辑、保存与重开测试工程和测试程序，资源依赖与错误可见。
G1-ENG-02 [C] 测试逻辑对不同 ECU 型号可配置、可复用；具体 CAN ID、DBC 信号、按键识别和波形阈值不得写死在通用系统中。
G1-ENG-03 [R] 工程能协调测试程序、参数、DBC、台架能力、适用的波形/烧录等资源，并指示引用缺失、冲突或版本变化；不规定究竟拆成几个文件/配置层。
G1-ENG-04 [R] 运行一旦开始，本次使用的程序/资源/配置身份清晰可核，编辑中的修改不悄然改变已启动的结果解释。

### B. 测试程序与交互
G1-AUTH-01 [C] 使用图形界面组织、修改、撤销、保存、重开可执行测试程序，而非要求工程师修改 C#。
G1-AUTH-02 [C] 一套统一程序模型支持准备/测试/清理、顺序、条件/IF-ELSE、SWITCH、WHEN/等待、循环、变量、子程序、异常及必要的步骤判定；首个实物闭环无需所有高级节点先一次完成。
G1-AUTH-03 [C] 支持运行、停止、查看活动步骤、预期/实际、单步/断点/运行到等必要调试体验；不可中断动作的实际停止时机不能虚构。
G1-AUTH-04 [R] 测试编辑、编译检查、执行和显示应表达一致的步骤含义；未满足资源/前置条件应给出准确原因。
G1-AUTH-05 [R] 支持程序复用/参数化及编辑中的局部定位，以便一个动作/判据在多个测试中使用；不强制采用 ecu.test Package/TBC/TCF 层次。

### C. 刺激、观测与判定
G1-STIM-01 [C] 可通过现有主控 USB 控制适用的 CAN 收发、IGN、夹具电磁阀以及 KEY_SIM 按键模拟；不把 20 开关等同为 20 路独立 ECU 逻辑输入。
G1-STIM-02 [C] CAN 环境支持多个不同报文周期持续发送；测试中修改同一 CAN ID 的所需数据信号，保持其他报文正常周期发送。无需先决定“每用例一个 CAN 环境文件”。
G1-STIM-03 [C] 持续环境、离散动作、持续观测、条件判断在一次真实测试中可存在重叠时间关系；程序能在需要时控制刺激及采集的启停。
G1-STIM-04 [R] 应能描述/观察动作请求、设备应答、持续状态以及出错/结束时的受控处理；未被物理验证的输出仍可处于未知。
G1-OBS-01 [C] 接收并展示 DUT 的真实 CAN 广播/收发日志；DBC 信号定义能支持报文解析、信号显示、测试判断及用户所需的 CAN 编辑。
G1-OBS-02 [C] 支持测试过程的连续信号记录与波形查看；首个实体自动测试闭环必须可使用 ECU 广播调试信号的时间序列判定。
G1-OBS-03 [C] 判定是可配置的状态、数值、响应时间、波形特征/参考容差及期望无动作等，不内建 EPB 驻车/释放规则。
G1-OBS-04 [R] 判据应使用来源明确的有效数据；无报文、缺帧、无效/断连与有效零值不能相互替代，ECU 自报电流不冒充独立外部测量。
G1-OBS-05 [R] 既能通过在线观测参与 WHEN/IF/等待等流程判断，也能对所采集的一段波形进行评价；相同记录能否重新分析由后续设计在保留旧 Run 原始判定的前提下实现。

### D. 执行、异常、专业工具与结果
G1-RUN-01 [C] 用户可以在统一工作环境中执行和调试测试程序，实时看到动作/观测/判定和总运行状态。
G1-RUN-02 [R] 设备断连、操作超时、持续刺激未知、参考资料缺失、波形数据不足、写盘失败均有可解释状态，不能默认为 PASS。
G1-RUN-03 [C] 保存每次运行的步骤、实际观测、结果和必要日志；重测不覆盖此前结果，测试次数与不同 DUT 件数分开。
G1-RUN-04 [R] 运行事实应能关联本次实际程序/资源版本、刺激与采集时间、证据源、波形判据与 Verdict，能够追踪未完整归档。
G1-TOOL-01 [C] 独立手动台架支持必要的 IGN/KEY_SIM/CAN 控制与 CAN 监视，为测试程序开发及日常检查服务，不强制进入自动测试流程。
G1-TOOL-02 [C] CAN/DBC、Wave、UDS、Flash 等是实际使用工具，既可独立操作又可按适用条件参与测试；以后可以扩展其他工具，不允许各工具复制实现一套测试程序引擎。
G1-TOOL-03 [R] 自动测试与手动工具不得无序争用相同真实设备输出；共用观察源必须不互抢数据。
G1-PROD-01 [C] 扫码枪直连 PC 获取既有 DUT 编号；系统可在后续通过可编辑规则关联型号/资源/测试并追溯，但不负责发明或制作实体码。
G1-PROD-02 [C/R] 后续生产流程可组合扫码、正确资源匹配、受控刷写、测试与统计；具体先后、权限、烧录策略、扫码格式暂未确定，**不得阻塞首个真实自动测试闭环**。

### E. 质量与系统约束
G1-Q-01 [C] 实际 R1 工位离线可用，不以外网、云服务或远程鉴权作为设备测试前置。
G1-Q-02 [R] 物理刺激、CAN RX、DBC 解码和波形记录具备可追踪时间信息和采集质量；时延、波形精度、帧损失阈值必须在具体能力实施与实验后确定。
G1-Q-03 [R] CAN/IGN/夹具/KEY_SIM 等真实输出必须区分请求、ACK、ECU 自报数据和独立外部观察，不以“设备已应答”代替物理动作完成。
G1-Q-04 [R] 程序及资源损坏/版本不符、连接中断、停止和清理失败要明确提示；不因 UI 关闭或消息缺失而自动宣称设备已复位。
G1-Q-05 [C/R] 测试编辑/运行/日志 UI 可操作、可解释、可调试；交互层级应与工程师真实任务匹配。具体 Dock、窗口、字体与视觉规范属于后续设计。
G1-Q-06 [C/R] 主控/KEY_SIM 固件与 HOST 是可维护工程资产；固件当前冻结修改，未来变更须基于影响与验证。CanTool 和历史 src 是参考资产，不能直接成为新架构约束。

## 五、整体任务关系及追踪
用户不是“分别操作 35 个功能模块”，而是在工程中完成**配置→编排→运行→观察与分析→判定→结果复核**。以上行为可重叠发生，不能被软件 UI 的页面划分绑死。核心必需关联：
(1) 工程资源引用 ↔ 程序及适用 DUT/台架；
(2) 持续刺激 ↔ 程序控制 ↔ 实际动作时刻；
(3) 原始 CAN ↔ DBC 解析 ↔ 波形时间序列；
(4) 在线等待/判断与波形比较 ↔ 同一次 Run；
(5) Run 数据与版本 ↔ Verdict、异常及记录提交；
(6) 独立工具与自动测试 ↔ 同一真实硬件/观测能力，适用时仲裁操作。

## 六、首个完整真实自动测试闭环：未来验收，不是硬件现已完成
必须在**同一个可明确追溯的真实 ECU 运行**中提供以下证据，不能将互不相关的组件演示或 Mock 测试相加冒充：
V01 用户编辑并保存/重开工程与程序，步骤与 DBC/资源引用有效；
V02 真实 CAN 环境周期发送且运行中部分信号更新，其余正常继续；
V03 实际对 DUT 施加经允许的 IGN/KEY_SIM 等适用刺激，设备应答和物理事实分开；
V04 收到 DUT 的真实 CAN，连续解析至少一组相关信号形成波形和时间关系；
V05 依据可配置规则给出波形或时序判定、总体 Verdict，缺数据和明确无动作不同；
V06 界面呈现步骤、动作、观测、异常及停止/清理状态；
V07 本次 Run、资产/规则版本、CAN/波形/判据、结果能够追溯，落盘失败可见；
V08 重开、再次执行、形成独立新 Run；旧 Run 不覆盖。
全部 V01～V08 = NOT_RUN。代表性 DUT 可采用 EPB，但不得将 EPB 工况固化为通用测试程序结构。

## 七、当前代码与研究成果的真实差距
- main 的 `StepDescriptorCatalog.Builtins` 将 CanSend、CanWait、UdsRequest、WaveCapture、WaveCompare 等声明为不可执行；`RunCoordinator.StartAsync` 仍接收 MockStation，不是首条实体闭环。
- closed Draft PR #10 提供进一步 TestDocument/条件/子程序/断点/Mock 调试候选，但未接实体执行验收。
- open Draft PR #27 中有受控真实 CAN RX+DBC、KEY_SIM 动作、Live Wave 和运行归档的若干独立候选路径；能证明相关代码存在，不能据此说已实现同一 Run 下完整闭环。
- 原 G1/G2/G3 的测试文档、版本、运行证据、共享 CAN、状态/资源责任等研究可以继承其**思路**；必须废除旧“先全面完成 B0～B6 才能研究自动测试软件”的前置顺序以及不恰当的固定场景分类。
- 本轮未修改两套 MCU 固件、未运行真实 DUT、未构建 AutoTest HOST；工程管理 CI 通过不能替代软件和物理验收。

## 八、未决事项及最迟关闭时机（不阻止本次 G1 评审）
**G2 需要整体研究的设计问题**：配置/映射层次及来源优先级、工程资源复用边界、同一 CAN ID 周期发送和临时单次发送的冲突语义、刺激与采集生命周期、测试编辑与运行快照、波形参考及判据资源形式、运行在线条件与事后分析的关系、手动工具资源仲裁、UI 工作空间组织。
**G3 需要逐项合同的问题**：步骤集合/参数验证、超时/中断/清理策略、原始 CAN/采样的时间基准、DBC 缩放/单位/位序、数据质量、波形评价语义、日志/报告数据格式、设备协议匹配、真实硬件实现边界。
**定向实测才可关闭的事项**：当前固件可支持的 CAN 发送调度精度/通道角色与 KEY_SIM 输出，真实波形采样质量及基准时刻，IGN/夹具实际动作与断电行为，DUT-specific 的 CAN/DBC/判据，供电/烧录安全、扫码枪真实协议。
**后续业务而非 G1 阻断项**：ECU 条码及型号配置匹配细节、生产顺序和复测策略、真实刷写协议及恢复、未来双 DUT 扩展。
上述未知须具备责任领域和关闭方法，但不应逼迫负责人在不掌握设计方案时臆测答案。
