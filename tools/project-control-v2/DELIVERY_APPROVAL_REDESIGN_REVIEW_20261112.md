# Project Control｜交付、候审、批准与执行边界审查设计

日期：2026-11-12
对象：通用 Project Control 管理系统
状态：**待负责人审阅的 4.6 研发候选；尚未发布正式版本、尚未合并 main、尚未运行完整 Windows/CI 验收。**
变更分支：`management/project-control-delivery-review-20261112`
范围：仅 `tools/project-control-v2/`，不改 AutoTest 产品源码或任何真实项目批准。

## 1. 真实失效场景

在 AutoTest 项目管理接管过程中，AI 没有展示完整需求候审正文、没有说明具体修改、未明确请求负责人的决定，就自行在 [Issue #22](https://github.com/ch3758134-prog/AutoTest/issues/22) 写入了完整调查评论（ID 6829697824 和 6830056975），并在答复中宣布“本轮交付已写入 GitHub”。用户不知道 AI 完成什么，也没有批准候选公开，更没有批准正式 G1/项目计划。AI 把“继续调查”偷换成了“自行交付”。

该问题不是「有没有 APPROVED 字段」的单点错误，而是**完整工程成果的展示、版本审查、允许对外流转、正式批准与后续执行**没有被建模成独立的动作。

## 2. 根因与拒绝的修补方案

- 以前 `record_ai_work_report` 保存的是摘要和状态，没有完整正文、差异、风险、发布目标。
- `request_process_review` 只校验过程责任的结构充分性，但其 `REQUESTED_NOT_APPROVED` 容易被当作“负责人已收到待审稿”。
- 普通管理 UI 只有一个写入令牌，未对用户正式审阅与 AI 保存草稿做分离；GitHub 直接宽权限可以绕开任何本地指令。
- 倘若把尚未展示的候审全文直接写入 Git 跟踪的 `management.json`，现有远端同步工具会把这些草稿一起发布，造成更严重的未经许可外传。

因此拒绝：简单增加“请记得汇报”的提示词、让用户手工填新一堆审批表、在 `APPROVED` 字段前加一个勾选、把所有研究草稿都禁止保存，或让 AI 根据用户一句“继续”自行认定审阅许可。

## 3. 设计决定

选择两层数据边界：
1. **AI/团队内部准备区**：原始研究、完整候审稿可本地保存，但存放在目标项目 Git 元数据目录的 `project-control/deliveries.json`，不是 `.project-control/management.json`。保留内容 SHA-256、修订、差异、限制及拟发布位置；不随项目管理远端同步自动发布。
2. **负责人审阅区**：UI 通过独立审阅令牌读取完整候审稿，展示为何做、正文、与上一版差异、来源、仍存风险、拟发布位置和具体待决。负责人明确选择退回、暂缓或允许**当前精确版本**公开为候审稿。更改候审正文以后必须重新审阅；无默认无限期通用许可。

正式项目/需求/设计/计划/Gate 批准**不是**上述允许候审公开。它必须独立持有可复核的有效版本、范围和真实人类权限；Codex READY 及真实设备动作再单独授权。普通进度报告可以向负责人持续交流，不强制每次小修改都等待签字；但不能把内部记录称为完整成果交付。

## 4. 实现内容

| 组件 | 新行为 |
| --- | --- |
| `delivery_review.py` | 状态 DRAFT_INTERNAL → AWAITING_OWNER_REVIEW → RETURNED_FOR_REVISION / ON_HOLD / RELEASED_FOR_CANDIDATE_PUBLICATION；精确正文摘要+版本；修改自动失效许可 |
| `web_server.py` | 个人私有 Git 元数据存储、独立私有 revision CAS、服务端原子写；普通管理写入不能触发 Owner 决定 |
| `GET /api/model` | 只返回候选数量，不返回私人待审全文 |
| `GET /api/delivery-reviews` | 使用普通管理或独立审阅令牌读取完整候选 |
| `POST /api/delivery-draft-action` | 普通管理 token 可以存草稿、修稿和准备审阅，不可批准候审发布 |
| `POST /api/owner-delivery-decision` | 只能用单独审阅 token；要求本次候选 SHA、正文版本、私有存储 revision、明确阅读声明和意见 |
| `web/index.html`、`web/app.js`、`web/app.css` | 增加成果审阅导航与完整全文审查；明示“允许发布候审≠正式批准” |
| `process_control.py` | 过去的过程审查请求仅是 PREPARED_NOT_PRESENTED；AI 工作报告是 INTERNAL_REPORT_NOT_DELIVERED |
| 角色与 Skills | 明确管理 AI 必须先呈现成果及具体决定；不能直接以 GitHub 评论充当成果交付 |
| `PORTABLE_MANIFEST.json` | 候选版本 4.6，纳入新协议和校验模块 |

## 5. 安全界限与真实不足

本次提供**一个可供工程验证的本地受控路径**，不是在 ChatGPT 网页端凭 GitHub 文件就拥有跨客户端强权限控制：
- 当前 ChatGPT 网页端与用户的本地服务并无自动连接；无法从网络一侧偷取本机私有待审正文，也不能默认写入本机审阅状态。
- 本地管理/审阅令牌不同，但都位于同一个用户会话中，不属于强真人身份认证。
- 已获候审发布许可的稿件**尚无**自动连接 GitHub 发表评论／建 PR 的受控发布事务；外部公开及结果核验仍需单独实现并实测。
- AI 如继续使用带有主线写入权的 GitHub 连接，能够绕过本地流程；真正 ENFORCED 需要 GitHub Branch Rulesets/受限 GitHub App/可信发布代理。仅写协作协议不能禁止绕过。
- 私有 Git 元数据不随仓库克隆传播，应建立审阅记录的明确备份/迁移策略；不应向用户谎称跨设备已经持久共享。
- 普通 `request_process_review` 的旧历史记录仍保留，不能据此推断负责人实际看过全文。

## 6. 反例验证计划及当前结果

新增单元测试 `tests/test_delivery_review.py`（12 项）：
草稿不等于交付、缺正文/证据/差异拒绝、提交待审不代表负责人已读、普通管理角色不能做主人决定、旧版本/摘要不匹配拒绝、明确授权仅允许候审、退回和暂缓、修改候审稿后许可失效、篡改发现、重复提交不升级以及本地审阅身份层级。

新增本地真实 Git + HTTP 测试 `tests/test_delivery_review_server.py`（2 项）：
写草稿不得改变 Git 跟踪的管理 JSON、普通 GET 不泄漏全文、私有 GET 需要令牌、两个 token 在读/写/主人审阅上权限不同、允许候审也不改管理批准。

本次已静态检查前端 JS 语法，发行包 manifest 中 45 个必需文件全部在候选分支存在；**没有执行完整 Python 回归、Windows 浏览器和 GitHub 端到端操作**。因此不能称本轮验收 PASS。
