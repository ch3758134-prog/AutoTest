## 2. 已经确认的产品职责

### BIZ-01｜当前定位与工程组织
AutoTest 是完全离线的 Windows ECU 测试与开发平台，**自动测试是核心工作**；专业工具辅助它，也应能脱离自动测试完成自身专业任务。当前一台 PC、一套工位、同一时刻一台 DUT。不同 ECU 型号及硬件版本使用各自工程，不要求混放在同一工程里。EPB 是当前真实验证对象，不允许把它的测试业务判据硬编码为通用平台行为。

### BIZ-02｜测试工程、测试项目、测试用例的用户语义
- **测试工程**：当前 ECU 的工程容器，含项目、DBC、Controller 按键配置、波形/判定、烧录资料和其他资源。
- **测试项目**：有序组织多项测试用例，作为选择和执行的集合，沿用后端 `TestProjectDocument`。
- **测试用例**：编辑、保存和实际执行的基本单元，沿用底层 Package / `TestDocument`；内部可以有 **准备 / 测试 / 清理** 阶段和普通/流程控制步骤。
- 主 UI 不要再把“测试程序”与“测试用例”并列为不同用户对象，也不用以 `Package` 英文命名干扰工程师。**仅调整呈现与业务语义，不重新发明第二套 TEST DSL。**
- 准备/测试/清理的视觉层级与优先顺序归 UI 专项设计，不由项目管理规定像素和布局。

### BIZ-03｜工程师的选择性运行
在研发、调试、抽检和非完整出厂检测场景中，工程师可以在测试项目中**勾选这一次需要执行的部分测试用例**，按当前选择运行，不应强迫执行完整出厂测试流程。允许不使用扫码枪进行这些工程师测试。勾选需求不意味着后端已经实现多包运行；G3-A2 负责项目级真实调度和证据。
**设计建议而非单独确认的最终规则**：工程默认启用 `Enabled` 与当次临时选择 `RunSelection` 应分开，以免工程师抽检意外改动生产方案。

### BIZ-04｜扫码生产运行
生产模式必须提供**真实扫码入口**。扫码取得 DUT 编号，经工程/配置/身份/资源与实际硬件预检通过、满足工位运行条件后，**自动开始已配置的生产工序**；不要求操作员对每一台 DUT 再点击“开始”。
扫码不是无条件物理写入授权。连续生产模式中的连接所有权、一次性工位就绪/授权、未知状态与异常阻断由 G3 技术设计在真实硬件能力上实现，不能未经批准跳过物理安全边界。生产与工程师调试共用测试执行模型，不做两套后端；运行对象和编号在本次 Run 期间固定，复测不覆盖原始记录。

### BIZ-05｜手动台架的核心目的
手动台架是工程师**不写自动测试用例也可以直接临时调试、快速观察和排故**的综合真实工位操作工具。能操作已配置的 ECU 功能按键、IGN、夹具、电气上适用的 CAN 报文，并在同一工具里查看 CAN 日志及 DUT 实际回应。**功能按键操作是视觉和操作上的核心工作对象**，不是辅助的原始硬件菜单。

### BIZ-06｜功能按键与 KEY_SIM 的真实关系
用户操作的是按 ECU 工程配置的“驻车、释放、无操作”等功能语义（具体名称由该 ECU 的按键配置决定），而**不是 20 个原始 K01～K20 开关**。KEY_SIM 的 20 Key 是底层电阻网络组合开关，支持组合闭合和保持，最终形成五路模拟电压给 DUT 识别；由 Controller/Profile 定义的真实功能按键映射到底层开关组合，再经 CAN0 控制。
- 手动台架不以 20 路开关方阵作为日常功能界面；
- 不把 20 个开关说成 20 路独立模拟量，也不把 CAN/USB ACK 说成电压已经实测；
- 不同 ECU 的功能按键、物理组合和识别范围由各自工程配置及现场确认决定。

### BIZ-07｜手动台架的连续按键操作
手动台架需要方便地组合已配置**功能按键动作**的按下/保持/释放/等待等短序列，用于真实按键行为模拟。它不是第二套支持完整 IF/SWITCH/子程序/所有硬件动作的自动测试编排器。复杂条件与整套检测流程使用正式测试用例。

### BIZ-08｜取消独立 CAN 工具要求
**不再要求独立 CAN 工作台作为初版产品工具**。手动台架需要包括：
- CAN1 报文发送（单次/符合真实能力的周期发送、停止），可从工程内 DBC 选择报文、编辑信号值，也可按需使用原始帧；
- 实时 CAN 收发和 DUT 响应日志，以及必要的过滤、查看与诊断能力；
- 按键、IGN、夹具与 CAN 的同一真实工位观察上下文。
自动测试、UDS、烧录仍复用正确的 CAN 传输、DBC 编码解码和设备服务。**取消的是独立 CAN 窗口这一产品义务，而不是删除 CAN 的底层能力。**
这与 G1 REQ-32/33 的历史独立 CAN 工具提法有局部冲突，见 `CR-CAN-01`。

### BIZ-09｜DBC、UDS、烧录、波形都是专业能力
DBC 专业编辑器用于完整 CAN 报文和信号的定义/修改/校验；测试用例中引用 DBC 报文并填写信号值，不必另建 DBC 模型。UDS 诊断、独立 Flash Lab、波形分析等既应有脱离自动测试的专业用途，又应作为自动测试步骤调用的底层能力。所有相关模块尽可能共用同一工程资源/修订、CAN/UDS/ISO-TP、设备会话和运行证据体系；不因为专业 UI 各自独立就复制后端。专业工具窗口和主 IDE 的具体展现由 UI 专项设计与用户实测验收。

### BIZ-10｜夹具、IGN 和手动/自动控制
IGN 和夹具既能在手动台架中人工操作，也能作为**测试用例步骤**编排，允许由测试工程师根据真实业务自己确定压紧、等待、测试、释放等顺序，不硬编码单一工序。**自动测试与手动台架绝对不应同时改变同一设备输出**；所有权和状态需统一。主控 ACK、GPIO 状态与真实机械/电气结果分开，缺少独立确认时不得编造“已到位”。

### BIZ-11｜真实 DUT 主电源不属于 HOST 控制
当前 DUT 主电源由独立外部电源设备供电，**当前上位机及主控板不需要控制它**。主控板代码里的历史 `SET_ECU_PWR` 等供电命令为此前实测/开发残留，不得据此增加初版 HOST 电源开关、自动供电步骤或默认“供电控制”能力。未来固件可以在另一个获批工作包中优化，**固件源码存在命令 ≠ 当前台架实际可用/需要的软件能力**。

### BIZ-12｜失败处理、交付与 UI 协作
测试失败、错误、恢复、继续或终止等策略应参考 ecu.test 等成熟测试软件，支持**工程师可配置的灵活异常处理**，而不是由 PM 不断追问每个 ECU 应如何失败后处理，也不硬编码“失败必立即停止/必全部复位”。具体物理输出状态未知或设备断连时，必须遵循真实设备安全与已验证恢复流程。
本阶段面向真正能运行、能实测和可交付的初版：**UI 专项**负责 IDE 式视觉、操作、布局和 HTML/WPF 用户试用反馈；**PM/后端**负责系统职责、接口、G3/G4 授权与真实集成。UI 专项研究不能因项目管理反复讨论布局而被阻断，但也不能把未接线的 HTML 原型视为可用真实设备产品。
