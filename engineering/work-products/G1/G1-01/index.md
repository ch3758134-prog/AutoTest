# G1-01｜利益相关者、产品价值与阶段目标（M2 候审）

> 状态：未批准；不得把候选设计/历史实现直接当作正式系统需求。输入是负责人近期说明、P0 范围和 G0 可证事实。

## 一、产品角色与基本任务

| 角色 | 实际目标 | 不代替其确定的内容 |
|---|---|---|
| 研发测试人员 | 同一 HOST 中创建工程、DBC 与资源，配置、编辑和执行自动测试，使用 CAN/UDS/波形/设备诊断 | 每一种测试节点、信号、判定阈值、界面细节尚待设计/试用 |
| 生产检测人员 | 对不同型号、不同电压需求 ECU 完成扫码、型号匹配、烧录、自动测试、保存结果和统计 | 权限、工位提示、异常复测和码格式未实测 |
| 维护/调试人员 | 排查 USB、双 CAN、IGN、夹具、按键与 ECU 连接，定位设备/软件/配置故障 | 不得将 ACK 当机械或电气反馈 |
| 产品负责人/现场测试方 | 审批目标和重大技术取舍，操作或授权实体台架复验，按证据决定版本状态 | 不要求负责人替研发者完成全部技术方案 |
| ChatGPT + Codex 开发执行链 | ChatGPT 统一研究/接口/代码/UI；Codex 只做本地明确机械操作并提供回执 | AI 自审不等于独立现场 QA |

## 二、产品的近期可用价值

**H3：真实 ECU 可编辑自动测试闭环。** 在统一 HOST 中创建/保存工程，导入/编辑 DBC，选择设备资源和测试步骤，连接现役双板执行真实 DUT 交互，观察当前步骤、预期/实际/错误，并保存运行证据。H3 必须有真实 ECU 实测，不是 WPF 原型演示；开始阶段先将硬件通路 B0～B6 逐项复验。

**H4：生产检测闭环。** 同一 HOST 接收实物扫码编号，根据可编辑的规则匹配 DUT 型号、通信参数、烧录配置和测试程序（具体字段待试用），按出厂要求执行 CAN 烧录与测试，保存每次运行并汇总不同 DUT 数量、测试次数和结果；重复测试不得覆盖历史。H4 是后续产品能力目标，其前置的 CAN/UDS/烧录接口研究可以和 H3 并行进行。

## 三、当前约束与负责人明确立场

- 本期 1 PC / 1 DUT、现役主控/按键 PCB、12V/24V 不同型号 ECU、夹具电磁阀和外部扫码枪。当前不将新增灯/蜂鸣器、额外 PCB 或双 DUT 纳入近期实施。
- 两套 MCU 固件和新 HOST 都是持续研发资产。现役固件在初始复验阶段先保持不改，但可在后续工作包中迭代；新 HOST 重新设计，研究并利用历史 `src` 成果，不被它的旧目录/兼容约束束缚。
- 研发与生产使用**同一套 HOST**，但如何通过工作空间、权限和操作引导区分，仍是 UI/使用试验决策，不阻断设备核心开发。
- 具体扫码编号、烧录参考协议、测试判定、波形精度、UI 最终视觉及操作需要代码和实际试用反馈逐步收口，不在 G1 预先虚构。

## 四、需求成熟度与关闭机制

`CONFIRMED`：已有明确负责人意图，作为候审要求；`CANDIDATE`：工程建议或使用设想，只作为后续设计研究输入；`TO_VALIDATE`：要依据实测/使用反馈进一步确定。**任何成熟度在本包批准前均只是候审数据，批准后也不等于功能实现。**

新信息先登记、按来源分类，分析是否影响受控 G1/G2/ICD/G3/固件/记录，再给出最小变更及相关回归；不因一项 UX 调整重启全部 Gate，也不允许绕过已批准的公共合同。需求索引见 `data/requirements_reclassified.csv`，当前 46 条候审要求。
