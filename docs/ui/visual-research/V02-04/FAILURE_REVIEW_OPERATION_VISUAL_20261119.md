## 三、源码比对所揭示的实现方法问题

原型在 `UI/AutoTest.TestEditorPreview/` 中：
- `MainWindow.xaml` 约 40 KB；`MainWindow.xaml.cs` 约 43 KB：一个窗口直接容纳几乎全部布局、命令、输入、工作区响应及错误跳转。它可以启动研究原型，却没有实现真正的设计系统和分组件视觉治理。
- XAML 的 `CaseColumn=255`、`InspectorColumn=380`，步骤行内部标题列 `390`；还设定独立的 1170 DIP 响应阈值。上述固定数值来自手工设置，并非根据中文长步骤名、专业字段和不同 DPI 的真实测量。
- `BaseButton`、`PrimaryButton`、`QuietButton` 是局部按钮外观；`StepTemplate` 只是原生 ListBox 行、固定列、文字类别、Unicode 小箭头与状态文字。**这不等于有完整的步骤/分支/编辑组件**。
- `CaseSearch`、`StepSearch` 为普通 TextBox，截图证实其空值外观不自解释。WPF 原生 TextBox 不自动提供水印语义。
- `SampleData.Create()` 确实创建了 12 用例、第三用例 40 步，并把活动用例/节点设为第三用例的 T09。截图却展示第一用例（0 步）。可能是后续手动选择，也可能是界面初始化/列表选择同步，**当前没有操作时间线，不能断言根因**；但测试样本曾被设计为保障首轮高密度评审，结果没有保障真实截图出现高密度状态。
- `PreviewSelfCheck` 验证的是样本数量/树身份/JSON 往返，不能检查字体、布局、视觉层级、首次可发现性、点击路径和空态。此前“静态检查 PASS”不能推导 UI 产品质量。
- `ProblemPane` 等辅助区域、A/B 选择器和研究原型说明是为研发存在的机制；暴露于产品主工作区时需要单独评估是否占用过多注意力。原型不是正式产品，但不能借“原型”掩饰其无法检验成熟体验的缺陷。

**关键因果链**：
先确定三栏+固定宽度 → 填入原生 WPF 控件/文字命令 → 为复杂操作补 C# 事件 → 用源代码配对/静态 SVG/对比度检查宣称设计已足够成熟 → 没有先审查实际渲染与空/满两种工作状态 → 用户看到一套功能表单而不是专业编辑器。

## 四、外部成熟产品证据与真正的迁移边界

### A. TEST 产品：参考操作/工作对象组织，**不是照搬视觉皮肤**
- NI TestStand Step Settings 官方：https://www.ni.com/docs/en-US/bundle/teststand-api-ref/page/tsref/step-settings-pane.html
  明确 Step Settings 与当前选中步骤关联，包含内建、类型特定与 Module 设置；部分自定义类型仍用弹窗。可借鉴「当前对象持续参数化」，不能照搬旧界面字体/表面。
- ecu.test 2026.3 Work Window：https://docs.tracetronic.com/help/ecu.test/2026.3/en/Main-program/Editor/Test-case-editor/Work-window.html
  实际把测试内容、注释/Tag、变量映射、属性、录制、分析与报告置于相应工作区。可借鉴「编辑文档是中心，不同专业信息具有正确的上下文」，不能将其所有工作区简单复制成三栏。

### B. 现代桌面 IDE：参考空间、视觉层级、当前文档和工具窗体验，**不是照搬代码编辑器**
- JetBrains Islands：https://blog.jetbrains.com/platform/2025/09/islands-theme-the-new-look-coming-to-jetbrains-ides/
  明确重点是编辑器与工具窗更清晰的分隔、导航更突出、当前 Tab 更可识别；厂商使用两套方案的 mockup 问卷、A/B、访谈与使用统计。它的「现代」并非只是圆角。
- JetBrains 正式主题说明：https://blog.jetbrains.com/platform/2025/12/meet-the-islands-theme-the-new-default-look-for-jetbrains-ides/
  分区边界、可调节工具窗、活动标签和焦点稳定。AutoTest 必须研究怎样用文档/活动用例/步骤对象建立同样稳定的注意力路径。
- Visual Studio 2026：https://devblogs.microsoft.com/visualstudio/a-first-look-at-the-all%E2%80%91new-ux-in-visual-studio-2026/
  设置搜索、可访问对比和编辑器与应用外观独立，都表明结构与皮肤共同服务工作场景，非换色完成。

### C. 视觉与 WPF 技术：**不能把原生旧控件手写 Style 当作现代设计**
- Fluent Layout：https://fluent2.microsoft.design/layout
  间距表达语义关系、突出重要对象，而非机械增加大片白色区域。
- Microsoft WPF .NET 9 Fluent theme：https://learn.microsoft.com/en-us/dotnet/desktop/wpf/whats-new/net90
  官方已提供现代 Fluent 风格路径；WPF 架构并不注定老旧。项目目标是 .NET 10 + WPF，未来可对比原生 Fluent、成熟 WPF 组件库与独立专业控件的组合，但不能在本轮未经检验就宣称某一库是答案。
- WPF UI（lepoco）官方项目：https://github.com/lepoco/wpfui
  是可选的成熟现代主题/组件参照，不应仅通过加入依赖来代替专业组件设计。
- Carbon Tree View：https://www.carbondesignsystem.com/building-blocks/core/components/tree-view/guidelines
  选择、展开、焦点、层级导航有独立语义与控件表现；Test 编辑器不能只是 ListBox 加 Unicode 箭头。

## 五、修正重点不是从 A 改成 B

之前 V02-01 过早把设计焦点放到「属性在右还是在下」，即布局优化的局部问题。真正缺失的先决决策是：
1. TEST 的主编辑**文档对象**是什么：项目/用例/当前阶段/步骤如何保持稳定身份、标签、导航与上下文？
2. **三种关键工作状态**如何设计：无工程/无用例、空用例、内容丰富的用例；加上部分错误/断点/运行准备状态。任何方案只覆盖 40 步漂亮截图都不够。
3. 步骤结构是**什么专业视觉组件**：区分阶段、流程容器、分支槽、叶动作、摘要、诊断；当前选中有可见标识，且焦点/断点/运行状态各自独立。
4. **真实参数编辑的连续任务**如何穿过主结构和详情：选中一个 CAN 步骤，如何不靠记忆 HEX 就能选择报文/信号、修改期望，定位错误，再继续下一步？
5. 信息密度应该由内容长度、结构深度、窗口大小共同约束；不能先选固定列宽再让数据迁就它。
6. 全局 Shell、工具窗口、步骤工具栏、字段面板各自承担哪些命令；哪些可以就近，哪些是文档级，哪些必须隐藏/禁用。

A/B 布局比较要在这些决策之后再做，且必须针对同一任务和真实 Windows 视觉图评审。

**第三批｜场景驱动视觉候选**：先拿一个完整的真实世界任务：从打开工程→打开测试用例→插入一条 CAN 信号判定步骤→选择 DBC 信号→编辑条件和时间→看到有效性→保存。至少覆盖空用例与 40 步复杂用例，先画完成度高的 100% 浅色候选，制作密度、字号、层次、图标和状态规范，务必直接看到可辨认内容，而非空白骨架。

**第四批｜专业组件研究/定义**：步骤行/容器/分支/类型化 Inspector/资源选择器/命令区/问题反馈；定义编辑契约与视觉状态，避免用“一个普通 TextBox + 一堆原生按钮”冒充专业 UI。

**第五批｜极小实际 WPF 垂直切片**：在有真实 Windows 截图校验的前提下仅实现一个连续任务闭环，不实现 40 步全部操作，再扩展。保留 main 和现有正式设备合同不变。确保运行时打开的默认状态、选中与属性确实一致。

## 七、需要修正的「现代化」定义

**现代化 = 工作对象清晰可识别 + 稳定的文档/工具工作空间 + 成熟的信息密度与排版 + 可预测的编辑动作及反馈 + 系统一致的专业组件/状态 + 响应式及可访问性 + 专业视觉精细度。**

不是：页面是浅色、面板有圆角、文字变灰、按钮带蓝色、布局分三栏、内置 40 条研究数据、支持很多键盘命令。

## 八、当前审查判断

- 原 R01～R06、V01 对工作模式和视觉原则有可复用价值，不能简单废弃。
- V02-01/02 研究了具体结构和行为，部分结论可信，但没有提供足以直接决定界面表现的详细专业组件设计。
- V02-03 四张 SVG 构成视觉候选，**未在 Windows 原生环境与空/复杂状态之间做对应复查**。
- V02-04 现存 WPF **可供记录失败案例和功能代码参考，但其视觉设计未被用户接受，不应作为正式视觉基线或继续零碎修饰**。
- 本轮审查仅研究、核对与归档；不改变用户的主线或当前原型分支。

**最终结论：先重建「任务—对象—交互—视觉」的完整设计单元，再考虑 WPF 实施；不得把单个具有可点击能力的窗体误认成一款成熟产品。**
