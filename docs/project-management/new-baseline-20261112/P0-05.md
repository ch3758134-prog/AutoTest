# AutoTest｜P0-05 工作成果、审查与交付控制

- **版本**：v0.1｜2026-11-12
- **状态**：候审；未批准、未发布为正式项目基线
- **上游**：新基线 P0-01 v0.2、P0-02 v0.1、P0-03 v0.1
- **目的**：保证每项成果真正可审阅、可批准、可追踪、可执行，而不是以生成文档、PR 或 Git 提交冒充工程完成。

## 1. 交付的对象必须清楚

工作成果可以是研究报告、需求、架构/详细设计、源码、设备配置、试验方案、实测记录、技术审查意见、项目计划或正式发布包。不同类型的成果有不同验收标准。

每份需要正式审查的成果至少说明：稳定编号、名称与版本、面向的实际问题、依据/来源、完整正文或可核对内容、相对上一有效版的差异、重要限制/风险、关联工作及**本次具体申请批准的范围**。

对于源码和实机结果，还需绑定精确 Git commit、环境、输入配置、原始证据和未完成的验证；对没有产生的证据直写“未验证”。

## 2. 负责人先看到实质结果，再作决定

工程协调者应当首先说明实际解决的问题、为什么开展、取得的结论及剩余问题，再呈现完整、可阅读的工作成果。对于复杂设计，技术判断和备选方案由专业角色先完成，不能把大量需要 AI 自己研究的问题当作“请负责人填表”。

明确区分六种事件：

| 事件 | 含义 | 不意味着 |
| --- | --- | --- |
| 研究/编写完成 | 候选稿形成 | 已审阅、已批准 |
| 内部审查完成 | 技术意见与证据形成 | 独立第三方审核、负责人批准 |
| 负责人内容批准 | 指定完整版本和批准范围生效 | Gate PASS、编码授权、实测通过 |
| GitHub 正式落档 | 已批准内容写入并回读 `main` | 新增未授权决定、已验收产品功能 |
| 实施与验证 | 精确范围内取得客观证据 | 不经负责人审核即发布或合并 |
| 阶段/发布批准 | 负责人依据适用证据作出决定 | 将未验收范围自动提升为通过 |

对于已经完整展示且明确批准的管理文件，**批准后的 GitHub `main` 落档是管理 AI 立即执行的后续动作，不再要求负责人对同一份原文重复批准一次**。若审批对象不明确，应仅澄清真正影响结果的一处信息。

## 3. P0 至后续阶段的成果组织

P0 管理治理与立项；G0 恢复真实硬件、代码和研究事实；G1 形成可验证要求；G2 决定系统结构与公共接口；G3 对被授权工作包做可实施的详细设计；G4 研发与集成；后续对真实系统验证、发布和恢复作出决定。阶段名称服务于本项目，不强制其他工程照搬。

不同阶段可以交叉开展合法的研究与准备工作，但不能跳过它们所必需的技术依据、审批及验证。**已有代码可以保留、审查并逐步集成**，不因重走 P0 而宣布所有真实研发退回零点。

## 4. 批量交付与逐项批准

同一阶段的多份候审文档可以一次以 Markdown 文件包交给负责人；每份文件必须能单独定位、阅读、修订与批准。负责人可以一次针对多个**精确编号和版本**作出集中批准，也可以只批准其中一部分。

在负责人决定前，候审 `.md` 文件由对话交付/本地工作区保存，不直接成为 GitHub `main` 的正式工作产品。批准后只发布获准的对应版本，不夹带未批准文件。

## 5. 专业任务与本地 Codex 交接

专业研究或设计任务应规定问题、责任、必需输入、输出、审查方式和下游依赖；正式编码任务还须提供批准的具体设计、允许路径/接口、精确基线、风险及可验证的完成标准。

Codex 不自行修复不属于合同的错误，不重新定义架构、不扩大修改范围；回传真实错误、日志、文件变更和提交。若需代码改动由专业角色修订方案并获得相应授权。

完成源码、构建成功、自动单测通过、真机联机成功和最终用户验收属于不同层次。涉及 ECU、IGN、夹具、供电、按键或刷写的实机操作需额外现场许可。

## 6. 交付前质量自审

交付方检查实际内容是否回答任务问题、术语是否清晰、来源与事实是否区分、是否有逻辑和接口冲突、是否给出适当的验证办法，是否正确声明未经取得的证据。技术自审不能伪称独立质量认证。

负责人收到的默认应当是**可直接判断的成果本身**，不是只有流程编号、文件数量、哈希或待办状态的汇报。工程机器记录置于附件或链接。

## 7. 发生退回、修订、冲突时

退回保留原版本与意见，作者按反馈形成新版本并说明差异；旧版本批准不继承到修改后的正文。GitHub 同名文件冲突、HEAD 变化或任务边界偏移要中止对应动作、先重新审查，不以覆盖或“修好再说”跳过负责人。

## 8. 本项验收边界

批准本文件即批准本项目的**成果编写、负责人审查、批量交付、正式归档、专业任务交接原则**；不等于当前所有工具已强制实施，也不授予任何具体源码/固件/实机任务权限。Project Control 4.6.1 在仓库中仍自述为 `CANDIDATE_NOT_RELEASED`；不能把其脚本/界面存在说成已经完成受信任审批系统的部署。
