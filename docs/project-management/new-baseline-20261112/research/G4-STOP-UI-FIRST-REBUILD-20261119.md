> **G4 状态**：`PHASE_WORK_STOPPED / DELIVERABLES_RETAINED / PARTIAL_FIELD_EVIDENCE / UI_BLOCKER_OPEN / NOT_GATE_PASS`。这是一项**阶段性收口/路径切换**，不是宣称 G4 R1 完整功能验收 PASS，不抹去已实测事实，不清理有价值后端代码。若要形成正式 Gate 结论，仍须以分项证据和未完成清单审查。
>
> **新开发分支**：`feature/ui-rebuild-20261119`；从 `main@1d6eeba8561a779640b20c5a3f384327a0018079` 建立。WPF UI 实现工作单独在此进行；不是管理交付分支，也不用于独立硬件实体实测。

> **管理分支**：`Project_Management`；本决策不写 `main`，不合并 `feature/g4-html-parity-20261115` 全量代码。

## 一、事实基线与当前问题

- 现有 G4 开发分支在本次检查时 HEAD：`feature/g4-html-parity-20261115@ce4dbd4401dac1a98ffa87885865d0b7c174df7f`。有真实工程代码、自动 TEST/DEVICE/手动台架/CAN/WPF 编辑工作及用户部分实测反馈，但尚无统一证明 G4 所有 R1 硬件与 UI 交付项目均通过的报告。
- 历史 UI 设计分支 `ui/ide-design@c13ea5eecb150e54e6e54ebe4a42d95441bc72e0`，保留 HTML `docs/ui/AutoTest_UI.html`、UX 决定和研究资料；历史 2026-11-15 自动测试 HTML 冻结档案位于 `main/docs/ui/archive/auto-test-20261115-ec75a9fe/`。
- **新旧界面设计的优先级**：上述 HTML、G3 冻结方案是本次重设计的重要研究/历史审查资产，但不能不经用户新批准就认作“整体 UI 永久冻结且禁止重画”。**此次用户明确选择完整重新设计**；新设计的正式基线必须由用户审查认可的明确界面与版本来确定，保留现有业务/硬件约束，不用旧 HTML 强迫照抄全系统。
- 近期 UI 研究明确的工作重点：真实可编辑操作、智能锚定快速编辑浮层、常驻步骤属性区、右键操作、保存/重开/草稿与执行快照分离；手动台架和自动测试优先；CAN Data 完整可见，DBC 负责信号编辑/解释；相关 UX 方案由 UI 专业依据具体版本提交用户体验审查，不得假称此记录已经批准每个像素。

## 二、两条分离的研发流

| 路线 | 职责与当前安排 | 禁止 |
|---|---|---|
| **原 G4 / 后端资产保全** | 现有 G4 源码及提交保留为可提取的已实现资产；将用户确认的实测证据、缺陷、版本记录与剩余工作登记。若另一个受控 HOST 集成任务正在吸收 G4 成果，应按准确提交与专门集成授权实施 | 不直接将整 G4 分支视为 UI 重建基线或整体合并到 main；不把局部实测升格为 G4 全部通过 |
| **新 UI 实现分支** | `feature/ui-rebuild-20261119` 只承担全局 Shell/导航、多窗口、编辑布局、控件与交互体验、真实本地 UI 状态/文件编辑保存和可运行 WPF 的用户操作验收 | 不在视觉开发期发送真实 USB/CAN/IO/UDS/Flash 请求，不建立假的设备/ECU PASS，不复制第二套业务引擎、TEST DSL 或 USB/UDS/Flash 后端 |
| **正式系统接线（后阶段）** | UI 全面认可后，以已验收实际后端为唯一业务执行事实源，按模块定点接入 PROJECT/DBC、DEVICE/CAN/KEY/IO、TEST、UDS/FLASH，然后 WAVE/SCAN | 不提前把未验收的 G4 后端耦合在每个 UI 控件，不为赶工重设真实通信协议 |

## 三、UI 优先工作包及可验收范围

`UI-01 全局交互与框架`：Windows WPF 浅色主题；Shell、菜单/状态栏、IDE 工程树、中央可切换的文档工作区、标签、窗口/独立专业工作台、缩放/分隔、空状态和错误呈现；不遮挡 Windows 任务栏，设计合理的最大化。

`UI-02 TEST 编辑与工程`：工程树（工程、项目、用例、公共流程、DBC、波形、编号等）、准备/测试/清理三个阶段、步骤树、IF/ELSE/循环/等待等控制、就地改名、多选、拖拽插入/移动/复制、右键菜单、常驻 Inspector、快速编辑浮层、保存/重开/撤销重做；用户勾选的临时选测与工程持久 Enabled 分开。公共流程与直接 KEY 设计必须遵守已批准的 G3 变更。**此阶段可验证真实编辑与文档持久化，但没有真实 TEST 执行结果可宣称**。

`UI-03 手动台架与 CAN/DBC`：按用户已认可的三栏方向：左侧 CAN 发送/编辑列表（完整 CAN Data HEX、周期、启动停止、DBC 信号值编辑），中间 20 KEY 快捷操作和 IGN/夹具操作，右侧可读的 CAN 实时表及历史/日志；用户术语 **ECU CAN / KEY CAN**，不可在业务 UI 用 CAN0/1/2 混淆。当前用户明确不需要将六路 LED 控制塞进**手动台架主区**；固件对 LED 的支持保留为设备能力，不等于 UI 主工作区必须显示六个操作。CAN HEX 与信号编辑双向同步、编辑不自动发送、浮层点击外部关闭且可右键属性展开。**无真实后端时不伪造发送/接收**。

`UI-04 专业工具窗口`：UDS、FLASH、DBC/CAN 专业工作台有相互独立的可用空间和页签/窗口管理；波形分析和扫码/生产纳入整体导航/信息架构，但 WAVE/SCAN 具体技术能力和完整联动实测仍受现有 G4 真实运行基线约束，不能把它们当作本轮已验收功能。专业窗口应可回到测试项目，不遮蔽工程树形成大量空白。

`UI-05 一致性、验证及验收`：中文术语、统一控件（输入/下拉/时间/HEX/资源选择/表格/浮层/日志）、单击/双击/右键/焦点/Tab/键盘/滚动的交互、保存时防丢失、窗口大小和 DPI 兼容、运行状态与不可用状态显式区分。**以用户能够真实打开 WPF 完整走通界面操作并明确认可为准，不以 HTML、截图或代码编译代替**。

### UI 先行的技术边界

- 已批准的 **领域对象**（Project/Test/DBC/StepNode/公共流程/KEY 命令）不能因为“先画 UI”就另造第二套业务模式。UI 允许构建隔离视图适配、轻量临时编辑状态、真实文档存储；编辑动作必须具备可保存/重开/撤销的结果，不允许一排不能点的假控件冒充已完成。
- 实体操作按钮在未接线时期应明确 `未接入真实执行`，不能连到虚拟成功路径；用于视觉评审的静态外观/空状态也必须明确，不得伪造 CAN 帧、ECU 返回或设备连接。
- 本阶段暂不要求真实硬件联调，因为其目的就是把完整 UI 用户体验独立定稿。后端原有实测证据不因 UI 分支无后端而作废。

## 四、G4 阶段遗留与专项关系

- 必须保留已经完成的可追溯部分实测，不追认所有“Windows Build/Test/实体运行”均 PASS。实测未覆盖清单单独登记；不再让 G4 WPF 分支承担新 UI 重画任务。
- 已开展/可并行的 FLASH 接入、UDS 独立 `AutoTest.UdsLab.exe` 实测仍独立推进；**不要等待 UI 重建完成才能继续专业测试**。新 UI 验收后按专门接口复用它们。
- WAVE、SCAN 的完整接入及真实自动测试联动应等 **新 UI + 已有 G4/TEST 真实执行链受控集成且获得用户实际验收**。由于原 G4 实施已阶段性收口，原先“等 G4 完成”的表述按本条替代，不再要求原 G4 分支本身达到全部设计成熟才允许后续接入。
- 原 `main`、FLASH/UDS、Main_Control/Key_Sim 的专业提交和行为不因本决定自动变更。

## 五、阶段门禁和负责人审批

1. `UI-DESIGN-BASELINE`：用户对**新完整界面方案**明确批准；固化设计版本和范围。
2. `UI-WPF-INTERACTION`：独立 WPF 程序可打开、编辑并保存工程/用例/请求/表格/选择与窗口状态；主要业务操作路径和视觉符合设计，用户逐屏验收。
3. `UI-BACKEND-INTEGRATION`：在独立后端分项已验收的前提下，才按模块启用实际命令；统一错误/UNKNOWN/日志/工位授权；继续现场实测。
4. `R1-SYSTEM-REVIEW`：对最终真实生产/实验流程另行综合验收，不由单一 G4/单一 UI 分支代替。

**此次批准的是阶段实施路线切换与新 UI 分支的建立，不是自动批准任何未经审阅的具体 UI 设计，也不是后端连接许可。**
