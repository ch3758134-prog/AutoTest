## 一、目标与边界

**产品目标**：单 Windows PC、单工位 DUT 为当前 R1 能力，预留后续 2 DUT 并行的上下文与资源隔离。通用 ECU 测试、出厂检验与研发工具平台，EPB 为第一个真实样本，但 UI、文案和流程不能写死 EPB。**一个正式 `AutoTest.Desktop` EXE、一个主 Shell、一个工程/Run/Station Context**；不新增平行正式 Shell、Test 引擎、CAN Hub、USB Session、SQLite 或资源存储。

**UI 分支直接负责**：
- 完整 R1 **产品界面设计**：整体导航与信息架构、视觉 token、字体/颜色/密度、亮暗主题、状态色、图标体系、Windows 高 DPI 和窗口尺寸适配、菜单/工具栏/命令搜索/快捷键、可停靠工具栏和多文档结构，参照成熟 IDE 与 ecu.test 的操作逻辑，避免纯大卡片仪表盘式表现。
- 可使用的 WPF/Prism **Shell 展示层与多文档工作台**：资源侧栏、活动入口、Document Host、Inspector、底部日志/诊断/运行结果、状态栏、工具区域、导航、可保存布局、Dock/Tab、文档激活与失效状态、全局命令 CanExecute、空/加载/忙/错误/未授权及 Mock/Replay/Physical 来源的统一呈现。
- 支持专业 View/VM 插拔的**明确 UI Extension/Region 边界**：给每类专业定义激活、上下文传递、Close/Dispose、错误/Status/Trace 反馈和快捷键争用策略；提供最小安全演示数据证明 Shell 能打开/关闭工具，而不是在 Shell 复制领域业务逻辑。
- TEST 编辑、调试、工程资源、DBC、诊断、波形、烧录、台架、扫码生产、记录报告的**全局一致交互规范**（菜单/工具导航、面板尺寸、通用提示和视觉规范）；具体专业页面的业务 View/VM 由各专业分支继续拥有。与专业所有者共同调整规范，不擅自覆盖尚未合并的 UI 专业补丁。
- 当前 13 个专业功能的 R1 可导航结构与集成清单，不用 13 个空占位页或只切换 Tab 就声称完整产品已经可用。

**UI 分支不负责**：重写 DEVICE/CAN/UDS/ISO-TP/Flash/WAVE/TEST/RECORD/SCAN 专业业务逻辑、修改物理输出门禁、独占全部专业页面开发或制造第二套公用 Contracts。当前专业页面按原分支继续开发，用户现场实测和改进归原专业所有。

**INTEGRATION 后续负责**：将成熟专业 View/VM 插入唯一 Shell，完成 Prism DI 注册、跨模块 Project/Resource/Session/Trace 适配、项目引用和完整联测。UI 分支拥有 Shell 视觉/导航/View 层设计与自己修改的 UI 文件；INTEGRATION 拥有宿主正式接线、跨模块公共适配、`.csproj`/`.sln` 和项目依赖。**需要共同修改 `PrismRegistration.cs`、`MainWindow.xaml(.cs)` 等同一路径时先申请主对话指定唯一修改方，不并行覆盖。**

## 三、必须实际设计与验证的通用操作

- 文件/工程：新建、打开、最近工程、保存/另存、Dirty、关闭提示、保存失败可恢复、Revision 过期和冲突提示。
- IDE：Explorer 双击/右键、树搜索与过滤、拖拽/插入位置提示、文档多标签、激活/定位/关闭/重新打开、Inspector 跟随 Selection、长操作 Busy 与取消、底部 Output/Trace/Problems 可显示和筛选。
- 测试：从步骤树导航到 Inspector、准备/测试/清理层级、插入 IF/ELSE/SWITCH/WHEN/Loop/子步骤、设置断点/单步/运行到/跳过的命令状态，预期/实际分离；**行为真实语义由 TEST 供给**，不在 UI 本地假造执行成功。
- 工程工具：打开 P02～P09 专业 View 不影响其他文档或同一设备 Session；关闭视图不关闭用户未要求停止的运行会话。保持右侧上下文/状态栏来源和设备/工程 Revision 可见。
- 诊断：操作时间线与原始 Trace 双层呈现，区分请求/传输 ACK/物理观测/ECU 响应/业务判定；不能用演示 Mock 反馈冒充真实硬件。保持各专业可导出。
- 视图与可访问性：文本层级清楚、用户可调整窗格与保存布局、键盘/焦点与输入法友好、没有不可读小字和不可解释图标；可扩展 Win11 主流屏幕分辨率与高 DPI；不要引入未经审查的字体素材包。

## 四、现有代码事实及不重复开发的要求

当前 `main` 有：
- `src/AutoTest.Desktop/Shell/MainWindow.xaml(.cs)`：旧 Test 中心 Shell 与 G4 工具入口；不能将现有 Mock 标题和菜单当成 R1 全功能。
- `src/AutoTest.Desktop/Bootstrap/PrismRegistration.cs`：Prism 目前主要注册 ProjectExplorer、TestEditor、StepInspector、RunMonitor 四区域。**正式 13 页不是全部已接入**。
- `src/AutoTest.Desktop/G4/ModuleToolsWindow.xaml(.cs)`：有多个专业演示 View 容器，某些 View/VM 构造函数直接创建 Mock 后端，BENCH 还是占位。它只能作为现役代码事实，不能复制成最终双 Shell。
- `src/AutoTest.Desktop/Bench/BenchContracts.cs` 有专业本地 `IBenchWorkbenchPort`；`WaveWorkbenchContracts.cs` 有 `IWaveWorkbenchBackend`；专业 Port 保留现有合同，正式接线后由 INTEGRATION 注入。严禁 UI 分支造第二套 USB/CAN/业务真实状态。

技术约束为 WPF + Prism 9 / DryIoc。历史资料曾建议 AvalonDock 作为多文档停靠方案；但当前 `AutoTest.Desktop.csproj` 已核对只见 `Prism.DryIoc` 直接包引用，**不能把 AvalonDock 已安装当成事实**。需要新增第三方 Dock 依赖或改公共项目文件时提出明确最小依赖/许可/适配审查，由主对话/INTEGRATION 统一批准和实施。不要自行写一个复杂不可靠的 Dock 引擎冒充专业方案。

## 五、交付节奏——R1 总体 UI 现在开发，后置实测

- **U1 / 设计继承与差异评审**：完整阅读上述 HTML + P01–P13 文档 + SAEF + 正式现役代码；给出现役页面/路由/样式到目标 R1 的可核对差异表、端到端操作流、视觉规范、页面责任和未解决依赖。不要反复问用户先前明确的通用需求。
- **U2 / R1 Shell 源码**：在 UI 自有范围逐步实现统一 Shell、视觉 token、导航、多文档/工具窗管理、Inspector 上下文显示、状态/错误和可测命令。可以用清楚标注的 Mock fixture 验 UI 行为，但不实现专业真业务和设备 Tx；不要求用户此时独立操作验收。
- **U3 / 专业接入契约**：记录每个页面的 View/VM 启动方式、上下文输入、Dock位置/生命周期、错误/Trace 适配，按功能/文件把接线工作交 INTEGRATION；不得因为专业分支尚未实测就停下 U2 的纯 Shell 工作。
- **U4 / 集成后验收**：成熟专业视图由 INTEGRATION 注册到唯一正式 Desktop，完成完整 Run/Resource/Session/记录场景、WPF 稳定性和真实用户操作体验，用户在统一软件上反馈 UI，再由 UI 分支修订产品级交互/视觉，专业行为 bug 回专业分支。

每个源码候选必须记录 BasedOnCommit、ChangedFiles、Shell/Region/Navigation 入口、已有专业视图复用清单、未接入项、Build/自动测试/截图/操作模拟证据、SharedContractImpact、后续集成要求。**Windows Build、专项自动测试尚未跑就写 NOT_RUN**；用户整体验收未进行就写 USER_R1_UI_NOT_TESTED。Codex 只机械应用/Build/Test/记录原始错误，绝不自行修复错误或重构。

**重要：用户已经选择“先专业独立验证、后统一产品 UI 集成”的研发方式。这不等于 R1 UI 设计与 Shell 研发推迟，也不等于要求 R1 UI 分支创建给用户现在单独实测的完整上位机。**
