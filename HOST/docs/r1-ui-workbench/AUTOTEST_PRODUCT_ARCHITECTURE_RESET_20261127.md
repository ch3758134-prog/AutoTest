# AutoTest R1｜产品、认知、业务模型与架构整体重建基准

版本：2026-11-27（UTC+8）  
生效范围：`R1` 上位机的后续产品设计、破坏性重构与验收。  
责任模式：项目管理、产品设计、系统架构、UI/UX 和源码实施由同一统筹负责人整体负责。不得以旧代码、旧模块边界、历史实施成本或过往“准入/发布/审批”模型作为目标产品的约束。  
性质：**目标架构决策，不是已经完成的代码交付或硬件实测结论**。

## 1. 为什么必须整体重建

既往开发长期沿“已有代码/模块 → 拼接界面 → 发现冲突 → 增加配置、校验和保护层 → 局部修补”运行，造成同一真实业务被多套抽象同时描述。典型证据：
- `ProductionAdmissionReview` 把 13 个开发内部事实变为正式生产前置许可，且三个关键字段固定为 false；
- `ProductionStartGate`、`ProductionPhysicalStation` 和 `ProductionWorkflow` 要求可信实体按钮事件、独立机械闭合证明、安全互锁证明，而用户已明确软件 START 不依赖实体按钮是否完成固件接入，夹具以 ECU CAN 通信反馈作**工位功能就绪闭环**；
- `AutomaticTestHomeViewModel.Run` 已有真实 FLASH + 整组 TEST 的工程运行路径，正式生产路径却另有一套未完整接通的 orchestration/record 机制；
- `StationDeploymentStore`、`ProductionProjectCatalog`、`NativeFlashPublicationStore`、`ProductionPreparationService` 重复形成部署、发布、冻结与确认操作语义；
- 波形的标准组、单路引用、判定配置、算法审查散落于多种对象；DBC 文档与工程资源引用边界仍未彻底打通；
- `ProductionRecipe` 等废弃术语/模型残留在底层，与“扫码只匹配完整 ECU 工程”相矛盾。

**这些不是“需要让某个校验更聪明”的问题，而是业务对象与运行所有权定义错误。代码必须服从新业务模型。**

## 2. 产品定义和工作区

AutoTest 是一款离线 Windows ECU 测试工程开发、专业调试与出厂检测一体化产品。首个完整现场型号是 EPB，单 PC、单工位；支持后续不同 ECU 型号以**不同 ECU 工程**承载不同 TEST/DBC/FLASH/标准波形，不需要重新开发工位平台。

四个工作区：
1. **生产检测**：一台 ECU 扫一个码，显示完整扫码原文和匹配工程，压紧夹具、通信确认、START、每次 FLASH、唯一 TEST 全量连续执行、记录结果、释放夹具；实时看到每个用例、FLASH 阶段、当前失败原因、历史和批量统计。
2. **工程开发**：创建/打开 ECU 工程，编辑唯一有序 TEST、公共流程和资源绑定，调试单步/单用例/勾选范围/整个项目，自动保存；调试无需扫码或生产 FLASH 前置。
3. **专业工具**：DBC 文件编辑、波形观察/采集/分析/标准建立、FLASH 原生参数和烧录、UDS、CAN 收发监视、手动台架；每个工具是完整的操作环境，而非围绕 TEST 拼凑的配置页面。
4. **设备调试**：检查 USB、ECU CAN/KEY CAN、IGN、KEY_SIM、夹具电磁阀、实体 START/STOP，显示实际接收/读回/错误；不借工程对象制造设备能力。

初期可共用一个 WPF EXE 和 Prism Shell，后期是否拆分 EXE 不改变业务语义。浅色、高可读、简洁、操作对象明确；系统诊断与内部 ID/哈希不在普通正文常驻。

## 3. 唯一对象模型与归属

- **ECU 工程**：一个 ECU 型号，一个有序 TEST 项目、一份生效 DBC、一份生效 FLASH 配置/固件镜像，多个标准波形、多个公共流程。工程名称与型号标记不同；打开/命名/修改/保存完整且直观。工程不能携带工位串口、夹具输出、实体按钮接线。
- **TEST 项目**：唯一正式用例调用序列；调用实例有独立顺序和结果，定义可被复用。正式生产必然从头到尾按此顺序执行，不需要二次选择、启用、发布或附加测试配方。工程调试的勾选/跳过/断点仅为临时运行状态，不能更改正式项目含义。
- **TEST 用例和公共流程**：一套步骤 DSL、一套执行器。公共流程在独立流程编辑环境创建、重命名、维护、复用，不等同于外部通用文件。逻辑结构使用统一编辑行为；流程调用支持来源定位。步骤直接编辑和调试，不需要与生产运行另行绑定。
- **DBC**：独立的标准文件编辑对象，可新建、导入、打开、编辑、重命名、另存、导出；工程绑定一份当前有效 DBC。名称、文件路径、工程引用身份彼此分离；正常编辑维护合法结构；不支持的扩展原文应无损保留，不能假装可写、不能静默丢失。
- **波形**：独立观察与采集工具；多路同次采样形成有明确采集时基、证据和质量的标准组；用户配置判定阈值与比较方法，工程引用标准和判定定义；TEST 自动采集/比较必须与工具使用同一实际算法与信号含义，不用字符串名拼接标准。
- **FLASH**：工程固定位置的原生烧录参数、唯一活动固件文件及系统内固定安全文件；专业工具负责真实调试。正式生产每次检测在 TEST 前运行 FLASH，不把 FLASH 当 TEST 步骤，也不加载外部 XML 配方或要求用户导入安全 DLL。
- **工位**：一套主控、扫码枪、夹具两路驱动、可选实体 START/STOP 输入。属于物理设备和工位设置，不是 ECU 工程的一种资源。
- **扫码身份**：保留完整原始编号，一个码同时代表唯一 ECU 和可提取的型号匹配信息；工位定义一种清晰识别规则，通过唯一固定标记命中完整工程；无法匹配或多重匹配时明确显示原始码及原因，不静默选择第一项。
- **检测记录**：一次 ECU 检测有一份完整运行记录，包含扫码原文、工程版本、固件、FLASH、全部测试用例的 StepOccurrence、关键 CAN/信号/波形证据及最终结果；批次统计来自完成的单台记录，而不是重复的第二套数据库事实。

## 4. 单一实际运行模型

**一套生产周期编排器调用原有实际 FLASH 和 TEST 内核；一个硬件会话管理入口；一种正式记录语义。** 不允许工程实测与生产检测各自复制 TEST 步骤解释、CAN 发送逻辑、KEY_SIM 动作或波形算法。

### 4.1 标准生产周期

`扫码并显示完整编号 → 唯一匹配工程 → 夹具压紧 → ECU CAN 闭环就绪 → 等待实体/软件 START → 工程原生 FLASH → 唯一 TEST 项目全部有序用例连续执行 → 结果归档 → 夹具释放 → 下一台`。

扫码、夹具就绪与 START 都是可观察到的实际动作/事件，不能变为给操作者填写的一套“准入许可”。START 触发动作只发生一次，实体和软件按钮共用一个入口。必须保证同一台 ECU 的运行会话不会因重复扫码/双击 START 重入。是否需要在实际工位上调整 START 与压紧的先后，仅由用户的真实工艺来确定，**不允许为此引入第二个流程编辑器**。

### 4.2 夹具闭环的准确定义

压紧后通过主控 ECU CAN 通道观察当前 ECU 的预期有效报文，作为此工位的**功能性夹具就绪闭环**。判定须使用压紧后新收到的报文、正确 CAN 通道、符合该 ECU 通信条件的 ID/格式/必要数据及有界等待时间；在特定 ECU 需要 IGN、诊断唤醒或进入 Boot 才通信时，按本型号已有工程通信事实安排，不把“任意帧”当夹具反馈。超时报告“夹具就绪确认失败 / ECU 无预期通信”，保留原始事实，不冒称机械夹紧。收到 ECU CAN 不证明机械传感器位置、气压或防护门安全；若工位需独立的人员安全防护，须由实际硬件安全设计承担，不能用 CAN 检测伪装安全互锁。

发出 `0x18` 夹具指令和读回 `0x19` 是主控输出层确认；它们本身不是 ECU CAN 闭环。当前固件 USB 失联时可能释放夹具，真实工位必须按实际断电和机构行为确定异常收尾，不可凭上位机的假定自动放行产品。

### 4.3 START/STOP

实体 START 的输入采集/消抖及 USB 上报属于固件，软件负责订阅事件并提交给统一启动处理器；软件“开始检测”直接调用同一个处理器。不存在 `TrustedPhysicalStartConnected` 这种独立用户配置或因固件未接线而禁用软件启动的条件。实体 STOP 和软件 STOP 同样共用真实停止请求，不能让两个入口表现出不同的 TEST/FLASH 清理行为。固件未实际提供 START/STOP 通信事件时，实物功能状态应写在硬件适配验证记录中，不能让未开发的输入阻止已有的软件流程。

### 4.4 TEST 连续语义

正式项目的所有用例处于一个真实项目运行作用域。用例之间持续保持周期 CAN、KEY_SIM 最后动作、IGN 和测试变量，直到 TEST 明确改变或项目结束按确定策略清理。KEY_SIM 保持时间结束不自动释放最后组合。单步/用例局部调试可用不同的运行范围，但复用相同动作语义，不另造执行内核。CAN 周期发送是否由上位机定时或固件广播实现，以主控协议事实为准；不能把 USB ACK 等价成物理连续发送证据。

### 4.5 运行失败与收尾

异常是业务运行结果，不是用户“没有准入资格”。设备断连、扫码无匹配、FLASH 失败、TEST 判定失败、CAN 超时、记录写盘异常均需显示具体阶段和原因，并保留已产生的事实，避免错误 PASS。危险状态下不盲目自动重新烧录或释放夹具；由真实工位接线与恢复策略决定可执行操作。真实必要的输入边界验证和硬件防误发机制保留在**所属模块内部**，不组织成额外可配置的生产准入系统。

## 5. 完整用户认知路径

- 初次打开：工程开发区引导“新建 ECU 工程”；新建后默认提供一个空 TEST 项目，允许先编辑用例再补 DBC/FLASH。正常编辑立即自动保存，不弹无必要的退出确认；启动恢复上次工程。
- 工程编辑：左侧是唯一 TEST 的实际用例顺序和公共流程入口；用例单击切换、双击编辑，行旁直接添加步骤，右键快捷、复制、排序、运行到此/跳过；右侧实时 CAN 监视可常驻且可调整，不用永久占据宽大的步骤 Inspector。
- 资源操作：DBC、标准波形、公共流程、FLASH 分别由符合其本质的专业环境维护；工程只呈现已绑定的真实对象和修改/替换入口，不要求用户接触内部 assetId/SHA。资源变化时在编辑处立即维护引用关系；真正影响判定语义的变化清晰提示工程师核对，不因普通版本号变化强迫重绑。
- 专业工具：CAN 发送以 8/64 字节完整数据为中心，DBC 解码常驻辅助；单次与周期启停明确；手动按键操作是可直接点击的动作，支持最后组合保持；UDS 和 FLASH 展示真实请求/响应、进度和日志；工具浮窗关闭主窗时统一退出。
- 正式生产：默认只有扫码输入、匹配工程、当前夹具/烧录/TEST 状态、实体/软件启动与停止、可读结果；纵向列出真实用例和失败原因，不要求操作者操作工程发布、配方、运行许可或工程编辑工具。
- 结果：单台一份详尽但易读的检测报告，能展开 CAN/信号/波形原始证据；批量统计独立呈现，不和工程调试记录混淆。

## 6. 代码目标结构

| 逻辑职责 | 唯一权威实现 | 明确不允许 |
|---|---|---|
| 工程内容及保存 | Project repository + TEST/DBC/WAVE/FLASH 各自完整编辑模型 | 同一状态存多套互斥配置文档；按旧工程迁移规则约束新工程 |
| 工程资源绑定 | Project resource resolver，集中维护引用语义 | 生产时重新选择 DBC/用例/FLASH 配方 |
| TEST 执行 | `RealRunCoordinator` 及连续 `ProjectExecutionSession` | 为正式生产再写第二套解释器 |
| FLASH | 统一原生 `CanToolFlashWorkflow`/真实 Transport | TEST 步骤中的烧录、XML/三文件回退 |
| 设备会话 | `HardwareConnectionService` 和唯一 CAN 接收/发送分发 | UI/专业工具各自再打开同一物理 USB |
| 扫码与工位 | 唯一扫码解释/工程选择、夹具 CAN 反馈和 START/STOP 事件 | 多套扫码配方、手动授权表单、实体按钮可信开关 |
| 生产执行 | 单个 Production Cycle Orchestrator，组合现有 FLASH + TEST + RECORD | 一条工程真运行、一条永远未接通的“正式许可运行” |
| 证据 | 单次 RunId 贯穿全部阶段的增量归档 | 工程验证记录任意改名为生产 PASS；独立伪造“可信写入器” |
| UI | 四工作区共享项目和设备状态 | 技术许可/指纹/开发阶段口径占据操作界面 |

## 7. 必须删除或重新实现的现存旧合同

1. **整体取消** `ProductionAdmissionReview` 的 13 项许可模型与硬编码 false；取消为取得运行权而维护的 `TrustedPhysicalStartConnected`、`TrustedFixtureAndInterlockReady`、`VerifiedInspectionWriterConnected`。真实通信与存储问题在相应动作发生处解决，不能仅把“阻断”一词改成“提示”。
2. 将 `IProductionPhysicalStation.PressAndVerifyAsync` 需要独立机械传感器/互锁证据的旧合同，重建为当前工位的夹具动作 + ECU CAN 功能闭环；物理人员安全另按真实硬件能力执行。不要创建假传感器适配器。
3. 统一实体/软件 START 进入一套去重启动处理；移除禁止软件 START 的生产 UI 代码。实体 START 事件接入工程量另行实物验证，不让开发状态成为业务条件。
4. 正式生产不再悬挂未注册的 `IProductionPhysicalStation` 和 `IVerifiedProductionCommitSink` 后让用户永远无法运行；用现有已实现的真实 USB、FLASH、TEST、RECORD 能力构成可执行路径，并保证无记录成功时无法得到完整 PASS。
5. 审核 `ProductionProjectCatalog`、`StationDeploymentStore`、`NativeFlashPublicationStore` 和工程导入的实际数据职责：保留真正必要的工程完整复制、一次运行稳定快照与追溯；删除重复“发布/批准/安装许可”概念以及操作员必须理解的手工步骤。
6. 清理 `ConfigMatchService.ProductionRecipe` 及残余旧 TCF/TBC、独立 FLASH 步骤、工位脚本、历史 UI 入口及不可达分支。不兼容旧工程，允许破坏性调整 Schema；无需保持不再有效的类名和文件结构。
7. 合并波形标准组、判定设置与真实 TEST 比较引用的对象模型，统一多路时基、缺帧/间隙、有效样本、容差/时间偏移、未知结果及证据；不能仅因看到波形曲线就宣布判定完成。
8. 彻底审查 DBC 解析—编辑—导出—工程映射全链，明确支持的 DBC 标准语法；用户可以直接正确编辑常见 CAN ID/信号/注释/枚举并得到无损保存结果，不以“保守只读”代替专业编辑器的核心能力。
9. 审查 WPF 主窗、浮窗、布局、自动保存、启动恢复、工具窗口退出、运行状态同步和消息提示，按完整操作链改动，而不是仅对截图中局部控件调色。

## 8. 实施和验收要求

实施以 **R1 唯一开发分支** 为准，`main` 保持交付基线；不因历史管理文档或旧 Gate 条款暂停产品修复，不新建研究/功能分支，不启动 CI。对已验证的 CAN/UDS/FLASH/KEY_SIM 基础能力优先复用，不重复从零验证；改动涉及真实物理行为时必须在现场实际核对，不能把模拟、静态审查或编译成功宣称为产品完整实测。

代码整改不能分割成只保证局部编译的孤岛：至少要能回答“第一次创建工程如何编辑和绑定 → 工程调试如何运行 → 扫码后真实生产如何直接运行 → FLASH/TEST/夹具/CAN/记录怎样共用一套事实 → 发生失败如何恢复 → 关闭重开数据是否一致”。

验收分四种事实，不混为一谈：
- 源码实现（结构和调用链确认）
- Windows WPF 编译/启动/交互（用户本机）
- USB/ECU/夹具/扫码枪/烧录真实行为（用户实物）
- 单台检测记录与批量统计闭环（真实 RunId 和可追溯证据）

**本文件取代此前把审批、发布、可信实体输入、独立机械传感器证明当作产品必要使用步骤的局部结论。仍可保留实际电气安全约束、真实设备故障处理和持久记录，但必须以正确的领域职责实现，不得重新引入新名字的“准入平台”。**
