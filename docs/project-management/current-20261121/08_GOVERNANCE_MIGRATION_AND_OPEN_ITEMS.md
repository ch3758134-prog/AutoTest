# 08｜历史资料治理、当前分支清理与下一轮决策

## 1. 本次“重新整体整理”实际批准了什么

负责人 2026-11-21 批准对 AutoTest 进行全面的项目管理资料重整：审核新旧要求、识别被覆盖的事实、统一系统模块/领域责任、列现有源码与现场验收状态、建立当前阅读入口。**批准的是“整理与追溯”**，不是授权项目管理凭整理结果自行改变 TEST DSL、安全 USB 协议、WAVE 算法、SCAN 生产策略或最终 UI 视觉方案；这些变更继续单独按专业与负责人审批。

项目管理正式权威写入 `Project_Management`；不要把它当作 `main` 已合并的新技术源码。原 P0/G0/G1/G2/G3 原始审批记录、研究报告 HTML/Markdown、G4 合并证据、R1 开发文档都保持原文可查；新文件解释“目前应以什么为准”，不回写篡改历史结论。

## 2. 四类旧材料的使用规则

| 材料 | 今后如何定位 | 必须避免的错误 |
|---|---|---|
| 已批准且未被新决定覆盖的 P0/G3 | `APPROVED_ACTIVE`，产品和业务、安全目标仍在 | 因为 R1 未实现就直接删除需求 |
| 用户随后明确修订的方案 | `SUPERSEDED`，在 [02 决策台账](02_DECISION_SUPERSESSION_LEDGER.md) 写新值和来源 | 旧 GPIO、旧 CAN、旧按键配置、旧 G4 页面规则继续当当前真值 |
| 技术研究 / 审查建议 / UI HTML / PR 自述 | `REFERENCE / PROPOSED / SOURCE_CANDIDATE` | 自动提升成硬性接口、现场验收或用户已批准最终设计 |
| 真实 Windows/设备测试证据 | `BUILD_VERIFIED / FIELD_VERIFIED_FOR_EXACT_CASE`，明确 HEAD、工程和条件 | 实测单次 EPB Flash 成功就把 R1/全部车型宣称通过 |

后续 AI 新任务应在每次写入前依次查：当前决策台账 → 相应原批准文档 → 最新专业研究/源码 SHA → Windows/实体证据 → 需要负责人明确表决的差异。不以相似文件名猜权威。

## 3. 当前分支与 PR 债务

- **整机**：`main` 当前固定 `ffb23f8...`，`R1` 最新 `fa3b18e...`；R1 有大量真实功能候选仍待 Windows/现场统一验收，暂不直接合并 main。PM 不能把功能性变更当资料迁移偷偷提交。
- **固件**：`Main_Control` 旧式独立根与 main 三工程平级结构 diverged；新 0x42/0x43 和 IGN/IO 源码需要 Keil/实物门禁后定点移入整机 `Main_Control/`。KEY_SIM K19/K20/电源/温升未实测清理之前保持风险清单。
- **旧 G4**：`feature/g4-html-parity-20261115` 实际仍在远端，历史 PR #61 已合并并保存代码，用户已要求删除但**当前没有实删成功记录**；标 `RETIRED_PENDING_REMOTE_DELETE`，不得再从这里继续交付。清理应确认该分支没有新未接收提交、开放 PR 的依赖后通过有删除权限的 Git 入口办理，不能把“退役”写作“删除”。
- **旧 UI**：UI 专项与多个旧 `feature/ui-*` Draft PR #63、#66、#68、#69 及功能分支长期并存，不能让它们各自宣称全产品“唯一正式 UI”。按是否有明确用户批准、可运行的实际操作和当前接口来核对接收；只在批准后合并/关闭/删废弃枝，不能按名称自动清理。
- **TEST-RECORD**：PR #65 指向旧 `HOST` 分支仍 Draft、未合并，B-01/C-01 已静态修复；R1 已定点接入相似成果。未来清理需要列出两条线的精确 diff、Windows 验证证据与对应报告状态，避免再次把 PR 合入 R1 造成重复改动。
- **FLASH/UDS**：专业 PR #55/#60 仍 Draft，既有实测限定于具体版本；R1 受控复用现有底层，不将整个独立 UI 分支强行合并到主界面。
- **WAVE/SCAN**：Issue #71/#72 的 W-00～03/S-00～03 属研究候审；当前研究分支较 R1 主线会持续落后，不能把研究分支的整个旧源码树 merge 到 R1 覆盖新提交。

## 4. 后续变更必须有的最小审查记录

```text
DecisionId / 旧结论及精确出处 / 新证据及精确 HEAD
变更类别：BUSINESS | HARDWARE_FACT | API | UX | DATA_SCHEMA | SAFETY | RELEASE
谁提出/谁批准（用户原话或明确审批）/ 时间
此前状态→新状态、为何取代、未覆盖范围
涉及领域/文件/兼容与迁移/不可逆硬件风险
源码状态/Build 状态/设备状态/证据路径
下游 UI/TEST/RECORD/PROJECT/DEVICE/FLASH/WAVE/SCAN 交接对象
回滚或失败后的可恢复措施/当前剩余疑问
```

若只是“研究提出更成熟做法”，不得写 `BUSINESS_APPROVED`；若只是有代码无现场，必须写 `SOURCE_EXISTS / FIELD_NOT_VERIFIED`。运行期间的新型号、DBC、按键物理组合、Flash 资源无法核对时优先 fail-closed、明确现场调查路径。

## 6. 每个专业 AI 的接管规则

- **项目管理**：这个目录是第一入口；负责统一决定和版本冲突审查；不得代替专业直接声明实体 PASS。
- **R1 主研发**：以最新 `R1` + Issue #70 开发完整 TEST/FLASH/RECORD，依据 [05](05_R1_RELEASE_AND_ACCEPTANCE.md) 一次性交付，不让 WAVE/SCAN 大研究影响基础真实运行。
- **WAVE**：Issue #71、W-00～03；先向 TEST/RECORD 复核明确冲突与证据类型，再逐项实现受审增量；每次比较最新 R1。
- **SCAN**：Issue #72、S-00～03；不能修改扫码即烧录权限与用户“编号独立绑定”的决定；生产规则/复检需数据合同审核，开发运行仍可无扫码。
- **UI**：`ui/ide-design` 的最新 UX/视觉研究，以真实任务验收为核心；R1 的运行界面只做最少必要功能，合并前核对实际 WPF。
- **Main_Control / Key_Sim**：原理图、PCB、固件与现场工况相互验证，先解决 GPIO/USB/电气真实性，不能要求 HOST 为补“硬件不存在能力”增加虚假 UI。

**本次完成定义**：现行入口、状态分层、系统真值、决策继承、候审研究/源码与实测分离、受控后续变更均能在单处找到。**不是**清空历史文件、删除所有旧分支或整体功能验收 PASS。
