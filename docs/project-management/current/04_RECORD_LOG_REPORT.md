# AutoTest｜原始证据、测试日志、单台与批量报告
**2026-11-21｜产品方向已确认；统计字段/完整性/真机结果尚待验证**

## 1. 必须划清四种产物
| 对象 | 内容与目的 | 默认行为 |
|---|---|---|
| **完整 CAN 日志及原始附件** | 本次 CAN 发送接收原帧、时间/通道/ID/全部 Data，另含 UDS/Flash 阶段证据、实际 WAVE 时间序列 | 真实检测期间持续收集并归档，尽可能有完整底本与完整性/丢帧标记；具体容量与持续采集质量待验 |
| **测试日志** | TEST 步骤时间线、关键动作、实际测量、异常、失败原因，关联对应原始帧范围 | TEST 执行时按步骤配置的**关键数据提取**生成结构化事件；系统固定方式呈现 |
| **单台检测报告** | 针对一台 ECU 的**某一次完整检测**，扫码身份、烧录结果、哪些测试成功/失败、最终结论、失败位置 | **简洁、固定格式**，PASS/FAIL/停止/烧录失败都生成，不把每条 CAN 帧塞正文 |
| **批量检测报告** | 一批或一个生产范围里多少台不同 ECU、多少次检测、失败/成功/复检及必要统计 | 单独的**固定格式**方向；批次如何划分、首次/最终合格、计数规则未定，先专项研究 |

不能把“完整 CAN 日志也就几分钟”误读为“报表要贴全量 CAN 数据”。原始底本供分析验证；TEST 步骤提取关键观测进入结构化事实，日志展示过程，报告概括结果，二者都能按 RunId/StepOccurrence 回查证据。日志和报告不独立运行判定逻辑，也不靠 UI 日志文字推测 PASS。

## 2. TEST 编辑器与记录模块的关系
工程师在测试步骤配置**动作、观测源、预期值/容差、判据，以及需要提取的测量/结果项**；无需在每个用例插入“保存 CAN 日志”“生成报告”的步骤。日志展示方式/报告版式由上位机固定实现，允许极少量基础配置（路径、名称等），不另造高灵活报表设计器。

同一 StepId 在循环、调用和重复尝试时必须有独立 StepOccurrenceId/时间序列范围；报告中的“实际响应时间 90ms”等只可由真实、同一 Occurrence 的采集值推导，不得从无来源的变量或另一轮通过步骤借证据。系统还需为烧录及 WAVE 定义对应**不同类型**的真实证据，而不是硬塞进 DirectDbcSignal 规则。

## 3. 一次报告对应一次真实完整检测
一个唯一编号可有多次历史完整检测，每次都形成独立的 Inspection/Run 事实、烧录 Attempt、TEST CaseAttempt、日志、附件和报告；历史不能覆盖。
- PASS：必须有本次真实烧录、按已启用树执行、正式判据和必需的记录完整性；否则不升级正式出厂合格。
- FAIL：明确烧录失败或具体用例/测量失败，保留已完成步骤的原始事实；未跑测试不可标“已执行 FAIL”。
- STOP/CANCEL/UNKNOWN：如实写中止位置、原因和记录完整性；不得伪造 PASS。
- 程序断电/磁盘问题导致无法即时形成完整报告时必须保存可恢复的**已捕获证据**和不完整状态，不能承诺物理断电后仍保证生成完整 PDF/HTML。

## 4. 批量报告未定稿的事项
真正需要联合 SCAN/REPORT 研究的不是“任意字段排版”，而是以下统计口径：
- “当前一批”起止/身份及是否必须人为开始与结束批次。用户已确认生产界面就绪即可扫码，不能先强制创建批次才能启动正常生产。
- 扫码次数、完整检测次数、**唯一 ECU 数**、本次 PASS/FAIL/中止数量、首次通过数量、复检次数、最终状态与出厂放行是否区分。
- 同一序列号之前 PASS/FAIL 后重新扫码是否弹窗或限制：用户目前明确**不决定，暂时不要按历史状态复杂化**。
- 批量报告的固定样式、附件链接、是否导出列表、异常补录、统计可复算及数据丢失标记。
用户只批准**需要单台报告与批量报告两种产物**，不等于上述字段或政策已经获批准。

## 5. 数据现场与硬件现场要分开研究
**数据现场**：持续保存原始 CAN、Flash/UDS、DBC 判定值、波形、步骤事实，不应在 FAIL 之后才开始采集；失败可回看当时状态。
**硬件现场**：是否要求 FAILED 后夹具不松、IGN 不变、等待调试人员观察；目前用户尚未给冻结要求，不预设“FAIL 自动释放”或“FAIL 保持夹具”，由工程测试模板与真实安全边界共同研究。
