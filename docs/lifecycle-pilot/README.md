## 必须继承的设计判断

1. 产品身份只定义产品是什么，简洁稳定；R1、EPB 首个测试样本、CAN/按键硬件实现、具体版本及研究发现属于相应工程层次，不能混在四字段“产品定义”里。
2. 研究与设计 AI 在正确证据、概念和工程对象上形成可审查修订；系统应充分解释语义、关联、适用条件、未知与判断理由，**不靠禁词、固定十领域表或手写特殊案例阻断模型**。
3. 不采用四套独立管理系统。研究、设计、实施、测试、AI 项目经理和本地 Codex 在统一事实与修订模型上按权限协作；管理 AI 可推进研究与提案，但不能代替人批准设计、实物验收或自行修改治理协议。
4. 编码工作须有真实批准的详细软件设计和精确版本合同；受影响的下游设计/实施包应失效并重审，无关工作不应因另一个对象仍在讨论而全局停止。
5. 不把 CI、Mock、真实硬件、用户操作和最终验收合并成一个百分比。项目 GitHub/SQlite/现场证据有不同的真实性、版本和恢复责任。
6. 工程全生命周期可反向修订。发现不符合可以回到需求、系统组成、架构、接口或详细设计重新判断，而不是让编码 AI 自行补设计。

## 历史文件如何使用

本目录原有的产品需求研究、KEY_SIM 变更案例、UI 审查、技术预研门禁和 AutoTest 项目盘查都可作为**来源或候选研究材料**。其范围、日期与是否被批准要逐条核对；不能仅因材料出现在 Git 就自动转成正式工程基线。

**下一步优先验收**：以真实 AutoTest 工程事实和可访问的源码/台架证据，走通一次“AI 工程认识 → 具体对象修订候选 → 用户审查 → 更新设计/输入失效 → 审批后的实施包 → GitHub/验证回馈”。在此之前，页面数量、自动任务调度和漂亮的进度百分比都不构成成熟度证明。
