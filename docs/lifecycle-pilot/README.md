# AutoTest｜演进式系统工程管理试点（候选 v0.1）

> **状态：PROPOSAL / NOT_APPROVED / NOT_IMPLEMENTED。** 本目录只用于审查未来管理工具所依据的模型，不替代已批准 SAEF，不修改 AutoTest 产品代码，不批准任何物理操作或烧录。
>
> 代码参照：`main@4530aba0079e8b2344e4ff5e706049450458a45b`（2026-11-09 查询时）；当前候选 PR 另有独立 HEAD，不能当作 main 已交付。

## 1. 管理对象与目标

管理完整 AutoTest（HW、两套 FW、HOST、夹具、电源、扫码设备、配置与测试数据、外部 DUT 接口），**不管理 AI Agent**。负责人决定产品与技术取舍；AI 负责调研、梳理、影响分析和在批准工作包范围内协助实施。目标是让实施 AI 快速取得**完整且版本一致**的设计依据，同时允许从实现或实测回退到需求、系统架构、子系统架构及详细设计。

首要成功判据：真实发现导致 L1/L2/L3/L4 修订时，系统能自动定位可能受影响的下游项，保存旧批准历史，阻止受影响部分沿用过期实施依据；不阻断无关工作包。

## 2. 与 SAEF / GitHub 的权威关系

- SAEF 的 `engineering/control/work_products.json`、`project_state.json`、批准记录与工件目录是**历史批准事实**；本试点不覆盖、不改写。
- G1 的 `AT-SYS-001～046` 有可定位的文本；早期记载 78 条历史需求，版本关系尚未核对。禁止简单合并统计或凭索引断言全部现行适用。
- `main` 是当前正式软件代码参照，Draft PR 是候选；构建/单测/真实硬件/用户验收相互独立。
- 原始板级资产、固件 ZIP 与现场日志仍有不完整归档项；有登记哈希不等于全部文件可恢复。
- 新工具**只能索引和校验既有正式工件**，不能自行认定旧 Gate 失效、通过新 Gate 或批准变更。

## 3. L0～L6 是知识层次，不是一次性开发流程

| 层 | 工程对象 | 典型内容 |
|---|---|---|
| L0 | 产品上下文 | 使命、CONOPS、场景、边界、约束、硬件事实 |
| L1 | 系统/产品需求 | 可验证的行为、性能、安全、交付范围 |
| L2 | 总体系统架构 | HW/FW/HOST 分工、系统边界、ICD、运行场景 |
| L3 | 子系统架构 | 模块责任、状态所有者、数据及接口分配 |
| L4 | 详细设计 | 数据结构、时序、状态机、异常、调度与验证设计 |
| L5 | 实施工作包 | 精确设计版本、可改文件、依赖、验收与准入 |
| L6 | 代码、集成与验证 | Git SHA/PR、CI、应用操作、真实台架/用户证据 |

任何层的试验和实现发现都可产生影响 L0～L5 的变更。仅**受影响的设计工件和工作包**需复审，不将已通过 Gate 的全部历史推翻。研究原型和真实测试可以在限定安全范围内提前执行，用于发现尚未可知的产品事实，但不能冒充正式功能交付。

## 4. 最小管理对象（不创建 100 张任务卡）

| 类型 | 必填字段 | 作用 |
|---|---|---|
| Context / Fact | id、来源、适用硬件版本、证据级别、当前事实状态 | 保存背景与新发现 |
| Requirement | id、版本、状态、内容、验证条件、来源 | 产品/系统要求 |
| Architecture / ICD / Design | id、版本、状态、覆盖对象、合同/不变量、受影响依赖 | 决定如何实现 |
| Decision / ADR | id、问题、备选、依据、结论、批准者及时间 | 防止 AI 重做已批准的取舍 |
| Change Request | id、起因、来源、影响对象、替代方案、审批、关闭证据 | **向上反馈** |
| Work Package | id、目标、受控输入版本、依赖、范围、准入、退出/验证 | 允许 AI 正式编码 |
| Verification / Evidence | id、适用配置、方法、原始证据、结果、关联对象 | 区分 Build、Mock、真实台架与用户接受 |
| Baseline | id、修订集合及哈希、作用范围、有效时段、审批 | 供实施 AI 取一致的上下文 |

**关系**：`derives_from`（上级需求来源）、`allocated_to`（架构分配）、`defined_by`（设计约束）、`implements`（实现）、`verified_by`（证据）、`depends_on`（依赖）、`supersedes`（替代）、`impacts`（疑似受影响）。关系需包含具体修订身份；不能只存文件路径或最新标题。

**三个独立状态维度**：
1. 设计：`DRAFT / UNDER_REVIEW / APPROVED / SUPERSEDED`。
2. 实现：`NOT_STARTED / IN_PROGRESS / IMPLEMENTED / INTEGRATED`。
3. 验证：`NOT_RUN / FAIL / LIMITED / PASS`，附 `STATIC / BUILD / UNIT / MOCK / REAL_BENCH / USER` 证据类型；不同等级不得互换。

## 5. 向上反馈的闭环（最核心功能）

1. **发现**：L6 运行、用户试用、台架实验或代码审计形成 `Finding`，附原始证据、版本、适用范围；不直接修改已批准的需求。
2. **分类**：判断为事实错误、需求变化、架构缺陷、详细设计缺口、纯实现缺陷或探索假设。
3. **影响分析**：以受影响对象的特定修订为起点，沿 `derives_from / allocated_to / defined_by / implements / verified_by` 展开下游；输出 `POTENTIALLY_IMPACTED` 清单，不自动判定全部失效。
4. **提出方案**：列出保留、局部修订、替换、进一步实验的选项；估算相关风险、成本及回归范围。
5. **批准**：产品负责人明确批准受影响对象的新修订及适用版本。旧版原样可追溯；未批准则维持候选。
6. **实施准入**：工作包锁定批准的需求/设计修订、目标源码 SHA、文件范围、验证合同。依赖修订被替代时，工作包标注 `REVIEW_REQUIRED`，不可静默沿用。
7. **验证与反馈**：记录不同级别证据；新事实可以再触发下一次 Finding/CR，形成演进式循环。

**实施准入（ready-to-code）的五个必要条件**：①目标和验收可测；②上游相关设计为批准且未被影响标记；③跨专业接口/依赖明确；④源码边界及安全限制明确；⑤验证方法和退出条件明确。若未知无法消除，拆分为**实验/研究工作包**，不能让正式编码 AI 擅自确定。

## 6. 本次只验证一个真实演进案例

参见 `cases/CR-KEYSIM-001.md`：现场反馈“20 Key 经电阻组合合成 5 路模拟电压、允许组合保持”可能要求从 L6 回到 L1/L2/L3/L4 的局部修订；包括设计/实施/验证影响，而不自动宣布已具备电压任意设定功能。

只检查如下闭环是否可由本地工具呈现：
- 从 `AT-SYS-011` 定位相关系统约束；
- 显示上级架构、候选下游详细设计、代码和 B4 电气证据缺口；
- 登记不同选项与审批，保留老版本历史；
- 审查后生成一份**可供 AI 编码使用**的工作包上下文包；
- 编码和验证的新发现能再次回流。

## 7. 最小产品试点的退出判据（批准之前不开发 UI）

- 能从本地文件读取、全文检索和浏览 L0～L6、图形依赖和修订链。
- 能识别“有代码但无物理验收”和“旧设计已批准但被新事实挑战”的不同状态。
- 能生成精确的变更影响清单、差异及需重新评审的工作包。
- 试点数据与现有 SAEF 无损共存，单机离线可用，Git pull 可刷新；不需要数据库登录/外部服务。
- 能产生明确、版本固定的 AI 编码上下文包，但不替 AI 执行未经批准的设计变更。
- 实际 UI、运行和数据校验验收完成后，才决定是否扩展为完整生命周期管理应用。
