# Project Control｜产品定义与研发生命周期分离：系统行为规则

**用途**：为通用 Project Control 后续软件设计、AI 入场和交付行为提供清晰的需求边界；不覆盖 AutoTest 已批准 P0 原文，不自动构成新项目批准。

## 不再把三层对象混为一个“P 阶段”

- **产品定义**：长期稳定的产品身份、目标用户、核心价值、主要能力类别与外部边界；是产品信息实体。
- **项目定义**：围绕该产品的一次研发活动的目的、目标、交付范围、约束、负责人、资源与成功标准；是项目章程实体。
- **生命周期管理**：工程过程活动的组织、职责、输入、工作成果、审查、批准、验证、交接和变更；是项目治理和执行实体。

允许一个项目关联多个版本的产品定义，或一个产品经历多个研发项目；不应让“阶段从 P0 到 G0”引起产品定义内容自动变化。

## 对话审批和 GitHub 落档

1. 研究、需求、设计、计划、Gate 等正式工程成果必须**先在对话中完整展示**，说明版本、差异和具体需要决定的事项。
2. **只有对话里明确批准的准确版本**才可正式落档；未批准稿默认留在对话或本地私有工作区，不自动创建 GitHub Draft PR、Issue 候审评论或提交候审文件。
3. 一经批准，在当前授权管理分支内直接保存**准确获批原文和独立批准记录**并远端回读；不再追加“允许把已批准的成果上传吗”的二次批准。
4. 管理工具的普通代码研发属于已委任的开发动作，可在 `Project_Management` 直接编辑并提交，不创建额外分支/PR；但代码提交不等于正式工程内容获批或产品功能已验收。
5. 对超出授权范围的重大变更，需要事先提供完整候审成果和影响，不得靠工具可写权限代替负责人决定。遇到 GitHub 失败或 HEAD 冲突如实报告，不强推、不伪称已落档。

## 现存批准版本与当前 GitHub 布局的关系

AutoTest 的 P0-01～P0-08、P0 Gate `PASS_WITH_LIMITATIONS` 保留为独立准确版本。GitHub 后续采用单仓四分支，属于**管理实现布局变化**，必须记录为变更事实；不自行重写历史批准文件的正文。Project Control 的工具分支和目标业务源码分支可以共享同一个仓库 URL，但应准确区分读写分支，不把旧 `main` 管理工具副本视为新的开发权威。

## 产品定义的质量检查

判断一份“产品定义”是否越界的简单测试：删掉 P0/G0/G1、当前主控板型号、首个 ECU 类型、WPF/Prism、分支和近期排期以后，产品的主要身份仍然清楚。如果必须靠这些研发背景才能辨认产品，那么定义需要重写；详细信息应迁移到项目范围、工程现状或技术设计。

另一个反例：把所有 R1 工具列为产品定义会使任何工具增加/删减都被误读为产品身份变化。正确做法是产品定义维持主要能力类别，具体工具的范围与验证标准进入需求版本。

## AI 接管时应看到什么

先看到产品定义的准确当前版本，再看到项目章程与有效批准，然后根据当前任务选择需要的历史事实和工程过程。产品定义变化、项目范围变化、设计变更和阶段批准必须作为**不同类型的事件**处理；工具不因为字段齐全就自动升级批准状态。AI 报告必须分清“产品是什么”“项目现在要解决什么”“本轮推进的工程过程”“真实证据和下一次决策”。
