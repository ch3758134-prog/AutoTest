# RFC-001｜可信研发控制架构与 AI 协作｜候选方案

- **状态**：PROPOSED / NOT APPROVED；仅用于 PR #28 审查，不修改现行交付协议与主线生产代码。
- **目标用户**：单人产品负责人 + 多个专业设计/预研 AI + 只负责编码的 AI + 本地 Codex + 真机验证者。
- **适用范围**：以软件为主、可能具有多 MCU 固件、PC 程序、多个 Git 仓库、多个部署目标的系统；不预设 AUTOSAR、CAN、ECU 或固定硬件。
- **独立判断**：不采用“项目管理 AI / 编码 AI / 用户 HTML / Codex 四套独立工程数据接口”。它们是**同一工程控制体系**的几种受限使用者。
- **参考**：现有 `docs/delivery/01_交付协议与审批门禁.md`；GitHub branch protection/rulesets、required checks、Issue dependencies；Codex AGENTS.md 逐级指令；Automotive SPICE 系统/软件工程过程区分。RFC 仅从中提炼适用控制原则，不冒称任何标准要求产品完全照此实现。

## 1. 为什么需要重新审查 V0.5

1. **本地 SQLite → Git 仅导出**：本地记录目前是设计工作事实；复制到 Git 的快照可能滞后，也尚不能安全从 Git 恢复。在远程多 AI 协作中无法保证所有执行者收到同一个有效基线。
2. **身份只有文本声明**：`actor="Owner"`、`agent_role="DEVICE"` 和公共本地写入 token 并不建立相互隔离的可信身份。尤其 `/api/studio/bootstrap` 公开返回同一个可写 token；任意能访问本机服务的程序可尝试以负责人身份调用审批接口。当前令牌只适合浏览器防护的一部分，不是 AI 角色授权方案。
3. **指令不是限制措施**：AGENTS.md、Skill、任务 MD 只能引导模型；源码改动范围必须从实际 Git diff 校验，受保护规则须由受信控制层及 GitHub 执行。
4. **工作包只绑定一个 repo/source SHA**：通用系统需要一个产品工程基线同时引用多个软件仓库、工具链/固件/板型/产品配置。编码包允许单仓库单范围，跨仓库交付应拆成多包 + 集成工作包。
5. **“已领取”不是“已执行/已完成”**：任务领取器只是原子登记，尚不能启动或监督独立 AI 对话，也没有可靠失败恢复、续租、身份验证和回写闭环。
6. **缺少真实计划与完整恢复**：没有版本交付计划、时间/依赖管理和工程仓库双向同步，不能宣称具备完整项目管理或自主代理能力。

## 2. 设计目标和非目标

### 目标
- 单一权威协议，统一设计、计划、实现、验证和交付的对象关系。
- 系统/软件架构可以在已验证事实基础上迭代；编码 AI 对产品需求、架构、公共接口无决策权。
- 从 Git 可恢复完整**已批准**工程基线；本地草稿可以离线编辑，并能以 PR 进行审查发布。
- GitHub 承担源码/任务/PR/CI 实际执行历史；现场试验证据可保存在受控本地，Git 只存指纹和适用信息。
- 软件管理、计划、问题回溯与人的决策，在同一 UI 展示并带来源与更新时间。
- 能测试权限、过期输入、共享文件冲突、无证据验收、重复派发等负面路径。

### 非目标
- 不开发四种独立的管理数据库、四套工程文件格式或四个项目真相。
- 不把 ChatGPT 对话标题、AI 自报“完成”、Issue 关闭数、GitHub 绿灯当作产品验收。
- 不允许 AI 自动批准设计、修改自身运行协议、批准主线合并或实施未授权物理输出。
- 不在当前阶段自动启动多代理、承诺持续后台运行或把单机 localhost 当作真正多身份安全隔离。

## 3. 一套领域模型、三个权威存储、多个适配器

```text
  参与者：产品负责人 / 研究与设计 AI / 计划管理 AI / 编码 AI / Codex
                              |
              统一的受信工程控制服务
     规则引擎 + 准入计算 + 版本选择 + 审计 + 任务包生成
                     /          |          \
         工程配置仓库          GitHub          现场证据库
       需求/架构/决策          源码/Issue/PR     测量/日志/配置
       已批准版本快照          CI/commit         文件hash/判定
                     \          |          /
                   本地工作区（草稿和索引）
                              |
                    同一 Web 工作台
```

**权威性按数据类型划分，而非按页面/角色划分：**

- **工程配置仓库（Git）**：经过审查的产品配置、需求、系统架构、软件架构、详细设计、接口、重要技术决定、任务协议与版本基线。可以在 AutoTest 当前仓库内起步；多仓库产品要声明唯一 `engineering_repo`，并引用多个 `software_repos`。
- **GitHub**：Issue、PR、提交、CI 执行结果、版本化源码和审查历史；同步时必须记录精准 SHA、采集时间、分页/错误状态。其 PR/CI 不授予工程设计批准。
- **试验/验证证据库**：保存真实硬件和离线测试原始数据及可追溯身份；工程仓库记录证据哈希、配置和判定，不能把敏感生产数据推到公开 Git。
- **本地 SQLite**：离线编辑中的**候选草稿、索引和缓存**；不是多人协作的已批准事实权威。应提供 Git 导入、冲突检测和恢复，不得以本地未发布修改覆盖已批准 Git 基线。

## 4. 固定协议与项目级配置的区别

### P0：跨项目固定、需版本升级的运行协议
- 命令/数据模型的必填字段、审批语义、证据等级、工作包生命周期、分工权限、例外处理、Git PR 与合并门禁。
- 机器可检查的 schema 与 policy 版本；由受控治理 PR 更新，普通项目管理 AI 和编码 AI 无权修改。
- 正式协议只有一个权威文件及配套校验器；`AGENTS.md` 和 Skill 是**入口指引**，只能引用批准的协议版本，不能复制另一套有冲突的规则。

### P1：允许每个产品单独配置的规则
- 产品家族/版本/板型、工程仓库与实施仓库、构建工具链、设备接口、验证等级、代码所有权与 CI 配置。
- 可以修改，但影响已分发工作包时必须重新评估；版本基线保存原有效值。

### P2：可以持续演进的工程设计
- 需求/假设/预研、系统分解、软件组件、接口、单元详细设计、验证计划、设计决策；任何层次均可提出修改。
- 已批准设计不能直接就地覆盖；只能产生新修订，通过审查再影响下游。

### P3：日常执行计划
- 工作队列、任务安排、依赖、估时、风险与问题。管理 AI 可在受控权限内提出/更新非基线计划，但不可触发设计批准、篡改测试证据或跳过 Gate。

## 5. 能力模型：角色可做的事，而不是四份独立 API

| 参与者 | 允许的关键操作 | 必须禁止的操作 |
| --- | --- | --- |
| 项目管理 AI | 同步只读状态、创建/维护计划候选、拆分建议、识别阻塞、发起工作包提案、催办和汇报 | 修改固定协议，批准架构/实物验收，伪造 CI，直接合并 main |
| 系统/软件设计 AI | 生成需求澄清/候选架构/详细设计、风险研究和变更提案 | 自称已经获得负责人的真实审批 |
| 预研 AI | 创建候选实验、建议方法和判据、分析授权实验的真实证据 | 自行认定实物验证通过或绕过设备安全授权 |
| 纯编码 AI | 接受 CODE_READY 包、修改允许路径、编写指定测试、提交专业 Draft PR，报告设计缺口 | 技术选型、修改系统/软件架构、改公共接口合同、修改固定协议 |
| 本地 Codex 执行器 | 用 exact SHA 检出、编译/运行被允许的命令、收集失败日志/证据；特定授权时领取机械实施任务 | 自主修改设计、自行处理错误、超出工作包修改其他文件、无授权操作硬件 |
| 产品负责人 | 批准重要设计/技术路线/例外、确认实物/用户验收、做交付决定 | 仍须在正式审查与版本控制下操作，不通过“填写 Owner”字符串假冒批准 |

**限制不能仅靠服务端相信一个 `role` 字段。** 后续必须有可信的执行者身份和细分操作许可；即使独立 AI 在相同 Windows 用户下，也需要运行器/OS 权限隔离或仅允许它接触受限仓库/代理 API。现有 localhost 服务可用于个人工作台，但不能声称它已经提供 AI 间的强身份安全边界。

## 6. 工作包不是聊天指令，而是有固定修订的合同

最小的机器可读工作包必须包含：

```text
TaskId / TaskType / ProjectId / ProductBaselineId / PolicyVersion
RequirementRefs (id,revision,hash)
ArchitectureRefs (id,revision,hash) / DetailDesignRefs (id,revision,hash)
EvidenceOrResearchDecisionRefs (where applicable)
RepoTargets [{repository,base_sha,allowed_paths,blocked_paths}]
Dependencies / SharedInterfaceOwner / CIProfile / VerificationContract
AcceptanceCriteria / SafetyConstraints / ContextManifestHash
ExecutorRole / DispatchAuthority / ExpiryOrRevalidationConditions
IssueRef / PRRef / EvidenceRefs / StatusHistory
```

- **CODE_READY** 校验用于“纯编码”类型：不能只靠一段总体架构说明放行；必须有被批准的软件单元详细设计（接口、行为、状态、并发、错误/恢复、可判定测试）。
- 研究/设计类型不能伪装成 CODE_READY，但允许在明确的研究许可下继续调查以消除不确定性。
- 上游设计变更、代码基线变化、实验结论重开、公共接口冲突会使相关任务包 **STALE/REVIEW_REQUIRED**；不影响不相关的其他模块工作。
- 任务包严格禁止任意自定义“执行脚本”在无审查时作为特权命令运行；执行命令来自信任的 CI/工作包允许清单。
- Codex 领取必须从受信控制服务获得 manifest 和精确设计上下文，领取只表示 ACCEPTED，不表示已编译或验收。

## 7. 实际协作状态分离

- **工程对象**：DRAFT → IN_REVIEW → APPROVED → SUPERSEDED（或 REJECTED）
- **研究**：OPEN → EXPERIMENT_AUTHORIZED → EVIDENCE_REVIEWED → DECIDED / REOPENED
- **执行**：PLANNED → CODE_READY → DISPATCHED → CLAIMED → PR_OPEN → REVIEWED → INTEGRATED
- **验证**：NOT_RUN / FAILED / PASSED / NOT_APPLICABLE，分别记录 UNIT、INTEGRATION、TARGET_HARDWARE、USER_ACCEPTANCE。
- **计划**：NOT_SCHEDULED / SCHEDULED / AT_RISK / BLOCKED / DONE，可独立于上面的状态变化。

不要将上述状态压成一个“项目完成率”。真正的版本交付还须独立判断能力、风险及证据。

## 8. AI 管理者的工作闭环

1. 从 Git 批准基线 + GitHub 真实事件 + 验证证据构建最新项目视图。附每条数据的来源和同步时间；不可联网时保留陈旧标识。
2. 比较产品目标和计划，检查未解决的需求/技术/设计/编码/集成/实测阻塞，生成有依据的 **下一步建议队列**。
3. 允许低风险的计划整理、分类与 Issue 维护走预授权范围；设计基线、代码派发、外部写入、硬件实验、合并和验收分别有权限门禁。
4. 形成下一项研究/设计/实施/验证工作包提案，依据任务类型选择不同的完成/准入合同。
5. 经审批的编码包才进入专业队列。执行 AI 实际领取并产生专业 PR；项目经理只读 CI 事实并决定是否需要设计者重新研究或继续验证。
6. 每个回合记录本次推进、阻塞和决定，使负责人可以在 UI 直接介入，且历史可从 Git 及日志恢复。

**项目管理 AI 的职责不是替代人直接作出产品决定，而是根据确定的工程事实不断组织下一件可推进的工作。** 阻塞需要反馈，不是让 AI 重新临时编造设计。

## 9. 用户网页不是另一个管理系统

同一数据模型提供：
- 项目驾驶舱：目标版本、实际与计划进展、下一项里程碑、GitHub PR/CI、延迟原因、需要人决定的事项；
- 产品/系统图谱：需求 → 系统元素 → 软件系统/组件 → 单元设计 → 代码 PR → 验证；
- 预研与实测：候选、实验、原始证据、适用配置与风险；
- 变更和影响：哪些设计及工作包过期，估计影响到哪些交付计划；
- AI 工作队列：可接任务、已认领、实际执行/阻塞、设计版本、真实提交和验证情况。

每个状态有明确来源链接、基线身份和更新时间。没有可信日期/证据时显示“未知”，不以虚构进度补白。

## 10. 高风险边界和 GitHub 保障

- GitHub 规则集和 Required Checks 应约束 main；不能把 `AGENTS.md` 当作安全控制。适用于单人负责人环境的规则不能强制要求一个根本不存在的第二审批人。
- CI 应由受信基线中的工作流提供，按 PR exact HEAD 和适用配置执行；防止在高权限 workflow 中检出不可信候选代码。
- 校验实际 diff 与允许文件范围、共享接口所有权、协议/任务包版本和测试要求。测试失败时保留原始日志，不能由编码 AI 私自扩大设计范围。
- 区分编译、单测、集成测试、真实设备与用户验收。实物日志默认本地受控，Git 只存可复核指纹/摘要。
- 安全凭证按执行者最小权限发放。当前同一 localhost CSRF token 不作为授权凭据。未经验证的权限机制禁止启用无人值守的 AI 写入/审批。

## 11. 从 V0.5 的迁移，不另建一套重复管理工具

**M0｜完成协议审查（当前）**
- 此 RFC 作为候选；保留现有 UI、数据和测试，不强行改变 AutoTest main 的交付协议。
- 定义一致性、角色越权、过期输入、真实归档恢复与交付追踪等验收场景。

**M1｜可信数据内核与权限**
- 确定 Git 工程配置模型和版本 manifest，增加本地草稿与 Git 批准基线的双向导入/发布/冲突检测。
- 拆分项目经理、设计者、编码器、验证器的受限命令能力；负责人审批不能只依赖文本姓名和公共 token。
- 增加可机器验证的 protocol/schema/version 和 GitHub 必需检查。

**M2｜项目计划与自主协调**
- 基于真实产品能力、工作包、Issue/PR/CI/实测证据，生成版本计划、依赖、阻塞、下一步候选和审查队列。
- 先实现单回合可重放、可审计的 AI 管理决策；经过实证后再考虑自动循环和多代理常驻运行。

**M3｜受控 Codex 交付与验证**
- 完整任务包含多个软件目标的基线引用，按单实现仓库分拆；工具链和命令精确指定。
- 编码权限受限定路径和受信 CI 校验，PR exact HEAD 收集测试与实测证据，失败反馈设计层。
- 形成跨 GitHub 与本地管理系统的真实可追溯闭环。

**验收优先级**：先证明一次需求/未知技术 → 预研/实测 → 被批准设计 → CODE_READY → Codex 编码/PR → CI → 真实验证 → 发现问题后返回设计的端到端闭环，再扩展甘特图和更多 UI 页面。

## 12. 需要用反例验证的系统不变量

1. AI 声称角色为 Owner、伪造请求头或读取公开 bootstrap，不得越权批准架构/实物验收/合并。
2. 模块 A 改动共享接口，模块 B 的旧编码包不得继续派发；不相关模块 C 不应被全局停工。
3. 工作包完整但 source SHA 不存在/错误或设计修订不一致，不得标为 CODE_READY。
4. Issue 关闭、Draft PR 绿灯、单测通过不能自动令产品能力显示 USER_ACCEPTED。
5. 本地草稿与 Git 批准版冲突，必须展示差异及选择，不能静默覆盖。
6. 项目负责人可以从 Git 仓库完全恢复已批准的工程关系及决定，不能依赖原本的聊天记录。
7. Codex 交付尝试修改超范围文件、主线或协议文件，CI/受信提交审查必须拒绝。
8. 研究/实测失败有来源和适用配置，重试保留历史，旧结论重开使相关编码包失效。
9. 同一任务不能被两名编码者同时领取；超时/故障恢复必须有明确重派与审计。
10. 无有效 GitHub/现场同步时 UI 标记 STALE/UNKNOWN，不得用缓存推断最新交付情况。

## 结论

**优先修正确认事实与权限，而不是扩展四套互不约束的 AI API。** 对外使用体验可以按角色优化，但所有写入通过统一的工程控制服务、统一协议和可独立检验的版本/证据准入。没有这个底座，再多 Skill、AGENTS.md、计划卡片和代理对话都会重复当前的管理混乱。
