# 12｜AutoTest 扫码编号、产品识别和工程路由专题研究（讨论稿）

**状态：DISCUSSION / NOT APPROVED。** 日期：2026-11-27（按用户最新截图文件时间标记，具体仓库提交仍以 Git 为准）。本文件是业务概念澄清，**没有授权自动修改生产条码合同**。与“11｜多工程生产系统架构研究”配套。

## 一、问题定位

当前“扫码如何选择工程”把三类本来独立的问题合成一张配置表：物理扫码枪输出一段什么内容、这段内容如何得到 ECU 唯一身份、哪一份已安装工程负责检测该 ECU。现在界面强制选择“单工程 / 分隔字段 / 编号登记表”，在一个工位有多种真实供应商条码格式时不能合理扩展。用户此前已明确不接受必须预填 ECU 型号、ProjectId 进入外部条码或日常反复发布工位配置。

正确拆分：
1. **物理输入层**：COM/PnP 设备、扫码原始文本、完整帧/错误帧和时间；原样立即展示，不能因业务匹配失败而藏起来；不得把扫码本身当作物理 START。
2. **编码理解层**：标识方案 + 解析器。获取实际可证明的单位序列号、产品识别码、批次或硬件版本；不要求任何标签都包含所有字段；格式不明就是格式不明。
3. **产品归属层**：条码提供产品码时可直接查产品；只提供流水编号时需可信的编号归属表/MES；无归属来源且多份候选工程时拒绝猜测。单一有效工程的工位可以把完整扫码原文作为身份，无需人为补字段。
4. **工程版本路由层**：产品识别 + 现场明确规定的硬件/批次条件 → 唯一安装版本（ProjectId+PackageHash）；一工程可适用于多个产品，也可同产品保留多个历史工程版本。只有一个版本可用于当前条件，失败不能回退到最近打开的工程。
5. **执行记录层**：一台实体 ECU 的稳定身份不同于某次检测 RunId；重新扫码既不是新增产品，也不是隐含的复检通过。实际完成复检时使用新 RunId 关联原单位及具体工程版本。

## 二、已经确认的 R1 源码事实

- SerialScannerWorkbenchViewModel / AutomaticTestHomeViewModel.Scanner 已将真实 COM 原始扫码与业务接受状态分离。
- ProductionProjectCatalog 当前只有一个全工位 Mode：Single / Fields / Registry；Fields 使用分隔符与固定字段序号；Registry 使用整串序列号查表；routes 通过 (product_key,hardware) 绑定一个安装包版本；单工程模式支持显式唯一绑定。
- 当前序列号校验主要限制 ASCII 字母、数字、下划线、点、连字符，长度最多 64 字符；无法直接假定支持全部合法客户标签、GS1 AI、变长字段或多个条码格式同时存在。
- 当前工程包导入与受控版本管理已建立源码候选，但无 Windows 编译与现场证据。正式实体 START、机械到位反馈和完整生产记录仍未满足；不因扫码解析而开放生产。
- 工程产品属性 EcuModelCode 不能替代条码产品识别规则；用户已经拒绝为运行扫码强制输入此字段。

## 三、由易到难的真实运营场景

| 场景 | 实例（仅虚构格式示意） | 能确定什么 | 推荐处理 |
|---|---|---|---|
| 工程师单板实测 | 任意扫码文本 `TEST-001` | 观测文本，未证明产品身份 | 工程调试使用当前已打开工程，不做正式生产计数 |
| 生产线本次只启用一份工程 | `00012345` | 设备编号（按工位的有效识别合同） | 不填写型号、不配分隔符，默认当前唯一有效工程 |
| 多产品共线，码内包含产品信息 | `EPB-A|00012345` | 产品键 EPB-A + 单位序列号 | 受控规则提取、查找产品路由，唯一匹配即选择工程 |
| 多产品共线，条码只有编号 | `00012345` | 只能知道编号 | 经已核对的编号归属表/MES 查产品；没有归属时拒绝 |
| GS1 条码 | AI (01) 商品识别号、(21) 序列号、可选 (10) 批次 | 按 GS1 码制识别产品与单件信息 | 必须采用合规 GS1 解析（含必要分隔符），不能简单以竖线/字符串索引切割 |
| 同一单位复测 | 同一真实条码再次扫描 | 仍是同一单位 | 保持 UnitIdentity，新的物理检测才创建新 RunId 和可追溯复检链 |

注意 GS1 AI (01) 标识 GTIN，(21) 为序列号，(10) 为批次；这只是支持标准标签的一种可选解析，不意味着 AutoTest 自己必须采用 GS1。
来源：https://ref.gs1.org/standards/genspecs/ 与 https://support.gs1.org/support/solutions/articles/43000757407-which-data-elements-application-identifiers-ai-should-must-be-used 。

## 四、反对继续沿用的配置方式

不再让生产操作者在每次扫码前选择“单工程/多工程”、填写字段 1/2/0、填写硬件版本、手动激活另一个工程。也不应在每份工程编辑器里重复保存一份“扫码枪规则”。

当前 R1 管理界面提供的“三模式”仅是一个可演示的初级配置，不应被认定为长期设计定稿。工业现场常见多供应商/多标签规则并存，必须按**规则集合**和**产品路由**分别建模；每份已启用规则需要正反例验证、唯一性检查及版本快照。不能按顺序盲目选择第一个匹配规则。

建议专业管理入口只有“生产工程”和“编号识别”两类配置，扫码输入、身份解析、归属关系、工程选择的详细调试只在“编号识别”管理工作台展开；正常生产主页仅显示原始扫码、识别后的 ECU 编号、选中工程及不能启动的准确原因。

## 五、推荐的可视化调试流程（不是额外生产启动步骤）

1. 管理员点击“测试扫码”，由真实 COM 扫一条现有标签；界面立即显示原始值。
2. 系统展示能被可靠解析的信息。如果条码包含多段数据，明确指出哪段被当成产品识别码、哪段是单位编号；不明确时给出“未确定”，不臆测。
3. 选择可信归属来源：码内产品字段、离线编号归属表、当前唯一有效工程；不强制填写额外 ECU 型号。
4. 预览“这条码 → 产品/ECU编号 → 唯一工程版本”；用有效/无效样例检查规则冲突。
5. 确认规则启用后，不影响已运行会话，新增扫描才按新版本判断。配置更改留有修订和操作记录。

## 六、必要的领域合同（待讨论）

建议明确 `BarcodeObservation`、`IdentityParseResult`、`ProductOwnership`、`RoutingDecision`、`RunIdentity` 五个不同对象。比如
`BarcodeObservation = raw + COM设备ID + receivedAt`；
`IdentityParseResult = parserVersion + canonicalUnitId + optional productKey / batch / hardware`；
`RoutingDecision = packageSha + projectId + ruleVersion + rationale`；
`RunIdentity = canonicalUnitId + RunId + exact packageSha`。

产品身份唯一性的范围必须由业务规则证明：不同供应商或产品系列可能使用重复的序列号，因此“序列号字符串”不一定天然全球唯一。对现有已经认定唯一的扫码枪编号，不得擅自加前缀重写历史 ID。

## 七、先达成共识、再施工的开放问题

1. 正式生产的真实码由客户/供应商已经确定，还是由 AutoTest/生产现场可以制定？这一点决定是否需要多种解析规则和 GS1 支持。
2. 多工程混线时，产品信息来源是条码本身、工位本次任务，还是外部编号登记？**绝不能把多工程路由建立在对纯序列号的猜测上。**
3. 同一产品在不同硬件版本与工艺变更下怎样选择唯一生效的工程版本？按产品 / 硬件 / 批次等真实已知条件配置，不凭名称或“最新版”猜选。
4. 编号改绑和生产线返工/复检如何授权与审计，尤其此前记录的产品归属是否可被更正？

目前只形成候选方案，不需要用户立即提供正式条码样本才能继续工程调试。正式编码规则确定后再实现更多解析器；此阶段**不擅自添加强制型号字段、不重写历史 ECU 编号、不将抽象规则当作真机验收**。
