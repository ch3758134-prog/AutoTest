# P0-02｜AutoTest 生命周期与阶段计划

> **工程工作产品**：SAEF v2.0 · `P0-02` · v001 · 提交负责人审查
> **交付边界**：仅明确阶段准入、依赖、责任、输出及准出规则；**不等于批准 P0 Gate、技术基线或编码授权**。审批状态以本地 `work_products.json` 与授权记录为准。

## 一、目标与计划依据

本计划把 AutoTest 的**完整产品范围、分阶段交付**组织为可审查、可恢复的工程过程。项目面向公司内部研发、生产检测和维护人员，以自动测试为主，兼顾调试、故障复现及维护。当前 EPB 是首个实际被测对象，UDS、CAN 烧录、多 ECU 适配、双 DUT 等均保留在产品总范围内，不在本计划承诺交付版本和日期。

**规范依据**：`FRAMEWORK/catalog.json`（SAEF v2.0，P0—G5 的阶段与工作产品）、`FRAMEWORK/standards/07_Gate评审与批准.md`（Gate 签审）、`DELIVERY_PROTOCOL.md`（增量交付）。**项目输入**：负责人已批准的 `P0-01 v004` 内容及 `AutoTest_Engineering_Master_v2.1.html` 历史资料。后者只用于识别既有研究与候选证据，**不自动形成 SAEF 工作产品批准或 Gate 迁移**。

本项目采用**证据驱动的相对日程**：依赖关闭、交付物接受和 Gate 授权构成阶段推进条件；日历工期、资源工时、性能及生产验收阈值目前均未确定，不凭空填写。研发可以在获准范围内按工作包渐进迭代，但“形成设计、完成编码、编译通过、单测通过、实机通过、发布接受”必须分别记录。

**编号一致性说明**：历史 `AutoTest_Engineering_Master_v2.1.html` 使用 G0—G6（G6 为接受/发布）；当前 SAEF v2.0 的正式流程使用 **P0—G5，且 G5 包含发布**。这里不改旧文档，也不宣布历史 G6 自动通过。历史成果向新工作产品的映射与证据审核由对应阶段办理。

### 2.2 先后依赖与推进规则

1. **同一 Gate 内逐项交付**：ChatGPT 按 catalog 合同完成一项工作产品及自审报告，负责人批准后，Codex 按批准包落档；确认落档后再关闭该项并组织下一项。
2. **工作产品接受 ≠ Gate 通过**：某一 Gate 的全部必要工作产品完成后，另行汇总配置、证据、限制并申请 Gate 审查；Gate 由负责人决定。
3. **历史成果继承须经证据映射**：已有 G0/G1/G2 研究成果可以直接引用、减少重复研究，但原 HTML 的阶段状态不能自动写入 SAEF 审批记录；缺口经审查定位后只补缺口。
4. **未获实施授权不得启动 G4**：G3 的设计/工作包内容获批准后，仍需明确允许文件、集成前置条件和执行授权，方可开始该工作包的编码。
5. **验证可以分层但不能降级冒充**：项目已明确以真实软硬件通路和可操作的简易上位机为主要阶段验证形式；具体顺序、用例、通过阈值由后续 G1/G2/G3、P0-06 及验证工作产品制订，不由本计划规定。

**资源配置原则**：当前按“负责人 + ChatGPT 技术总控 + Codex 机械执行”组织，不虚构独立部门、人力或确定工时。Windows 开发机、两块现役板卡、工装、ECU、编译/调试工具与外部数据是实际依赖，**其可用版本及现场条件由 P0-07 / G0 核查**；本计划不声称所有设备当前已就绪。

## 四、里程碑与审查条件

以下是**顺序性条件节点**，不是时间承诺或软件发布版本：

| 节点 | 触发条件 | 审查后允许的下一动作 | 明确禁止 |
|---|---|---|---|
| **T0：P0-01 落档确认** | 负责人已批准 v004；需收到 Codex 的 apply、审批登记、校验和 Git 状态回传 | 形成 P0-01 关闭证据，继续 P0-02 审查/后续 P0 工作产品 | 未见真实日志就标记“已归档” |
| **T1：P0 工作产品齐备** | P0-01…P0-08 均有 ACCEPTED 与对应证据 | 编制正式 P0 Gate 审查包 | 以八份文档存在代替批准 |
| **T2：P0 Gate 决定** | 完成配置/权限/追踪/恢复核查；负责人批准或附限制批准 | 按决定范围组织 G0 的正式工作产品接收 | 自动迁移历史 G1/G2 PASS |
| **T3：G0/G1/G2 资料接收与逐 Gate 审查** | 每个阶段逐项完成工作产品、差异关闭或受控限制、审批和 Git 基线 | 进入获准的下游设计范围 | 不审查直接“批量 PASS”或重写历史批准对象 |
| **T4：G3 可实施合同** | 具体工作包的详细设计、接口、测试、文件范围获审查 | 申请对应范围的 G4 授权 | 仅凭架构草图启动编码 |
| **T5：G4/G5 验证与发布** | 真实编译、测试、台架与使用证据逐层形成 | 按准出决议进入后续组合验证或发布 | 以 ACK、单测或 UI 状态冒充实机/业务验收 |

**迭代处理**：同一工作产品被退回时修订同一 ID 并重做内容审查；已接受的基线发生实质变化时执行受控变更，不静默覆写；一个阶段中可开展不改变冻结接口的研究，但不得把“研究开展”写成“Gate 已通过”。
