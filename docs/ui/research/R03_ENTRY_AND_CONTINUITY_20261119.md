# R03｜复杂工业级 PC 软件：入口、持续工作与整体交互架构候选

**研究日期**：2026-11-19  
**工作分支**：`ui/ide-design`  
**前置**：R01 全产品设计原则；R02 工作空间/对象/命令/上下文/状态/恢复六系统与五上下文模型  
**研究结论状态**：RESEARCH_COMPLETED / UX_ARCHITECTURE_PROPOSAL / USER_OPERATION_NOT_VERIFIED  
**责任边界**：只做全产品 UX 设计研究，不改 HOST WPF、TEST/PROJECT/DEVICE 或固件。

## 0. 本轮真正研究什么

不讨论 DBC 信号表的位置，也不再以“用户应该选择哪个三栏布局”开启设计。研究者必须独立解决：第一次启动、无工程、恢复上次工作、文件和任务之间切换、专业工具并行、运行/编辑、故障/中断和保存恢复的产品级机制。

重点是：**入口不是单张欢迎页，工作区不是一组导航页签，工程不是软件会话，当前选中对象不等于已经在操作它。** 决策既需要成熟产品证据，也需要在未来真实可操作 Windows 原型中被验证。

## 1. 成熟软件的产品入口：同一问题，至少四种可行策略

| 产品及一手事实 | 启动/工作入口机制 | 好处/适用条件 | 不应复制的部分 |
|---|---|---|---|
| Visual Studio（E17,E18） | 启动窗提供打开已有、创建、打开文件夹以及“无需代码继续”；启动行为可改最近方案/空环境/开始窗口 | 既照顾新用户，也照顾每天继续工作的专家 | AutoTest 不必把无工程会话假装成已保存测试工程 |
| Siemens TIA Portal（E19,E01） | 支持自动载入最近工程、恢复该工程的编辑器和选择启动视图 | 工程密集型使用中可减少多次重复进入和找文件 | 双视图不是每个软件都必备的固定产品结构 |
| Adobe Photoshop（E20） | Home 提供最近文件、打开/新建、教程；工作时可返回 Home | 首次使用能理解任务，熟练使用能直接打开内容 | 图形创作模板和云文件不是工业测试任务 |
| ecu.test 2026.2（E21） | 启动时选择或创建 workspace；可设置直接进入上次 workspace，也可拷贝样例/教程 | 正式工作空间边界清晰，同时不让空环境毫无参考 | 不应未经调查就给 AutoTest 添加强制 workspace 命名 |

**研究推论：** 没有一种“现代软件必须有首页”的标准。合格入口是基于当前用户状态：新用户有可理解的首个动作，熟练用户能立即继续上次工作，损坏资源时能恢复，软件内部工具不会因为缺少正式工程就全部不可达。

**推荐作为原型候选的入口策略（待操作验收）**：
- 有上次有效工程 → 直接进入上次测试任务；不用显示欢迎页。
- 无有效工程 → 同一个主程序显示轻量任务入口：打开工程 / 新建工程 / 探索编辑 / 进入适用的专业工具；不需要先输入工程名称才能看看编辑器。
- 恢复失败 → 显示原工程路径、失败原因、重新定位、最近工程；保留未完成会话数据，不静默建立替代工程。
- 用户主动退出当前工程 → 返回“无正式工程工作状态”，而不是退出软件或冻结工具。
- 若未来存在专用生产模式，它可使用同样后端，但不默认允许“扫码即进入未保存的工程草稿”。

这不是一套全新虚构的 TEST/PROJECT 格式：探索编辑必须调用正式编辑组件与领域数据模型，保存/归档是另一条业务路径。

## 2. 主窗口是“工作环境”，不是“功能目录”

### 2.1 四个层级，不对应必须存在的四个页面

| 层级 | 用户心智问题 | 应出现的内容 | 不该出现的内容 |
|---|---|---|---|
| Application | 我现在用哪套系统，哪个工程？ | 当前工程、全局工具、最近工作、设备总状态 | 每一种 TEST 步骤参数 |
| Task Workspace | 我现在是在编辑、运行、诊断还是分析？ | 当前工作的关键对象/关键操作/反馈 | 无关专业工具的所有按钮 |
| Document/Object | 我处理哪份文件、哪个步骤、哪项信号？ | 选择、编辑、撤销、导航、校验、引用 | 实体设备控制入口自动乱入 |
| Observation/Status | 修改/执行后发生了什么？ | 校验问题、连接事实、运行事件、错误、证据 | 把未确认的 ACK 误当作物理成功 |

与 R02 的五上下文配合，产品只需一套应用 Shell；任务环境和文档容器可以组合，专业操作类工具允许独立副窗口。**层次是职责划分，不是把用户强迫点击四层菜单**。

### 2.2 进入某任务时，先决定“什么必须在眼前”

- 编辑任务：当前文档/对象及对象相关命令占重点；工程树可帮助导航但不应独占空间。
- 运行任务：选择范围、设备准入、当前执行状态、错误与结果占重点；编辑快捷入口存在，但不能覆盖事实区。
- 诊断/手动工具：刺激、响应、时间记录和硬件安全状态在同一操作上下文中形成闭环。
- 分析任务：信号、曲线、证据及检索占重点；不会为了显示工程树而缩小主要绘图画布。
- 没有对象：展示与当前任务有关的空状态和进入方式，不能只留大片空白和禁用按钮。

因此，“全产品一致”应体现为命令语义/字体/视觉层次/状态标签/输入反馈，而不是每个工作区都固定左树中表右属性。

### 2.3 全局菜单与当前对象命令分开

全局只放真正跨资源的操作：工程打开/切换、保存状态总览、工具入口、设置/帮助、工位状态、后台任务。对象编辑器自己提供插入/复制/校验等命令；常用命令靠近被操作对象，右键菜单作补充而非唯一入口。微软 WinUI LOB 指南区分稳定导航、多文档页签和命令菜单，并明确响应式布局不可简单全尺寸缩小（E23）。

## 3. 用户行为不是“页面跳转”，而是“对象持续处理”

### 3.1 建议的单个对象交互循环

`发现/定位 → 选择 → 在眼前直接修改 → 查看本地合法性/实时反馈 → 继续编辑/关联操作 → 正式保存 → 必要时实体执行 → 观察真实结果`

每个环节必须有明确的对象指向，不能隐式改变其他层级。例如“选中 CAN 行”不是“发送 CAN”；“在文件树选中用例”不是“更改下次运行计划”。

### 3.2 工作连续性不等于无限自动保存

应清楚区分：
- **字段输入缓冲**：正在编辑但尚未完成的文本，不可悄悄转为正式参数；
- **文档草稿/事务**：已通过模型/引用规则的修改，可以保留撤销；
- **正式保存**：明确写入 PROJECT/DBC/TEST 文件、修订与依赖一致性；
- **软件会话快照**：窗口/工具/编辑位置及可恢复未保存内容，是恢复用，不代表正式资源已保存；
- **运行快照与证据**：由真实 TEST/DEVICE 产生，不受后续编辑改变。

Visual Studio Hot Exit 可以作为机制证明（E05,E16），但是否在 AutoTest 实现同等级别的会话恢复，仍须 PROJECT/TEST 正式能力评估；不能写临时假格式骗过用户。

### 3.3 打断后继续工作是核心体验，不是例外

NN/g 关于复杂软件中等待和中断的研究建议展示过程信息、保留工作思想和历史上下文（E22）。这意味着不仅恢复窗口尺寸，还需恢复“我正在做什么”：活跃项目、文档、对象、过滤条件、游标、未完成参数和后台任务。恢复内容应按风险分类，**不能恢复之前的真实物理输出命令作为自动重新执行**。

## 4. 用户旅程 1：第一次打开，想看编辑器

**原设计失败**：把资源创建前置为了解界面或试用编辑器的必要条件。

**候选流程**：
1. 启动后无上次有效工程，进入完整主程序而不是强制工程新建弹窗。
2. 中央“开始工作”显示三个主要入口：打开已有工程、建立新工程、探索编辑环境。专业工具从全局入口可达。
3. 探索编辑 → 打开正式 TEST 编辑器的未归档合法样例会话，界面明确“未属于正式工程/不能运行”，但提供真实步骤插入和属性操作。
4. 用户随时可退出、重开、转正式工程；需要保存成果时明确选择工程归属和资源合法性检查。
5. 设备未连接仅影响实体执行，不阻止普通离线编辑。

**验收失败条件**：仍需创建假工程、给“未命名”强迫取名、展示一套和正式编辑器不一样的体验、按钮看似成功却只改虚拟对象。

**工程缺口**：正式 TEST/PROJECT 能否支持未归档文档、依赖检查、导入/归档流程，需专业团队适配；仅 UI 层不能偷偷做第二 DSL。

## 5. 用户旅程 2：继续昨天已经准备好的真实测试工程

1. 启动识别上次工程及打开的测试项目/当前选择，按用户既定方向直接进入“运行当前任务”。
2. 真实设备状态单独读取：工位未连接不影响恢复工程和编辑位置。
3. 运行区直观看到本次勾选用例、资源预检、设备状态；编辑时共享同一个当前项目和用例。
4. 只有提交并验证的正式项目资源才可进入 Run 预检；一次 Run 建立不可被编辑随意改写的配置快照。
5. 运行结束返回工程任务现场，报告/证据可追踪；工具切换不能把运行目标悄悄变为别的用例。

注意：是否自动在启动时打开“最后编辑的用例”并不必然等于“立刻开始执行”；这两件事应完全分开。

## 6. 用户旅程 3：工程师中断工作、打开第二个专业工具

1. 从工程编辑环境打开手动台架，原文档页签和选中步骤保持。
2. 工具窗口内可按专业任务进行输入/编辑/查看；使用共享工程资源但有临时编辑会话。
3. 打开 DBC 编辑器或波形窗口时，台架的报文列表、过滤器及选中对象不被重置；如果共享资源发生版本变化，必须可见且有明确刷新/确认机制。
4. 关闭工具，只结束该工具工作会话；不删除当前工程资源，也不未经授权改变实体设备状态。
5. 若正式 Run 已获得工位独占租约，其他工具仍可查看允许查看的内容，但所有写入实体操作按设备域合同明确阻断。

**归纳**：工具独立窗口不是“另一个程序”，而是同一应用里服务于特定任务的持续工作环境。

## 7. 用户旅程 4：一次真实执行失败并回到编辑

1. 运行过程显示真实阶段、步骤、错误及原因；命令可用性由真实执行状态确定。
2. 发生失败后允许查看对应执行事实、时间线、设备错误、测量和证据；报告是独立的历史产物。
3. 从失败步骤跳回对应测试用例的编辑器，定位原步骤定义，但保留 Run 所用的冻结快照；不能用修改后的定义替换历史。
4. 保存修改后，新的运行必须重新做预检，之前的结果不受影响。
5. 返回运行视图后，依然能找到刚才分析的证据和关联对象，而不是重新打开一串文件。

NI TestStand 文档强调执行窗口跟踪、断点与调用栈，过程模型还包含 UUT 识别、记录和报告（E25）。这些是分析/执行分层的产品参考，不能据此替换 AutoTest 当前 TEST 的失败处理规则。

## 8. 状态反馈与操作等级：保证简洁但不失真

| 操作风险 | 典型行为 | 候选 UX 要求 |
|---|---|---|
| R0 浏览 | 打开、搜索、定位、选中 | 不多次确认，不改变正式资源 |
| R1 可撤销编辑 | 改字段、移动步骤、切换信号 | 直接操作、撤销、即时标错、保留未完成输入 |
| R2 正式资源提交 | 保存/覆盖/删除/更新引用 | 完整校验与冲突检测，必要时明确确认不可逆变更 |
| R3 工位物理输出 | CAN/IGN/夹具/KEY 等真实控制 | 身份、所有权、许可、请求/应答/外部结果分层反馈 |
| R4 高后果操作 | Flash、正式生产启动、不可逆实体动作 | 真实 preflight/授权/取消/审计，不因 UI 简化跳过安全门禁 |

这是**UI 风险分层建议**，不是重新定义硬件/安全授权。不同实体命令的真正危险性由 DEVICE/FLASH/TEST 专项确定。

## 9. 准备制作的可操作原型：四种状态、一套共享任务模型

原型 P1（无工程）：完整 Shell 可进入工程打开/创建/探索编辑；无假运行。重点验证用户不需要先填写工程名就能找到并操作正式编辑器。

原型 P2（工程空白）：有正式工程但无测试项目/用例；展示创建第一项测试内容的任务引导；创建后直达编辑现场，而不是再找资源。

原型 P3（已有工程）：恢复上次项目/用例，运行与编辑共享选择；显示真实设备状态，运行操作无实测权限时清楚禁用。

原型 P4（恢复问题）：上次工程被移动/损坏或工作区处于未完成草稿；让用户重新定位/恢复；不静默替换和丢失上下文。

**重要：** 不要求每种状态写成一个独立大页面；它们可以是同一工作环境根据上下文切换的内容状态。是否真正需要类似 TIA Portal 的独立任务首页，需实际 UX 实测后决定。

### 原型任务检查

- P1：打开软件后无需建正式工程就能查看真实编辑体验。
- P2：新建第一个项目/用例完成后自动进入内容编辑，不重复导航。
- P3：切换运行/编辑仍是同一当前项目/用例，工位未连接能编辑但不能实体运行。
- P4：工程丢失后能定位并恢复，非强制从零新建。
- 全局：主窗口与独立工具一致性、Windows 原生关闭/缩放、屏幕分辨率和 DPI、状态提示以及输入焦点。
- 后续 R04：用同一个完整原型添加对象相关直接编辑、上下文命令、版本/保存反馈、恢复历史和跨工具任务。

## 10. 仍然需要验证的设计分歧

**D01 任务入口形式**：独立欢迎页 / 主窗口空状态 / 可折叠开始面板。当前优先尝试“同一主窗口的空状态”，原因是减少一次导航且不污染熟练用户的运行入口；但需要实际操作验证，不能提早冻结。

**D02 无工程临时编辑**：正式编辑器未归档会话能否稳定使用同一领域模型、如何管理引用与保存；这不是 UI 的一项随意数据结构决定。

**D03 多工作环境**：保持运行与编辑两个主任务页签作为当前用户已确认的工作安排，但多窗口/工具切换时是否显示可见工作历史，由实测再定；不因为 IDE 案例就强制上自由停靠。

**D04 工业操作模式**：工程师和生产操作员是否需要单独的启动入口/界面权限，当前保留为后续场景级问题。用户未要求现阶段拆分两套软件，不能自行冻结生产模式为新进程。

## 11. 下一轮任务和研究边界

R04 应进入“统一对象操作语义与专用编辑工作区”深度研究：
- 使用 T01~T16 的真实连续任务，对比 VS/Ignition/TestStand/Fusion 等的对象选择、直接编辑、上下文命令、属性、批量、撤销、导航和保存。
- 将操作规则落实为可交互的 WPF 原型范围和验收脚本；优先解决入口与编辑连续性，再扩到完整工具。
- 对 UI 无权实现的临时领域模型、正式保存版本、共享资源刷新和真实 Run 状态，向专业团队输出精确接口需求，而不是写第二套业务模型。
- 不预先规定所有页面三栏或同一 inspector。拒绝拿旧 G4 XAML 当设计基线。

## 12. 研究结论

真正的入口重设计不是把“新建工程”变成“体验编辑器”一个额外按钮，而是**清楚区分用户正在继续工作的软件会话、正在处理的编辑内容、正式资源和真实执行权**。

当前采用的全局设计方向是：任务更容易进入；编辑现场保持；资源归属明确；专业工作区可以不同；真实物理操作的授权及证据与普通编辑绝不混同。

**R03_RESEARCH_COMPLETE / INTERACTION_ARCHITECTURE_CANDIDATE / NO_WPF_CHANGE / NO_USER_VISUAL_ACCEPTANCE / NO_FIELD_VALIDATION**。
