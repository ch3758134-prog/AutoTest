### 本次发现并解决的高优先级错误

1. **P0 / TEST Project 运行前静默换最新版资源**：此前冻结整组用例时读取最新 TEST，并把 `PackageRevision/PackageSha256` 重写为当前资源版本；即使用户没有点击“更新引用”，也可能直接执行新的内容。改为在运行前检查 `row.Revision/row.Sha256` 与实际 Asset 和重新打开的文件三方一致，否则完整阻断，不得偷偷升级。冻结对象严格使用 `row.ToEntry()`。
2. **P0 / 后台步骤计数清除已冻结批次**：此前 `StepCountLabel` 属性通知也进入 `RowChanged`，导致真实运行前检查完成后异步统计步骤数就可能撤销准备状态。现只让会影响执行的字段或资源版本变化失效冻结；纯显示性字段通知不影响准备。相同资源修订重复刷新不发通知。
3. **P0 / 同版本 SHA 漂移错误地可“一键采纳”**：现在仅 Revision 严格递增才允许显式更新；相同 Revision 不同 SHA、资源移除、修订倒退均定义为不允许采纳的修订来源异常，必要时先恢复受控资产。项目失效总标志覆盖上述情况，而不仅是“存在较新版本”。
4. **P1 / KEY 在等待保存期间旧按钮仍可能执行**：异步 `SaveKeyActionsForCloseAsync` 之后增加最新点击序号复核；双击编辑、右键操作、后续点击和关闭窗口会作废过时的发送意图。
5. **P1 / TEST 项目名称规范化引起永久 Dirty**：成功保存后仅在名称输入未发生更新的前提下回写实际已存名称，避免首尾空格导致无尽自动保存，同时不覆盖保存期间新输入。
6. **P1 / WPF 定时器异常造成操作界面崩溃**：TEST、TEST Project、原生 FLASH 的异步自动保存定时器均有异常边界，失败保留草稿并报告。手动台架和 KEY 属性窗口不再仅把自动保存错误隐藏在 Trace，而有可见状态信息。
7. **P1 / KEY 与 CAN 自动保存时机不合理**：原 7 秒轮询、4 秒闲置及 KEY TextBox 保持焦点会导致有效修改迟迟不保存。改为短周期检查和 2 秒闲置后保存；仍由真正资源校验阻断非法草稿，运行前必须用同一持久化合同。

1. **真实 TEST 执行器彻底禁止内部自动重绑定 DBC/WAVE**：此前 `RealTestWorkbenchService.Prepare()` 会再次执行 `BindCurrentRunResources`，使已经严格冻结并预检的 DBC/波形映射在最后执行前被替换为工程当前最新版。现在准备真正 TEST 的 `PlanCompiler` 直接使用原始作者保存的 `TestDocument`；底层 `LiveDbcSignalService`、`ConfiguredStationActionPort`、`ConfiguredWavePort` 已严格验证对应资产修订和 SHA256，失配即拒绝执行。原始资源证据不再被无授权地“修好”。
