# AT-PRODUCT-001｜AutoTest 软硬件产品定义与激励—响应模型（研究候选 V3）
> 2026-11-10｜记录用户对候选 V1/V2 的实质纠正。本文件仅为可审查研究候选，不是产品正式基线、G3/G4 修改许可、编码任务、GitHub main 变更，也未导入本地 Engineering Workbench。

## 0. 本轮澄清的直接事实与历史错误
- 用户明确 AutoTest **包含 Windows 上位机、主控板、按键板**，不是“上位机软件接第三方硬件”的产品。被测 ECU（DUT）是外部测试对象。
- 用户明确这套系统的设计目的是**模拟 ECU 的全部外部刺激**。现阶段主要可讨论的刺激方式为 **IO 控制、CAN、按键**；未来 ECU 类型与激励能力需可扩展，不能把当前现役硬件能力写成最终产品边界。
- 用户明确对**接收到的 CAN 数据**的处理远不止接收；相关能力与其用途仍需具体梳理，不能未经讨论将其限缩为 DBC 解码或 Wave Verdict。
- 既有“Windows ECU 自动测试 IDE”定位将产品本体缩为软件，“以测试程序为中心”描述又遗漏了物理激励与观测目的。这两个候选均必须重新研究，不能自动标为批准。
- 现有仓库有历史 `SIMULATION_ONLY` README、现场 USB/CAN1 RX 的有限用户实测记录与较旧 R1 看板；这些资料的阶段和证明范围不同，不能用其中某一项替代产品本体定义。

## 1. 新的候选产品定义（非批准）

**AutoTest 是一套由 Windows 上位机、主控板、按键板及其必要接口构成的、面向不同 ECU 的可扩展软硬件一体化外部激励模拟与响应测试系统。**

其目的，是在受控、可配置、可编排、可复现的条件下向被测 ECU 提供或模拟所需的外部输入和操作条件，观察 ECU 的实际响应，并以统一的工程资源和测试模型对通信数据、信号、事件、状态变化、时序与测试结果进行分析、记录和判定。自动测试程序统一编排刺激、采集、条件、诊断动作、判据和异常流程；专业工具可在程序之外独立调试；出厂检测是重要应用场景，但不能反过来定义全部系统架构。

“模拟全部外部刺激”在本阶段是产品**能力覆盖目标**，不是已验证能力宣称。必须按 ECU 型号和适用硬件版本维护刺激覆盖矩阵，区分“支持/条件支持/未支持/未知”，不得假定当前 R1 硬件已经具备所有 ECU 输入类型。

## 2. 必须分开的三个概念

### 2.1 激励（Stimulus）：系统如何主动作用于 DUT
- **IO/电气激励**：当前已确认的控制对象涉及 IGN、夹具电磁阀及实际支持的电气控制点。ECU 电源控制、数字/模拟输入、PWM、故障注入等是否存在以及电气参数如何定义，需逐项依据硬件与实际要求审查，不因名称“IO”而自动宣称支持。
- **CAN 总线激励**：单帧发送、周期报文、按信号值编码的报文、时序联动等作为候选功能；应确认实际发送路径、通道、仲裁、时间与可观察回执。
- **按键激励**：现役按键板 20 Key 电阻网络组合形成五路模拟电压，模拟真实按键，支持组合闭合/保持（这是模拟 ECU 电气输入，不是向 ECU 发送 20 个抽象数字“按钮事件”）。
- **覆盖范围和扩展机制**：其它 ECU 可能需要更多类型刺激。每种刺激须配置硬件能力与限制、可用通道、强度/有效值、时间、操作授权以及安全状态，不假定永久只有上述三类。

### 2.2 观测与解释（Observation & Interpretation）：系统如何理解 ECU 响应
- 当前重点为**CAN RX**：真实物理帧、通道、时间戳、周期、源设备与质量信息的连续采集。
- **协议与数据处理**：CAN ID 监视、过滤、记录、回放；DBC 解析与在线信号解码、缩放、单位、位宽、有效范围、状态位；诊断通信的请求/响应与 ISO-TP/UDS 语义须与普通被动 CAN 数据监视分清。
- **状态和时序分析**：从信号/报文形成可使用的 ECU 状态、事件触发、时间关系、窗口、超时、缺帧、异常以及统计；相关具体规则需要继续与用户核对，不能单凭此表冻结。
- **波形与判定**：对合适的信号/事件保存参考、分析实际曲线、窗口与误差、输出具有明确证据来源的判定。Wave 不是 CAN RX 的唯一消费者或最终目标。
- **测试结果组织**：原始观测→可追踪的解析结果→时序/逻辑判定→StepFact/Verdict→运行记录/报告，任何判定都必须能回查实际输入、刺激上下文及所用规则版本。

### 2.3 自动测试执行（Orchestration）与专业工具
- 测试程序是把**刺激、等待/条件、响应观察、诊断/烧录、比较判定、控制流和异常清理**组织成可编辑、调试和执行的流程，而不是产品本体的全部能力。
- **CAN、DBC、UDS、Flash、Wave、手动台架**等专业工具可独立操作，并与自动测试程序调用的相应能力共享一致语义、真实设备会话和工程资源；独立工具不等于两套测试引擎。
- 测试程序运行与现场工具的底层硬件控制须经过统一访问仲裁、日志、用户授权与安全校验，避免独立界面操作与自动程序竞争同一通道。
- 生产扫码、测试结果放行、报告与统计属于特定应用流程；不能以生产检测主线代替完整的工程开发与调试用途。

## 3. 对软硬件架构与工程管理的直接影响

1. 产品结构必须以**系统工程**管理：主控板/按键板电路、固件、硬件通道、协议与上位机均是产品构成与配置项，不只是上位机外设。
2. 必须建立 **Stimulus 能力矩阵**：每个外部刺激需求映射到 DUT 接口类型、供电/电压/时序边界、硬件板卡/版本、驱动命令、运行上下文和实际测试证据。
3. 必须建立 **Observation/Processing 能力矩阵**：区分原始 CAN RX、解码、状态推导、协议交互、波形、逻辑与时间判据、结果追溯，不要只列“CAN 工具”和“波形工具”。
4. 测试程序的动作与判据，应链接到上述已确认的刺激/观测能力以及具体硬件 Profile；它不能声明某个 ECU 外部刺激已覆盖但没有物理执行路径。
5. 需要确认**刺激发出时刻、DUT 响应采集时刻、解析/判定依据**之间的统一时间基准及数据关联。时间同步与精度需以设备证据判断，不能直接宣称已实现。
6. UI 应围绕真实操作中的工程资源、刺激配置、CAN 数据分析、测试程序调试与执行上下文组织，不能让软件层的 IDE 外观掩盖软硬件综合测试的目的。
7. 设备能力“可计划”“源码存在”“CI 通过”“实际输出实测”“ECU 响应已判定”是不同证据层级；不可借用户意图推断现役主控板已提供所有激励。

## 4. 首轮需要主动调查的事实缺口（不得以空白当作不受影响）
- **系统覆盖定义**：“全部外部刺激”指每一个具体 ECU 外部输入信号的可配置覆盖目标，还是更广泛地模拟整车/环境？需按真实业务与工程边界定义。
- **IO 范围**：当前主控板在现役固件下哪些 IO 可由上位机控制/反馈？哪些控制仅是固定夹具动作而非 ECU 刺激？供电、电压、故障场景何者已支持？
- **CAN RX 数据用途**：用户所说“处理更多”具体有哪些现役场景：数据库/DBC、信号派生、周期监测、超时规则、响应关系、波形判定、事件与状态机、测试脚本引用、统计等；需查既有设计与实际使用。
- **激励与观测关联**：AutoTest 是否需要明确的刺激动作时间线、定时发送与触发采集，如何保证硬件/PC 时钟的可解释性？
- **适配边界**：EPB 现阶段首例之外，哪些 ECU/输入类型预期需要支持？现有按键板是否可配置替换、或属于某类 ECU 的特定扩展？
- **版本和追踪**：当前硬件及固件版本、上位机驱动/协议、控制器配置、DBC 与判定规则如何形成可验证的组合？
- **验证策略**：本地用户已经确认的 CAN1 RX 证据不能扩大推定 CAN TX、IO 模拟电压输出和整套联合测试能力均已完成。
