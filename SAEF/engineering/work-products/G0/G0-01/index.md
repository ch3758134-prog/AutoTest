## 事实范围与输入来源

本阶段问题依次为：**系统由哪些实物构成 → 每块板有哪些物理资源 → 板级对外形成什么能力及限制 → 是否支持既定要求 → 现役固件利用到什么程度 → 哪些仍需实物证据**。这不是从现有软件函数倒推硬件应当具备的能力。

输入强度由高到低、但各自证明不同命题：`ORIGINAL_HASH`（文件身份）、`SCHEMATIC`（设计电路）、`DATASHEET`（器件额定能力，不证明实装）、`SOURCE`（代码所写行为，不证明已烧录）、`OWNER_REPORTED`（历史使用陈述）、`ASSEMBLY`（实物装配核对）、`MEASUREMENT`（仪器测量）、`BENCH`（设备功能实测）。不能用单一“已核实”覆盖全部层级。

**物理拓扑（概念级，不替代逐引脚线束）**：扫码枪以外部设备身份向测试系统提供 DUT 唯一编号（接入位置、传输协议待核）；Windows PC —USB→ 主控 PCB；主控 PCB 双 CAN 设计资源分别服务按键 PCB 与外部 DUT；主控其它物理输出接工装及 DUT 外部信号；按键 PCB 的模拟开关/电阻网络最终接 DUT 的外部输入。外部输入电源由台架提供，不将板内电源控制等同于控制 DUT 供电。

## 自动测试识别设备：扫码枪（新增事实）

- **使用事实（`OWNER_REPORTED`）**：自动测试使用的外部扫码枪读取当前 DUT 的唯一编号，是**工位识别数据输入**，不是对 DUT 施加的电气激励；扫码枪不是主控/按键 PCB 的内建能力。当前确认的是使用目的和读取结果，不代表已确认品牌、接口、驱动、编码格式或软件集成完成。
- **系统边界**：扫码枪是配套工位外部设备，其识别信息进入自动测试流程；不等同于自研主控或按键板的组成部分。无法由现役两张 PCB 原理图确定其型号、供电、连接口和驱动方式。
- **证据边界**：现有五份 HW/FW/HOST 源资产的文件哈希不能证明扫码枪已接线、识别成功或已经和测试记录绑定；后续需现场设备信息和原始扫码输入记录。
- **下游 G1 必须明确**：编号解析、扫描与实际 DUT 对应关系、未识别/重复/冲突处理、扫码与每次测试记录之间的关系，及扫描对测试流程的影响。G0 不先行冻结这些行为。

## 与 P0 最新产品边界的一致性（2026-11-03）

- **系统边界**：主控 PCB、按键 PCB、两套固件、工装、HOST 与配置记录都是 AutoTest 内部工程对象；外部 EPB ECU 是 DUT。
- **不把技术现状升格为长期要求**：现役 CAN、USB、模拟输入、电磁阀等记录在 G0 是配置事实；系统应支持何种测试场景、性能和后续扩展由 G1 决定。
- **不把历史 HOST 方案升格为现役配置**：历史 `src` 的能力抽象和运行内核可被 G2 研究继承，但不得以旧代码的能力角色覆盖实际硬件约束。
- **P0 工程状态**：P0 新版本的内容已获用户批准；本地受控换版与 P0 Gate 必须依据实际执行回执核对，不在 G0 静态分析中自动认定已完成。
