# R02｜现代复杂工业工程软件：全链路工作方式与工作区体系研究

**日期**：2026-11-19  
**承担角色**：AutoTest UI/UX 专项，研究而非后端开发  
**研究对象**：现代复杂 Windows 工业/专业 PC 软件的一般交互机制，后续仅把结论映射为 AutoTest 候选  
**阶段**：RESEARCH_COMPLETE；DESIGN_CANDIDATE；IMPLEMENTATION_NOT_STARTED；USER_UX_NOT_VERIFIED  
**前置**：R01 基础理念（六系统）与用户要求：研究者自行深入研究成熟产品，用户通过 Windows 实际使用反馈微调  
**输出**：已核实产品机制、通用模型、具体任务脚本、可验证设计假设、冲突与下一轮计划

## 1. 研究问题和方法

本轮不是“如何摆放工程树/属性栏”。需要解答以下更根本的问题：

- Q-A：复杂软件启动后，用户如何从意图直接进入工作，而非理解内部类/模块/文件的层级？
- Q-B：工程、文档、对象、工具、设备和一次操作/执行分别属于哪些独立上下文，切换时哪些必须保留？
- Q-C：专业编辑和实时操作如何在同一产品中保持直达、可控、低重复操作？
- Q-D：长期任务、中断、未保存工作、资源冲突和设备异常如何恢复？
- Q-E：何种 UI 一致性必须贯彻全产品，何种专业布局必须允许不同？

方法：查证厂商的一手官方帮助/产品机制，抽象为可被证伪的设计假设；不是安装软件的上机实测、访谈或对各产品优劣的定量排名。参考证据编号 E01~E15，详见 SOURCE_REGISTER。所有设计建议明确标 `推论/候选`。

## 2. 厂商机制：不是截图对照，而是用户操作链对照

### 2.1 Siemens TIA Portal —— 同一产品具备不同工作入口（E01,E02,E03）

**已核实**：Portal View 按任务组织工具，用户选择任务后可以按需要自动进入 Project View；Project View 提供工程树、工作区、编辑器栏、Inspector、任务卡、可折叠区域和进度状态；视窗布局能够保存与键盘恢复。

**设计推论**：软件的“进入工作”和“深入工程”不是同一件事。入口不必总是工程文件树；但这不等于 AutoTest 必须复制 TIA 的 Portal 主界面，更不应机械设计两套冗余大页面。是否需要单独首页，应根据第一次、日常复用、生产三种任务验证。

**反例警告**：复制项目树+编辑器+右侧任务卡的空间布局，却不提供对象上下文操作和直接任务入口，只会做出老式多栏窗口。

### 2.2 Visual Studio —— 文档、工具窗口、未完成工作和正式保存是不同对象（E04,E05）

**已核实**：VS 区分 Document Windows 与 Tool Windows；不同窗口可停靠、浮动、多显示器排列，并保存和恢复布局。VS 2026 18.11 Hot Exit 选项可恢复未保存新文件、未保存编辑、撤销历史、页签/窗口布局；其官方说明特别强调这属于会话恢复，**不是故意保存文档到磁盘/代码仓库**。

**设计推论**：没有正式工程，并不必然等于不能拥有编辑工作会话。AutoTest 若允许未归档的编辑会话，应该使用真实领域编辑器及内存/恢复保存机制，后续归档正式资源；不能新建一套与正式 TEST/PROJECT 不兼容的虚拟文档。UI 会话恢复、正式工程保存、资源版本发布必须有各自标签和操作。

**版本约束**：Hot Exit 是微软 2026 18.11 的可选新功能，不能宣称所有版本的 VS 默认具备，也不自动构成 AutoTest 必须复制的要求。

### 2.3 Ignition Designer —— 同一框架内部随资源而变的专业工作区（E06,E07）

**已核实**：Designer 的项目浏览器可选择资源，也可直接点击画布中的对象以选中；属性编辑器反映当前选择。不同资源类型拥有不同的工作区：画面编辑可配组件面板和属性面板，报警流程则使用专用 Pipeline Block Editor。官方支持 Design/Preview 切换和搜索/替换；并发编辑时处理资源冲突。

**设计推论**：不要“一套通用的右侧属性表”强行用于全部资源。共同的只是选择—命令—校验—保存行为；每种专业对象可以有自己的工作空间。快速修改字段应该在对应对象附近完成；复杂参数用长期可见的专用编辑区。

**反例警告**：将每种资源都变成一个统一表单，或者只做一个只读表格加弹窗，会让熟练用户在对象与编辑窗口之间反复移动。

### 2.4 Autodesk Fusion —— 围绕目的切换工作空间，按当前上下文露出命令（E08）

**已核实**：Fusion 的专业能力分 purpose-driven workspaces，工具栏按设计目标组织；某些上下文选项卡仅在激活相应命令时出现。设计历史/时间线允许调整具体特征。

**设计推论**：工作空间不是所有工具的总目录，而是与任务有关的一组对象+命令+反馈。常驻全局栏只保留全球性任务；专用命令按编辑器和选中对象出现。应避免同时永久展示所有专业按钮。

### 2.5 NI TestStand —— 开发编辑与操作员执行目的不同，但共享正式执行体系（E09,E10）

**已核实**：Sequence Editor 用于创建、编辑、执行、调试测试序列；包括断点、单步、变量及执行跟踪。Operator Interfaces 更聚焦操作员执行，不提供完整序列修改界面；两者复用正式 TestStand 引擎/API。

**设计推论**：测试编辑器与执行环境不必共用全部控件。运行视图突出选择、工位、当前步骤、真实结果、停止与错误；编辑视图突出步骤结构、属性和资源引用。它们共享本次工程/任务上下文，但执行配置必须冻结，不能被即时编辑误改。

**边界提醒**：NI 支持多个并发执行，不构成 AutoTest 单工位一台 DUT 也要并发的依据。TestStand 的 Setup/Main/Cleanup 语义不应由 UI 擅自复制其异常处理合同。

### 2.6 ETAS INCA —— 仪表选择、布局和实验上下文长期保持（E11）

**已核实**：INCA Experiment Environment 允许按需增加测量/标定窗口、XY/YT 示波器，选择变量放入仪表，具有保存仪表设置和布局的操作。

**设计推论**：测量和实时观察应该保留用户的信号选择、筛选、游标和窗口位置。不能把它们当成每次打开都复位的临时日志。如果数据源断连，界面保持历史观察上下文并清楚标识数据已停止更新。

### 2.7 Windows 命令设计、NN/g 与 ISA-101 —— 操作和安全是两层设计（E12,E13,E14）

**已核实**：微软建议同一命令由多个上下文一致调用，主要命令按重要性显示、次要命令可按窗口宽度溢出；NN/g 指出复杂软件应减少工作记忆负担、记录思想/上下文、逐步露出相关高级能力；ISA-101 关注工业 HMI 的态势感知、操作差错和生命周期。

**设计推论**：全产品的快捷键、鼠标、菜单、状态标识保持规则一致，但不能对“可撤销的本地编辑”和“写入真实物理设备”使用同等的风险约束。ISA-101 适合作为设备与生产运行状态设计的参考，不是要求每个工程编辑器采用控制室 HMI 式画法。

## 3. 产品心智模型：五种上下文 + 两类容器

### 3.1 五种必须分开的上下文（候选 UX 领域模型）

| 上下文 | 具体内容 | 生命周期 | 退出/切换时保留 | 禁止混淆 |
|---|---|---|---|---|
| `AppSession` 软件会话 | 主窗口位置、最近工程、打开文档、工具窗口、布局与焦点 | 安装后的跨启动使用 | 会话可以自动恢复 | 不等于正式工程已保存 |
| `ProjectContext` 工程 | 当前 ECU 工程、正式资源/引用/修订/配置 | 正式文件的版本历史 | 存盘、重新打开、版本校验 | 不等于运行设备已准备 |
| `EditorContext` 编辑 | 当前文档/对象/未完成输入/撤销历史/局部视角 | 文档打开期间，允许会话快照恢复 | 对象选择、光标、局部草稿 | 不等于已生效资源 |
| `StationContext` 工位 | USB/总线身份、物理输出状态、独占租约/连接时代 | 实际台架连接及资源所有权生命周期 | 应保留身份/事实记录，不能伪造断线后的已知状态 | ACK 不等于物理完成 |
| `ExecutionContext` 运行 | Run ID、用例选择、运行快照、真实事件与报告证据 | 每一次独立真实执行 | 历史不可逆追溯、报告引用 | 不等于当前编辑草稿 |

以上是 UI 需要表达的上下文划分，不要求后端直接照这些类名建新业务模型。实际实体合同以 TEST/PROJECT/DEVICE 为准。

### 3.2 两类容器（不是同一个东西）

- **文档/资源**：可选择、可编辑、可保存、可引用，有文件及修订；典型视图在文档页签中。
- **专业工作空间/工具**：服务一个持续任务，可能跨多个文档与实时数据；可以是主区域的一种任务环境，也可以是独立工具副窗口；不必产生新工程文件。

由此可得：选择工程资源 ≠ 切换全局任务；激活文档 ≠ 切换工位；工具副窗口存在 ≠ 设备连接；编辑改变 ≠ 执行输入发生改变。

### 3.3 统一命令面应回答的问题

任一按钮或快捷键应标明：`操作对象`、`命令作用域`、`可用条件`、`是否修改正式资源`、`是否造成真实物理作用`、`是否可撤销`、`结果/错误展示位置`。否则不能仅以“按钮已出现”为验收依据。

## 4. 从成熟产品归纳的五类工作流程

### 流程 A：启动/恢复/进入工作

1. 启动后先判定：有可恢复的上次正式工程、无工程、新近文件丢失、工程损坏/不可读；不再不加区分地显示同一个空文件树。
2. 上次工程有效：恢复工程及任务，打开上次关联视图；保持原用户已确认的自动测试运行主线。
3. 没有工程：软件仍提供完整工作入口，可看最近内容、选择新建/打开、探索编辑能力及不依赖工程的工具。**无需立即输入工程名称才能查看编辑器如何工作**。
4. 若允许临时编辑，只能使用真实编辑组件和其合法对象模型；“临时”有明显标签、可恢复，不是虚构 TEST 第二套 DSL。
5. 原工程丢失或有冲突：明确报告真实问题、原路径和恢复/重新定位路径，不静默新建替代工程。

风险：不能只依据 VS Hot Exit 就默认实现完整 session restore；需要正式模型能支持未命名文档和原子保存恢复。

### 流程 B：资源组织/打开/编辑/保存

1. 先从任务或资源入口找到需要的对象，单击选择、双击或显式命令打开，不因单击便执行破坏性操作。
2. 当前对象选择和详情应同步；高频属性可直接修改，复杂参数在持续可见的专业编辑区域显示。
3. 编辑只改变草稿/领域事务；合法性校验在适当时机出现，错误被明确定位。
4. 用户可切换查看其他对象，未完成输入不能被静默丢失，也不应把整个软件困在无法切换的字段。
5. Ctrl+S 或正式资源保存时提交完整事务并进行合法性、外部修改冲突校验。
6. 保存失败仍保留编辑现场；已落盘版本与尚未完成草稿明确区分。

### 流程 C：使用工具完成临时工程任务

1. 从当前任务上下文启动工具，不强迫先创建无关的工程资源。
2. 工具窗口保留输入内容、选中对象、过滤器、观察位置等，即使切换至其他工具。
3. 已保存资源与临时输入要清楚区分；修改 DBC/信号等共享资源不应毫无提醒地改变待发送数据。
4. 编辑和执行有明确边界；只有经真实硬件所有权及授权，才能操作实体。
5. 关闭工具后主工程和当前文档保留；关闭主窗口按已批准的生命周期安全处理全部子窗口。

### 流程 D：正式运行与观察证据

1. 确定运行目标、临时选测、工位、当前正式配置。
2. 预检后建立冻结的运行快照；运行期间主窗口展示与当前 Run 绑定的事实。
3. 不得把 USB ACK、ECU 报文、物理测量和测试 PASS 混为同一状态。
4. 允许观察、停止、追踪错误；可编辑性及硬件并发依 TEST/DEVICE 合同门禁。
5. 结束后把 Run 与报告/原始证据持久关联；回看报告不应自动更改当时运行记录。

### 流程 E：中断/崩溃/异常恢复

1. **本地恢复（Session Recovery）**：记住窗口/文档/输入位置和可恢复草稿。
2. **正式保存（Document Save）**：合法资源写盘、版本/引用检查。
3. **执行记录（Run Evidence）**：真实历史证据独立保存，不得“恢复出未发生的 PASS”。
4. **设备异常（Station Recovery）**：断线后物理状态未知不能由 UI 自行猜测并恢复输出。
5. **布局恢复（Layout Restore）**：多屏/DPI 变化时确保窗口仍位于可见工作区域，可一键重置。
6. **用户继续工作（Resumption）**：显示正在处理的对象和上次行动，不让用户凭记忆重新寻找。

## 5. 对全产品 UI 的候选结构（非布局冻结）

### 5.1 一个真实应用层

全局承担：当前工程切换、应用会话恢复、工具统一入口、设备总状态、全局搜索/命令、后台任务与帮助。它不承载各专业编辑器自己的细节参数。

### 5.2 工程/文档层

当前工程树 + 专业文档编辑区 + 文档页签/任务上下文。不同对象用不同专用编辑控件；没有工程时工程树可以显示引导与最近资源，而不成为阻断其他软件能力的空屏。

### 5.3 任务环境层

用户的工作可能是“工程编辑”“自动测试运行”“诊断调试”“测量分析”“生产操作”。各环境显示自己最重要的命令和反馈，不要求相同的表格、同一组常驻属性区。操作型工具可继续是独立受主窗口管理的 Windows 副窗口。

### 5.4 观察和状态层

统一对象/资源引用、真实连接与执行事实、消息/错误、后台任务。但“全局状态”不能代替专业工具详细观察；真实执行日志和编辑校验错误是两类不同信息。

### 5.5 避免的反模式

- 强制“建工程 → 起名字 → 才能发现编辑器长什么样”；
- 只有只读展示表格，改一个值必须打开多层模态弹窗；
- 每种专业工具都硬套三栏/通用属性表；
- 所有命令挤在主工具栏，用户不知哪些与当前对象有关；
- 工程树同时承担全局导航、资源组织、工具入口、运行范围与状态；
- 切换对象直接清空尚未完成输入，或 invalid-field 锁死全部导航；
- 工具打开就重置选择、过滤和布局；
- “已发 USB 请求”显示为“ECU 响应通过”；
- 未绑定资源的示例前端被称为完整正式工程；
- 为避免用户误操作而让全部普通编辑变成多次确认。

## 6. 任务验证脚本：下一轮原型必须可操作，而不是截图通过

这些是 **UX 任务脚本**，不是已实现的功能，也不是实际 ECU 运行测试。

| ID | 真实任务类型 | 应观察到的关键体验 | 主要失败信号 |
|---|---|---|---|
| T01 | 首次打开没有工程的程序 | 看得到软件能力，能进入编辑体验或工具 | 强制工程命名才能查看编辑器 |
| T02 | 正常重启继续上次工作 | 恢复工程、当前任务、打开文档与观察位置 | 重新从根目录逐层寻找 |
| T03 | 上次工程移动/损坏 | 知道原路径及修复入口 | 静默创建空工程、丢失上下文 |
| T04 | 新建合法临时编辑内容 | 使用正式编辑组件，保存前不冒充工程资源 | 第二套伪 DSL 或无法导入 |
| T05 | 在工程树中定位资源 | 搜索、选中、打开和批量操作可理解 | 选中即改变运行任务 |
| T06 | 编辑对象多个高频字段 | 连续修改、及时反馈、不反复开弹窗 | 每次都需右键属性/改值 |
| T07 | 编辑中字段尚未完成 | 不丢稿；明示错误；不写盘无效值 | 无法离开对象或数据悄悄丢失 |
| T08 | 复制/撤销/移动复杂对象 | 结果可预测并保留引用/身份合法性 | 结构被破坏且无法撤销 |
| T09 | 打开第二工具查看同工程资源 | 保留当前工具状态，资源版本有标记 | 参数突然改、窗口重置 |
| T10 | 工位未连接仍需编辑 | 离线编辑可用，实体操作清楚禁用 | USB 断线导致整个应用不可用 |
| T11 | 运行前核对当次选测 | 仅影响本次 Run，不暗改工程默认 | 勾选导致正式 Enabled 变化 |
| T12 | 真实 TEST 正在运行 | 事实与许可一致，编辑锁定的原因明确 | UI 自行显示 PASS/继续写硬件 |
| T13 | 执行失败后定位证据 | 从 Run 定位步骤、日志、相关文件 | 只显示失败却无下一步 |
| T14 | 长任务期间切换视图 | 进度持续、任务不被窗口切换打断 | UI 卡死或误认为任务停止 |
| T15 | 关闭重开后找回未完成工作 | 分清会话恢复、正式保存和设备状态 | 恢复草稿被误当作已发布文件 |
| T16 | 1366x768/150% DPI、多屏撤回 | 核心操作可见，子窗口能找回 | 遮挡任务栏/浮窗无法恢复 |

正式原型验收除“能否完成”外，记录：首次定位操作的时间/步骤、窗口切换次数、重复输入次数、错误恢复是否丢信息、是否看懂当前真实状态。具体达标阈值待基准原型实测后确定，不凭空规定。

## 7. 本轮的可操作设计结论及置信度

| 结论 | 依据层次 | 目前状态 |
|---|---|---|
| 必须区分软件会话、正式工程、编辑上下文、真实工位、真实执行 | 多个厂商操作机制 + 用户故障复盘 | UX-CANDIDATE，强烈建议 |
| 没有工程时软件本身仍可工作；临时编辑需正式领域组件 | VS/TIA/Fusion 比较 + AutoTest 用户诉求 | UX-CANDIDATE，需要 PROJECT/TEST 适配评估 |
| 文档窗口与工具工作空间不等同，操作工具不自动生成工程文件 | VS/INCA/Ignition 机制 | UX-CANDIDATE |
| 不对全部工具采用同一种三栏和 Inspector | Ignition/Fusion/INCA 机制 | UX-CANDIDATE，强烈建议 |
| 运行与编辑可保持共享上下文但不同操作重心 | NI TestStand 机制 + 用户已有决定 | USER_DIRECTION + UX-CANDIDATE |
| 会话恢复与正式资源写盘是两种事务 | VS Hot Exit 与原有项目管理要求 | UX-CANDIDATE，强烈建议 |
| 实体执行、设备应答与最终结果分层 | 工业 HMI 思路 + 现有安全合同 | 既有业务边界不可由 UI 改写 |
| 第一版不强制上完整自由停靠 UI 框架 | 成本/任务权衡推论 | 待 WPF 实际测试 |
| 先测跨窗口任务闭环而非逐页视觉 | NN/g / ISO 人本设计思路 + 用户反馈 | UX-RESEARCH_DECISION |

所有 `UX-CANDIDATE` 目前只属于设计建议，不宣称用户已正式批准特定页面和完整实现。

## 8. 目前缺失的证据与下一轮

1. 当前是官方文档/手册研究，**没有进行任何厂商软件的完整实机操作，也没有 UX 效率定量对比**。
2. 各软件的功能版本不完全一致；采用当前查到的官方页面作为具体事实证据，不能把历史截图当最新界面。
3. AutoTest 的 PROJECT/TEST 能否以正式模型支持无工程会话、未命名草稿与真实事务恢复，须下一轮向相应领域接口提出 **能力请求**，不能由 UI 偷写第二模型。
4. R03 必须输出“主应用工作区与上下文状态流”可操作原型，覆盖 T01~T16 的至少核心入口 T01~T06、T09、T15。先让用户实际操作再冻结。
5. 随后 R04 逐对象深入：测试项目/用例/公共流程、CAN/DBC、UDS、Flash、Wave、Scan、Record、Device。每个领域研究成熟工具的完整操作过程，但不重复 R01 基础设计。
6. 不直接用旧 G4 WPF 拼接新设计，不以 UI 新主题已安装宣称交互重构完成。

## 9. 需要用户决定的事项

**当前没有必须由用户立即裁定的问题。** 入口、工作区、状态和草稿/保存分离均可先提出可以实际操作的候选原型。用户以真实操作反馈微调，避免让用户代替设计师选择控件、布局或技术校验规则。

后续若出现“同一软件是否提供独立的操作员简化入口”等真正改变产品工作方式的分歧，先提供完整比较和真实原型，再集中请用户裁定。
