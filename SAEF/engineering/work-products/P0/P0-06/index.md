# P0-06｜AutoTest 质量计划与评审策略

> SAEF v2.0 / `P0-06` · **M2 修订候审，尚未替换本地 ACCEPTED 版本**。以本地已接受文档为父版本，旧哈希、审批记录及差异表见本包。

## 一、目标与计划依据

质量目标：使每次工程决定、工作产品、实现和现场验证都能与其**真实输入配置、原始证据和授权者**对应，防止“文档完成=代码通过=设备验收”的混淆。依据 SAEF 的 Gate、验证与证据标准，按工程风险裁剪独立 QA 职责；本项目没有第三方质量认证，也不伪称独立部门审核。

## 二、工作范围与依赖

- 覆盖 P0—G5，阶段内工作产品可分批审查，Gate 批准必须单独进行。
- 当前 P0 的审查对象是治理规则是否明确、可执行、可恢复；**不要求**先完成 USB/CAN、HOST、固件构建或现场台架验收。
- 自 G0 起，分别核对图纸/源码/实装/实测；G1 核对需求清晰可测；G2 核对系统分配、接口和重要失效；G3 核对可实施的模块/文件/函数、契约和测试；G4 核对编译/单元/集成；G5 核对系统验证、部署恢复和现场交付证据。
- 已批准的历史材料可以作为审查输入，但是否满足当前 SAEF 工作产品合同需逐项引用，不由 AI 自动改 Gate 状态。

## 三、活动/责任/输出

| 质量活动 | 职责 | 最小可复核输出 |
|---|---|---|
| 交付方自审 | ChatGPT | 本项目的验收条款→正文定位→证据→符合/偏差/未验证；指出范围越界 |
| 机械完整性检查 | Codex 执行 SAEF 脚本 | 实际命令、退出码、SHA-256、错误、变更清单；不判技术质量 |
| 技术审查与批准 | 负责人依 ChatGPT 提交的完整决定包 | 被批准的具体 ID+版本/哈希、范围、限制或退回意见 |
| 缺陷和风险复查 | ChatGPT 分析、负责人裁决 | ISS/CHG、影响面、处置决定、证据/回归 |
| 真实硬件/现场验证 | 经负责人明确授权的现场人员 | 设备/固件/工装配置、真实操作、预期/实际、原始测量及异常 |

独立性补偿：作者自审明确标识为“交付方技术自审”，不能冒称独立审计；通过原始数据留痕、不同的负责人签审和必要的独立专业人员复核形成制衡。高风险物理输出由后续专业验证计划定义具体联锁和放行条件。

## 四、里程碑与审查条件

每个工作产品提交前按 `catalog.json` 检查：必要章节齐全、证据可定位、事实与推断分离、未决项有责任与下游位置、相邻工作产品未产生矛盾；交付方提供 `READY_FOR_OWNER_REVIEW / REWORK_REQUIRED / BLOCKED_BY_EVIDENCE` 之一的自审建议。

**Gate 评审**采用 `FRAMEWORK/contracts/GATE_review_template.md`：阶段范围和输入配置、每项 ACCEPTED 工作产品及证明、开放项及阻断影响、Git/外部原件身份、风险与验证追踪、自审建议。仅负责人能够签署 `PASS` / `PASS_WITH_LIMITATIONS`；缺少代码/实测证据时不能冒充通过，缺少 Gate 必需的 Git commit 与可恢复资产时不得批准。

**分阶段验证原则（仅制度层）**：将来的验证路线由 G1/G2/G3 的正式合同和对应验证工作产品确定。原则上先以有操作与观察能力的简易上位机验证真实通信/硬件路径，再验证各能力单元和正式 HOST 组合，最后做系统现场验证；此处不制定具体指令序列或阈值。

## 五、风险与证据

| 风险 | 预防/发现/处理 | P0 准出证据 |
|---|---|---|
| 单人+AI 自审独立性不足 | 标明自审、负责人最终签审、必要时专业复核 | P0-03 责任记录 + 逐项报告 |
| 仅凭脚本 PASS 声称技术合格 | 每种证据声明实际覆盖边界 | check 日志 + 内容审查相互独立 |
| 现场高风险动作被误发 | 权限前置；没有真实操作授权不执行 | P0-03 授权和操作停止规则 |
| 来源/版本不明 | 变更前哈希与 Git/资产索引 | P0-04 与检查日志 |
| 阶段遗留被自动提升为 PASS | 阻断范围、责任、关闭证据和负责人决定 | Gate 未决事项表 |

**本项可批准内容**：质量活动及 Gate 评审策略；P0 内实际执行证据必须由 Codex 回执与负责人决定提供，质量计划本身不宣称所有控制已运作成功。
## 独立设计验证、构建与现场实测的证据分级

- `SOURCE_REVIEWED`：源码静态核对，不证明可编译。
- `BUILD_PASS`：在记录的工具链和源码配置下构建成功，不证明硬件正确。
- `UNIT/CONTRACT_PASS`：模拟、数据或接口测试通过，不代表真实 ECU 通路。
- `BENCH_PASS`：真实板卡/ECU/工装在记录的供电、固件、DUT、CAN、线束配置下通过指定测试用例。
- `INTEGRATION_PASS`：已验证的多个模块组合后，通过相关跨模块及异常用例。
- `SYSTEM/RELEASE_ACCEPTED`：当前声明功能范围由负责人据实测/回归/部署和遗留问题批准。

**UI 质量也是验证对象**：视觉设计 Token、共享组件、不同 DPI/中文/长文本及状态样式在组件展示程序中验证；导航/步骤编辑/属性和运行状态在实际 WPF 可操作界面验证；最后以真实任务走查判断生产与研发是否可用，不能用 HTML 原型代替 WPF 实现。

对于夹具，不可用主控 ACK 或收到 DUT CAN 报文宣称已机械到位；对于电源，未查明供电切换前不得自动加到 ECU；对于烧录，必须建立目标确认、不可逆动作的失败与恢复试验合同。
