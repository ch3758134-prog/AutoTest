# AutoTest｜P0-04 配置与基线管理

- **版本**：v0.1｜2026-11-12
- **状态**：候审；未经项目负责人批准，不作为有效项目管理基线
- **上游**：新基线 P0-01 v0.2、P0-02 v0.1、P0-03 v0.1（已批准并在 GitHub main 落档）
- **目标**：说明怎样识别、保留、变更和恢复工程内容，而不是指定软件模块的具体内部设计。

## 1. 管理对象和事实边界

AutoTest 是软硬件一体化 ECU 测试系统。配置管理同时覆盖：（1）产品目标、需求、架构、详细设计与管理决定；（2）Windows HOST 的源码、依赖、构建和发布；（3）主控与按键板的 PCB/固件版本、协议及现场实装；（4）工装、供电、线束、CAN 通道、扫码输入和测试环境；（5）工程配置、DBC、测试程序、诊断/烧录/波形资源；（6）测试事实、原始日志、判定与报告。

**同一对象的不同证据不可相互代替**。GitHub 有固件源码不等于实物已烧录该版；存在设备驱动不等于真实 ECU 闭环已通过；工程配置可保存不等于已通过真实用户操作验收。

目前 GitHub 仓库为 `ch3758134-prog/AutoTest`。当前管理工作由该仓库 `main` 保管正式版本。`local` 等分支的开发成果须单独识别，不能自动作为已集成或已批准的主线。旧 `SAEF/`、历史文档和已撤销的方案仍有追溯价值，但它们不能自动代替 2026-11-12 重新建立的 P0 基线。

## 2. 单一正式基线与工作分支

1. **正式项目管理结果**：经负责人批准的完整工作产品、审批范围和所需引用材料提交 GitHub `main`。每个审批对象有唯一 ID、版本及精确文件路径，提交后核对远端内容和提交 SHA。
2. **候选成果**：未经批准的草稿保留在交付方私有工作区或作为本对话可下载的独立文件，不自行放入 GitHub 正式管理路径并标记为有效。
3. **软件专业研发**：允许受控开发分支、独立提交和 Draft PR。功能设计、源码实施、合并与实体测试具有各自授权，不能由一次管理文档批准派生。
4. **主线安全**：提交正式管理结果不得覆盖未经复核的业务源码，不合并 `local`，不改动历史审批事实；遇到并发 HEAD 变化时停止直接写入、重新核对，严禁强制覆盖。
5. **项目管理软件本身**：`tools/project-control-v2/` 属于通用工具研发资产；它的候选实现、发行状态和本项目工程批准必须分开说明。其存在不等于 AutoTest 已部署全部管理工作台接口。

## 3. 版本身份的最低合同

一项受控对象至少具备：对象类型、稳定标识、存放位置、版本或哈希、来源、适用项目/设备范围、当前状态、责任人、上游关联及变更历史。不同对象采用适当的身份方式：

| 对象 | 最低可复核身份 | 关键补充 |
| --- | --- | --- |
| 正式管理文档 | 文件路径、工作产品 ID/版本、Git blob/commit、批准记录 | 批准的正文与远端正文一致 |
| HOST 源码 | 仓库、分支、完整 commit、工作树差异、SDK/依赖 | 编译与测试结果必须绑定精确 commit |
| MCU 固件 | 工程/Target、源版本、编译器、映像哈希、板卡型号 | 现场烧录身份须有单独证据 |
| PCB/工装与工位 | 修订、装配状态、连接、供电约束、校验记录 | 图纸/现场/实际测量分别标识 |
| ECU 工程数据 | 工程、资源身份/修订、DBC、程序、匹配规则、HEX、配置引用 | 运行时固定资源快照，禁止无意漂移 |
| 运行证据 | RunId、时间、ECU/工位、应用配置版本、原始数据、结果 | 历史追加，不能被后续编辑覆盖 |

首轮台架资产的当前身份与适用性应在 G0 调查核对；P0 不虚构未经读取的映像哈希或现场版本。

## 4. 正式批准后的 GitHub 落档动作

当负责人针对**已完整展示的确定工作产品版本**明确批准时，工程总协调在同一轮工作中：

1. 固定批准对象的版本、正文、范围、附带条件和原始审批语句。
2. 核对 `main` 最新 HEAD、目标文件现存内容及可能的并行更改。
3. 在 GitHub `main` 创建该版正式文件，或按批准范围受控修订已有文件，同时更新独立审批记录；提交必须为非强制快进。
4. **回读 GitHub** 验证每个目标文件的实际内容及新的 `main` HEAD，向负责人提供链接与结果。
5. 冲突、权限失败或文件不一致则报告 `APPROVED_NOT_FILED`；不谎报已入账、不强制推送、不借机修改别的对象。

本条是本项目管理 AI 的工作责任。当前 GitHub `main` 没有启用分支保护/Ruleset，不能声称平台已经强制阻止越权写入。以后如需强制约束，应另行评审账号权限、分支保护和授权发布通道。

## 5. 变更、回退与历史保护

正式文件修改必须先说明原因、原有效版本、拟变更部分、影响的下游要求与验证；获得对**新版本**的批准后产生新提交，不改写旧 Git 历史。对已有研发资产，只审查受到影响的工作，不能因为 P0 重批就把历史代码一律删除或认定全部无效。

高风险固件升级、设备输出、刷写或工位接线修改另需现场授权与可恢复方案。数据迁移须备份原工程、提供回退途径，并在真实文件上检验。禁止把删除分支当作管理清理动作而不先核对独有提交和保存策略。

## 6. 备份与可恢复性

Git 追溯不等于充分备份。对大文件、原始 HW/FW、真实运行数据和离线工作环境，应记录独立可恢复副本；恢复验收需在隔离位置核对文件内容及相关工具可读取性。个人数据/产品标识、种子密钥与证据中的敏感信息应避免未经必要性评估上传公开仓库。

## 7. 接收判据与开放事项

**本项批准将确定**：正式基线在哪里、哪些资产必须有版本身份、批准后如何核对远端、如何保留历史并控制变更。

**本项批准不意味着**：所有资产已经盘点完成、现役两套固件身份已验证、独立备份恢复通过、项目管理软件已形成可信的强制审批服务、或任何业务源码获得合并授权。

待后续调查：`local` 与 `main` 的准确差异和交接边界；真实测试设备/固件/工位的现场身份；工程资源和测试运行快照能否完整复现；项目管理持久化台账如何与已批准 Markdown 形成唯一生效关系。
