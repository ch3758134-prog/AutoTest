# P0-01｜AutoTest 项目章程、范围与近期目标（M2 受控修订候审）

## 一、系统使命及应用主体

AutoTest 是面向 ECU 的**软硬件一体化开发与测试台架系统**。当前使用对象是公司研发、生产检测和维护人员，以自动测试为主要业务，同时支持研发调试、诊断、烧录、波形观测和故障分析。当前 EPB ECU 为第一个真实 DUT，但不作为通用 HOST 内核的固定产品模型。

项目完整产品包括台架 PC、现役主控 PCB、按键 PCB、两套 MCU 固件、夹具及其电磁阀、工位供电与连接、外部扫码枪输入接口、Windows HOST、工程/DBC/测试程序/烧录资产、运行记录与验证资料。**ECU/DUT 是被测对象，不是 AutoTest 自研控制器**。上述系统元素的物理连接、当前电气能力与证据等级由 G0 负责，不在项目章程宣称已经实测。

## 二、产品边界与两种通用性

完整台架当前以 ECU 测试为主要领域，受现役 PCB 与工装能力限制；**Windows HOST 的测试编辑、资源管理和执行核心应保持 DUT 无关**，不得将特定 EPB 信号名、某一 ECU 的测试流程或合格规则内置为平台前提。特定 DUT 的通信、烧录、项目、信号和判定在工程资源/项目配置中表达。

当前仅面向一台 PC、一台真实 DUT 和现役两块 PCB 推进，12V/24V 对应不同 DUT 型号需求。两路电源为台架供电设施，**不预设 HOST/主控可直接控制电源通断或自动切换额定电压**。电磁阀接主控板控制夹具，现无机械到位独立反馈；从 DUT 收到 CAN 响应也不能直接宣称机械到位。

扫码枪是外部输入设备，用户团队设计 DUT 实物标签所使用的编号方案；HOST 读取编号并按本地可编辑规则关联型号、通信参数、烧录资源和测试项目，**不负责生成或打印 DUT 实物编号**。扫码设备物理接口和匹配算法暂未确认，不在 P0 固定。

## 三、近期可用成果与长期能力

**近期核心成果 H3（候选里程碑）**：经真实台架复验后，形成稳定 USB/双 CAN/IGN/夹具/按键设备能力、工程及 DBC 管理、自动测试程序的图形编辑、执行、结果与日志。优先让工程师能自己编辑并运行一条实际 ECU 自动测试链路。

**生产完整成果 H4（候选里程碑）**：在同一 HOST 上完成扫码→配置匹配→必要的 CAN 烧录→自动测试→历史记录与统计。出厂测试需要烧录，具体协议和恢复条件取决于用户后续提交的参考程序及真实 ECU 实测。统计应区分不同 ECU 数量与测试次数，允许同一 ECU 合法复测但历史不得覆盖。

未来可增加其他 ECU、双 DUT、灯/蜂鸣器及其他硬件，但**当前不作为首批实物实施范围**；未来扩展需需求与变更审核，不凭架构图承诺已实现。

## 四、研发资产及工程策略

现役两块 PCB 是当前固定硬件设计输入，严重硬件缺口需单独变更评审。**主控 MCU 固件、按键 MCU 固件、新 Windows HOST 都是可持续设计、实现、修改与维护的软件资产。**两套现场固件在重新复验时保持原版本，是为了减少变量，并非永久冻结。

历史 `src(20261030-022559).zip` 是重要的**既有研究资产**：资源/能力、测试领域与执行、DBC、USB、记录及 UI 视觉和操作的思路和源码都需要逐项继承分析。新 HOST 不强制沿用其目录或接口，也不能丢弃有效成果。已知旧项目在 UI 设计、自动测试系统和不同功能的兼容与实测环节遇到阻碍；由 G0 记录可证事实，G2 决定继承策略。

研发实行**统一系统设计 → 成批详细设计 → 并行模块实施与独立验证 → 按依赖增量集成 → 实机与使用反馈 → 需求和架构受控修订**。每次测试的设计、构建、模拟、台架、系统验收是不同状态，不互相替代。Gate 与动态工作包双轨运行，详见 P0-02。
