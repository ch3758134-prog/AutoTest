# P0-05｜AutoTest 工作产品与交付规范

> SAEF v2.0 / `P0-05` · **M2 修订候审，尚未替换本地 ACCEPTED 版本**。以本地已接受文档为父版本，旧哈希、审批记录及差异表见本包。

## 一、目的与适用范围

对 AutoTest 的所有项目文档、图纸引用、代码定位和验证证据实行**单一来源、固定 ID、按合同交付**。SAEF v2.0 `FRAMEWORK/catalog.json` 已定义 P0—G5 的 **55 项工作产品**；此处只确定它们怎样编制、交付、审查和重建阅读页面，不再建立平行的项目模板体系。

## 二、责任与权限

- **ChatGPT 工程总控**：使用实际资料形成工作产品和自审报告，给出来源、影响和审查建议；涉及工程设计时应从系统到文件/函数定位，但只在对应 Gate 达到相应深度。
- **项目负责人**：审查成果与现实意图是否一致、决定批准/退回；不承担填模板或代替工程设计者查漏的职责。
- **Codex**：按标准 ZIP + 命令机械应用、运行脚本和回传实际结果，不自主填写工程内容、补图或改审批状态。

## 三、执行规则

1. **权威文档**：`engineering/work-products/<Gate>/<ID>/index.md` 为受控原文；配置状态以 `engineering/control/work_products.json` 为准。原始图纸、源码、实测日志独立保存并被引用；HTML 由脚本生成，是只读视图。
2. **最小内容**：严格遵守 `catalog.json` 的目的、必要证据、验收条件和规定章节；当前 P0 不提前写 G1 需求、G2 架构及 G3 文件函数设计。内容不足标明待证；无价值的重复文书不建立。
3. **可追踪**：每份文件注明工作产品 ID、主题、输入来源、关键决定、下游用途和未决项；技术阶段建立需求→系统/软件元素→接口→代码/硬件→测试→证据的双向链；G0 区分原理图、源码、实装、实测证据等级。
4. **人读/机读共用**：中文正文用 UTF-8 Markdown，稳定绝对唯一 ID；文件发布和 Windows `.cmd`/ZIP 命名采用 ASCII；表格和图表必须能离线阅读，包含对象编号、必要单位、来源和图例；生成器不能吞掉错误或将缺图判成功。
5. **工作产品批量审查**：允许一次交付多个工作产品，**每项独立列出符合性、证据、批准建议**；负责人可一次明确批准多个 ID 的具体版本。单个工作产品须能独立定位，不能用一份汇总 PDF 替代正文。
6. **机器交付**：使用 `SAEF-delivery/1`：唯一 Delivery ID、`delivery.json` 列出精确目标相对路径及旧/新 SHA-256、`payload` 只含允许修改的文件。执行顺序为 `dry-run → apply → check → site → 回执`，批准记录另用 `SAEF-authority-decision/1`。不把审批 JSON 混入普通内容交付 ZIP。

## 四、记录与例外处理

- 交付存档：Delivery ID、实际输入配置、逐文件 SHA-256、自审报告、批准引用、受控执行日志和退出码、修改清单。独立超大二进制只记录原件可恢复路径及校验，不重复塞入交付包。
- 批量应用出现任一哈希冲突、目标不在白名单、已接受工作产品不可覆盖或脚本失败时，**整体停止**；Codex 不自行修复。已批准但本地未应用的工作产品不得被报告为“本地归档完成”。
- 历史 HTML 作为参考资料保留，但不能从历史描述直接补签当前 SAEF Gate，也不允许修改已批准 G1/G2 技术内容。

## 五、验收与审查证据

| SAEF 原始合同 | 本项交付位置 | 判断依据 |
|---|---|---|
| 工作产品目录 | §一、§三第 1–3 项 | 明确使用现有 55 项 catalog，不再造第二目录 |
| 对读者可用 | §三第 2、4、5 项 | 正文可单独阅读，图文链路和阶段粒度明确 |
| 对机器可用 | §三第 6 项、§四 | 唯一 ID、受控相对路径、哈希、schema 和检查机制 |
| 交付后版本可信 | §三第 6 项、§四 | 脚本验证只管形式，负责人审批和日志另行保管 |

**边界**：本规范定义写什么、怎么交，不代替 P0-06 的质量判据或 G3 专项编码合同。
## 集中候审与滚动详细设计的交付合同

SAEF 的 55 项正式工作产品 ID 保持不变。支持一次集中**内容评审**涉及多个工作产品，但并不允许批量跳过每项文件的哈希/审批或各 Gate 的独立准出。历史研究 HTML 和独立 UI 原型属于**研究附件**；真正的权威文件是本地受控工作产品及其审批记录。

G2 总体设计应包括硬件/双固件/HOST、扫码输入/匹配、自动测试编辑运行、工程数据、UI 视觉资源及交互的完整分层和接口责任；G3 按当前批准的工作包细化到模块/文件/类/关键函数、时序/状态/错误/测试，不强迫一次编完未来所有功能。

每份候审内容应能回答：来自何处、已明确还是待实测、影响哪项下游合同、如何判定通过、上一批准版本是什么。禁止只在主档案新增一段口号而不修订负责的正式工作产品。
