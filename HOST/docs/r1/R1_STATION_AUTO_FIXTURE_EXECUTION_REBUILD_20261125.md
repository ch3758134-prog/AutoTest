# AutoTest R1｜自动夹具与生产准备执行链重构报告

## 一、问题与根因

用户现场要求：**真实自动检测必须控制夹具，不能只在手动台架压紧/释放；生产准备要描述真实可执行工艺，而不是字段登记。**

对 R1 源码核查结果：
1. 主控固件 `ASW_IoCtrl.c` 已有两路独立输出：夹具1 PTB1 / J1-B5、夹具2 PTC2 / J1-B4，USB `0x18` 设定、`0x19` 读回，0=释放、1=压紧；ACK 和 MCU GPIO 不等于机械到位。
2. 手动台架已有真实夹具控制，`AutomaticTestHomeViewModel.Run.cs` 也能执行**工程旧工位流程**的 BeforeStart/AfterFinish，但通过 `SendManualClampAsync` 取得手动授权，和完整项目 TEST/FLASH 无统一运行所有权。
3. 生产配置存在 `UseClamp1/UseClamp2`，工程发布规则却阻止使用旧工程 Clamp 动作，要求“标准工位夹具配置”；实际执行器从未读取那两个字段——典型“保存了配置但不会控制夹具”的断裂。
4. 正式生产运行的可信实体 START/机械到位/Inspection 已显式阻断，不能因补夹具代码便跳过；工程整组验证才是当前真实台架执行入口。

## 二、本轮代码已经实施的方案

### 1. 唯一工位夹具动作计划

新建 `StationFixtureExecutionPlan.cs`，从**已发布** `ProductionFixtureConfiguration` 产生确定性的压紧/释放序列：
- 未启用任何输出：不发送夹具命令，界面显示“不会自动装夹”，不暗中启用。
- 只使用一路：仅操作所选一路。
- 启用两路：必须指定 `FirstClamp=1/2`，压紧按照显式次序，释放反序；没有顺序拒绝保存/发布，不按编号擅自猜测。
- `MovementTimeoutMs` 作为每步 USB ACK＋MCU GPIO 回读的最大允许时间；不是机械气缸到位确认。
- 工程旧 `BeforeStart/AfterFinish` 中不允许再次包含 Clamp；否则拒绝整组开始。保留工程特殊 IGN/Wait，但其执行归属同一工位会话。

### 2. USB 硬件防护

`PhysicalCommandFence`、`WinUsbByteLink` 和 `HardwareConnectionService`：
- 新增工位所有的 `AuthorizeStationFixtureScope`，绑定**真实工程冻结指纹、WinUSB 连接世代、允许输出掩码、是否允许工位 IGN**，范围有效期受限。
- `AuthorizeStationFixtureChange` 和 `AuthorizeStationIgnChange` 每条都登记准确值；USB `0x18` / `0x12` 按次消费许可（消费后即使 USB 出错也不得自动重试）。
- FLASH / TEST / DID 物理授权期间不能穿插工位输出动作；新的 FLASH/TEST 清理此前未发送的夹具/IGN 单次许可，**工位作用域本身保留**到整个周期结束以便受控收尾。
- 独立手动台架 CAN/KEY/IGN/LED/夹具、UDS DID、CAN 码率切换不能借用工位作用域。主控断开重连则 `Reset` 作废旧世代全部权限。
- `SendStationFixtureAsync` 实际发送 `0x18`，随后读取 `0x19`，必须 GPIO 匹配才允许继续；`SendStationIgnAsync` 同理使用 `0x12/0x13`。**都不宣称机械位置或 ECU 端子电压已实测**。

### 3. 完整整组真实执行

`AutomaticTestHomeViewModel.Run.cs`：
- 从本次扫描绑定的**已发布工位版本**冻结 `StationFixtureExecutionPlan`，对工程师展示真实输出通道和顺序，并要求明确确认。本次确认没有实体生产 START 语义，结果只能写 ENGINEERING_VERIFICATION。
- 再次检查扫码观测 ID、项目文件与 COM 会话，防止确认弹窗期间换 ECU。
- 先验证工程/test/原生 FLASH/CAN 码率、同一发布工位身份；成功后授予本次工位夹具作用域。
- **FLASH 之前自动压紧所选夹具**，每条精确 USB 指令＋GPIO 回读；每一步操作意图和读回均更新持久化工程验证记录；中断、超时或回读不一致就不能继续 FLASH/TEST。
- 原生 FLASH → 测试项目准备 → 全部有序用例 → 项目收尾共享现有连续物理 TEST 会话，周期 CAN 跨用例保留逻辑不变。
- 工位 IGN/Wait 收尾执行完、真实测试作用域已关闭、工程验证记录已落盘、主控仍是原连接、正常流程执行完成，才按反序发送释放动作并再记录。
- 取消、USB 故障、FLASH 未验证、TEST 异常、证据落盘失败：**不自动释放夹具**，记录机械状态 UNKNOWN，留给现场受控恢复；必须撤销本次工位输出授权。
- 当前仅限工程真实实测，正式 Inspection/PASS 不会自动开放。

### 4. UI 整合

生产准备首页增加可见的“自动测试夹具工艺”：
- 夹具 1 PTB1/B5、夹具 2 PTC2/B4 勾选（不启用时不会运行）；
- 双路先后顺序，明确显示自动压紧与反序收尾；
- 行为有实际下游执行器，不是另开第三套脚本或只供说明；
- 原高级工位页同步支持顺序/反馈来源/超时；保留真实设备能力和未接线提示。
- 项目 TEST/FLASH 的原位置不变：产品工程由开发区编写；发布操作只冻结该版本。

## 三、设计取舍和未解决阻断

1. 两路输出极性来自当前 R1 主控固件源码：0=释放、1=压紧；**烧录到当前主控硬件的版本及外部电磁阀方向仍必须现场核对**。固件枚举丢失触发两路释放请求不能替代机械安全急停。
2. 主控当前没有正式可验证的夹具压紧/松开机械传感器反馈，只有 MCU GPIO。因此工程验证中的“输出指令已应答且 GPIO 匹配”**不能**推出气缸已经压紧。
3. 生产 START、STOP/互锁可信输入和可用的正式 InspectionAttempt/RECORD 写入尚未接通，正式出厂测试仍 **NO-GO**。不应通过手工字符串填写这些来源或软件 START 来冒充已完成。
4. 此处引用已发布工位 `StationProductionConfiguration`；工程源文件资源 ID、修订或 SHA 不一致仍严格阻断，不自动“修好引用”。
5. 没有编译并在实际主控硬件上实测本轮更改。任何 GPIO/机械动作时序、气动释放、USB 断连处理、代码编译均不宣称已通过。

## 四、静态验证与待做 Windows 实测

已增加测试合同源码：`StationFixtureExecutionPlanTests` 单/双路顺序、禁用零动作、未配置顺序拒绝；`StationFixtureScopeFenceTests` 跨 FLASH/TEST 保持物理 Scope 但阶段禁止夹具、单次 exact 许可、连接代际与手动授权隔离。**未运行测试/CI 或本地 Build**。

现场顺序：
1. 本地 Codex **只拉取现有 R1、编译并启动**，不修改程序逻辑。
2. 在手动台架先确认主控固件 `0x18/0x19` 支持及夹具实际压紧/释放方向、外部阀供电/气源等安全条件。
3. 在生产准备勾选实际夹具通道；两路时明确配置顺序；保存并**重新发布**工位，确认资源 ID/SHA 没有损坏。
4. 扫真实唯一编号，在工程整组实测明确授权后观察：夹具 USB 0x18 与 0x19 回读 → FLASH → 项目准备及所有用例 → 项目收尾 → 记录落盘 → 夹具反序释放。使用独立机械位置/电气观察，不能只看 GUI。
5. 断开主控、拒绝 GPIO、取消运行或故意触发 TEST 异常时，确认后续 ECU 判定被阻断、夹具结果 UNKNOWN、不会误生成生产 PASS，也不会无授权自动重试或释放。
6. 确认此前跨用例周期 CAN 报文在整个 TEST projectScope 内保持并用外部 CAN 记录，源代码的 Host USB ACK 仍不是物理周期证明。
