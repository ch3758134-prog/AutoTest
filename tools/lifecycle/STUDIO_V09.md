# Engineering Workbench V0.9｜受控产品研究协调（候选）

> 本文件对应 GitHub Draft PR #28。工具运行于本地 Python/SQLite/HTML；它不是已发布的正式工程基线，也不会自动修改 AutoTest main 或用户现有数据库。

## 为什么 V0.8 不够

V0.8 能阻止产品定义被随意修改，并要求十个领域的影响评估；但过去 AI 可以直接填写十个领域的“无影响”，系统只能检查格式，无法强制它在影响判断之前提交研究材料。用户还需要自己录入产品定义，管理 AI 不具备提交完整候选的受控渠道。

V0.9 的第一阶段把 **AI 候选 → 人工接纳为正式议题 → 自动生成研究事项 → AI/研究者提交材料 → 负责人复核证据 → 领域判断 → 工作包影响确认 → 版本化发布** 串接起来。

## 已实现的实际约束

1. **AI 提出定义建议，不立即生效**：受限 manager token 仅能 POST `/api/studio/governance/suggest` 创建 `PENDING` 建议；不得由同一权限接受/拒绝、创建正式变更、批准研究、派发编码或发布产品定义。建议保留旧定义指纹、拟定义全文、引用与提出人。在建议阶段不暂停既有 CODE_READY 工作。
2. **负责人决定是否正式立项**：HTML 的“产品定义治理 / 变更”展示 AI 定义候选。负责人核对来源并明确接纳，后台一个事务创建正式 `REVIEW` 变更、保存原始建议的处理轨迹，自动生成十个固定研究任务。拒绝的建议同样保留历史，不改变工程基线。
3. **十个研究任务是代码生成的必需项**：研究问题覆盖定位、用户、流程、能力、系统边界、架构、接口硬件、验证、实施、交付风险。它们不依赖可能缺失的关系图，不能由 AI 删除来缩小审查范围。
4. **AI 只能交候选材料**：manager token 可以 POST `/api/studio/governance/research/submit`，提交具体任务 ID、任务修订、事实陈述、来源引用、明确的局限。服务端标记来源为 `AI_CANDIDATE`，不接受客户端伪造的“已审查”状态。候选本身不能完成任务，也不能批准产品定义。
5. **负责人逐项复核**：只允许 owner token 审查研究候选，接受或要求继续研究。任何重新调查都增加研究任务修订，历史材料保留，旧材料不能在新任务修订中静默复用。研究结论仍是记录在案的人的判断，不能自动证明来源真实。
6. **复用既有技术调查**：候选可链接现有 `Research` 模块的技术研究 ID；必须有经过实验结果审查并选择方案的 `DECIDED` 结论。引用时固定研究修订。技术调查重新打开或修订，产品定义门禁将报告引用已过期。
7. **领域结论必须发生在研究之后**：`DefinitionGovernance.review` 要求相应任务已经审查并固定研究修订。重新开展研究后，旧领域影响结论无法继续满足发布门禁。
8. **每个实施包影响判断也固定整体研究版本**：原 V0.8 的 `IMPACT/NO_IMPACT/UNKNOWN` 逐包裁决仍必须进行，而且会固定十项研究的统一指纹。任意必要研究重新开启并作出新判断后，先前的实施包影响结论需要重审。
9. **发布仍由事务控制**：未完成研究、尚未评估领域、缺失工作包判断、关系与“无影响”结论冲突、证据过期、基线指纹变化，都使 `gate.ready=false`；只有 owner 明确签发才能更新本地受控定义版本。
10. **研究内容随工程档案保存**：单项目 JSON 包含建议、自动研究任务、所有候选提交、人工审查决定、领域研究版本、受影响实施包和正式基线；恢复到空工作区时检查任务/提交/决定的身份归属及引用，保持历史完整性。

## 操作流程（在你本机）

- 通过原有 GitHub SSH 工作树拉取经本轮 CI 核对的准确 HEAD，启动本地服务并**使用既有工作区数据库的备份副本**试运行；不要直接覆盖当前正在使用的工程数据。
- 进入驾驶舱 → **产品定义治理 / 变更**。查看是否存在受控产品基线、当前未决正式变更、AI 定义建议。初次导入的文本保持 `UNBASELINED`，不能冒充已批准定位。
- 你可以先与项目管理 AI 长期讨论 AutoTest 的真实定位。AI 将其拟议文本、问题、事实依据提交到 `governance/suggest`；你在 HTML 中审阅，接受后才进入正式研究。
- 进入某一正式定义变更 → **查看必需研究与候选证据**。逐条研究、对比来源和实际对象；可使用已有技术研究结果，不需要为每个产品概念编造硬件实验。
- 负责人按实际证据确认研究，然后进入影响分析，最后检查具体工作包和变更发布门禁。结果与不确定点必须分别保留；没有证据不得填成确定的“无影响”。

## 接口及权限

| 接口 | owner | AI manager token |
|---|---|---|
| GET `/api/studio/management/context` | 读取 | 读取 |
| GET `/api/studio/governance/suggestions` | 读取 | 读取 |
| POST `/api/studio/governance/suggest` | 可提交候选 | 可提交候选 |
| POST `/api/studio/governance/suggest/accept` | 人工接纳为正式研究 | 禁止 |
| POST `/api/studio/governance/suggest/reject` | 拒绝候选 | 禁止 |
| POST `/api/studio/governance/research/submit` | 提交候选证据 | 提交候选证据 |
| POST `/api/studio/governance/research/review` | 人工复核 | 禁止 |
| POST `/api/studio/governance/research/reopen` | 重新开展研究 | 禁止 |
| POST `/api/studio/governance/review` | 领域影响评估 | 禁止 |
| POST `/api/studio/governance/publish` | 签发本地受控定义 | 禁止 |

真实 HTTP 权限由服务端根据请求令牌**重新判断**，不能根据 `author` / `reviewer` 等文本字段授权。实现中 AI 与 owner 是本地能力令牌，而不是可信独立用户身份。

## 策略版本和数据迁移

规则已升级为 `product-definition-control/2`。由旧策略创建而尚未发布的重大变更不会被偷偷认作已满足新规则，应按新策略重新提出并开展必需研究。旧版已发布的定义只保留历史批准状态，不因本次软件更新自动修改内容或重做真实验收。

数据库 schema 使用增量建表/补字段；本次不会触碰用户现有 sqlite 文件，只有用户在本地启动升级后的工作台才会进行必要 schema 初始化。升级前应备份原数据库，使用副本验证导出/恢复及浏览器操作。

## 治理的真实边界

- **没有实时后台自治 AI**：系统建立明确的研究队列和权限约束，但没有自行在后台运行 AI、自动检索所有外部资料或自主验证证据真实性。
- **引用 ≠ 证据真实性**：审查人仍须检查原始文档、Git HEAD、现场记录和实验条件；程序只验证关联身份、明确记录和修订一致性。
- **owner token 不等于强隔离**：同一 Windows 用户能够访问原始数据库或令牌的其他进程，仍可能绕过网页。这需要可信的操作系统账户/服务、签名与 GitHub protected branch rulesets，不能宣称已解决。
- **全量十领域适用于重大产品定义变更，不强加于 UI 文案等低风险修改**。后续需可验证的变更分类与适度裁剪。
- **与真实 AutoTest 关联**：这是可复用的通用工程管理内核。具体产品定位、EPB 硬件接线、CAN、UDS/Flash、波形和出厂流程仍需以 AutoTest 当前正式设计及真实实测核实，不能用模板直接签发结论。
