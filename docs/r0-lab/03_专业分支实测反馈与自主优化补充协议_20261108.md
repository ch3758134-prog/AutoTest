# AutoTest R0-LAB｜专业分支实测反馈、自主优化与问题升级补充协议 v0.1（候审）

依据 `main` 中 `docs/r0-lab/00`、`01`、`02` 设计；适用于 DEVICE、PROJECT/DBC、WAVE、UDS、FLASH、BENCH/UI、TEST、SCAN/PRODUCTION、RECORD、INTEGRATION。本文解决“用户在各专业对话现场试验、该对话独立诊断和优化”的闭环，不替代已批准 G3/G4，也不扩张任何物理输出授权。

## A. 专业对话的职责不止首版编码

从现在起，**各专业对话对本专业从 R0 首次可测到 R1 定型的整个学习过程负责**：专业 UI 方案、可用诊断入口、自动测试、现场故障分析、修正、复测建议、经验固化。用户在该对话里讨论并确认专业操作体验；主对话只承担跨层裁决和汇总，不代替每一个专业做所有局部调试。

一轮实测可以失败多次：每次记录版本、可复现输入、真实输出、错误层级、代码差异和验证证据；不得用删除断言、改大超时、伪造 PASS 或放开 Mock/Physical 门禁来“修好”。不要求其他专业等待。

**一个专项候选的软件完成状态与现场验证状态必须分开**。允许同一分支同时有新 UI 功能开发、Mock 自动回归和等待用户现场试验的功能；等待现场反馈不能阻止无关开发。

## B. 故障处理权限——问题在哪里，修改权限不自动扩张

| 归类 | 举例 | 专业分支可做 | 必须升级 |
|---|---|---|---|
| UI / 使用体验 | 输入流程繁琐、字段不足、错误信息不清晰、原始 Trace 不可读 | 本专业 View/ViewModel、专业页面和对应测试直接修订；用户在分支中确认 | 改总体 Shell/全局交互规范时提交总 UI/主对话 |
| 本专业业务逻辑 | Wave 参考对齐、Flash Job 阶段显示、UDS 响应解释、生产身份规则 | 在已授权专业文件内修订，补失败复现测试 | 涉及跨模块合同/状态语义时申请 |
| 共享通讯基础 | USB/CAN、ISO-TP 帧处理、UDS Client 基础策略、公共超时语义、SessionGeneration | **先**提供原始帧、最小复现、失败定位、建议修改和影响范围 | 主对话指定唯一共享代码负责人，确认后才能改 |
| 物理链路或 ECU 行为未知 | ECU 不响应、Bootloader 时序不明、地址/Seed-Key/电压未知 | 收集完整原始事实、调整专业诊断展示和实验参数（不越过安全边界） | 依赖真实资料、用户现场信息；不能猜测改底层或冒险发送 |
| 公共资源/记录/Prism | Resource Revision、RunId、共享记录、Shell 导航/DI | 用现有合同开发并提交缺口 | 主对话和 INTEGRATION 统一设计和接线 |

**UDS 和 Flash 即便由同一个对话负责，仍是两个修改权限角色。** Flash 任务默认只能修改 Flash 专业代码、UI 和测试；如果发现疑似 ISO-TP/UDS 通讯 Bug，要单独建立 UDS 核心问题单，附原始 Trace 和独立复现，由主对话审查后才转交指定 UDS 核心维护角色。不允许在 Flash 代码提交中夹带 UDS/ISO-TP 修改。

**DEVICE** 对 USB 和 CAN 底层负责，但同样不能自行扩大物理输出授权；**BENCH** 修改台架页面不等于有权修改 DEVICE 或固件；**WAVE** 修改曲线不等于修改 DBC 编解码和时间戳原理。

## C. “可供现场试验”必须是一款能够诊断的软件，不是只有运行按钮

专业 UI 至少要呈现：

1. 当前项目、ECU/Profile、资源 Revision、设备身份、SessionGeneration、模式（Mock、Replay、Physical）和连接/作业状态。
2. 可操作的参数编辑、发送/执行/停止及其明确使能或拒绝理由；操作前状态与操作后的结果独立显示。
3. **操作时间线**：用户动作、业务阶段、开始与结束、耗时、预期、实际、错误和具体反馈。
4. **原始证据区**：USB/CAN Tx/Rx（相应功能）、PDU/帧/字节、来源、时间戳、超时与重试、NRC、丢帧或时钟质量；并提供过滤、复制和导出。
5. **故障定位区**：失败层级（UI / 应用 / UDS / ISO-TP / CAN / USB / ECU / 物理反馈）、关联 ID、最后有效响应、Uncertain/Unknown 与建议检查项。
6. 自动保存或一键导出**完整本次诊断包**：软件 Git SHA、Profile/Resource 版本、场景参数（经脱敏）、原始事件、错误及必要时间信息。不能只截图一个弹窗、进度百分比或 PASS/FAIL。

所有功能需区分 `RequestIssued`、`TransportAccepted`、`EcuResponded`、`PhysicalObserved`、`BusinessVerified` 五种不同事实。没有物理反馈就显示“未观察/未知”，不能从 USB ACK 或 CAN 已发送推断 ECU 实际改变。Trace 落盘失败、溢出或丢帧要明确告警，不允许静默丢失后仍宣称数据完整。

包含 ECU 身份、种子/密钥、操作员和真实运行资料的日志留本地，导出时支持脱敏；不得将原始敏感日志未经核查上传 Public GitHub。

## D. 现场故障处理流程（用户在原专业对话内即可完成）

1. 用户描述现象并提供操作步骤、软件版本、必要截图或诊断包。专业对话立即针对现有代码和实际 Trace 进行分析，不要求用户先回主对话。
2. 专业对话区分：确认代码缺陷、UI 操作问题、目标 ECU/物理条件未知、共享基础缺陷待定位；允许并行存在多个假设，但报告中标明证据和可信度。
3. **在该分支可编辑范围内**，专业对话直接给出完整改进设计、精确代码补丁和相关测试；用户按需批准操作体验修订。Codex 仅按指定内容机械应用、Build/Test、回收原始错误，不自主修复。
4. 超出修改边界的，只递交**最小升级单**，不让本专业工作整体停工：现象、最小复现、原始请求/响应/时间序列、出错层级和建议的最小共享修改、会受影响的其他工具、必须增加的回归测试。
5. 本专业保留 Issue 状态与候选版本，修复后的软件自动测试照常进行；用户根据风险、方便程度决定何时复测。需要真实验证的功能，在拿到复测证据前不得标记 LAB_PASS。
6. 只将跨模块影响、正式合同改变、候选版本摘要和用户批准的最终专业行为汇总到主对话，后者负责 SAEF、GitHub 统一基线与系统级回归。

**不得把“还没拿到用户复测”作为停止下一项无关专业功能开发的理由。**

## E. 用户优先进行现场试验的顺序（不是开发串行顺序）

- **首先 DEVICE USB**：枚举、VID/PID/Instance、WinUSB 连接失败阶段、原始请求响应/SEQ、GET_VERSION/只读命令、断线和日志落盘。当前 USB 尚未实测成功，DEVICE 专业对话为现场排障第一响应者。
- **然后 CAN + DBC + WAVE**：先 CAN RX 原始帧，核对设备 CAN Role/时间质量，再 DBC 解码、Wave Live/Replay/参考；独立证明受控 CAN Tx 和实际反馈，不能仅凭 Wave/DBC 判断 Tx 已验证。
- **随后 UDS**：先真实受限诊断读服务与 ISO-TP 分帧、NRC、P2/P2*、断线重连，严格对应同一个设备会话。
- **再 FLASH**：先完整 Job/镜像/Mock/日志，再经独立物理授权和 Bootloader 证据进入真实刷写；必须以成功写入、校验/版本回读和真实证据确认，而不是以作业进度为成功。
- **之后 SCAN + BENCH**：扫码枪识别、身份规则、状态透传、按键与五路电压、控制请求/真实响应/实际观测区分。
- **综合 PROJECT + 总体 UI + TEST/RECORD**：最终 13 页工程工作台、工程资源流转与操作体验，但最小工程/Revision/Profile 合同必须更早提供给 Wave/UDS/Flash。

专业对话可以在用户未进入该专项试验时继续其专业功能、UI 和自动测试。某个单元的现场问题只阻断与其真实依赖相关的物理测试，不自动阻断其余模块开发或 Mock/Replay 联测。

## F. 每个方向额外必须注意的可观察性

- **DEVICE**：Native WinUSB 调用阶段、错误码、设备路径/接口、USB 请求响应、SEQ、超时、CAN 数据与物理端口映射、收发统计、SessionGeneration；连接失败也必须有完整导出。
- **PROJECT / DBC**：DBC 原始位布局、ByteOrder、Factor/Offset、有效性与物理值，原始 CAN 帧和解码值同屏；编辑/保存/Revision/资源引用变更有历史。
- **WAVE**：源帧→解码→采样点、原始时间与时间质量、丢样/空窗、游标、参考版本、对齐与每处判定依据；能跳回原始 CAN 帧。
- **UDS**：Tx/Rx PDU、SF/FF/CF/FC、SID/NRC、ResponsePending、P2/P2*、会话、请求关联与诊断服务 Profile；支持失败导出。
- **FLASH**：镜像段/地址与哈希、ECU/Profile、Job 阶段、每次请求/响应、块序号/实际确认字节、NRC、失败位置、Uncertain、写后校验结果；日志中不明文泄露 Seed/Key。
- **BENCH**：Controller Revision、请求状态/KeyMask、USB ACK、实际电压/ECU 反馈四层事实；失败恢复和实际设备状态有明确提示。
- **SCAN/PRODUCTION**：扫码原文、识别规则版本、配方选择、RunId、复测/去重、失败不放行原因；与测试/记录的链接可追溯。
- **TEST**：编辑节点和 Run Snapshot 版本、每步 Expected/Actual、异常分支/取消/清理、StepFact、原始证据链接。
- **RECORD**：RunId/JobId/CorrelationId 聚合、OperationTrace、来源 Mock/Replay/Physical、统计去重、查询和完整导出。
- **INTEGRATION**：正式 WPF 入口及工程上下文、DI/Prism、唯一 Session/共享 CAN、统一 Trace 出口与受控公共服务；不得用仅能打开窗口来宣布联调通过。

## G. 交回主对话的最小摘要（不用搬整个分支聊天记录）

每次完成一项实测反馈的有效迭代，提供：`Specialist`、`IssueId`、`GitBaseSha`、`Symptoms`、`EvidenceReference`（原始日志本地路径/脱敏摘要）、`RootCause`（证据/可信度）、`ChangedFiles`、`TestsAndResults`、`LabRetestStatus`、`SharedContractImpact`、`UserDecision`、`NextOwner`。不需要每次 UI 文案微调都打扰主对话，只在要改变跨工具接口、运行权限或正式产品体验基线时升级。

## H. Git 与状态

各对话以读取当前 `main` 为起点，记录 BaseSha；写入前重新核查 Head，不能覆盖其他专业的新版本。普通专业私有修改可按用户明确授权的方式进入统一 `main`；没有得到写入许可就交付变更候选与准确文件差异，由主对话协调。共享核心层由唯一代码负责人修改。禁止 force push、重置/清理本地工作区。

状态彼此独立：`DESIGN_ACCEPTED`、`CODE_BUILT`、`HOST_WIRED`、`READY_FOR_MOCK_REPLAY`、`READY_FOR_PHYSICAL_LAB`、`LAB_OBSERVED`、`LAB_REVISED`、`LAB_RETESTED`、`R1_ACCEPTED`。不能因为 Mock 通过便宣布实机 PASS，也不能因为用户尚未复测而停掉其他功能。
