# G1-03｜系统功能要求与当前开发范围（M2 候审）

> 46 条条目是**候审需求索引**：34 条左右属负责人明确意图，工程建议与待实验事项并非已冻结的产品承诺。正式状态仅由本地 SAEF 批准后的文件决定。具体数据载于 `data/requirements_reclassified.csv`。

## 一、编制原则

- **系统级要求**描述完整台架应表现的行为，不把旧 HOST 类名、WPF 控件、脚本语言或某款 EPB 的 CAN 信号当成默认系统要求。
- `CONFIRMED` 表示负责人当前明确意图，批准本 G1 后成为受控目标；`CANDIDATE` 是工程设计建议，**批准文件并不等于逐项批准实施方案**；`TO_VALIDATE` 需要真实试验确定指标和细则。
- 实施优先级与验证等级分别管理：`B0/B1…` 真机链路、`H3` 研发自动测试闭环、`H4` 生产闭环、`专项` 为后续专业服务。允许前期接口预研并行，不冒充实现。
- 新 HOST 与两套 MCU 固件均是系统内可维护软件资产；固件持续迭代须通过修改影响分析、构建、版本身份和台架回归。

## 三、需要保持一致的三条业务关系

**设备与测试分离**：具体硬件能力来源于 G0 与按板卡/固件版本验证的设备接口；工程资源绑定 DUT 与工位，测试程序使用资源而不是直接写死“主控 CAN1/MCU CAN0”。外部电源不是默认软件可控端点。

**编辑与运行分离、语义同源**：UI 编辑的程序和运行编译后的执行计划是不同生命周期对象，但节点类型、输入参数、流程控制、预期条件与结果字段必须有可验证映射。可视化编辑器不允许凭展示方便改变运行语义；已启动的运行上下文不应被编辑窗口静默改写。

**扫码、烧录、记录形成完整生产关联**：从外部扫码读到 DUT 身份后，解析/匹配、资源与型号、通信配置、烧录目标/HEX、测试工程及运行结果应有明确关系；一台 ECU 可以有多个 Run，不以编号重用作为历史覆盖条件。用户团队设计实体码；HOST 提供匹配编辑，不自行生成物理码。

## 四、近期实施限制与批准边界

当前不是从零采购通用测试硬件：主要用现役双板、单 DUT；新增外设暂不进入 H3/H4。计划首先实现正式设备核心加诊断入口复验 B0～B6，再由工程/DBC、编辑与执行、UI 设计系统等工作包并行开发，并在 H3/H4 逐步集成。首个 H3 需要真正的 ECU 测试运行与真实结果；H4 需要实际扫码枪、烧录程序与生产统计实测。**所有报告初始实测状态均为 NOT_RUN**。
