## v0.3 负责人确认的需求事实（较 v0.2 优先）

1. **系统角色：通用 ECU 测试平台。** 平台提供和编排真实硬件激励、CAN/DBC、波形、诊断、测试步骤、数据及记录能力。测试工程师在测试程序中定义具体 DUT 的测试项目、期望、阈值和 PASS/FAIL 条件；平台不得预设 EPB 驻车、释放或任何型号的出厂合格标准，也不能在用户已声明的测试程序之外自行提高或改变产品判据。
2. **测试程序规则与平台正确性分离。** 程序业务判据是否适合该 ECU，由测试工程师及实际产品规范负责；平台负责准确执行所编辑的步骤/条件/比较/状态转换，按数据有效性与运行错误形成可靠执行事实，并记录所用判据。用户编辑了不适合的阈值不等于平台执行错误；但平台误执行、误解码、误报结果仍属于平台问题。
3. **当前 DUT 主电源为外部独立设备直接供电和控制。** HOST、主控板、按键板当前不控制该供电及台架上其他外部电源设置。不在现阶段 HOST 增加 DUT 电源通断步骤、软件按钮或自动供电能力要求；外部电源的准备可作为测试前置条件。固件存在 `SET_ECU_PWR` 字段不改变这一现场事实。
4. **IGN、夹具电磁阀、按键网络为当前平台需要组织的实体控制能力。** 夹具除了可以单独手动操作外，必须能作为可编辑/执行的测试程序步骤，用于连续扫码、装夹、真实测试与释放的自动工作流程；实际执行仍依赖真实硬件通路验证，不因源码存在而认为实测已通过。
5. **停止/异常策略暂不做 ECU 专用固定决策。** 参考 ecu.test 的配置机制：可选择发生 ERROR/FAILED 后继续或中止、配置异常恢复用例或后置步骤、记录人为终止原因；只复制成熟的功能思想，不把 ecu.test 可能支持的端口复位能力假定为现有硬件已具备。优先保证可观察、明确中止、保持真实状态未知与受控配置；具体停止后的 IGN/夹具/按键动作留待真实台架实验确定。

本版从系统需求中删除“平台决定 EPB 出厂证明范围”“HOST 负责 DUT 电源控制”两类错误前提；未更改已批准 P0/G0，也未正式批准本次 G1 候审稿。

## 审查摘要

本轮不重新定义 AutoTest，不因历史 UI/Mock 代码存在就保留相关功能，也不要求先清理全部旧分支。`main` 暂作正式管理/集成基线，但**不保证稳定**；`local` 是持续研发成果来源。另一专业对话正在研究的技术方案，只有在形成可审查成果后才纳入相应需求或设计变更。

**本轮要求形成的产品行为：**用户可以独立建立工程、配置资源、编辑测试程序并调用真实硬件及专业工具，观察 ECU 响应；系统按用户编写的测试步骤和判据执行、评价、记录，不代替用户决定某型 ECU 的出厂合格条件。生产人员通过扫码匹配正确配置，按可编辑流程组织装夹、测试、释放并追溯。不能用 Mock 或 UI 演示替代真实执行。

本稿仅提出**系统级用户需求**及验证方向，不冻结 WPF 布局、内部类/文件、USB 具体帧字段、固件引脚、UI 风格参数、性能数值或具体 ECU 的测试程序。

## G1-01｜用户与业务边界

| 使用者 | 需要完成的工作 | 系统应交付的结果 |
|---|---|---|
| 测试工程师 | 建工程、导入 DBC、配置资源、编写和调试测试程序 | 可保存、可重开、可执行的工程及测试程序 |
| 研发/故障分析人员 | 连接硬件、单独使用 CAN/UDS/波形/手动台架等工具 | 可观察的命令、实际响应与诊断证据 |
| 生产操作员 | 扫码、核对 DUT 身份和匹配配置、按已定义工序运行 | 每件 DUT、每次运行独立且可追溯的结果 |
| 现场维护人员 | 排查 USB/CAN、板卡、IGN、夹具、按键及软件异常 | 可定位故障阶段的记录，不虚报硬件到位 |
| 项目负责人 | 审查研发工作与交付证据 | 真实功能状态、限制和待决定事项，不是自动“完成”状态 |

**适用边界：**完全离线 Windows 工位；现阶段一台 PC、一台 DUT；以现有两块板卡及其持续可维护固件为实际硬件基础。平台面向不同 ECU 配置，EPB 不成为通用软件的固定业务逻辑。软件通用性不代表当前台架能够产生或测量任意 ECU 的全部外部条件；实际能力须经过硬件配置与适用性检查。未来双 DUT 或其他硬件扩展是可扩展性方向，**不进入本轮实际交付承诺**。

## G1-02｜完整用户任务与成功条件

| 场景 | 用户完成任务的必要过程 | 可核查的成功表现 |
|---|---|---|
| UC-01 工程准备 | 创建/打开工程，添加、编辑、删除、导入资源，保存并重开 | 资源、引用和修改可恢复；错误文件不使整个工程无响应 |
| UC-02 CAN/DBC 配置 | 导入/编辑 DBC，选择报文与信号，配置发送或实时观察 | 编码/解码依据当前 DBC，报文和信号可追溯到工程资源 |
| UC-03 测试程序设计 | 在工程内新建程序，增删改步骤、条件/循环、参数和引用，保存重开 | 所见步骤与实际待执行语义一致；错误在运行前可定位 |
| UC-04 研发执行 | 连接真实设备，选择工程/程序，在程序中编辑期望和判断，检查条件，执行并单步观察 | 实际输入/ECU 响应按用户定义的程序判据执行，记录步骤评价、停止与日志；平台不另定产品合格线 |
| UC-05 独立工具 | 打开 CAN、UDS、波形、烧录测试或手动台架工具 | 工具可独立完成其职责，也可按适用接口参与测试程序 |
| UC-06 生产运行 | 扫实体码，匹配 ECU/程序/配置；按用户编写的流程控制可用夹具动作、执行检测、在适用时释放夹具 | 支持连续扫码与程序化装夹/释放；身份或配置不匹配时不运行；每次 Run 独立保存 |
| UC-07 失败与复测 | 断连、缺帧、设备超时、测试失败、重复扫描与复测 | 状态清楚、历史不被覆盖，恢复前置条件和结果可核查 |

这些是业务任务，不是强制固定页面顺序；具体 ECU 是否烧录、判断什么状态合格，由工程配置和测试程序指定。夹具程序步骤必须可编辑且可用于生产循环；扫码触发与具体工序顺序由项目配置。外部独立电源不属于当前台架可被 HOST 编写的动作。

## G1-04｜质量与可用性要求

| ID | 要求 | 应如何验证 |
|---|---|---|
| Q-01 | 离线可用：没有互联网仍能开展已配置的工程、诊断和测试工作 | 断网条件下执行完整用户任务 |
| Q-02 | 可操作性：中文、键鼠、右键、层级、焦点与状态反馈一致；不以大量无关弹窗替代直接编辑 | 真实 WPF 任务走查，含不同 DPI/长文本 |
| Q-03 | 响应性：工程资源树及基本编辑操作应及时反馈，耗时操作可取消/报告，不能长时间假死 | 代表性工程规模的实际测量，阈值依据数据确定 |
| Q-04 | 工程数据安全：资源引用、保存、删除及文件损坏有明确处理，不能无提示毁坏历史 | 保存/重开/失败/冲突/损坏用例 |
| Q-05 | 真实证据语义：请求、主控 ACK、CAN 实际帧、ECU 内部报告量及测试程序评价分开；系统不把程序 PASS 描述成未经定义的产品物理认证 | 真实数据、用户配置判据和运行记录交叉核对 |
| Q-06 | 可靠性与恢复：错误/中止的可配置策略参考 ecu.test，记录中止、失败、清理与未知物理状态；不预设 IGN OFF、夹具释放、按键全部释放为统一安全结局 | 测试程序异常分支及实际设备断连试验 |
| Q-07 | DUT 无关：通用层不依赖单一 EPB 型号或固定信号，适配受现有物理硬件能力及配置限制 | 不同 DUT 的资源替换及工程验证 |
| Q-08 | 维护/扩展：工具、硬件/固件和工程配置的变化可受控验证，不凭旧 Mock/旧 UI 结构强行兼容 | 接口变更影响审查与回归 |

**不在 G1 凭空定数值：**CAN 帧率、USB 响应、波形精度、生产节拍及 UI 延迟必须以代表性设备和数据测量，再设具体可验证阈值。现有 HOST `CAN_RX_IND` 接收路径采用 HOST 到达时间，不能声明跨设备高精度硬件时间戳能力。

## G1-05｜接口与工程数据边界

| 边界 | G1 应明确的交换对象 | 设计/实测后才确定的细节 |
|---|---|---|
| HOST ↔ 主控板 | USB 请求响应、设备身份、CAN 与输出操作 | 协议细节、超时、固件兼容 |
| 主控板 ↔ DUT/按键板 | 双 CAN 通道、报文及状态，区分 MCU/PCB/业务命名 | 物理连线、速率、周期精度、质量与硬件时间基 |
| 按键板 ↔ ECU 输入 | CAN `0x730` 20 位开关掩码形成五路电阻网络条件 | 各型号识别电压、可实现组合、负载条件及实际板卡版本 |
| HOST ↔ 工程资产 | DBC、测试程序、配置、波形参考、烧录资料 | 文件模型、版本、引用一致性 |
| 扫码枪 ↔ HOST | DUT 标签输入与匹配结果 | 码格式、输入设备特征及生产规则 |
| HOST ↔ 记录 | Run、DUT、步骤、操作和报告事实 | 数据库结构、保留策略、导出格式 |

一套 ECU 测试工程可配置多个资源，但某次 Run 必须保留当时所用身份与配置；记录间关系由 G2 数据设计详细确定，G1 不规定必须拆成多少文件或数据库表。

## G1-06｜异常、停止与恢复

| 异常 | 必须达到的用户可观察结果 |
|---|---|
| USB 断开、无 ACK | 记录最后已确认的步骤、已发命令和未知状态，不能把超时等同于命令没有生效，不能认定物理动作已完成 |
| CAN 缺帧、错误通道或旧数据 | 能区分无帧、过期、解码失败、超时，不能据此给出无依据的 PASS |
| 夹具、IGN、按键操作失败 | 区分主控响应、GPIO 回读及真实电气/机械结果；按可配置错误处理路径记录并停止或进入恢复步骤，具体动作待实机确定，未知状态保持未知 |
| 正在执行时编辑、扫码或使用另一工具 | 不改变已锁定运行对象；冲突需显式处理 |
| 测试停止、单步/跳过及异常路径 | 支持参考 ecu.test 的可配置中止处理、恢复测试包、执行前后条件与终止原因记录；不预设自动复位全部物理输出，也不把动作请求当成实际到位 |
| 烧录错误或设备断线 | 标记失败/未知并记录已确认阶段；仅依具体 ECU 恢复流程处理，禁止静默重复不可逆动作或假定可断点续传 |
| 资源文件损坏或版本不符 | 保护历史原件，解释受影响的操作，不把损坏数据当有效配置 |

## G1-07｜需求验收与证据矩阵

| 验证链 | 最低实际证据 | 当前状态 |
|---|---|---|
| V1 工程/DBC | 建工程 → 导入与编辑 DBC → 保存重开 → 发送/解码正确 | NOT_VERIFIED |
| V2 程序编辑 | 创建多种步骤 → 条件/循环/参数 → 保存重开 → 校验与调试 | NOT_VERIFIED |
| V3 设备与手动台架 | USB/双 CAN → IGN/夹具/按键的手动调用与测试步骤调用 → 响应、日志与错误 | NOT_VERIFIED |
| V4 真实 ECU Run | 编写判据 → 执行已编辑程序 → 收集 ECU CAN/电流波形/诊断 → 按程序规则评价 → 报告 | NOT_VERIFIED |
| V5 专业工具 | UDS、波形、CAN、独立烧录测试等专项按真实能力逐一验证 | NOT_VERIFIED |
| V6 扫码与生产 | 连续扫码匹配 → 测试程序控制夹具压紧/测试/释放 → 失败/复测 → DUT 追溯 | NOT_VERIFIED |
| V7 异常/恢复 | 断连、缺帧、错误配置、烧录异常、数据损坏等负测 | NOT_VERIFIED |

每项实际验收需记录 HOST commit、工程/DBC/测试程序版本、设备/固件、DUT、步骤、实际数据和结论。单元测试、UI 演示、历史 SAEF 报告不能替代本次实测。

**三类验收证据严格分开：**

1. **通信/控制通路：**USB/CAN 指令和返回、时间、错误码；只能证明对应路径的观察事实。
2. **ECU 功能响应：**有效输入条件、ECU 实际报文/诊断/内部测量及 DUT 专用判据；可形成明确范围的 ECU 功能 PASS。
3. **独立物理性能：**实际校准仪器测量的电流、电压、力、位移、扭矩等；只有测试目标需要且确有此类证据时才声明对应的物理 PASS。

每次运行应能追溯：**用户配置的测试步骤/判据 → 实际执行动作与数据 → 比较和运行状态 → 证据存档**。具体测试是否充分覆盖某 ECU 的出厂规范由测试工程师/产品规范决定，不由 AutoTest 对判据本身作产品合格性审核。报告按事实准确区分观测类型，不将程序 PASS 自动命名为未执行的独立物理性能认证。

## G1 Gate｜本次仅提出候审意见

**建议：PASS_WITH_LIMITATIONS，但必须由负责人在本对话决定。**

G1 的成果是系统级需求、用户任务、接口与异常边界、验收方向及开放事项，**不是**全面 UI 详细设计或所有实体测试完成。若批准，允许以这些需求作为 G2 架构/交互与专项技术研究的输入，并按开放事项闭环；不能据此直接认为某项软件功能已实现或授权真实烧录。

建议限制（原 G1-L01～L05 保留，并新增 L06 进行证据限定）：

- **G1-L01**：UI 任务模型尚待专项研究与操作验证，不能冻结历史失败的 UI 方案。
- **G1-L02**：USB/CAN/IGN/夹具/按键的实际能力仍须在对应实测中核实；DUT 外部独立电源不属于 HOST 控制能力，今后改变台架架构须另行审查。
- **G1-L03**：烧录/UDS/波形的专项参数与异常恢复未全部定稿，不能擅自扩大到未验证 ECU。
- **G1-L04**：扫码与生产工序、统计验收需真实样本；不得以测试次数充当出厂 DUT 数。
- **G1-L05**：当前 HOST 基线仅供继续研发，旧 Mock 执行器虽已在两个分支删除，但稳定性、真实功能和集成能力仍须逐项验证；`local` 不自动合入 `main`。
- **G1-L06**：平台必须忠实执行用户可编辑的测试判据、记录数据质量和结果，不代替用户裁定特定 ECU 的出厂合格规范；ECU 报告量不能冒充独立测量，缺少的外测能力不自动形成硬件新增要求。
