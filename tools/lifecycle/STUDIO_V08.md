# Engineering Workbench V0.8 候选｜产品定义变更控制与工程治理准入

> 这是当前 Draft PR 的待审查实现，不是已经发布的生产治理系统。**旧数据库不被本次 Git 提交自动更新；现有业务基线也不被自动批准。**

## 1. 用户实际操作

在项目驾驶舱选择 **产品定义治理 / 变更**，或从项目管理 AI 页面打开该入口：

1. 系统显示现有项目资料为 `UNBASELINED`、`BASELINED` 或 `DRIFT`，列出定义指纹、最近签发的本地版本和所有历史请求。
2. 点击“提出产品定义修订”：输入拟变更的产品定位、完整定义、版本/变体、为什么改、可追溯原始来源。只登记 `REVIEW` 候选，不直接改变项目正式字段。
3. 根据系统预定义的十个领域，逐个调查并填写结论：`UNKNOWN`、`IMPACT`、`NO_IMPACT`。每项必须有分析理由和至少一个明确的来源引用。若为 `IMPACT`，必须指认真实工程对象及其当时修订；找不到对象时先补齐追踪，不准空白跳过。
4. 未评估、`UNKNOWN`、证据缺失、基线版本变化、受影响对象修订过期等都会令 `gate.ready=false`。用户不能调用普通项目编辑接口绕过。所有要求都满足后，才出现“正式发布”。
5. 用户确认发布：后端在同一个 SQLite 事务中重新校验准入、更新项目定义、形成不可覆盖的版本化基线、写审计事件，并根据**已审查的语义关系**将受影响工作包标记为待复核。不相关的工作包不自动停工。
6. 工作包复核同样必须核对当前修订、处于 `APPROVED`，填写实际复核依据。此操作只消除某次定义变更标记，**不会**绕过详细设计、源码、关联、CI 或设备安全等其他门禁。

初始项目可以有导入的产品简介和对象，但**不意味着已形成受控批准版本**。建立第一份正式受控定义也需要提交内容变化与逐领域审查，不把历史文本自动升级成批准事实。

## 2. 受信执行约束（不是聊天提示词）

- `Store.update_project`：直接修改 `summary/body/version/variant` 明确拒绝；仅行政项目重命名可普通更新。
- `DefinitionGovernance`：固定版本 `product-definition-control/1`，强制十领域矩阵、完整源参考、受影响对象版本、批准状态和乐观并发。
- `Execution.dispatch/claim/packet`：必须有匹配当前项目内容的已发布定义基线，且不存在仍在审查的重大定义变更；否则拒绝生成/分发/领取编码任务。旧已派发任务在执行看板显示 `BLOCKED_BY_PRODUCT_DEFINITION`；AI 队列不返回这些任务。
- `Store._readiness`：已发布产品定义造成的定向实施复核会阻塞关联工作包，直到复核状态解除，其他 CODE_READY 条件不变。
- `Management.context`：明示定义是否已批准、未决重大变更及派发阻塞；管理 AI 只有提案能力，`PRODUCT_DEFINITION_REVIEW` 也仅为规划候选，不能替代正式定义请求或审批。
- `studio_server.py`：网页读审查结果；带本地 owner token 的接口才能提出、逐领域审查、拒绝或发布定义；仅持 manager token 的 AI 无法经这些路由写入。
- `studio_restore.py`：工程 JSON 导出/恢复包含版本快照、影响审查、工作包失效记录；恢复需空工作区和结构/哈希校验，原始物理日志、文件、Git 历史不在 JSON 内。

## 3. 不允许“关系图缺少边 = 无影响”

系统采取**两个审查维度**：

1. 固定的领域矩阵，不依赖用户事先建立完整追踪图。因此产品定位变更即使缺少“硬件”“验证”等节点，仍必须审查相应领域并写明依据。
2. 对明确判定为受影响的对象，沿已经审查的工程语义关系计算下游工作包并生成复核。候审关系不等于已确认；没有找到的关系必须作为缺口研究，不能自动判断没有影响。

对 `NO_IMPACT` 的理由与来源**仍需负责人核实**。代码能验证字段、归属和修订，不具备证明人类文字或外部证据真实性的能力。AI 可以提出覆盖性意见，但不能由 AI 自己宣布研究充分。

## 4. 当前明确不能宣称的安全能力

**尚不具备强身份隔离。** 同一 Windows 用户可读取本地浏览器工作台的令牌，拥有数据库文件写权限的程序也可能绕过 API。owner/reviewer 字段只是审计标识，不是经验证的电子签名。当前只能用作本地单人受控候选，不能授权不受信 AI 进程在同一 OS 用户下自由调用特权接口。

**尚未将规则绑定 GitHub 受信合并门禁。** 本地 SQLite 发布是本地工作区状态，不自动获得工程 Git 仓库和正式 main 的受信批准；后续还需签名/不可抵赖审查、GitHub rulesets/required checks、受保护的协议版本与准确 HEAD，阻止 PR 绕开治理。

**研究覆盖不是自动真理。** 十领域是产品定义重大变更的最低覆盖范围；真正有风险的技术点还需有实际研究任务、可重复实验、原始数据和可追溯决策。未来应支持对不同变更分类进行适当裁剪、跨仓库配置以及独立检查关联完整性，而不是不加区别要求所有局部变更重做十大领域。

**旧已批准成果的身份没有被自动确认。** 导入的 AutoTest 历史字段/候选关系不会被直接认定为产品定义已审批、真实设备已验收或代码已交付。

## 5. 必须通过的关键反例测试

- 空产品基线不能派发或领取编码任务；单纯 GitHub CI 绿灯不能取代受控定义。
- AI manager token 无权批准或发布；旧项目更新路由不能直改产品定位。
- 缺一个领域、`UNKNOWN`、没有证据、`IMPACT` 没有明确映射对象不能发布。
- 受影响对象修订更新会使原审查过期；两个并行候选不能交叉覆盖新的有效版本。
- 已识别受影响的工作包必须复核，无关工作包保持 CODE_READY。
- 发布/审查历史可完整导出到 JSON 并恢复到空工作区；篡改已批准定义内容/哈希必须被拒绝。
- 普通改名称不等同重大产品变更；未修改产品语义的候选不能伪装成新版本发布。

## 6. AutoTest 下一实际研究议题

先使用上面的治理流程登记候选和逐域研究，**不得**将本说明视为用户已经批准某个新产品定位。先导入实际 GitHub/SAEF 证据并逐项核对，后由产品负责人作出明确版本裁决。
