# 06｜现代全产品 UI/UX 与 R1 工作界面：双轨且不相互否定

## 1. 先分清三种档案

1. **方法研究**：《现代复杂工业级 PC 软件的产品与交互设计理念研究报告 v1.0》，已正式归档，编号 `UX-FOUNDATION-RESEARCH-20261119-01`，状态 `RESEARCH_COMPLETED / ARCHIVED / PRODUCT_UI_NOT_FROZEN`；“工作空间、对象、命令、上下文、状态、恢复”是研究工具，不等同于 ISO 规定的强制布局。原文及完整审查：[UI/UX 研究原档](../new-baseline-20261112/research/UI-UX-FOUNDATION-20261119/README.md)。
2. **全产品活动设计**：`ui/ide-design` 下 `docs/ui/research/R01～R06`、`docs/ui/governance/` 和 `docs/ui/visual-research/V01～V03`。这里研究窗口、工程/文件生命周期、实际对象操作与独立工具工作环境。版本与职责单独审查，不自动覆盖现有工位业务合同。
3. **R1 可运行界面**：`R1` 当前 WPF TEST/台架/Flash/项目的定点交互修复，主要保障现场用起来，不是全产品新视觉交互正式验收。

旧 G4 冻结 HTML、各种 Preview EXE、UI 重建 PR #63/#66/#68/#69 等只作为**有版本的历史/候选**。它们的存在不授予代码合并权，尤其不能拿演示页面自动替换 R1 真 TEST 的能力。

## 2. 当前仍有效的用户体验约束

| 领域 | 当前人机操作要求 | 反模式 / 对应边界 |
|---|---|---|
| 产品视觉 | Windows WPF/Prism、现代浅色 Fluent 方向、白底/高对比、清晰字体与状态区 | 不再用深蓝大底、低对比深字或灰色旧控件假装专业 |
| 入口 | 启动尝试恢复上次工程，直接面对 TEST 主任务；工程和文件树单击切换 | 不让用户穿过多层页面才能找到一个正在执行的测试 |
| 工程生命周期 | 左侧树+文档页签+右侧上下文，新增/编辑/保存/关闭/恢复/资源引用有明确规则；修改后自动保存需兼容修订治理 | 文件管理不只是“导入路径”，不能丢用户已改对象；资源修改不能静默更新其它 TEST 冻结引用 |
| TEST 编辑 | 新步骤先入树或列表并立刻选中；右侧步骤属性常驻；添加步骤分类/搜索；准备/测试/清理结构清楚；可直接编辑 CAN / KEY / UDS / 流程与结果记录规则 | 非要新建一堆资源、反复打开属性弹窗、在很窄的长列表里滚动 |
| 执行 | 同一用例编辑和运行共享文档/状态；“此步骤/此用例/勾选范围”与停止/失败/证据明确 | 只有“运行整个项目”的大按钮，或扫码设置尚无就禁止调试 |
| CAN 编写 | 报文原始字节是第一编辑对象；Classic CAN 8 B 或未来 CAN FD 64 B 的 UI 表达须与协议能力分离；DBC 是辅助填写/解析 | 用 DBC 作为强制前置、隐藏字节、扩展 ID/周期启停语义不清 |
| 手动台架 | 独立于主 TEST 的“工具”窗口；CAN 发送在左、CAN 监视/日志在右，完整 Data 可见；支持多个周期报文；KEY 20位动作采用一致的浮窗/属性编辑，清晰停止与保持 | 过度嵌入/遮挡、只能编辑一条 CAN、KEY 依靠难读网格 |
| 专业工具 | 工具称“工具”，UDS/烧录/DBC/波形/手动台架具有足够独立操作空间，**附属窗口绑定主窗口关闭**；需保留 TEST 上下文 | 每个工具覆盖工程树；另起一个不随主窗退出的进程 |
| CAN 工具边界 | **不单独新增一套重复 CAN 工具**；CAN 发送、监视、日志仍必须由手动台架和测试运行入口支持 | “不做 CAN 工具”被误读为“取消 CAN 监视或日志” |
| DBC 编辑 | 报文列表 + 信号列表 + 当前信号详细参数；可批量连续编辑，中文名称/单位与编码一致，编辑时规范校验 | 必须先手工加 DBC 辅助信息、名称冗长不清、非法字段可随意保存 |
| UDS 调试 | 可连续交互并保存会话/服务序列，专门独立使用，但后端复用唯一诊断/烧录能力 | 独立 WPF 工具成功就冒充 TEST UDS/Flash 自动流程已经接通 |
| 可恢复性 | 主窗退出关闭所有工具窗口，自动/手动保存和断电后数据责任明确；执行停止需恢复操作现场 | 关闭一窗留下其它窗口占设备、弹窗失焦、执行后无法追溯错误 |

## 3. 现代工业级软件的原则在本项目如何使用

针对具体工作任务考核，而不是“满足多少风格词汇”：**第一次启动→选择工程→编辑用例→设置步骤及判定→运行→核查证据→改正→重试→查看历史**，每一步都应能说明当前对象、可用动作、确认状态、失败如何恢复。

强调**动作和事实分离**：例如 UI 可以显示主控波特率“已配置”，但不能仅凭 0x43 把 ECU 总线标“通讯正常”；UI 可以显示扫码“匹配成功”，不能直接显示“出厂 PASS”；CAN/UDS 命令完成仅表示相应设备接口事实。

正式 UI 评审应以具体操作脚本、真实可用界面、用户反馈、键鼠操作、工程恢复、焦点、可读与状态正确为依据。不会依据任何单独 HTML 截图、Source-code Preview 或旧 G4 的“像不像”给整个产品判 PASS。

## 4. 哪些还没有得到定版批准

- `ui/ide-design` 的 V03-02、UX-I01～03、UI-03/04/05 批次、新组件和窗口布局仍需按相应用户操作验收，不能用研究归档代替。
- WAVE 新 V2 对比/误判策略、SCAN 独立绑定/配方等**后端合同**由各专业/项目管理评审，UI 只承接字段和状态，不因工具需求重新建立后端协议。
- R1 自动保存、CAN 周期发送、手动台架浮窗和新版 TEST 样式目前有源码候选，但未据此确认所有 Windows/现场行为正确。
- 对需要重做的旧 UI 代码，采用**有证据的定点清理**，不能把稳定后端或工程兼容路径一并删除。

## 5. UI / R1 共同验收的最小真实场景

一个用户：打开上次 ECU 工程，在 TEST 用例中添加 KEY/CAN/判定/Flash 步骤，右栏修改并保存，选择两个用例运行；同时可打开手动台架和 UDS/波形工具，完整退出后没有孤立工具进程、硬件会话，重新打开工程及报告可恢复。其余生产扫码及波形 V2 的复杂操作作为独立验收脚本附加。

**结论**：UX 方法研究已归档；全产品 UI **没有最终冻结**；R1 运行 UI 必须可真实使用但不代表完整新 UI 正式准出。
