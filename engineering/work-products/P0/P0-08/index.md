# P0-08｜AutoTest 风险、决策与变更管理

> SAEF v2.0 / `P0-08` · **M2 修订候审，尚未替换本地 ACCEPTED 版本**。以本地已接受文档为父版本，旧哈希、审批记录及差异表见本包。

## 一、目的与适用范围

从 P0 到 G5 建立风险、问题、ADR 与配置变更的闭环。它们是**控制记录**，不应把系统功能设计或现场故障处理细节放在 P0。当前已冻结的固件及现役 PCB 可以在新证据表明必要时提出变更，但不得绕过审查擅自改动。

## 二、责任与权限

- ChatGPT：收集/分析风险与问题，判定关联的需求、架构、接口、源码、验证和物理装配影响，提出处理方案、优先级及停止建议，起草 ADR / CHG / ISS。
- 项目负责人：接受或退回重大技术决策、风险处置及变更；涉及物理输出、固件及正式基线改动时唯一授权。
- Codex：仅依已批准的文件/命令执行和归档；任何未授权的扩大范围、冲突或意外失败均停止，保存原始状态及日志。

## 三、执行规则

| 控制对象 | 触发 | 最低字段 | 处理闭环 |
|---|---|---|---|
| 风险 RISK | 存在可能发生的不利结果 | ID、触发/原因、概率/影响级别、关联项、责任、对策、复查节点、阻断范围 | 登记→评估→响应→复查/关闭 |
| 问题 ISS | 已观察到错误、冲突或证据缺口 | ID、实测/源码/图纸来源、适用配置、现象、复现方法、严重度、责任及现状 | 记录事实→分诊→解决/延期→核对证据→关闭 |
| 决策 ADR | 重大架构取舍、接口/依赖/配置策略变动 | ID、问题、约束、备选方案、依据、影响、是否可逆、决定/批准者、替代关系 | PROPOSED→负责人批准→实施/验证→保留历史 |
| 变更 CHG | 修改已批准需求、架构/ICD、固件、硬件或受控工作产品 | ID、旧/新版本、申请原因、影响矩阵、风险、修复方案、测试/回归、回滚、审批 | 申请→分析→授权→执行→验证→评审关闭 |

**变更影响矩阵必须逐项覆盖**：项目范围与需求、软硬件架构/接口、源代码与构建、现场硬件/固件及工装、资源/数据迁移、测试用例与证据、部署/运维/文档。若某项不适用，必须写 N/A 和理由。重大风险未经接受时不能借“后面再测”自动放行。

## 四、记录与例外处理

- 使用 SAEF 既有 `FRAMEWORK/contracts/ADR_template.md`、`CHG_template.md`、`ISS_template.md`；控制 ID 不复用。记录由项目受控 Markdown/JSON 或编号索引引用，正式事实与历史决定不可覆盖。
- 尚未解决的硬件/固件事实差异（如装配、实际烧录版本、按键通路等）登记 ISS 并注明依据；允许在不触发相关物理风险、不修改冻结基线的前提下继续无依赖的上位机设计。
- 变更影响范围未明、版本不一致、涉及未授权物理动作、缺少批准或原始失败证据时，停止**受影响的工作包**；不因为单一事项无限阻塞其他不依赖的纯设计任务。
- 风险级别与是否要独立专家复核由影响与证据决定；本制度不声称项目已获得第三方功能安全评估。

## 需求、架构及迭代中的变更分级

**发现新需求/新现场证据**不等于立刻修改冻结的 G1。先登记来源、证据等级、影响对象与最晚关闭节点：如果仅影响未批准的工作包/页面视觉细节，在该工作包设计中解决；如果影响共用数据结构、测试步骤语义、设备协议、运行仲裁、固件/硬件输出或已批准要求，建立 `CHG` 与必要的 `ADR`，经负责人批准后实施并做影响回归。

每次真实试验反馈都要判断它是**新事实**、**固件缺陷**、**HOST 实现缺陷**、**测试设计缺陷**还是**产品要求变更**，不能将“收到错误报文”直接当成架构必须推倒重来。

开展并行开发时，接口版本、工作包文件所有权、合并顺序和契约测试属于变更影响范围；任何冲突应只阻断受影响工作包，不无理由阻断其他独立研究和设计。

本次本地状态中 P0 8 项已接受、G0/G1 尚未落档；旧 P0 修订不能使用直接覆盖。M1 的工具候审与项目工作产品内容批准是不同的决定。
