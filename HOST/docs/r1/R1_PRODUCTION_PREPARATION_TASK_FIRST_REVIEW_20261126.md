# AutoTest R1｜生产准备界面职责重构：研究、实际实施、独立复评

## 目标、边界和依据

- 仅对现有 **R1** 提交源码；**main 不改、不新建分支、不主动运行 CI、Windows Build 或台架**。
- 用户现场明确反馈：首次进入生产准备不理解固定型号/编码含型号/编号登记表，不理解重复绑定产品、正反样例和两层发布；界面顶部把不可修复的 GUID/SHA 资源错误直接长篇展开。
- 一份 ECU 工程已定义唯一型号、正式 TEST 调用树、原生 FLASH、DBC/波形和 KEY_SIM；它们只在开发区编辑。生产准备**只**核对工程、呈现工位状态、提交受控发布；生产执行由扫码和真实硬件门禁独立决定。
- 真实主控/按键板：主控 USB，ECU CAN 为 FlexCAN1 的 A12(H)/A1(L)，KEY CAN 为 FlexCAN0 的 B11(H)/B1(L)；KEY_SIM 仍属于 TEST 步骤而非扫码配置。该模块不改 KEY_SIM、CAN 或硬件固件。
- 生产部署目前仍是经过 SHA 验证的**当前工程路径/版本绑定**，不是完整自带所有资源的独立安装包；不宣称已解决自包含交付。
- 正式生产 `TrustedPhysicalStartConnected=false`、`VerifiedInspectionWriterConnected=false`；没有机械到位和互锁可信证据时，绝不能因为“发布成功”获得正式 RUN/PASS。

## 独立研究结论

把技术上应该分离的数据合同（ECU 工程、扫码设备、编号解析、发布快照、实体生产记录）直接翻译成多张面向所有人的配置表，是原交互失败的根源。

唯一正确的简单路径：
1. **当前工程**：自动读取型号、名称、正式 TEST 个数与资源状态。内部 GUID、SHA 和资源 ID 错误收起，保留“查看工程问题”专用诊断。
2. **工位设备**：显示真实主控 USB/ECU CAN 回读、真实 COM 连接和 START/互锁/机械反馈仍待验收；物理设备可在安装时配置，不要求插着扫码枪才能发布工程。
3. **版本发布**：用户主动点击后，系统自动建立空白固定工位的唯一型号工程绑定；如存在多型号/不一致绑定，必须显式处理，绝不暗中改动。严格校验 TEST/DBC/波形、原生 FLASH、发布指纹，先发布 ECU 工程再发布产品/工位规则。取消、版本变化或资源错误时拒绝完整成功宣称。

扫码默认整串唯一编号：`ProductionBarcodeRule.Serial`、默认字符集 `[A-Za-z0-9_.-]+`，编号必须满足 `Parse` 现有严格限制；固定工位型号来自已发布工程/产品绑定，不从编号猜测。由此**默认固定工位且无自定义规则时，无需事先录入任何扫码正反样例才能进行离线发布**。这是对旧“必须用扫描枪现场试扫后才许发布工程”的设计修正，**不等于真机扫码已验证**。

多型号或复杂条码采用原有 `BarcodeModel`、`RegistryModel`、分隔、固定字段、正则、UT1、CSV/型号映射，仍严格要求正/反样例以及发布资源冲突校验，正式运行必须使用真实已绑定 USB PnP 扫码设备且保持会话一致。

## 实际源码实施

1. `ProductionPreparationWindow.Guided.cs`：默认首页仅“当前产品工程 / 工位设备 / 发布与生产准入”，隐藏历史繁杂字段和长 GUID/SHA；资源详情提供独立诊断弹窗，保持错误原始信息；按真实主控/ECU CAN 和真实 COM 状态显示，不伪造到位。
2. 同文件：`GuidedPublishAsync` 不再检查扫码枪在线、30 分钟实扫、PnP 或强制收集样例。固定型号且没有绑定时，从**当前打开的正式工程**生成唯一绑定后保存；已有多型号/不一致绑定不会被静默覆盖；项目确认取消即不发布工位。工程冻结与 `StationProductionConfigurationStore.PublishAsync` 的全部 SHA/TEST/FLASH 校验仍保持。
3. 同文件：现场扫码只执行纯编号解析预览，不隐含触发 FLASH/TEST/项目冻结/生产准入；删去原先“绑定工程/采用最近实扫样例”的默认重复操作与无用代码。
4. `ProductionPreparationWindow.xaml.cs`、`MainWindowViewModel.Production.cs`：把实际主控 USB/ECU CAN 已回读状态通过只读函数交给准备页；扫码变化只更新诊断；原工程受控发布仍由唯一原函数执行。
5. `StationProductionConfigurationStore.InspectRules`：为唯一固定型号、只有一条标准“整串编号”规则、无显式样例的情形允许**离线发布**；若用户添加了任何自定义规则或不完整样例，仍要求正反例，继续阻止旧版假样例和空反例。
6. 老 R1 草稿可能含自动生成的 `SN001234/SN|BAD`。普通固定工位发布时仅对这组完全匹配的旧演示样例提供一次明确的清理确认，绝不把它当真实扫过的码，也不静默清除真实用户规则。
7. `ProductionIdentityConfigTests`：更新默认离线发布规则合同、加高级编码规则必须校验正反例的回归，以及旧假样例拒绝、空反例拒绝等测试源码。

## 当前静态审查与下一次 Windows 验收

源码回读 17 项针对性一致性检查通过，包括发布不依赖 scanner、默认绑定、保留高级路径、样例合同、主控读回、XAML 标签配对、硬件准入不解锁。**Windows 构建 NOT_RUN；C# 自动测试 NOT_RUN；WPF 现场视觉 NOT_VERIFIED；真扫码与生产工位 NOT_VERIFIED。**

本地启动后必须观察：
1. 首屏不再出现技术字段和长 GUID 堆栈；资源错误只显示数量，并可展开完整证据，无法修复的工程问题仍拒绝发布。
2. 未接扫码枪，只有完整有效的 TEST/FLASH 的单型号工程也能完成**离线发布**；重启后版本仍一致。
3. 默认整串编号无需正反样例；复杂规则无样例仍拒绝；旧演示样例只在明确确认后转换。
4. 固定型号草稿为空时从当前工程自动绑定；多型号/不一致/工程外部被修改不能被隐式覆盖；取消工程确认或资源 SHA 变化不能报告整体成功。
5. 发布成功不自动运行 FLASH/TEST，不向夹具发电，不生成 Production PASS；实体 START/正式 Inspection 未就绪时生产继续阻断。
