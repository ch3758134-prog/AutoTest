# AutoTest R1｜以完整用户任务为中心的系统重构合同

日期：2026-11-27  
分支：`R1`  
性质：**当前产品与交互设计的实施约束**，不是根据单个截图的逐项修补清单，也不是已通过实物验收的声明。  
复审依据：R1 实际 `ProjectWorkspaceService`、`MainWindowViewModel`、TEST 编辑器、真实执行器、专业工具、工位扫码、FLASH 及生产记录代码。

## 1. 本次纠正的不是界面尺寸，而是工程思维

过去的错误顺序是：先按代码模块造按钮、资源和检查入口，再要求用户理解内部对象、提前选择配置、处理各种“尚未就绪”，等到实测反馈才修某个按钮。即使每个底层服务存在，产品仍然不可连续使用。

**新的唯一正确顺序**：先确认用户要完成哪件事 → 定义用户看到/编辑的对象 → 每一步的操作与即时反馈 → 保存/离开/失败后如何接续 → 真实设备运行产生何种事实 → 最后把职责映射到唯一业务模型和源代码。用户不需要认识 AssetId、Revision、TCF、工位部署、published FLASH、可信准入、第二套配方。

任何新能力若需要新增一种“用户必须提前配置、确认或启用的中间对象”，必须先证明它是物理或业务上不可避免的用户目标；否则应内化到工程与专业工具，不再追加一套流程。

## 2. 单一用户对象模型：可见对象比技术模块少

| 用户看到的对象 | 唯一持久身份/归属 | 能做的自然操作 | 不能再出现 |
|---|---|---|---|
| ECU 工程 | 一个型号、一个工程；自身保存资源归属和固定扫码标记 | 新建、打开、自动保存、改名、切换、关联真实身份 | 额外工程发布、部署许可、独立生产方案 |
| TEST 项目 | 工程内唯一有序用例调用清单 | 查看顺序、新增用例、直接编辑用例、复制/移动/移除调用、整组调试 | 第二套启用、另选测试方案；无用例还显示“已就绪” |
| TEST 用例 | 独立的可编辑步骤树，连续项目按引用顺序执行 | 单击选择、双击/行内编辑、插入步骤、撤销、自动保存、运行步骤/用例 | 为保存普通编辑要求扫码、硬件准入或隐藏的技术参数 |
| DBC 数据库 | 专业 DBC 文件编辑器管理文件；工程仅绑定一份当前 DBC | 文件新建/打开/导入/编辑/导出、从工程绑定/替换/解除 | 把编辑器当静态预览、非法编辑内容先保存后到生产才发现 |
| 标准波形 | 波形专业工作台持久创建/采集/管理，工程引用标准 | 多路观察、采集、建立标准、可视比较、绑定 TEST 波形判据 | 把波形伪装成普通 DBC 文件或无入口的资源附件 |
| 公共流程 | 公共流程独立编辑，使用同一 TEST 步骤模型、被用例调用 | 创建、编辑、复用、选择引用、浏览实际调用关系 | 只提供引用 UI，却无法用同一真实执行器执行 |
| FLASH | 工程内固定原生参数与固件；专业工具调试 | 选择真实 HEX、编辑 CAN/UDS 参数、保存、实烧与诊断 | 外部配置文件/独立发布步骤/把烧录塞入 TEST 步骤 |
| 单台 ECU | 扫码原文就是本次身份；固定标记识别工程 | 扫码立即显示完整内容、匹配工程、执行、复检、报告 | 用户填第二个型号/序列号、扫码后隐藏原文、重复扫码默默算新一台 |
| 检测记录 | 每台正式检测的父 Inspection，包含完整运行序列、FLASH 与逐用例/步骤真实证据 | 查看本次、按编号查历次、单台报告、批次统计和导出 | 每个 TEST 用例都被当成“一台”，父记录写了但历史窗口查不到 |

**对象构成的箭头只有**：

`扫码原文 → 固定型号标记 → 一个 ECU 工程 → 当前 FLASH + 有序 TEST（调用当前已保存用例）→ 真实设备步骤 → 单台记录`。

专业工具先建立可用 DBC/波形/公共流程，工程再引用它们。不会在生产侧重新选择一个产品配方。

## 3. 必须一口气审查的用户任务，不能按截图逐项拆开

### A. 第一次打开软件 / 没有工程

- 清晰地提供“新建工程 / 打开工程”，专业工具可在合适的独立模式使用。
- 新建只需要名字与存放位置；没有实物 ECU 参数时仍然能完整编辑。
- 新工程立即拥有一份唯一有序 TEST 和一个**空白可编辑用例**，新建后直接进入步骤编辑。此空白用例不是模拟测试，不提供 PASS，正式生产不可运行空白步骤。
- 关闭再打开恢复同一工程及最近有效编辑对象；没有“尚未发布”的工程许可，也不弹日常自动保存确认。
- **当前实现**：`CreateReadyToEditAsync` 已调整为同操作生成真实 TEST 项目、首个用例和二者的持久引用；新增格式/重开源码测试。待 Windows 运行验收。

### B. 编排 TEST / 编辑任意用例

- 唯一顺序清单就是 TEST 项目；新增步骤从当前阶段/行/分支旁的 `+` 操作。
- 添加动作时只出现**真正能使用**的步骤；所有类别及搜索由同一动作目录生成，单击可添加，之后立即编辑参数；保存成功后可继续添加下一步。
- CAN 发送以完整字节数据（8/64 B）、ID、周期/单发为核心；DBC 信号作为常驻辅助；按键使用 20 Key 实物动作语义；条件判断/循环/变量行为符合唯一运行器。
- 右侧临时属性编辑不应被点击空白误关，双击/行内编辑须可完成，错误输入保留在当前字段供修正；没有隐藏的“请先被允许编辑”。
- 自动保存后 TEST 项目必须立即使用已保存定义；跨用例变量、CAN 周期、KEY 组合、IGN 状态在同一连续项目作用域内继承；局部调试的勾选只控制这次范围，不改变生产正式顺序。
- **当前实现**：已修正新工程首用例、选择器类别单一来源、跨用例变量项目解析；`CallPublicFlow` 真实执行链仍缺失；复杂步骤浮层/输入 UX 仍未全量 Windows 交互验收。

### C. 资源的独立创建、绑定和被 TEST 使用

- 在专业工具中完成 DBC 文件工作流；导入非法内容时直接说明具体格式问题，不能靠生产运行时另设审查。
- 标准波形在真实波形工作台采集、保存、选择，TEST 中选择已建立的标准；标准及其样本应随工程进入实际生产包。
- 公共流程在其步骤编辑器创建并从 TEST 中选用；若还不能真实执行，产品必须明确状态，不能出现“能添加、能保存、到执行才突然不支持”的假入口。
- FLASH 参数可以逐项编辑成草稿，但正式烧录绝不接受缺固件、未知地址或假的 HEX。支持的 ECU OEM 方法要由真实参考确定，不能捏造。
- **已发现真实断点**：`TestStepInspector` 有 `CallPublicFlow` 编辑入口，而 `PlanCompiler` 与 `RealRunCoordinator` 仍不支持执行；`RecordHistoryWindow` 只检索 SQLite 用例记录，`ProductionInspectionArchive` 又存独立父记录。二者必须作为**架构整合**解决，不增加新审批层。

### D. 工程调试

- 直接选择步骤/用例/勾选连续范围运行，设备不连时仍能完整编辑与检查结构。
- 调试与正式生产使用**同一 TEST DSL/硬件执行内核**，只是上层真实运行范围和正式 FLASH 前置不同。
- 运行过程始终可见步骤状态、CAN 监视、失败原因、可追踪证据。停止先取消正在进行的真实工作，后清理；未得到有效 ECU 响应不能伪称通过。

### E. 一台 ECU 的正式生产

- 扫码 → **立即显示原文** → 匹配整个已安装 ECU 工程 → 软件/实体 START → 固定两路夹具压紧 → 收到实际 ECU CAN 新帧作为通信就绪 → 每次必须原生 FLASH → 连续整套 TEST → 单台报告/归档 → 夹具释放。
- 不做“用户许可”“发布批准”“可信准入”或重复选择 TEST。型号标记绑定是工程/设备长期配置，不是每台机器操作。
- 实体 START/STOP 固件未接入前软件 START 可调试；CAN 通信反馈仅证明 ECU 可通信，**不能替代独立机械安全设施**。
- 出现 USB、ECU CAN、FLASH、磁盘/报告真实失败，应说明实际发生了哪一阶段、哪台编号、能否安全继续；不得让上一次 DUT 身份被新扫码覆盖。

### F. 报告、复检与批次

- 用户看的是**一台 ECU 一次正式检测**，不是几个用例数据库。按完整扫码号查历次，复检是新 Inspection，与历史关联。
- 报告包含真正的 FLASH、TEST、失败步骤、测量数据及 CAN 证据；父汇总与子用例 Run 一致。PASS 只能在收尾及报告完成后提交。
- 统计按父 Inspection 计数；不能因为一个项目执行十个用例而统计出十台。
- **已确认尚未闭环**：生产父记录 `%LocalAppData%/AutoTest/records/inspections/yyyyMMdd` 与历史窗口 SQLite 查询入口未整合；当前日统计不能代替可用的生产记录查询与完整批次报告。

## 4. 统一交互原则：每个动作都要有结果，不能只看有无代码

每个工作区中的每一个操作都必须同时回答六个问题：

1. **我在哪里？** 当前 ECU 工程、TEST、用例、资源、DUT 的身份始终明确。
2. **我现在可以做什么？** 自然主操作显眼；次要高级参数只在需要时出现。
3. **做完会怎样？** 新增后马上出现在用户所在位置，编辑后可继续操作，保存后消费者读取当前定义。
4. **失败在哪里？** 错误归属于正在编辑/执行的具体对象和字段、报文、用例或阶段；技术堆栈写日志，不让“工程操作未完成”成为常态交互。
5. **怎样恢复？** 输入未丢失、编辑器不突然关闭、重新打开能继续，真实硬件状态未知时不宣称安全。
6. **数据是不是同一个？** 编辑器、执行器、扫码匹配和报告不可分别持有一套含义不同的项目/步骤/运行结论。

**禁止以“新增一个防误操作门槛”替代设计。** 写入输入有效性和资源引用应由编辑器保证；真机通信、驱动、FLASH 和报告的真实失败保留真实处理。

## 6. 完成判断：必须做真实任务回归，而不是对一张截图打分

1. 不连设备：从空目录创建工程 → 自动打开首用例 → 连续添加 CAN、KEY、IGN、信号判定、IF、循环 → 修改/撤销/自动保存 → 关闭重开 → 所有数据和视图接续一致。
2. 不连设备：DBC 文件创建/导入/修改/导出 → 工程绑定 → TEST 选择信号 → 波形标准与公共流程创建/绑定 → 项目顺序变化、引用升级、删除与失败恢复。
3. 连真实设备：USB 自动连接、手动台架按键保持、CAN 单发/周期跨用例、波形多路采集与判定、UDS/FLASH 日志、异常停止。
4. 正式生产：完整单码输入可见 → 识别整个工程 → START → 两夹具 → ECU CAN → 每次 FLASH → 全量 TEST → 单台 PASS/FAIL/UNKNOWN → 报告 → 可从历史查询 → 复检与批量统计。
5. 交互回归：至少 1366×768、1920×1080、100%/150% 缩放；单击/双击、浮窗、切换、输入非法内容、断开、重启/退出均不丢编辑。
6. Windows Release 编译、真正打开 UI、真实 ECU 与外设验收分别记录。**代码存在、测试编写、GitHub 提交、截图看起来不错都不是整机交付。**

当前项目治理继续只在 `R1` 改真实源码；`main` 保持基线，不主动跑 CI，不用 mock 冒充硬件结果。下一轮必须按这六条真实路径整体审查并完成交叉修复，不把用户指出的某两处小问题当成交付目标。
