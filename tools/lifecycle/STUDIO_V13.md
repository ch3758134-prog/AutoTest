# Engineering Workbench V1.3｜AI 受控工程修订与真实权限边界

> 2026-11-10，AutoTest 管理系统 Draft PR #28 的候选版本。GitHub 分支内的代码变更**不会自动更新用户 Windows 本地 SQLite**，也不会修改 AutoTest R1 正式产品需求、固件、现场设备或 main。必须在副本做实际迁移与人工验收。

## 一、纠正 V1.2 仍存在的两个核心漏洞

### 1. 编码授权曾依赖已经退役的四字段产品定义

旧 `Execution._product_definition_gate()` 继续从 `definition_baselines`（项目的 `summary/body/version/variant`）读取审批状态。这使新的独立产品身份完全不能真实约束 Codex 派发，也会因任何产品身份候选讨论无差别冻结所有执行。

V1.3 已改为：

- 编码派发、任务领取及执行包生成要求 **`product_identity_baselines` 中有负责人签发的规范产品身份版本**。
- 项目历史 `summary/body/version/variant` 以及历史 `definition_baselines` 不能冒充这个授权条件；升级后如没有新产品身份基线，编码派发仍将被拦截，不能自动迁移旧批准。
- 未被批准的产品身份候选本身不是阻断所有其他工作的理由；**已发布变化中确实受影响**的工作包根据 `product_identity_invalidations`、设计输入修订等进入待复核状态。
- 仍保留从旧历史继承来的开放失效记录，不在未经审查的情况下解除原有的实施风险。

### 2. 老接口曾通过只读启动信息泄露负责人写入密钥

此前 `GET /api/studio/bootstrap` 直接返回 `csrf: owner_token`。只要管理 AI 能访问本机服务，无需破解任何身份，就可以获取这个令牌，绕过它本应仅有“提出候选”的权限。**这使先前对 AI 受限接口的断言在本地 HTTP 威胁模型中不成立。**

现在启动信息不返回任何负责人凭据。HTML 默认可只读浏览，需点击“负责人授权”并粘贴由本地启动进程单独提供的密钥，验证后才启用需要审批的写入操作。密钥仅在当前网页内存中保存，不放入 `localStorage` 或工程导出。HTML 不能通过 GET 找回这份密钥。

**单机最简启动**：

```powershell
python tools/lifecycle/studio_server.py --repo D:\01_Projects\AutoTest_HOST --port 8765
```

启动终端会输出本次随机生成的 `Owner access key`，只粘贴到工作台本机网页授权界面，不发给 AI、Codex、GitHub Issue 或聊天。

**启用受限项目管理 AI 访问**时，必须同时通过 `--owner-token-file <owner-secret-file>` 和 `--manager-token-file <manager-secret-file>` 指定预先创建、彼此不同且至少 32 字符的密钥文件；启动服务不会再通过只读接口提供负责人密钥。密钥文件应放在仓库以外，明确限制谁可以读取。不能把本机启动密钥记入工程档案或源码库。

**剩余的真实安全边界**：如果不受信任的 AI 或 Codex 进程能以同一 Windows 用户直接读取 SQLite、负责人密钥文件或控制工作台进程，那么 HTTP 令牌无法从操作系统层面阻止它自行修改数据。达到企业级的真正强制约束还需独立 OS 身份、受控代理进程、文件 ACL、受保护 GitHub main/PR 门禁，以及禁止执行 AI 获得负责人的凭据；不得把目前本机 Token 当作硬件隔离或可信用户身份。

## 二、修订现有工程对象，不建立第二套需求系统

`studio_amendments.py` 为现役 `objects` 的需求、系统组成、能力、架构、接口、详细设计、工作包等建立**候选修订审查层**，不复制现有工程对象。

项目管理 AI 有权限调用：

```text
GET  /api/studio/amendments?project=<project-id>
GET  /api/studio/amendments/detail?id=<proposal-id>
POST /api/studio/amendments/propose
```

候选数据必须包含：

- 项目与具体目标工程对象 ID、目标当前修订号 `base_revision`；
- `proposed_patch`：只接受 `title/body/meta/parent_id` 中实际变化的字段；`meta` 代表**完整替换元数据**，必须慎重比较；
- 自然语言 `reasoning`，说明为什么当前需求、架构、接口或设计需要改变；不能用产品定义覆盖它们；
- `source_refs` 对话、源码、文档或实测依据；`knowledge_ids`（可为空）引用已记录工程认识，并固定其当时修订；
- 服务端根据持有的不同凭据自行标注 `AI_CANDIDATE/OWNER_CANDIDATE`；客户端不能自由宣称自己已批准。

AI 候选**不会变更实际工程对象**、工程关联、CODE_READY 或 GitHub，也不会以字段变多、文字变长、关键词出现作为正确性的证明。

### 审查与应用分离

只有负责人可以执行：

```text
POST /api/studio/amendments/review
POST /api/studio/amendments/apply
```

`review` 明确区分 `REVISE`（同意进入形成新草稿的单独确认）、`RESEARCH`（继续调查）及 `REJECT`（本次不采纳）；必须记录语义和影响理由以及人工复核依据。

`apply` 只能操作已获 `READY_TO_APPLY` 的精确修订，且引用的工程认识版本仍然未变。应用在 SQLite 的**同一个写事务**里同时生成工程对象新修订和关闭候选，没有先改对象、后改候选的竞态窗口。原已批准对象回到 `DRAFT`，历史批准快照保留，下游依赖按既有输入修订规则变为不满足准入，**不自动批准新版本**。

为避免用户绕过系统，`Store.update_object` 和普通 HTTP 编辑入口**不再允许直接修改已批准的工程对象**；即使由本机负责人发起，也要进入候选与影响审查。已进入 `IN_REVIEW` 的草稿如果又被修改，回到 `DRAFT`，防止内容变化后沿用原审查状态。未批准草稿仍可直接编辑。

## 三、HTML 真实协作方式

1. 项目管理 AI 先读取 `/api/studio/management/context`，结合工程认识、对象版本和实际来源对问题作语义调查。
2. AI 若判断已有工程对象需修订，通过受限接口提交指定版本的修订候选，而不是把更新塞入产品定义或随意修改源码。
3. 用户打开 **AI 项目管理与审批 → AI 工程对象修订候选**，看到原始文本与候选文本的并列对照、来源、AI 推理，以及已有受控关系图上的直接关联线索。
4. 用户可以要求继续研究、拒绝，也可以通过两次明确操作复核并生成对象的新草稿版本。若原设计发生了其他版本变化，旧候选会失效，不能直接套用。
5. 草稿新版本继续走已有工程对象批准、关联、详细设计准入、源码提交限定、构建测试和实物验证等独立步骤。

用户若从原工程对象的编辑入口打开已批准版本，也只会**创建附理由和依据的候选**，不能绕过上述审查。

## 四、数据完整性与验证

新增 `engineering_amendments` 独立表，包含对象快照、精确修订、差异、来源、知识版本、负责人范围判断及应用后的修订号。工程导出带有全部记录；在**空工作区恢复**时检查原对象修订快照一致、知识引用存在、应用后的对象修订和候选差异匹配。旧备份缺少新表时保持为空，不会虚构候选或已批准记录。

自动化验证包含：AI 只能提案、不能自审/应用；负责人也不能直接覆盖已批准对象；审查与应用必须分离；内容和知识源修订冲突拒绝；跨项目与禁止字段被拦截；已批准设计修订导致原编码包失效；IN_REVIEW 内容变动重回草稿；旧/新档案往返和篡改拒绝；HTTP 启动接口不泄露负责人密钥。

**CI 通过是后端规则与 JS 语法通过**，不是在用户 Windows 浏览器中完成全部点击验收，也不证明 AI 的工程理解已经通过真实评测。

## 五、保留但不粉饰的待办

- 对 AutoTest 已导入的真实 SQLite 先作只读备份，再在副本演练 V1.3 启动、授权、知识候选与修订流程；不会通过 GitHub 自动远程修改用户本地数据库。
- 改进受控工程关系的 **跨多跳动态影响分析**、决策冲突与对照证据，不能把当前单跳“关系提示”冒充全面影响审查；实际 AI 的正确性仍需真实案例和人工判断。
- 针对仓库写权限和本地进程权限，需要独立代理身份及 GitHub branch protection 才能从强权限边界阻止 Codex 自行修改 main 或 SQLite；目前 API 令牌不是 OS 沙箱。
- 需按源证据逐项研究 AutoTest 的系统组成、外部刺激、CAN/DBC/测试程序、现役设备状态，不将历史上下文直接视为签发的工程事实。
