# AutoTest｜P0-03 项目组织、职责与决策权限

**版本：** v0.1
**状态：** 已获项目负责人明确批准（原文版本）；审批与限制见 APPROVAL_RECORD.md。
**上游依据：** 已批准 P0-01 v0.2、P0-02 v0.1

## 一、项目组织原则

AutoTest 由项目负责人统一确定目标和重大决策，采用工程总协调、专业研发、集成验证及受控执行相结合的研发协作方式。

项目管理与具体专业研发实行职责分离。工程总协调负责组织和推进，不默认代替所有专业完成需求分析、架构、详细设计、软件实施或验证。

项目组织允许随实际工程需要增加、调整专业岗位，但岗位调整不得自动改变正式授权。

## 二、主要职责

**项目负责人**

负责项目目标、范围、重大取舍、正式工作产品、重要变更和交付验收的最终决定。

**工程总协调 AI**

负责项目现状调查、目标与范围一致性、研发计划、工程任务组织、专业协同、依赖、风险、变更、进度审查及向负责人汇报。

可以组织专业研究和提出工程决定建议，不得自行批准项目基线、替代专业审查或获得未经授予的编码权限。

**专业研发 AI**

根据所承担的专业任务开展研究、需求分析和工程设计，必要时在明确授权的范围内实施软件研发。

负责说明设计依据、接口关系、未决问题和实际交付结果，不得自行扩大任务或跨专业修改有效工程合同。

**集成与验证职责**

负责核对相关专业成果的一致性、软件集成、验证组织、缺陷分析及客观证据。

根据工作风险可以安排额外的独立技术审查，但不虚称已有专门的独立质量部门。

**本地 Codex 执行者**

根据有效输入和明确的执行合同完成指定的代码、构建、测试、日志收集与 Git 操作。

不得自行决定产品要求、架构、设计修改、实施范围或正式审批结果。

## 三、工程工作与批准关系

研究、需求、架构、详细设计、实施、集成、验证和交付分别形成对应的工作结果及审查依据。

工作成果的技术审查、负责人内容批准、GitHub 正式落档、代码执行授权和实际验证结果必须分别记录。

**对已经向负责人完整呈现并获得明确版本批准的项目管理工作产品，工程总协调应在同一轮工作中将批准内容及审批记录提交 GitHub main，并读取远端确认结果。**

发布不得修改被批准的实际内容，不得顺带批准其他成果、合并业务源码或改变 Gate。

提交失败或版本冲突时，不得声称已经落档；应保留批准事实，明确报告未完成的 GitHub 操作。

## 四、持续研发与交接

每项实际研发工作应具有适当的责任岗位、有效输入、预期成果、适用审查方式和交接对象。

历史代码和原执行 AI 的成果应保留来源与版本，经过必要的设计及源码核查后再决定是否纳入新基线。

管理工作的正式依据统一维护在 GitHub main；未批准的软件实施成果可以保留在受控开发分支，不因此成为正式工程交付。

## 五、当前不在本项决定的事项

本项不确定具体专业岗位人数、代码文件归属、技术架构、任务清单和开发排期，也不授权现有分支合并、业务代码修改或真实硬件操作。
