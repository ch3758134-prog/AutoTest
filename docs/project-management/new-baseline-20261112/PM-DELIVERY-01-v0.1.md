## 1. 负责人的交付意图与本计划的主要判断

近期要先得到一套**工程师能够真实编辑、真实执行、检查结果**的 Windows 工作系统，不是先凑齐专业工具窗口，也不是以模拟器证明软件完成。它是后面扫码连续检测、烧录接入以及正式报告的基础。

本计划据此将研发组织为：**优先工程师编辑—运行链（A）**；**烧录可独立并行实测（F）**；A 与 F 均有足够证据后接入**扫码与烧录的第一版实际交付（V1）**；随后形成带完整执行报告与可追溯操作体验的**第二版交付（V2）**；独立专业工具作为长期、按业务需求扩展的产品能力（X）。波形**标准波形取得和自动判定**属于 A，不能因为“完整波形分析界面”放在 X 而将它延期。

“V1/V2”在本文中是**项目业务交付批次**，不对应 G1/G2 Gate，也不表示历史 `V1Workspace`、G4 v1、源代码旧版本的有效性；是否对外正式发布要另有发布/验收决定。

```text

    A3 TestProject → 有选择的多测试包真实调度、夹具及设备动作
    A4 CAN/DBC 观测、标准波形取得/判定、步骤判据、调试和最低运行证据
                          ───────────┐

    F1 复原参考配置/步骤/协议与风险       │
    F2 独立烧录 WPF 工作台、真实 CAN1 实测 │
    F3 日志、恢复策略、指定 ECU 稳定性验证 ┘
                          ↓
V1｜完整首版工作链：扫码 → 工程/配方匹配 → 按真实测试程序执行
```

## 3. A｜工程师编辑—真实运行链：优先交付和具体细节

### A1｜工程与配置：验证用户可以连续操作

**用户可见行为**：创建/打开 ECU 工程；导入、查看、编辑、保存、重开 DBC；组织 Controller、TCF/TBC、测试程序、测试项目、波形配置与标准参考；打开资源时即进入可编辑工作区；删除、重命名、保存/撤销操作应明确说明引用影响、修订冲突及错误，不得卡住或损坏项目。

**现有实现**：`ProjectWorkspaceService`、`Dbc*`、`ControllerConfig` 等已有真实代码；不按历史失败 UI 推倒重来。

**实际验收**：Windows 上以真实工程操作；关闭后重开验证文件与引用一致；DBC 实际编辑产生的编码/解码必须可复核。未编译、未实测不能写“通过”。

### A2｜步骤编辑、流程控制与实际调试：不是只有“有编辑器”

需要逐项实际操作验证：

- 创建一个测试包即有清晰的起始编辑位置；新增步骤后直接进入目标和参数编辑，不需要另找属性页。
- 写 CAN 报文时可选择 DBC 报文、编辑信号物理值或原始字节；没有 DBC 时说明需要导入；映射与物理通道正确。
- 按键操作能选择已命名功能键或实际 20 Key 掩码、保持/释放/定时等适用动作；IGN、SOL 作为实体动作，能力与安全条件经验证后开放。
- 结构编辑：准备/测试/清理、IF/ELSE、SWITCH/CASE、WHEN/等待、循环、变量、表达式、子程序及异常路径。添加、移动、复制、删除、右键操作、撤销/重做、保存重开及错误定位要保持结构与语义一致。
- 调试：单步、暂停/继续、运行到、跳过和停止必须有明确可见的执行状态；具体不可中断物理操作及停止后行为以实测后设计为准，不能只提供无效按钮。
- 运行前把“不支持执行的步骤”和“有效步骤但目标无设备/资源”明确区分，不得编造成已执行。

**差异事实**：当前步骤模型注册的类型不等于 `RealRunCoordinator` 已全部解释执行；UI 对步骤的呈现不等于具有稳定的编辑器交互。需要逐功能修复、回归、实测。

### A3｜测试项目勾选与真实调度

**已有基础**：`TestProjectDocument` 内有包列表、顺序、`Enabled` 和资源修订，`TestProjectWorkbenchViewModel` 可组织这些内容；但当前 `RealTestWorkbenchService.ExecuteAsync` 以**单个** `TestDocument` 作为运行入口。

**G2 要设计的责任**：项目级选择与冻结 → 按选择执行各测试包 → 每包自己的准备/测试/清理及异常策略 → 工位/设备占用由统一运行上下文管理 → 项目级总结果、子包结果与步骤事实追溯。一个包失败是继续、停止还是执行特定清理由用户定义的执行策略决定；不得由项目管理 AI 私定。

**验证**：勾选 2 个包并禁用第 3 个，实际执行顺序、进度与结果符合所见；失败和人工停止保留原包及项目级事实，重试不得覆盖原记录。具体 UI 选择体验需要用户 Windows 操作反馈。

### A4｜波形标准参考、自动判定与最低运行证据

**正确的能力划分**：

1. **实际波形采集**：从 DUT 适用的真实数据源（目前重点为 CAN/DBC 信号）得到有时间与质量信息的序列；采集不是判定。
2. **建立标准波形**：工程师从完成的真实采集证据中**明确选择并保存**一条具有名称、资源身份/修订、来源与适用条件的参考；不能自动将最新或失败的 DUT 记录提升为标准。
3. **自动波形判定**：测试步骤在明确执行窗口采集实际波形，使用所选标准波形及可编辑的比较配置（对齐/时间偏移、幅值容差、覆盖率、缺样、超差比例/持续时间等）判定；允许数据不足时形成 INCONCLUSIVE/ERROR，而不是虚假 PASS。
4. **专门波形分析界面**：供人工深入对比、缩放、定位、查看多个通道和结果；这是后续可扩展工具，不是判定能力的前置条件。

**当前代码调查**：`WaveReferenceWorkspaceService` 已能从已完成、数据质量合格的采集证据中手工“提升为命名参考”；`ConfiguredWavePort` 已有采集、停止、查找已保存参考与执行比较；`WaveReferenceCatalog/Repository` 已有标识、修订和指纹机制；`WaveComparator` 有有界时间对齐和容差比较。上述仅为源码存在证据，不能宣布实测成功。

**建议 UI 取舍（供 G2 后续设计）**：优先在工程的波形配置/测试步骤中提供轻量的“采集真实波形 → 查看质量/基本曲线 → 明确保存为标准 → 选择标准并配置判定”路径，**复用同一采集和参考存储服务**。不必先独立开发完整波形分析软件；以后专业波形分析窗口也复用相同数据及 reference catalog。是否需要独立“标准波形采集工作台”由工程师实测易用性来决定，不应在计划阶段武断冻结 UI。

**欠缺需核实**：参考如何直接在 UI 发起真实采集；被采集信号、DBC 修订、DUT 工况、采样质量能否明确追溯；参考的现场选择、标定、保存与重开是否便捷；多通道需求、波形判定误差及速度是否符合实际工程实践。

**A 的运行结果最低事实**：步骤进度、原始观测及数据质量、用户配置的判据、比较结果、异常与实际执行结果、Run/测试包身份及其资源指纹须能保留和查询。这个是 V1 后续真实问题排查和 V2 正式报告的数据基础，不把它等同于已完成美观的报表/生产统计。

## 4. F｜CanTool 参考烧录：独立研究与实测专项

**目标**：先有一个**可以独立连接现有 USB 主控、使用固定 CAN1 与真实 ECU 完成指定烧录任务并可靠诊断问题的烧录工作台**，再决定怎样由通用测试步骤和生产程序调用。用户希望尽可能复原 CanTool 的配置语义、操作顺序、日志和界面操作方式，以降低现场排查难度。

**第一阶段 F1：来源复核与流程复原**。专项对话先取得实际参考源码、配置文件、相关 DLL/安全访问算法资料及合法适用范围；逐阶段复原镜像读取、目标和通道、诊断会话、SecurityAccess、擦除/请求下载/TransferData/结束、校验/复位/版本核验，以及 CanTool 的实际参数来自何处。必须区分“源码读到的路径”和“已在当前 ECU 真实验证”。找不到源码或配置就明确缺失，不猜 Seed/Key 算法。

**第二阶段 F2：隔离的独立测试应用**。基于现有 AutoTest 的真实 WinUSB/CAN1/ISO-TP/UDS 能力复用必要后端，必要时在受控的专项分支增加**独立 WPF 可运行入口**：选择 HEX/目标配置/安全算法 → 连接 → 预检 → 按阶段显示真实响应与错误 → 执行与导出日志。界面可以优先仿照 CanTool 的任务流程，不与当前主 HOST UI 竞争重构，也不因为名称相同就直接复制不可核证的私有算法/第三方授权代码。

**第三阶段 F3：实机验证与稳定性**。先在现场确认 ECU/映像/电源与恢复条件、刷写授权及适用的安全前置条件；记录每一阶段请求响应、NRC、超时、实际传输量、校验与重启身份，按实机结果处理故障。任何中断不得自动无条件重试擦写/解锁，不认为 CAN ACK 就是 ECU 已写入。

**第四阶段 F4：纳入自动测试**。经过 F3 对指定 ECU 的验证、设计审查与代码集成后，测试程序/生产流程调用同一烧录执行服务，绑定当次 Run 和配置、阶段/失败证据。独立烧录调试工作台保留为故障排查入口，但不能在自动测试同时抢占 CAN1 与 USB 设备。

**专项组织建议**：单独一个研究/实测对话担任 FLASH-LAB；研究阶段不需要立即建分支，真正独立实现时开少量短期专项分支，从经核实的实际工作基线提取必要代码，禁止直接改 `main` 或覆盖仍在实测的 `local`。正式任务先经过相应设计与授权；不将“参考 CanTool”理解为已取得运行该 ECU 实机烧录的许可。

**必须交回项目管理对话的成果**：来源/配置逐项对应表、阶段和参数决策表、与 AutoTest 现有 UDS/Flash 后端的差异、独立 WPF 工作台具体范围、真实 ECU 的构建与试验原始证据、可安全集成的接口与版本、未验证项和风险。

## 5. V1｜首版完整工作链：扫码与烧录纳入真实自动测试

**进入条件**：A 工程编辑—运行链在真实 Windows 与代表 ECU 上满足可操作的核心流程；F 的指定 ECU 烧录已在独立实验台架中形成可复核证据，并明确其配置和恢复限制。未满足时可以继续开发扫码 UI 或数据接口，但不宣称完整 V1 已交付。

**交付能力**：

- 工程/配置/DBC/Controller/TEST/标准波形构成正确的实际资源关系；测试项目选择多个包并执行，用户测试程序决定具体判据。
- 扫码枪数据进入本次 DUT 身份与配置匹配，防重复和错误沿用；启动、装夹、点火、按键、CAN/UDS/波形及烧录由实际程序及适用工序组织；DUT 主电源独立控制。
- 烧录不是每个 ECU 的默认强制动作，必须由适用测试流程显式选用；已有 Flash-Lab 的真实证据和后端实现须受控集成。
- 每次 Run 保留 DUT/测试程序/资源/设备、步骤原始数据和判定；异常、中断/失败可定位；复测不覆盖历史、下一件扫码不会继承上一件运行身份。
- 夹具动作如由测试程序控制，应以真实硬件能力与执行策略核验，绝不靠模拟或自动假定“机械已经到位”。

**V1 不承诺**：成熟正式报告设计器、完整生产统计看板、独立高级波形分析工具、适配全部 ECU 或未经测试的硬件控制。G1 关于报告与统计的最终产品要求仍有效，只是排入后续分期；因此 V1 是**受限业务交付批次**，不能单凭 V1 宣布所有 R1/G1 已验收完毕。

## 6. V2｜执行报告和结果管理：以真实生产行为完善

**任务**：在 V1 已持续产生可信运行事实的基础上，完成正式报告的内容、可读性、查询/复测历史、导出、生产统计与结果关联（DUT、工位、Run、程序包、步骤、日志、波形、诊断、烧录阶段、资源修订、实际响应及结果）。

**设计形成方式**：先观察 V1 实际检视、定位故障、现场人员确认和出厂使用，再逐步决定报告模板、统计口径、筛选、字段、打印/导出与版本；不能拿没有真实来源的默认字段充满报表。报告展示可在 V2 反复修改，但 V1 已产生的原始证据不应被新版覆盖/更改。

**注意**：G1 REQ-22/44/46/47 及生产历史方面的要求仍有效。V1 未完成完整报告并不降低这些需求的最终验收标准；交付时要明确“已满足/部分满足/未完成”，不把阶段性 V1 说成产品全部完成。

## 7. X｜可持续扩展的专业工具

CAN、UDS、波形独立分析、更多类型诊断与硬件激励等专业能力按后续业务依赖不断扩展。已有基础功能可在主线研发过程中自然完善，不必为了“工具留到后面”禁止 V1 需要的 CAN、UDS、波形和 Flash 底层工作。

- **运行必需底层**：DBC、CAN、波形标准取得/自动判定、测试步骤所用诊断/烧录调用，按 A/F/V1 的依赖顺序实现。
- **独立高级工具界面**：按真实使用反馈开发，不与前述运行必需后端混淆。
- **新增 ECU 能力**：若仅改工程/配置与测试脚本，由项目使用者负责；若需公共接口/固件/硬件扩展，则触发相应变更影响审查。

## 8. 研发与实测的生命周期管理

### 8.1 两条并行轨道

- **正式 G 系列（G2/G3/G4/G5）**：分别对架构/接口、详细设计、实施与验收/发布形成可审成果、批准及适用限制；已批准 G1 不因反馈事件整体失效。
- **业务交付 A/F/V1/V2/X**：跨阶段开展研究、设计、实现和实测；每次要明确成果究竟达到源码、Build、UI 操作、真实硬件、集成还是正式产品验收层级。不能用“到了 G4 才能实测”的机械流水线阻断已有合法研发，但也不能拿研发中的实测替代批准和安全控制。

### 8.2 事件驱动的实际闭环（长期有效）

```text
用户实测/截图/日志/口述反馈
  → 确认软件 commit、工程与设备范围，记录未知事实
  → 分流：BUG / UX / GAP / 新需求 / 配置问题 / 硬件或固件 / 证据不足
  → 定位受影响的 G1 条款、G2/G3 设计和源文件/资源
  → 若仅为缺陷/交互执行修复：按既有权限局部设计/修复、最小回归
     若真改系统外部要求：形成 G1 定点修订与审批；若改公共接口：定点 G2/G3 审批
     若涉及实物/不可逆操作：独立现场风险与许可
  → 固定候选 SHA，Codex 做明确的构建/指定测试（不自主修代码）
  → 用户 Windows/实机验证 → 结果 PASS / FAIL / UNKNOWN 与原始证据
  → 提交下一小增量或按准入审查局部集成 main
```

**不要把口头反馈变成用户填大型表格的负担。** 用户只需描述现象或贴截图/日志，由研发/项目管理侧整理记录，允许缺少字段写“待证”。不通过本应由系统验证的内容来考核用户的测试程序判据。

### 8.3 周期交付与例行回顾

建议**随时交付可测小增量，每周一次简短收敛**；碰到危险实测异常、重要新需求或公共接口冲突，当次就处理，不等周会。周度只做四件实用的事：实际经过用户操作的版本与功能、未完成/失败事件及责任、需求/设计有无必要的局部修订、下一批可测增量和是否存在可安全纳入 main 的差异。无进展不为报表而编造成功。

**版本身份与周期输出**：开发候选 HEAD；Codex 实际 Build/Test 的 SHA 和原始日志；用户实测设备、配置与操作结果；本次变更影响和关联决定；拟集成版本与回退依据。周期总结不自动创建新 Gate、自动合并 main，也不改变已批准需求。

### 8.4 按范围逐步集成

- `main` 当前只是官方管理/集成基线，不假定稳定；`local` 持续在研，不整支盲合。
- 单个能力达到预期，提供准确文件差异、必要接口审查、Windows 构建、对应实测和回退信息，按适用权限将**可复核、可恢复的改动**纳入 `main`。
- 多个专业冲突时先确定共享对象所有权和实际版本，不能以“一个工具能运行”为由让另一工具抢 USB/CAN 会话。
- 项目阶段批准、单次代码集成、特定 ECU 实测和 V1/V2 业务交付是四种不同决定。
