## 1. 用户明确的使用事实与 PM 的错误

用户对 UI 反复反馈：手动台架用于不编写正式测试用例就可对 DUT 进行临时测试/调试；实际需要 CAN 实时观察、CAN 报文发送、当前工位支持的人工输入与 IGN/夹具动作等同屏协同。此次再次指出，旧 UI 将 EPB 的“驻车/释放”与“短按/保持/释放”等硬编码或高优先级呈现，说明 UI 和管理方都存在认识错误。

**PM 的错误之一**：在 BIZ-05 将“配置功能按键”写为“手动台架视觉和操作的核心工作对象”，由此把**综合人工激励与 DUT 观察**错误缩小成**按键操作软件**。  
**PM 的错误之二**：在 BIZ-06 用“驻车、释放、无操作”作通用说明样例，虽然括注“名称由工程定义”，仍把 **EPB 样例的 DUT 业务语义**带进了应当 DUT 无关的产品指南。  
**PM 的错误之三**：在 BIZ-07 对 Pulse/Hold/Release 这类**输入激励时序**的表述，被放在整体手动台架主工作流的中心，使 UI 专项误将其设计为固定三个主按钮；实际上并非所有 ECU 物理输入都可以用统一“短按/保持/释放”表达。

这三项是 **PM 对用户既有需求的错误归纳**，不是用户要求通用上位机内置驻车、释放，也不是对 UI 专项的单方面责任追究。

## 2. 四个层级严格分开

| 层级 | 定义 | 对正式产品的限制 |
|---|---|---|
| **被测 ECU 业务功能或判据** | 某一 ECU 实际业务动作/识别结果，由该 ECU 工程和测试工程师定义 | **平台不能自带“驻车/释放”等通用业务按钮、硬编码判据或示例执行默认值** |
| **外部输入条件/状态** | 该 DUT 需要被模拟的物理输入，如某开关组合、电阻状态、按键/开关动作 | 具体名称、数量、允许状态及适用时序必须来自**当前工程有效配置和实际硬件限制**；不能假定所有输入都是按钮 |
| **硬件实现** | 当前 KEY_SIM 用 20 个内部电阻网络开关的组合产生面向 DUT 的五路模拟电压条件，CAN0 控制；另有 CAN1、IGN、夹具等工位能力 | 20 Key 不是 20 个用户功能键；五路输出不是五个任意 DAC；USB/CAN ACK 不证明实际电压和 ECU 识别 |
| **激励执行动作** | 对经配置的输入状态执行设置、短时保持、持续保持、撤销、等待等受支持的变化 | `Pulse/Hold/Release` 是**已有按键型输入适配器的执行原语**，不是必须常驻的通用顶层操作，也不等于 DUT 的业务“释放” |

容易混淆的 **“释放”** 必须消歧：ECU 功能名称可能叫“释放”（某种业务功能）；输入激励的 `Release` 是撤销闭合/恢复输入条件。这两者绝不因为同一个中文词就自动等同。类似地，零掩码只能说明所控制开关未闭合，不能无证据声称 ECU 一定识别为“无操作”。

## 3. 手动台架真正的业务定义

> **手动台架是面向工程师临时调试、故障定位、响应收集的人工 ECU 试验工作台。** 不先创建自动测试用例，也可以使用当前真实工位已实现、已配置、已获适用许可的外部激励与观察能力；它不另建一套通用 TEST 流程编辑器。

**独立业务职责**：
- **CAN 真实观察与日志**：收发、过滤、定位和必要的 DBC 解码，观察 DUT 响应；
- **CAN 发送**：单次/适用周期报文、DBC 信号编辑、原始帧和停止；
- **当前 DUT 输入模拟**：根据工程定义提供适用输入状态（当前具体硬件包含 KEY_SIM 电阻开关组合），让工程师设置/撤销/按适用时序操作，并能看到观测依据；
- **工位控制**：IGN、夹具等当前真实支持的操作，与输入模拟在同一操作上下文；
- **观察/错误**：区分操作请求、主控 ACK、CAN 实际帧、ECU 响应、独立测量或 UNKNOWN；手动与自动测试之间的实体独占不能被 UI 绕开。

**本轮专项 UI 试用偏好**：左 CAN 观察、中实际输入模拟与 IGN/夹具控制、右 CAN 发送。这是用户对当前手动台架交互的明确反馈，交 UI 专项落实；PM 不借此冻结全产品窗口像素，也不能因调布局改变后台的职责。

**功能键/按键序列**：只有当前 ECU 工程确实配置了适用的按键型输入时，才呈现相应名称、有效状态、允许动作及短序列编辑；序列只模拟该类输入变化（如保持、等待、恢复），不是把所有工位功能编排成第二套 TEST。没有有效配置时应展示未配置及可完成的配置任务，不显示 EPB 虚构按钮或 K01~K20 的日常功能键阵列。

## 4. 核对到的真实源码：实现原语与产品能力不能画等号

静态依据 `local@a9a26ebfba1efcf032ff8ec8c435336a89469647`：

- `src/AutoTest.Projects/ControllerConfig/ControllerModels.cs`：`ControllerDefinition`、`ControllerState`、`KeyMask`、`ActionTiming`、`ControlInteraction`；当前模型偏向控制器输入状态，不直接定义 ECU 业务判断。
- `src/AutoTest.Projects/ControllerConfig/ButtonActionPlanner.cs`：`ButtonActuation { Pulse, Hold, Release }` 是已有按键执行计划的内部操作语义，不可直接等同所有 ECU 用户操作。
- `src/AutoTest.Desktop/Configuration/ConfigurationWorkbenchViewModel.cs`：`AddButtonAction` 默认创建“模拟按键N”和“松开/按下”状态，参数中有“短按默认保持时间”；**这是具体已存在的偏置实现**。它不能成为通用软件面向任何 ECU 的默认输入模型；后续须由 UI/工程配置适配研究判定修正方式，而不是仅把文字改色。
- `src/AutoTest.Desktop/Testing/ConfiguredStationActionPort.cs`：执行已配置状态或原始 Key 操作；存在 Pulse/Hold/Release 和硬件 ACK 逻辑。**源码存在不代表其可覆盖所有 ECU 物理输入或已经真机验证。**

建议 G3-UX 和项目配置专项将 Controller/状态的当前**实现形状**与平台**通用外部输入模拟能力**区分。需要扩展何种输入类型时必须以确有硬件可模拟的事实、实际 ECU 工程需求和受控接口影响为依据，**不因为 UI 错就提前推倒现有模型，也不把模型偏置固化到通用操作界面**。

## 5. 交付给 UI 专项的约束

1. 不默认生成“驻车/释放/模式切换”，不默认生成“短按/保持/释放”三个占据核心的操作按钮，不能直接让 Demo 示例名成为空工程的正式功能。
2. 用户当前查看的应是**对应 ECU 工程配置的外部输入条件和真实工位能力**。相关的功能/状态/操作来自有效配置、映射和实际支持；不支持的功能应明确说明缺失原因，而不是伪造。
3. CAN 观察、CAN 发送及 IGN/夹具均是台架独立业务职责，不从属某个输入状态；采用用户试用的左观察/中控制/右发送作为当前修订依据。
4. 波形、UDS、烧录、DBC 专项仍须研究完整专业工作流；不得被手动台架的按键语义扩散影响。
5. 把“短按”等具体动作作为**当前对象的可用参数/操作选择**研究，而不是全局固定功能定义；用户对交互与视觉最终验收仍由 UI 专项自己推进。
6. 不把设计解释、EPB 研究备注、模拟 ACK 或历史原型上下文当成正式 UI 实时事实。
7. 不重建第二套 Controller 或测试执行后端，不把后端枚举名未经审查直接显示成通用产品名称。
