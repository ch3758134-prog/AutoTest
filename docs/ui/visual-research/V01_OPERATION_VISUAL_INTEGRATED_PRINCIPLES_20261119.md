# V01｜AutoTest 现代复杂 Windows 工程软件：操作与视觉一体设计原则研究

**研究日期**：2026-11-19  
**身份**：AutoTest UI/UX 研究与设计专项  
**状态**：RESEARCH_FOUNDATION_CANDIDATE / DESIGN_PRINCIPLES_PROPOSED / PAGE_DESIGN_NOT_FROZEN / WPF_NOT_CHANGED / USER_UX_NOT_VERIFIED  
**证据**：独立登记于 [V01_SOURCE_REGISTER_20261119.md](V01_SOURCE_REGISTER_20261119.md)。内部依据为 R01～R06 及用户在 Windows 提供的首轮 UI 截图。
**本轮明确边界**：只研究“应当以何种原则同时决定操作与视觉”，不决定主窗最终结构、像素比例、控件品牌与 WPF 实施；不修改源代码；不冒充用户批准。

## 0. 核心发现：现代化不是换皮，而是视觉承载操作语义

**工作假设**：现代专业软件的质量来自“工作任务、信息对象、命令行为、反馈状态”和“空间、层级、对比、尺寸、组件、适配”的相互匹配，而非两条彼此独立的装修链。

过去 R01～R06 明确了【六系统】（工作空间、对象、命令、上下文、状态、恢复），但对每一个系统在屏幕上“如何被读懂、如何让用户直接行动、如何验证布局足够专业”的约束不够具体。旧 UI 分支使用默认原生控件封装，不足以证明上述六系统真正转化成了可使用的桌面产品。

研究推导式：

`用户具体任务 → 当下关键对象/关系 → 可用动作及风险 → 应呈现的视觉线索 → 鼠标/键盘连续操作 → 结果及状态反馈 → 用户可观察验证`

**反向检查**：每种视觉布局或颜色都要能说明它帮助用户“辨认哪个对象、知道可做什么、看见做成了什么”；每个操作机制也都要回答“界面上何处能发现它、如何分辨当前对象与结果”。任何一端单独成立都不算设计闭环。

## 1. 原则 P01｜任务优先决定空间与注意力层级

**操作问题**：人在不同阶段做不同任务。编排 TEST 时关注步骤及参数，运行时关注本次选择、当前步骤、真实状态，波形分析时关注时间轴/游标。功能模块目录不等于任务重心。

**视觉要求**：重要任务对象占有稳定可读的主要空间；附近是最相关的命令和必要反馈；与当前任务无关的内容可折叠、按需召回。空白、分割线、背景与对齐的用途必须服务内容而不是装饰。面板宽度使用根据数据和操作计算的最小可用尺寸、弹性空间与用户调整能力，不能默认三栏或固定宽度。

**证据互证**：R02/R03 对任务上下文的要求；Fluent S01 指明大区块分配、语义对齐与网格，JetBrains P01/P02 明确编辑器—工具窗区分、当前标签辨识。JetBrains 反馈来自其产品用户，不等于 AutoTest 最优布局已经验证。

**反例**：AUTOTEST 步骤操作堆在窄列，中央大面积空白；界面虽然整齐却把最重要对象压缩在角落。

**验证脚本**：给定“编辑等待步骤”情境，观察第一次注视能否定位当前步骤/详情/最常用操作；让用户连续编辑三个步骤，并记录视线移动、点击、是否反复找属性。无窗口实测前不人为宣布具体理想宽度。

## 2. 原则 P02｜对象层级必须同时具有信息层级与视觉层级

**操作问题**：一个 TEST 测试项目包含用例，用例内有“准备/测试/清理”阶段和嵌套步骤；当前步骤具有类型、名称、参数、运行状态。仅让树能展开，不等于用户能理解层级。

**视觉要求**：通过缩进、纵向节奏、组标题、结构连接、标签/图标、字体重量和选中态明确表达父子/兄弟/不同阶段。重要结构文字不能用比无关辅助说明更弱的小字。当前选择、展开状态、禁用状态、运行中状态之间不得采用一模一样的蓝色。

**证据互证**：R04 的 Step/Context 与 Selection 分离；Fluent S02 的 Windows 字体语义梯度，S04 的间距语义分组；Carbon P06 的标题、行高、表格扫描与选择规则。类型字号为参考而非中文字体冻结值。

**反例**：“准备阶段/测试阶段/清理阶段”和嵌套步骤都被渲染为几行同色细字，选中后仍难分辨自己选中的是阶段还是具体步骤。

**验证脚本**：仅看屏幕，不先解释，用户能否指出当前用例、当前阶段、当前步骤、选中与运行/禁用状态、哪个步骤是哪个父节点的子步骤。

## 3. 原则 P03｜选择、编辑和反馈必须构成可见的因果关系

**操作问题**：用户点击列表/步骤后期待一个结果；如果所选对象与右侧编辑内容没有关联，界面反馈失真。选中对象不等于执行物理动作。

**视觉要求**：选中对象应有稳定且清晰的视觉标识；详情区标题/对象身份与选择一致；若尚无选中对象则显示正确的空状态；字段更改后的草稿、错误和保存反馈出现在与该对象有关的位置。焦点、Hover、选中、正在编辑、执行中的状态必须在语义上区分，而非仅调同一种蓝色深浅。

**证据互证**：R04 对 NavigationSelection/EditorSelection/RunSelection/StationTarget 的独立要求；NI P03 选中步骤与 Step Settings 专用参数对应；Fluent S05 命令反馈自然嵌入界面；Ignition P04 按当前对象激活专业工具区。

**反例**：点击某个等待步骤后，步骤树出现选择迹象，但详情仍显示“请选择步骤”；即使代码事件已经执行，用户看来仍属于交互失败。

**验证脚本**：连续单击不同类型步骤，检查当前选择、类型化详情、输入焦点、改值提示始终一一对应；同时确认单击步骤不会改变“当次运行勾选”或实体输出。

## 4. 原则 P04｜命令重要性与操作频率共同决定视觉显著性

**操作问题**：“插入步骤”和“上移/下移、复制、删除、撤销”不是同一层级的命令；风险等级亦不同。必须区分常用主操作、对象局部次操作、结构高级动作、实体危险动作。

**视觉要求**：主操作应就近、可发现，其他常用动作可采用文字/图标的次级工具栏或行内快捷键；对象专属命令邻近对象或由右键提供补充；低频操作可收在菜单，但绝不把高频动作只藏右键。按钮不能全部同一重量/同一蓝色；高后果动作不能被普通 Enter 自动触发。

**证据互证**：R04 命令合同（对象、作用域、风险、撤销、反馈），Windows S05 和 Carbon P06 对行内、批量、工具栏命令以及反馈的说明；ecu.test P05 提供插入当前位置和拖放作为可供比较的不同操作路径。

**反例**：上移、下移、撤销、重做分散为多行视觉重量相同的按钮，用户既难扫视也难分辨主次；所有按钮都深蓝导致无操作重点。

**验证脚本**：不做指引，用户完成“新建→插入→复制→上移→撤销”，记录命令发现路径、重复窗口跳转/误点及是否需要先解释按钮用途。

## 5. 原则 P05｜信息密度依专业工作任务而定，不等于越宽松越现代

**操作问题**：工程师希望在一屏内对照多条 CAN 帧、DBC 信号和测试步骤；同时，UI 不能把行高、文字和点击目标压缩到难辨。

**视觉要求**：建立可分档密度体系（舒适/常规/紧凑）和控制语义；普通数据行、结构层级、编辑区和危险执行控制可以使用不同密度。视觉减噪应当删除无关装饰和重复说明，而非删除必要专业信息。数据多时启用虚拟化与过滤，避免用大卡片包装每条数据。

**证据互证**：R01 现代化≠空白多；Carbon P06 有从 24、32、40、48、64 的不同密度示例，并特别要求行高/工具栏协调。其单位与控件实现来自 Web，WPF 中文桌面需自有测量。

**反例**：为显得现代而创建过多空白卡片、夸张页标题，导致 1366×768 实际几乎看不到操作对象；或反过来将所有文字压缩成无法阅读的小号字体。

**验证脚本**：在 1366×768/150% 和 1920×1080/100% 下分别用 20 条测试步骤、30 个 DBC 信号、50 条 CAN 待发项评价可扫描性、当前行辨识、关键操作是否仍可见。最后再确认密度 token 数值。

## 6. 原则 P06｜视觉一致性是语义一致，而不是全工具页面结构完全一致

**操作问题**：TEST 步骤树、DBC 表、Wave 曲线、Flash 阶段、生产扫码具有完全不同的主要任务。

**视觉要求**：全产品共用字体/色彩/网格/图标命令语义/选中焦点/状态用语，但允许不同工作区采用不同构图：结构型强调层级编辑，密集型强调对齐和筛选，图形型强调画布与标尺，执行型强调真实状态与错误。只有共享对象/命令行为才共享组件，不机械复制空白三栏。

**证据互证**：R02/R04 的专业编辑器区分；Ignition P04 随不同资源出现不同工具面板；JetBrains P02 编辑区与工具窗采用可分辨层次。这些证明“统一规则 + 差异工作区”可行，不说明某个 AutoTest 布局已经冻结。

**反例**：每个专业工具都是“左列表、中空白、右属性”，波形的图形区域和发送日志被挤压。

**验证脚本**：在 TEST、DBC、Wave、Flash、扫码之间切换；检查共同规则是否可预测、主要工作对象的空间是否因专业用途相应变化。

## 7. 原则 P07｜渐进呈现必须结合真实工作频率

**操作问题**：复杂应用既不能把所有命令永久堆在用户眼前，也不能隐藏常用功能使熟练用户不断打开菜单/对话框。

**视觉要求**：先看用户当前任务与阶段。主操作直接可达，复杂参数在选择类型时逐步显示；高频高级操作必须有稳定入口及快捷键；全局导航与当前对象操作分开。必要时分为主要、次要、更多，而不是凭视觉喜好随意折叠。

**证据互证**：R04 O01～O12、高频对象编辑；Windows S05 命令与上下文反馈；Carbon P06 工具栏与批量操作；NN/g U01 识别胜于回忆。

**反例**：插入一个步骤需要不断返回“操作目录”找类型，或每次参数变更都打开一次模态弹窗；反过来 20 个动作按钮全部铺满主窗口。

**验证脚本**：比较新手首次配置与熟手连续处理 10 个步骤的完成路径；明确记录被隐藏命令的发现方式及二次进入代价。

## 8. 原则 P08｜颜色不是装饰，必须表达明确、互不混淆的状态

**操作问题**：单击选中、正在编辑、启用、已保存、未保存、已请求、已 ACK、ECU 已响应、判定通过、失败、UNKNOWN 等状态完全不同。

**视觉要求**：交互状态用文字/图标/位置/对比共同表达，不依赖单一颜色；执行状态具有事件来源和时间。错误必须能定位到出错对象，禁用控件须说明原因。已被激活的 Tab 和当前步骤必须明显不同于静止区域。

**证据互证**：R05 状态与证据合同；Fluent S02 字重/对比；WCAG S07/S08 对可读性和非文本视觉标识的要求；JetBrains P01 对活动标签识别的研究反馈。

**反例**：默认蓝色、Hover 蓝色、选中蓝色、启用蓝色、提交成功蓝色都几乎一样；没有设备时仍显示绿色“完成”。

**验证脚本**：不看日志，要求用户辨认“正在编辑的是哪个字段、哪份草稿未保存、当次 Run 是否有结果、设备状态是否已知”，若需要猜测则失败。

## 9. 原则 P09｜适配/可读性/可达性属于设计条件，而不是实施后的补丁

**操作问题**：用户在 Windows 不同 DPI、多屏和不同大小的主窗口连续工作。缩小后不能把重要按钮/字段挤出画面，任务栏必须保持可见。

**视觉要求**：重要区域可重新分配空间、滚动、收起辅助窗格，优先保住主要工作对象；不允许以单一全屏截图作为验收。正文和非文本控件应满足基本对比原则，键盘焦点可见且 Tab 顺序合理，鼠标目标足够明确。

**证据互证**：Fluent S01 的弹性/响应/自适应区分；S02 字体可读性；S06 WPF Measure/Arrange 与 DPI；WCAG S07 普通文字 4.5:1、大字号 3:1 以及 S08 重要组件外观 3:1。注意：WCAG 是 Web 规范，此处作为桌面产品设计下限参考，不冒充 WPF 自动合规证书。

**反例**：窗口最大化但超过任务栏；按钮文本被裁切/低对比；右侧属性区宽度固定导致中央区域只有空白或核心对象不可见。

**验证脚本**：明确要求 1366×768、1920×1080，100%/150% 缩放，窗口恢复与左右调整、键盘 Tab/Shift+F10、工具副窗口与任务栏实测；若没有 Windows 证据只标 NOT_RUN。

## 10. 原则 P10｜设计系统不是一个 UiKit 类，而是带语义、状态和用例的产品合同

**操作问题**：统一组件代码并不能自动产生统一的产品视觉体验。按钮、树、数据表、Tab、Inspector 等复用前必须定义其语义和使用条件。

**视觉要求**：设计系统分为以下层：
1. Foundation：字体与中英数/十六进制等文本用法、语义色、对比、空间栅格、几何、图标。
2. Interaction：选择/编辑/验证/撤销/悬停/禁用/加载/错误/恢复的状态图。
3. Standard components：按钮、命令条、树、表格、输入、导航、Tab、弹层、搜索与过滤。
4. Professional patterns：TEST 结构步骤、类型属性、CAN 发送计划、DBC 信号表、Wave 双游标、Flash 阶段等。
5. Example screens：正常、空、繁忙、失败、窗口变窄等完整示例。
6. Implementation mapping：WPF 可实现方法、尺寸约束、UI 自动或人工测试脚本。

**证据互证**：Fluent S03 语义 token；Carbon P06 分组件规定密度、状态、选中/工具栏/内联命令；R01/R04/R05 已有业务编辑与状态边界。

**反例**：一个 UiKit.cs 包装 Button/Border/TextBlock，然后以“组件系统已完成”直接进入所有专业工作区编码。

**验证脚本**：任选“上移测试步骤”和“CAN 删除待发帧”两个场景，检查它们是否复用同类命令及焦点语义，且专业组件在各自上下文仍有合适视觉重心。

## 11. 需要明确比较的设计取舍（不能凭偏好拍板）

| 冲突 | 不足方案 A | 不足方案 B | 合理研究决策方式 |
|---|---|---|---|
| 信息密度 vs 清晰度 | 全部压成小字与细行 | 全部改成大卡片大空白 | 对象频率/屏幕/DPI/目标尺寸分档测量 |
| 全局一致 vs 专业差异 | 全工具强制三栏 | 全工具风格各异 | 保持语义 token/命令状态一致，专业布局按任务独立 |
| 快速操作 vs 渐进呈现 | 大量按钮永久存在 | 高频动作只藏菜单 | 根据任务高频率、风险、上下文安排主/次/快捷入口 |
| 选择可见 vs 视觉噪声 | 任何选中都发蓝光 | 选中几乎无变化 | 文本身份+背景/边框/焦点清晰但不过度装饰 |
| 高风险输出 vs 离线编辑 | 所有编辑都确认 | 实体动作当普通按钮 | 区分编辑草稿与物理授权/事实反馈 |
| 布局稳定 vs 窄窗可用 | 全部固定宽度 | 随尺寸压缩到不可读 | 主工作区优先、辅助区折叠、最小可用尺寸与恢复布局 |

## 12. 案例交叉检查｜现有 TEST 编辑器为何不能仅修字号

用户真实截图观察（I02）：中央大量空白，步骤相关操作和层级被压缩；按钮视觉级别混乱；阶段/步骤文字层级难辨；选中后详情关系在截图中不清楚。以下仅为设计层分析，不把现象直接归因于某个未经实测的 Grid bug。

| 截图问题 | 对应操作缺口 | 对应视觉缺口 | 需要同时研究 |
|---|---|---|---|
| 核心步骤显示区域很窄 | 无法顺畅阅读长步骤树/选中后编辑 | P01 空间重心失当 | 工作任务优先级、树内容长度、详情宽度、折叠行为 |
| 准备/测试/清理像普通小字 | 阶段选择与步骤选择不明 | P02 信息层级不成立 | 阶段是否可选、可插入目标、展开/折叠及标题层次 |
| 上移下移/撤销等按钮拥挤 | 常用命令不成操作流 | P04 命令主次不清 | 本对象操作类型、频率、键鼠/菜单并行方式 |
| 选中步骤与详情不协调 | 选中后预期编辑无法发现 | P03 因果反馈薄弱 | Selected Step 身份、Inspector 更新、焦点与空态 |
| 混杂低对比与显眼蓝色 | 用户必须搜索和猜测 | P02/P08 视觉注意力错误分配 | 色彩/字号/语义 token + Windows 对比测试 |
| 巨大空白又显得拥挤 | 数据密度布局错位 | P05/P09 内容与视口不匹配 | 树内容数量、默认/最小宽度、DPI/缩放与响应式变化 |

**V01 不据此决定“左几像素/中几像素/右几像素”**；先要求下一轮比较不同完整布局，在真实内容下验证任务和视觉是否一致。

## 13. 原 R01～R06 与 V01 互相佐证矩阵

| 原研究 | 原来解决的“怎么操作” | V01 补充的“应该怎样呈现” | 下一轮证据 |
|---|---|---|---|
| R01 六系统 | 工作环境、对象、命令、状态与恢复 | 每个系统必须具有可感知、可辨认的层级与反馈 | 全局基础视觉方案 |
| R02 工具/文档 | 资源与工具上下文不同 | 编辑文档与工具窗在空间/标签/焦点上明确区分 | 主窗口多状态对照 |
| R03 入口/持续工作 | 第一次/恢复/缺工程不同入口 | 空状态内容、主要入口与任务进度的视觉显著性 | 启动三状态视觉原型 |
| R04 直接编辑 | 选中/字段/复制/撤销 | 当前对象与详情联动、类型化参数、命令主次 | TEST/DBC 具体场景 |
| R05 真实状态 | 请求/ACK/ECU 响应/证据不混淆 | 状态色、文字、时间、问题定位/UNKNOWN 的清晰视觉结构 | DEVICE/Flash/Run 状态样式 |
| R06 全域 | 工程/TEST/DBC/CAN/UDS/Wave 等全部任务 | 允许专业布局差异，统一视觉语义和命令系统 | 跨工具多屏原型 |

## 14. 本轮结论、边界与下一轮

**研究结论**：AutoTest 应建立“操作—视觉一体”的设计语言。视觉设计不是用户操作做完后的修饰层；每一种对象、命令、反馈与风险都需要同屏可理解的表现，视觉布局也必须由实际任务和数据密度论证。

**本轮没有完成/不能声称完成**：
- 尚未针对每个专业产品进行真实 Windows 上机操作对照。
- 尚未确定 AutoTest 的具体字体、颜色、间距、图标或任何页面结构。
- 尚未绘制并比较可操作的主窗口/TEST 页设计候选。
- 未修改 WPF，也未进行用户视觉验收。
- 本报告是 **设计原则候选**；用户尚未批准视觉 Design System 和页面冻结。

**下一工作轮 V02（建议顺序）**：
1. 针对成熟产品实图逐区做“任务→空间→层级→命令→反馈”案例拆解，而非仅引用产品介绍。
2. 选 TEST 程序编辑作为深度案例，建立不少于两种明确不同的完整视觉/交互候选（对比结构、信息密度与命令安放），同步保留已确认业务要求。
3. 归纳 Foundation tokens、标准组件与 TEST 专业结构组件的初版规范；不在未验证时冻结数值。
4. 先完成可以审查的真实内容页面/操作序列，再进入 WPF 实现。
5. 所有 V02/V03 均遵守已有总体计划“分批留档、用户最终统一验收”，但不得省略 AI 自检和视觉比较。
