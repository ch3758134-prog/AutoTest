## 三、P0 期间核对出的重要限制与下游关闭责任

### L-01｜管理规则已获批准，管理软件的强制执行链尚未部署

仓库具有 `tools/project-control-v2` 通用工具候选，但本次检查的 `main` **尚无**目标项目 `.project-control/` 和 `PROJECT_START_HERE.md`。现行审批仅以 GitHub 上的批准正文、审批记录和 Git 历史来追踪，不是经身份核验的全自动审批/任务派发系统；`main` 尚未启用 GitHub 分支保护或 Ruleset。

- **责任：** 工程总协调组织管理系统专项核对及目标项目接入候选。
- **允许当前推进：** 资料调查、需求研究、形成候审成果；继续在对话批准后直接归档已批准的管理成果。
- **关闭条件：** 在首次要求 Codex 从正式目标项目任务领取实施任务之前，形成并审查目标项目受控任务/批准记录入口，核对具体身份、版本和权限边界；不得用手工写 `APPROVED` 字样冒充外部授权。

### L-02｜产品和管理基线已定，但真实业务代码基线仍需交接判断

`main` 和 `local` 已经分叉；本次读取显示 `local` 相对 `main` 为 **ahead 35 / behind 84**（此数字仅对应本次检查）。`local` 已出现使用现有 `TestDocument`/`StepNode` 的真实执行实现候选、共享 CAN/DBC/波形与物理授权设计；其文档自行注明**未做 Windows 编译、UI 或真实 ECU 验收**。`main` 的旧 `RunCoordinator` 仍含 `MockStation`，不能把 `main` 和 `local` 的实际能力混为一谈。

- **责任：** 工程总协调联合 TEST、DEVICE、UI/集成专业。
- **关闭条件：** G0 固定真实代码/设计来源，形成按模块的 `main`—`local` 差异与适用性判断；之后再提出具体受控集成与验证任务，不执行整分支盲合。

### L-03｜硬件和双固件的具体在机身份尚未确认

主控板、KEY_SIM 按键板及相关固件存在历史研发资料。现役板卡/固件映像、准确编译器版本、项目 Target、线束及实际接线版本尚未经过本轮现场检查。用户已同意这些细节在后续相关研究及固件操作准备阶段补齐。

- **责任：** G0 硬件/固件调查专业及现场授权执行人。
- **关闭条件：** 在**任何固件代码修改、编译烧录或依赖现役固件能力的实体试验之前**确认对应板卡、Target、实际映像和现场条件，并形成相应试验/风险授权。此项不阻断无关的资料研究。

### L-04｜真实可运行/可复现性未得到当前证据

本次未进行 Windows Build、测试编辑器实际操作、CAN 通路验证、真实电阻组合电压测量、波形判定或 ECU 自动测试闭环。过去的实测、Mock、UI 截图或软件代码存在不得冒充最新版本验收。

- **责任：** G0/后续需求、集成与验证专业；实际设备动作由授权现场执行人负责。
- **关闭条件：** 在宣称相应功能完成时提供精确源码/设备/固件/资源/工位版本，运行步骤、预期与实际、日志和失败信息。**这不是 P0 文件管理阶段的前置实机准出条件。**

### L-05｜备份、敏感资产和发布保护仍需现场证据

Git 记录本身不是完整离线备份。当前 P0 审查未取得独立介质恢复演练、两套固件已安装映像核对、所有第三方依赖离线可重建及真实发布门禁的证明。

- **责任：** 配置管理/环境与验证相关专业。
- **关闭条件：** 在破坏性迁移、固件烧录、正式生产使用或发布之前，依据具体风险实施受控备份/恢复及必要的权限措施；G0 先编制资产证据与补证安排。

### L-06｜部分批准原文保留历史“候审”标记

P0-04～P0-08 为保存审批时正文不变，文件头仍带“候审”表述；审批后的真实状态由 `APPROVAL_RECORD.md` 和 Git 历史说明。**不能单靠文件头判断这些版本未批准。** 后续若需要统一状态展示，先形成与批准正文不冲突的衍生索引或受控元数据修订，不偷偷重写原审批对象。
