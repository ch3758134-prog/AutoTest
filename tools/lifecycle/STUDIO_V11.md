# Engineering Workbench V1.1｜独立工程认识、语义关系和 AI 候选交接

> 此文档对应 AutoTest GitHub Draft PR #28。V1.1 是管理系统候选，**不代表 AutoTest 产品定义、R1 设计、硬件固件或项目主线已批准**。正式 main 和用户 Windows 上已有 SQLite 不受本 PR 直接影响。

## 一、从 V1.0 再向前推进的问题

V1.0 加入工程概念说明和 AI 候选解释，但旧项目存储仍以 `summary/body/version/variant` 为核心。用户已经说明 AutoTest 包含上位机、主控板与按键板、系统的主要目的在模拟 ECU 外部刺激并分析响应，R1 与 EPB 则是阶段信息。若仍让 AI 只能修改一段 `product definition`，系统会鼓励把这些不同性质的信息混写；仅用提示词无法让下层工程认识具有独立身份、来源和演化历史。

V1.1 **没有擅自迁移或重解释旧项目**，而是增量增加工程知识图谱式的轻量数据层：可以独立记录主张、解释、来源、多个工程概念角色、已存在工程对象的关联、修订历史和认识之间的关系。

## 二、具体实现

### 1. 独立工程认识表

`studio_knowledge.py` 增加 `engineering_knowledge`、`engineering_knowledge_revisions`、`engineering_knowledge_links` 和 `engineering_knowledge_intakes`。

单条认识包括：
- **statement**：用户原话、工程资料描述、观察结果、AI 推断或开放问题；类型 `provenance` 是提交人的来源主张，必须核实。
- **interpretation**：说明为什么这样理解、适用范围、争议、不确定性与局限。
- **concept_ids**：可关联多个工程概念，例如同一事实同时影响“产品身份”“系统边界”“需求”。概念说明由 `engineering_semantics.json` 提供，概念分类不使用关键词、禁词或字数评分。
- **source_refs / related_objects**：来源线索及当前项目已有工程对象 ID。禁止凭空引用不存在或跨项目的对象。
- **origin_role / state / revision**：服务端记录是否由 AI 候选或本地 owner 候选提出。只有负责人可以 `ACCEPT / REQUEST_RESEARCH / REJECT`；审查结论本身不能证明外部来源真实性，不会改写其他工程基线。

已经接受或判为待研究/拒绝的记录保持**不可原地改写**，需要提出新的候选并用 `REFINES` 或 `CONTRADICTS` 等关系进行显式关联。候选修订采用预期修订号，保留完整历史。

### 2. 有意义的关系，而非简单贴标签

候选关系支持 `SUPPORTS / CONTRADICTS / REFINES / CONTEXT_FOR / IMPACTS / DERIVED_FROM`，每条关系必须有解释。AI 可以提出，不能确认。只有两端记录都已人工接受且语义版本内容一致时才能确认关系。

如果候选关系在项目研究阶段建立，其两端后来只发生“接受审查”而没有改变主张内容，允许关系在人工确认时自动固定新的当前修订；若有人真正修改了语句、解释、概念归属或来源，该关系必须重新核实。这避免形式化的审批修订号导致语义关系全部作废，同时保留真实内容变化的版本保护。

### 3. AI 批量候选包与去重

`POST /api/studio/knowledge/intake` 接受 `engineering-knowledge-intake/1` 格式，包括 `entries` 与使用临时别名的 `relations`。完整包在**单个数据库事务**内核对并创建候选记录；不自动确认任何条目，也不发布产品定义。相同项目、相同内容 SHA 的包重复提交时返回旧记录 ID，不重复写入。

该接口可以使用受限项目管理 AI 令牌。AI 仍不能通过 `/knowledge/review` 或 `/knowledge/link/review` 执行负责人审批。受限令牌也不能修改正式工程对象、GitHub main 或编码授权。

### 4. HTML 真实使用方式

本地 Engineering Workbench → **研发管理与 AI 建议审查** → **工程认识与语义关系**。

可在页面中：
- 看待审与已审核记录、原始来源、语义解释、相关概念及版本历史；
- 录入/修订候选，人工决定接受、待研究或拒绝；
- 建立、审查两项认识之间的关联；
- 点击 **导入 AI 整理的候选包**，粘贴 JSON 或选择本地 JSON 文件，确认材料数量后一次入库。

**对话中的 AI 仍不能直接访问用户的 localhost**。当前可用的交接方式是 AI 生成 GitHub 候选包或可下载 JSON，由负责人在 HTML 导入；未来如取得明确授权，可让本地代理使用受限管理令牌自动递交候选，仍须人工确认。

### 5. AutoTest 真实项目试用资料

`tools/lifecycle/examples/autotest_knowledge_pilot.json` 包含 9 条候选记录与 8 条候选语义关系，来自用户实际纠正内容：
- 产品本体包含 Windows 上位机、主控板和按键板；
- 系统目的为外部刺激模拟及 ECU 响应的分析；
- 主要刺激类型为 IO、CAN 与按键；现役按键板是 20 Key 电阻网络与 5 路模拟电压；
- CAN RX 处理仍需研究，不能把未知能力标为已完成；
- R1 出厂检测重点、EPB 首例属于阶段背景；
- 现场 CAN RX 观察与 CAN0/1 接线属于有条件的实际证据与配置；
- 自动测试程序属于刺激与观测能力的组织应用，不等于整个产品本体。

此示例可以下载后直接在 HTML 选择文件导入。**其中所有断言都是候选，没有一条因出现在示例文件里就被宣告已批准。** 引用目前多数是对话记录的说明性 URI，后续需要补入真实工程文件路径、源代码版本和原始实验数据，才可能构成强证据链。

## 三、兼容与恢复

- 旧 `projects.summary/body/version/variant` 继续完整保留，不自动重排为新含义，也不会偷偷为任何历史对象签发新产品定义。
- 新知识以独立表并行存在，不构成独立 `product_identity` 正式审批流的替代。产品定义变更仍使用原治理规则。
- 工程 JSON 导出包含知识条目、全部修订、关系、已导入批次及内容指纹；恢复到**空工作区**时检查跨项目引用、修订完整性、关系锁定和导入批次身份。旧版没有 `knowledge` 字段的归档仍可恢复。
- 该版本更接近真正的独立语义对象层，但距离全面重构规范化产品主数据模型、跨工程对象图谱、GitHub 保护规则与 ChatGPT 本地直连还有差距。

## 四、验证与局限

- 新增独立领域测试及 localhost HTTP 安全测试，验证 AI 不能自批、批量导入去重、修订冲突、跨项目关联拒绝、语义变化导致关系重新审查、旧归档兼容。
- GitHub Actions 仅能验证 Python 规则、API 和 JS 语法；不能证明 AI 已正确理解用户意图，也不能代替 Windows 浏览器人机验收。
- 本地 owner token 仍不是 OS 级可信用户隔离。任何拥有 SQLite 文件写权限的同 Windows 用户进程都可能绕过网页；需在更高信任边界补充系统隔离。
- 任何原始数据、事实陈述、source_refs、AI 推断、审查结论都需要区分，不能因为结构完整就宣称知识正确。

## 五、还需要的真实工程审查

重点不是尽快把全部条目点“接受”，而是用 AutoTest 当前真实资料和用户纠正逐项发现：
1. 哪些问题真正改变了产品身份，哪些只是 R1 或特定硬件实现的上下文；
2. CAN 响应处理如何从原始帧、DBC、事件与时序，进入统一测试判据；具体何处缺少实测或已批准设计；
3. 哪些既有设计和编码任务因此受到影响，以及哪些并无直接影响；
4. 一旦明确影响，再向正式产品定义、需求、系统架构或详细设计提交独立版本化变更，不能靠知识记录暗中改变它们。
