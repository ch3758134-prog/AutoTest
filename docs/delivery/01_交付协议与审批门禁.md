# AutoTest｜专业 PR 交付协议与统一审批门禁 v1

## 1. GitHub 是唯一正式交付载体

- 所有专业源码、测试、UI 和专业设计提交到 `ch3758134-prog/AutoTest` 对应专业分支，随后创建/更新指向 `main` 的 **Draft Pull Request**；**不直接提交 main**（主对话批准的受控工程治理/修订例外需明确留痕）。
- 使用一个 CandidateId 对应一个可审查的完整差异集，便于追踪。候选反复修订时更新同一个 PR，保留 commit 史；下一项独立功能使用新的候选/PR。WAVE/SCAN 等以前的 ZIP 须通过 Git 分支/PR 重新交付，不再让用户下载补丁后本地覆盖。
- `main` 是正式集成基线，不是所有专业开发共享的草稿工作区。并行改动隔离在 Git 分支/PR 中；重叠文件由主对话指定唯一负责人处理，不用强制推送改写他人历史。
- 有效交付地址是 `PR URL + exact head SHA`。仅发送“做完了”“已写代码”或只有 ZIP/截图，不构成候选受理。
- 禁止将 ECU 身份/条码原文、Seed/Key、真实设备数据、个人隐私、原始敏感 USB/CAN 生产日志直接推送到公开 GitHub；PR 里只写已脱敏的可复核摘要。原始私有证据可保留在本地受控目录，记录文件 Hash 与查找方式。

**禁止**以源码打包 CRC、XAML XML 解析、模拟输出或拉取成功冒充 Windows Release Build PASS、用户实际操作 PASS 或真实物理 PASS。每个 PR 只提交本专业有权限的路径；公共 Contracts、Shell/Prism、项目引用和设备门禁变化先走主对话批准的最小变更单。

## 3. 主对话审批状态（都要有依据）

1. `PR_SUBMITTED`：GitHub 存在，专业提供完整 PR 信息；代码尚未审批。
2. `REVIEW_CHANGES_REQUESTED` / `REVIEW_SCOPE_ACCEPTED`：主对话审查实际 diff/设计/安全/责任范围，说明通过或退回原因；通过**不等于编译 PASS**。
3. `LOCAL_VERIFY_PENDING` / `LOCAL_VERIFY_FAILED` / `LOCAL_VERIFY_PASSED`：主对话指定 exact SHA 给本地 Codex；仅依据本次 Windows 原始 Build/Test 与操作证据推进。
4. `USER_LAB_PENDING` / `USER_LAB_RETESTED` / `USER_LAB_ACCEPTED`：仅针对适用的专项功能，用户集中安排实测；不阻止同专业其他不依赖功能。
5. `MERGE_APPROVED`：主对话核对适用验收门槛、Git HEAD 和变更范围后明确允许合入；之前任何 Draft、Mock 或 Build 状态不得自动触发合并。
6. `MERGED_MAIN` / `HOST_INTEGRATED` / `R1_ACCEPTED`：Git merge、正式共用服务接线、系统/用户验收分别留证，不互相冒充。

**两条验收轨道**：
- DEVICE、WAVE、UDS/Flash、BENCH、PROJECT/DBC、SCAN 中可独立实测的功能：本地软件验证后，用户按设备权限和适用场景做独立实测，符合该项条件方可宣称对应现场能力已通过；是否允许先合入无物理副作用的独立代码由主对话单项审批。
- R1 UI、TEST、RECORD/报告：现在持续完成源码与自动/组件测试；用户完整操作验收在统一 HOST 接线后完成，不要求制造独立 EXE 或等 DEVICE 实测完成才继续研发。

## 4. 主对话每次 PR 审查的固定动作

- 获取 `main` HEAD、PR HEAD、merge base、变更文件与 diff；核对所有文件所有权与缺少的共享合同。
- 核对 G3/G4/SAEF 最新决定、候选源头、编码安全边界和原始日志/构建验证声明。
- 必要时提出精确代码问题和退回，**由原专业对话负责修订专业代码**，本地主机 Codex 不自主研究/修错。
- 审查通过后给本地 Codex **PR 号 + HEAD SHA + 允许命令 + 不可修改/不能上传的文件**；不同候选用 Git worktree 隔离。
- 验证回传后再给下一条明确决定：退回/允许专项实测/批准合并/保持等待。审批要以精确 commit 为单位；PR HEAD 更新后必须重新确认适用的验证结果。
- 仅经明确批准的候选才能由主对话或受控命令执行 GitHub 合并。合并后记录 main SHA，并在 INTEGRATION 后完成跨模块全量回归。
