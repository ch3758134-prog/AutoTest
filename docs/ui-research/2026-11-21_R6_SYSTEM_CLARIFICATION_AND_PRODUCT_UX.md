## 1. 全系统产品边界：六块能力、三种使用场景

### 1.1 六块能力的平等关系（不是 TEST 包含一切）

```
                                  AutoTest 桌面应用
              ┌──────────────────────────────────────────────┐
              │   工程师工作区   │   生产检测工作区   │  工具入口 │
              └────────┬──────────────┬──────────────┬───────┘
                       │              │              │
       ┌───────────────┴──────────────┴──────────────┴───────────────┐
       │ 独立工具 │ 通用资源 │ ECU 工程与 TEST │ 生产编排 │ 记录报告 │
       └───────────────────────────┬─────────────────────────────────┘
                                   │
                       统一真实设备与数据服务
                      USB / ECU CAN / KEY CAN /
                         UDS / FLASH / WAVE
```

- **独立工具**：[已确认] 手动台架、DBC、UDS、烧录、波形，无工程照样打开和完成独立任务；按需引用工程资源，不能默默改工程当前生效配置。
- **通用资源**：[已确认] DBC、固件/安全算法、烧录参数、参考波形、诊断服务序列可被多个体系使用；资源的所有权不是由“谁先使用”决定。
- **ECU 工程/自动测试**：[已确认] 一个型号一个工程、一套当前有效资源/TEST 树；开发可单步/单用例/勾选范围调试，不需要扫码或生产前置烧录。
- **生产检测**：[已确认] 独立工位操作流程，扫码→型号校验→夹具→等待实体启动→每次真实烧录→全部启用用例→自动记录和收尾；正常不要求鼠标。
- **日志/报告**：[已确认] 原始 CAN/附件、步骤测试日志、简洁单台报告、批量报告四层，跨工具和场景共用真实证据与身份。
- **设备/协议**：[已确认] 实际只有一套单工位 USB/CAN/UDS/Flash/记录服务，所有前端均不能重做硬件执行器。

### 1.2 三种任务，从同一应用进入

**工程师开发测试**：打开型号工程 → 选用例/步骤 → 编辑 CAN、KEY、UDS、判定 → 使用独立工具检查资源/手动操作 → 保存草稿与校验 → 运行步骤/用例/勾选范围 → 实际日志与证据 → 继续编辑。 

**专业工具独立操作**：从工具菜单打开对应窗口，即使没有工程也可新建或载入独立文件；设备连接、互斥操作状态在工具窗口有清晰反馈；选“使用当前工程资源”后才产生显式的工程关联。

**生产连续检测**：进入生产工作区等待扫码 → 按型号定位已安装工程 → 合法同型号直接处理/已知异型号才确认切换 → 发夹紧请求并获得合格的到位条件 → 等实体键 → 编程前检查与本次烧录 → 用例树全量自动执行 → 归档报告 → 显示本台结果直到下一次有效扫码。

### 1.3 不要设计成以下结构

- 工具 = TEST 步骤的另一页；工具打开强制要求选工程。
- SCAN = 复杂的 ProductVariant→WorkOrder→Recipe→FlashPolicy→TestProject 多级管理员向导。
- 每个型号一堆当班候选 DBC、固件和 TestProject，扫码后再让操作员选。
- 生产烧录必须人工往用例里插 FLASH 步骤，或者用户每台扫码后在电脑点开始。
- 每轮测试都由 UI 另造执行器或以读取到最后一帧判定 PASS。

## 2. 全产品信息架构与主窗口

### 2.1 全局信息架构（研究建议）

```
顶部：AutoTest | 工程 | 编辑 | 运行 | 工具 | 生产 | 视图 | 帮助
      当前工程：HydEPB       当前工位：USB / ECU CAN / KEY CAN 状态

[工程师工作区]  [生产检测工作区]           （两种上下文，非两套程序）

工程师工作区：
  左：型号工程资源树 / 搜索 / TEST 有序用例树
  中：文档标签 + TEST 编辑与运行共享上下文
  右：当前步骤参数 / 资源选择 / 校验原因
  下：问题 / 变量 / 步骤证据 / CAN 日志（可折叠）

生产工作区：
  全宽：当前型号 | 设备/夹具/实体键状态 | 当前 DUT
        当前大阶段：待扫码 / 压紧 / 等键 / 烧录 / TEST / 归档
        进度、最终结果、失败原因、上次结果
        次要入口：工位/型号配置、历史记录、异常恢复

工具：独立 WPF Owner 窗口，最多同时打开多个；不占用主工作区。
```

[研究建议] 主窗口采用两种模式及可切换文件文档，而不是永久在左侧挤进七八个功能导航。工程师工作区保留单击工程树切换文档；生产工作区无需看 TEST Inspector 和工具文件树。

### 2.2 窗口与生命周期

| 窗口 | 层级 | 允许无工程 | 是否能影响实体 | 关闭时 |
|---|---|---|---|---|
| AutoTest 主窗口 | 唯一应用主窗口 | 是 | 通过受控后端 | 结束/保留任务需依设备状态和授权流程，关闭所有 owned 工具窗 |
| TEST 编辑/运行 | 主窗口内文档 | 否（需要工程） | 调试运行才可申请 | 不弹第二套编辑器；选择与视图恢复 |
| DBC 编辑器 | 独立 owned 窗口 | 是 | 否（资源编辑） | 保存/恢复当前草稿，回收焦点 |
| UDS / FLASH / 手动台架 | 独立 owned 窗口 | 是 | 真实会话允许时申请 | 不可因关闭 UI 自动假定设备已安全停止 |
| WAVE | 独立 owned 窗口 | 是 | 接收/采集，不擅自发送刺激 | 实际录波安全终止、保存不完整状态 |
| 生产检测 | 主窗口模式 | 是，但任务未就绪不得生产 | 由实体状态机发请求 | 运行中禁破坏式切换 |

工具窗可同时打开观察；真实写入互斥需要下层调度，不能用“一个窗口独占整个应用”替代设备合同。窗口与任务归属必须分别显示。

### 2.3 视觉与交互系统

- 浅色、白底为主，信息密度可调；避免深蓝底/低对比文字、工具窗大片空白与“这只是原型/未来会接线”的大段说明。
- 使用真实产品语言：`等待实体启动键`、`CAN 周期发送 2 条`、`DBC 引用失效`、`本次报告尚未归档`；技术诊断留展开详情，不使操作员读堆栈异常。
- 按钮只做真实语义动作：`运行此步骤`、`启用周期发送`、`停止`、`采集标准波形`、`建立参考候选`。不把“目标状态”画成实际到位状态。
- 所有常规编辑自动保存；脏草稿可恢复、非法编辑有明确就地错误；运行仅使用最后冻结的有效快照。
- 工具资源有来源标记：`独立文件` / `当前工程资源`，只在改变所有权时必要确认；当前无工程不显示无意义错误墙。
- 搜索不打断测试树结构，命中高亮并支持定位；新增步骤先在列表插入并选中，右侧 Inspector 即可编辑；右键提供运行、禁用、断点、复制、删除和流程控制。

## 3. 工程与自动测试的完整交互研究

### 3.1 工程树的领域结构

```text
HydEPB（某 ECU 型号的唯一工程）
├── 自动测试
│   ├── 功能测试/            ← 分类目录：只组织、无执行步骤
│   │   ├── 静态驻车         ← 用例：准备/测试/清理
│   │   └── 静态释放
│   ├── 故障测试/
│   │   └── 通信故障
│   └── 公共流程             ← 同一 DSL，供用例调用，本身不计入出厂用例
├── DBC（当前生效：绿通通信矩阵）
├── 参考波形
├── 固件（当前生产目标）
├── 生产配置（型号识别、原生烧录参数、工位条件）
└── 历史记录/报告
```

**不是**默认同时摆三个 TestProject，或让用例树分类目录自身持有步骤。目录内顺序确定出厂执行顺序，`Enabled` 是工程永久生效，`Selected` 是工程师本轮临时范围；生产**不使用** Selected。

### 3.2 核心测试编辑器结构

- **用例首部**：名称、状态、阶段数量、失败/结果及当前运行范围；菜单与常用命令可从具体对象触发，不放一排几十个按钮。
- **列表**：准备 / 测试 / 清理是清晰的阶段分组；行内含执行状态、断点、禁用、动作摘要、引用/诊断；行高足以鼠标操作，仍保持多步骤密度。
- **步骤选择器**：按 CAN、KEY/IGN/夹具、UDS、WAVE、判断、控制、变量、流程调用分类；输入关键词立即过滤；插入后不弹另外的属性窗口。
- **右侧常驻 Inspector**：参数按“本步骤必须/可选辅助/记录提取”分组；所有修改立即写草稿并进行诊断。标准流程块（IF/ELSE、SWITCH、WHEN、循环、异常）展示有语义的嵌套子树，不只靠缩进数值伪装。
- **运行与调试**：编辑与运行共享选中用例、步骤、断点及变量；运行此步骤、此用例、勾选范围、单步/运行到、停止/异常原因；下一轮执行不能偷偷改变当前冻结内容。
- **失败控制**：用例可执行诊断/继续/终止/清理；出现历史 FAIL 仍累计为本次不合格，不能被后续 PASS 消除。底层 Flash 失败、设备未知状态及停止命令不可由 TEST 脚本绕过。

### 3.3 高频步骤的实际编辑体验

**CAN 发送**：完整 DATA 在界面核心区域直接显示；经典 CAN 根据当前硬件真实能力为 0–8 字节，ID 自动判标准/扩展，允许显式修改；支持单发/周期，明确是否已启用及运行所有权。DBC 只提供可选信号写入/编码，不成为发送前置条件。现有硬件没有 CAN FD 64 字节的现场依据，不应默认出现可执行 64B 选项。未来若支持 CAN FD 再做能力协商和解锁。

**KEY_SIM 动作**：20 Key 对应组合开关和保持时间；可保存可命名动作供 TEST 与手动台架引用；支持纯等待、多个 Key 同时闭合，不默认执行 `ReleaseAll`；当前真实高边和波特率按 DEVICE 合同。

**DBC 判定与关键测量提取**：搜索工程当前生效 DBC 中实际报文/信号；展示数值、单位、质量/失效原因、时间窗和条件；勾选需要进入结构化日志/报告的关键测量值，必须绑定同一次 `StepOccurrenceId` 和原始证据。

**公共流程**：与用例共享 StepNode/执行语义，允许流程互调、固定修订、依赖环检查；不是新建一个并行小语言。

### 3.4 自动保存、资源正确性与运行冻结

| 场景 | 交互建议 |
|---|---|
| 改步骤名称、参数、拖动、粘贴 | 自动保存草稿，状态栏只有真实存盘失败时提示；无需反复关闭确认 |
| 参数不合法 | 保留可恢复草稿，右侧就地错误，标记`不能运行/不能发布`；不是删掉用户输入 |
| 编辑 DBC 影响 TEST 信号 | 显示受影响引用、重新校验；正在执行的老 DBC/SHA 快照不受影响 |
| 运行中工程师修改步骤 | 影响**下一次**运行的草稿，不修改本轮冻结执行快照；明确“新编辑待下轮生效” |
| 关闭/切工程 | 自动保存与恢复；若实际保存失败则提示无法安全切换，不能静默丢内容 |
| 新建型号工程 | 根据通用模板预生成基本 TEST 和清理结构，供用户自由编辑；模板本身不跟随修改 |

## 4. 五个独立工具的成熟产品设计

### 4.1 手动台架

**推荐工作区**：左侧工位控制与按键动作按钮，中部多个 CAN 发送任务与完整报文，右侧实时 CAN 监视/日志；不嵌入 TEST 主工作区。按键动作按钮单击即发起一次真实目标操作，旁边独立的编辑/右键入口。编辑浮窗只展示 **20 Key + 保持时间**，不额外强迫用户设置一堆动作类型。

CAN 发送任务每条卡片可看见 CAN ID、标准/扩展、8 字节完整 HEX、DLC、单次/周期、周期 ms、启停及最近主控反馈；同一设备上多个周期发送允许明确启动/停止，左侧工位控制 IGN 与夹具目标分开显示“请求”和“已知实际反馈”。当无工程，仍可以不载入 DBC 直接填写字节；若有工程，DBC 可按需辅助。

### 4.2 DBC 编辑器

无工程可新建/打开独立 DBC；打开工程资源时明确为“当前生效 DBC”。三大操作区：左侧报文列表/搜索，中部可连续批量修改的信号表格，右侧当前报文/信号详细参数与位图。保证 Intel/Motorola、起始位/位长、符号、比例、偏移、最小最大/单位/枚举/复用等规范字段受校验；支持中文显示别名而不把不规范汉字硬写入 DBC 名称。修改自动保存对应资源，只有显式“纳入工程”才更换工程 DBC。

### 4.3 UDS 工具

连续服务序列＋当前服务 Inspector＋请求/响应时间线，保留边调试边编辑的流畅性；会话切换、TesterPresent、NRC、Timeout、Cancel、接收解析、变量与序列存储独立完成。不从生产扫码里获取必须配置，不需要预先创建 TestProject。复用已有 ISO-TP/UDS 实现；真实 ACK、ECU 正响应、否定响应和服务结果须分别可见。

### 4.4 独立烧录工具与生产 Flash 配置（不能混为一页）

**独立烧录工具**无工程运行，允许临时配置 APP/Boot 端点、Seed-Key Provider、Firmware、分块大小、诊断超时等真实支持字段；可显式选工程固件但不能反向静默覆写生产配置。布局：左侧文件与配置、中部十个真实阶段＋总体/分段进度、右侧 CAN/UDS 原始报文及阶段错误与证据。没有真实执行就保持未开始/0%，不可播放假进度。

**生产烧录配置**属于 ECU 工程的集中配置，固件当前唯一，原 CanTool XML 表达的有效字段在 AutoTest **原生可视化编辑**，保存固定工程位置，自动保存。创建项目时有合理默认但必须真实检查有效性。用户不需要平时选 XML 文件；技术专项需对照 XML 原字段与实际读写范围完成 schema、迁移和兼容。每次生产扫描后不重新挑 HEX/安全 DLL/编程参数。生产烧录是**实体启动后、TEST 前的工位阶段**，不要求在 TEST 步骤中放 Flash。

**进度与结果必须分层**：准备、Boot/App、会话、Seed/Key、擦除、数据传输、退出、校验、复位、App 恢复、必要软件版本后验与完整记录，是不同性质状态。实际软件版号若无支持的 DID，就显示“未核验”，不能用 APP 50 03 替代版本正确。Flash 中断后可能处于 Boot/内容不完整状态，不能默认宣称成功释放或立即允许下一台。

### 4.5 波形工具与“采集标准参考”

必须支持**多信号同屏**，共享时间轴；离散状态阶梯显示、数值信号独立单位轴，同单位可以叠加；多轨同步放缩/游标，支持多组采集与参考叠加和事件锚点。

**真正的入口链**：选择实时 DBC 信号 → 实时监控 → 配置采集（录制时窗、触发源、时间源/设备、合格样件标识） → 确认订阅就绪 → 真实采集开始/停止 → 审查 CAN 原始事实及时间质量/缺口 → 保存采集 → 建立标准参考**候选** → 审核/冻结版本 → TEST 从工程资源选引用与判定规则。工具无需工程也能采集并保存独立录波；关联当前型号工程时才获得工程参考身份。

**不能用曲线漂亮代替准确**：时序时间来源是主机接收时刻，不等于 ECU 内部物理事件；多路 CAN 上报并非硬件同步采样。画图抽稀不删除原始事实；高风险时间条件若被算法自由平移 50ms，就可能隐瞒响应超时。PASS/FAIL/INCONCLUSIVE/ERROR 四类判定与采样缺口/信号过期、参考批准状态、真实源证据关联。任何未验证的“+/-5% 默认容差”应为空而非写死。

## 5. 生产检测：一屏完成，不靠操作员鼠标

### 5.1 唯一业务状态机（已确认顺序 + 待硬件验证条件）

```
待扫码 ──扫码完整校验──> 型号/工程核对
   ├─ 同型号：无需弹窗 ─┐
   ├─ 已知异型号：确认切工程 ├─> 请求夹具压紧 ─> 确认真实就绪* 
   └─ 未知/歧义：拒绝 ─┘                         │
                                            等待实体 START*
                                                 │
                                        生产预检/配置冻结
                                                 │
                                   每次执行本台完整 FLASH
                                     ├─ 失败：不进入 TEST
                                     └─ 成功：版本后验状态
                                                 │
                                   按树顺序运行全部 Enabled 用例
                                                 │
                                   归档原始 CAN/TEST/Flash 证据
                                                 │
                                  工位收尾/在安全条件下释放夹具*
                                                 │
                                   显示本台 PASS/FAIL/中止
                                   等下一次有效扫码才覆盖结果
```

`*` **待现场**：夹具实际到位、实体 START/STOP 的输入和 USB 协议、机械异常收尾未形成正式电气/时序事实；UI 不能伪造“已夹紧”或自行创造 USB 命令。正式流程接入前必须以真实检测证据建立门禁。

### 5.2 生产工作区界面方案

- 最上方：`当前型号/工程`、`ECU CAN 速率`、`主控 USB`、`工位就绪`、`当前实体按钮状态`。
- 大面积中心信息：当前 DUT 型号、唯一编号、阶段、进度、故障原因；等待启动键时突出 `等待台架启动键`，**不显示“点击电脑开始”主按钮**。
- 阶段轨：扫码、压紧、等键、Flash、TEST、报告、结束，正在执行与未知态区别。
- 右侧/下方摘要：本台关键结果、最近 CAN/UDS 事件入口、单台报告与历史记录；不始终占三分之一空间展示未用的配置表。
- 结束后：最终结果大字显示，若前一台不合格展示失败阶段和原因；新有效扫码才进入下一台。正常同型号批量生产不用对话框/鼠标。
- 配置员入口（非每台生产入口）：型号识别字段、当前有效固件及原生 Profile、工位条件、报告固定配置，不出现必须配置 WorkOrder/Recipe 的繁复页；型号跨工程的确认仅作为例外。

### 5.3 真正需要展示的状态词

| 事件 | UI 可宣称 | UI 绝不可宣称 |
|---|---|---|
| USB 写出 IGN/夹具请求 | “已发送请求”或“主控已受理” | “机械夹紧已到位” |
| 主控设置 ECU CAN 码率并读回 | “主控报告 500kbit/s” | “ECU 已经有正确通信” |
| 扫码 CRC/型号匹配 | “编号格式与型号匹配” | “ECU 硬件身份已真实核验” |
| Flash 数据传输正常 | “传输阶段完成” | “目标软件已正确安装/产品已放行” |
| UDS 收到 50 03 | “应用会话恢复有响应” | “读回目标软件版本成功” |
| CAN 波形两条曲线相似 | “观察到数据/比较结果候选” | “无缺帧且满足物理响应时间” |

### 5.4 异常、暂停及后续处理

- 扫码时未就绪/运行中：不接受、不排队、不切换当前 DUT。
- 已知异型号：只有工程存在且当前可安全切换时才要求确认；工程自动加载其唯一当前资源、TEST、Flash。
- 夹具请求后没有可靠到位信息：`夹具状态未验证` 阻断继续，不能无条件倒计时视作到位。
- START 重复、按键长按、STOP、USB 中断、Flash 擦除中断：由待现场确认的设备语义决定可执行恢复，必须先有记录和“未知/需处理”状态，不能默认允许下一台。
- 正常 TEST 断言失败：交由当前用例或公共流程的可编辑逻辑继续/诊断/收尾，累积 FAIL 不得被后续 PASS 覆盖；底层 STOP/设备未知态仍不可越过。
- 同号复检保留独立历史记录，每次仍完整烧录；是否做额外人工复核/统计口径 **待业务决策**，不增加默认弹窗。

## 6. RECORD 与报告：四层证据与真实计数

| 层级 | 记录内容 | 交互入口 |
|---|---|---|
| 原始 CAN/设备附件 | 时间/方向/角色/ID/DLC/全部 DATA、USB/UDS/Flash/WAVE、丢帧/截断/完整性 | CAN 监视、步骤证据、历史附件 |
| TEST 日志 | 实际 StepOccurrence、动作、读到的值、判据、异常、允许继续情况 | 运行/调试底栏、失败定位 |
| 单台报告 | 某次完整检测 DUT 身份、固件/版本、Flash/功能结果、失败步骤/核心测量、最终结论 | 生产结束面板、历史记录 |
| 批量报告 | 独立 ECU 数、检测次数、结果、重复编号/复检等固定统计 | 记录/报告工作区，不混原始帧入正文 |

研发/生产来源必须可识别；工具单独 UDS/Flash 的诊断结果不能未经授权自动变为生产 PASS。`ScanEvent` 不等于 `InspectionSession`，一次检测可以包含一次 FlashAttempt 和多个 CaseAttempt；每个 Case 里的 StepOccurrence 再关联原始证据。**批次边界、首次/最终合格率、正式放行策略仍待 SCAN/REPORT 联合确认**，研发版可以展示简单事实计数而不能把候选统计当定稿。

**重点 UI 优化**：单台报告正文简洁，但每条关键观测可以“查看原始证据”；失败/停止/断线报告也存在，不用用户手动点保存；原始 CAN 日志完整性无法证明时明确标注采集不完整。

## 7. 实体与平台限制：不可因 UI 需要而编造功能

- 单 PC/单工位/同时一台 DUT；主控 MCU MK20DN512VLL10，ECU CAN 为 FlexCAN1 / A12(H)、A1(L) / USB 通道1；KEY CAN 为 FlexCAN0 / B11(H)、B1(L) / USB 通道0，固定 500kbit/s。
- 当前主控实物为**经典 CAN 最多 8 字节数据**；**不具备已验证的 64B CAN FD**，新 UI 先按真实 8B 设计。
- Main_Control 已归档新 IGN=HOUT1/PTC1/J1 C10；不得继续按旧 PTC10/C6 映射设计。夹具两路、电磁阀请求与机械到位是不同事实；RL_DRV 是内部电路控制，不作为业务 USB IO 按钮。
- KEY_SIM 20 Key 通过五路电阻网络输出；20 Key 不等于 20 路模拟电压采样；测试与台架同一个完整 mask 概念，允许 0 Key 纯等待。
- ECU CAN `0x42/0x43` 动态速率仅为固件候选并需真实设备/EEPROM/运行时验证；Boot Flash 支持的目标速率不能直接从 MCU 可选速率推断。
- 生产实体启动/停止按钮、夹具到位、电源断电后的物理状态均需现场和原理图核对，UI 只能显示真实可观测状态。

## 8. 对 V5 HTML 的逐项差异审查与处置

| V5 现象或设计假设（已读 HTML） | 与新产品合同的冲突 | R6 研究处置 |
|---|---|---|
| 生产 `prodConfig` 带 `taskId/recipe/flashPolicy/caseIds` | 型号工程应唯一；常规生产不让操作员配置 Recipe/用例子集；每次必烧录 | **移除主流程与主页面**中的多配方、多策略、勾选出厂用例；仅保留内部运行计划冻结/资源 SHA |
| `flashPolicy:'不烧录'` 为默认 | D12 每次正式完整检测前置烧录（含复检） | 生产工作区不能有`不烧录`选项；研发工具可单独烧录或不烧录，两个场景分离 |
| 生产页含扫描后 `检查计划/电脑确认` 动作 | D11 实体键启动、日常不操作鼠标 | 主流程改为扫码→自动夹紧→等待实体启动键；异常时才有人机确认 |
| `data-prod-case` 与 `caseIds` | 正式生产用整个 TEST 树所有 Enabled 用例 | 生产不显示本次用例勾选；工程师调试仍保留 Select 范围 |
| 默认 UT1 硬编码 CRC 作为主要业务入口 | 具体客户条码与枪设备尚未冻结 | UT1 仅是可选择格式示例，不把它定义成所有生产用户的唯一可用条码 |
| `stepCatalog` 把 `flash` 作为 TEST 类型 | 生产 Flash 改为独立前置阶段 | 旧 TEST Flash 节点的研发兼容另审；**不再指导用户在用例里配置生产 Flash** |
| CAN 编辑展示 `8/64`、`Math.min(64, ...)` | 真实硬件 classic CAN 8B；无 CAN FD 证据 | 物理启用状态只允许 0..8B；64B 仅未来能力扩展提案 |
| 独立工具标签虽存在，但大量数据来自 `state` 当前工程 | 无工程必须能打开工具和使用独立资源 | 将工具上下文分为`独立文件/会话`与`工程资源`，可显式导入/关联 |
| 波形多轨/游标已有 | 真实订阅/质量/标准参考批准未证明 | 保留多波形设计；增加与工具/工程相互独立的真实采集/审核/冻结逻辑 |
| 生产页面与工程右侧 Inspector 有并存/遗留 | 生产不应被开发编辑面板挤压 | 生产模式为整页站点界面，开发 Inspector 不参与 |
| HTML 内存数据/假设备空态 | 不能当正式产品可运行性证据 | 保留只作为 UI 交互验证，但显式标注设计档案，绝不宣称生产环节已通过 |

**技术上可保留的 V5 成果**：浅色视觉/控件方向、工程师编辑三栏密度、添加步骤/参数体验、工具 WPF owner 的产品边界、手动台架按钮与完整 CAN 数据、波形多轨与候选标准参考、DBC 连续编辑的方向。需要更换的是其**领域模型与生产任务组织**，不是仅换页面标题。

## 9. 统一组件、数据流与接口责任（WPF 实施边界）

### 9.1 只保留一套领域真相

```
MainShell / WorkspaceContext / ToolWindowManager
    │                   │                   │
    │ [工程师]           │ [生产]             │ [工具]
    │                   │                   │
    ├────── PROJECT 资源/文件管理 ────────────────┤
    ├────── TEST StepNode/编译/RealRunCoordinator ─┤
    ├────── DEVICE session + Physical-role CAN ────┤
    ├────── UDS/CanTool FLASH 共享真实协议后端 ────┤
    ├────── WAVE capture/references/comparison ────┤
    └────── RECORD Raw CAN/StepOccurrence/Reports ─┘
```

[研究建议] UI 的每个控件只有一个明确命令/数据源；不自行复制 `UiTestProgram`、`UiWorkspaceFiles`、Flash Job 构造、波形判定器、扫码统计库。生产是状态机**编排现有真实后端**，不是新增第二 TEST 解释器；`工程资产自动保存`与`运行时不可变快照`需要隔离。实际接口签名、事件订阅时序和工位 ownership 由 R1/专业源码映射后再写 WPF。

### 9.2 命令、设备状态与证据的三段反馈

- **Intent**：用户/自动工位请求发送、启动周期 CAN、压紧、开始本次烧录。
- **Acceptance**：本机/主控/后端是否接受指令，并给出当前所有者、忙、非法参数、设备断线等错误。
- **Observation/Outcome**：真实 ECU CAN/UDS 反馈、夹具传感/真实执行结果、波形测量/测试 Verdict 和报告归档；后两类必须具有原始证据关联。

不把 Intent 成功直接画成 Outcome 成功。不出现“安全电气状态”之类缺乏实际可观测依据的抽象标签。

## 11. 未决事项与不应自动引入的产品策略

以下均未被管理文档批准细化，不在本次研究强行定值：

- **U01** R1 首版准出是工程师完整 TEST/Flash/Record 还是包含完整生产工位；不自定 R1 Release 承诺。
- **U02** 扫码枪 HID/COM/POS、客户实际标签字段/CRC 与型号编码；UT1 是研究候选，不是客户通用事实。
- **U03** 实体 START/STOP 的真实 IO/USB 事件及夹具到位判据；不新增虚构硬件控制。
- **U04** 普通 FAIL 后是否保持夹具/IGN 硬件现场，安全收尾要实测/确认。
- **U05** 重复扫码后按上次 PASS/FAIL 如何提示与分流；不默认追加弹窗。
- **U06** 批次起止、唯一数量/首次良率/最终良率、正式放行政策和复检统计。
- **U07** 简洁单台与批量报告固定字段/版式；建议先研究实际有代表性的记录。
- **U08** 原生 Flash Profile Schema 与固定文件位置、从 XML 迁移方案、工具与生产资源可选复用的接口。
- **U09** Flash 中止/STOP/断电后 ECU Boot 与夹具状态的物理恢复。
- **U10** WAVE 采样质量、离散判定、参考审批与现有 RECORD 证据类型冲突的正式解决。
- **U11** 不同工位夹具差异的配置边界；首版避免为假想工厂做多层级方案设计。

[研究建议] 对这些问题保留明确接口/错误空态，不将未获批准的选择塞进日常页面；需要真实现场事实才能确定的先由对应 FLASH、SCAN、DEVICE、REPORT、WAVE 专业形成证据再决策。

## 最终研究判断

AutoTest 的成熟，不取决于在主窗口塞进多少工具栏，而是三种使用场景都能成立：

1. 工程师能持续编辑和调试**真正的测试程序**，资源、步骤、测量和记录保持同一个事实链；
2. 工具脱离工程也能独立完成专业任务，资源共享是显式、可追踪的，而不是依赖 TEST 的附属页；
3. 生产操作者在真实工位上**不需要每台鼠标操作**，扫码正确匹配型号工程，经夹具与实体键确认后每次完成烧录、全部启用测试、保存证据，并保留结果等待下台。

本研究支持这三条已确认的方向，同时对 UI 设计细节保留候选性质；任何真实硬件不可观测的条件，都不能通过一个看起来已经完成的界面伪造出来。
