# AutoTest R1｜生产准备 / 扫码 / 完整工程发布：9 分门槛设计审查与实施合同

基线：R1@a79b5abe2e058bf6f6ad4cbd7b5b07867b8b7b62；仅 R1 直接实施，不改 main，不新分支。**设计审查通过不等于 Windows 编译、真扫码或生产放行通过。**

## 1. 原界面实际问题

用户第一次打开「生产准备」时，被要求先从三种“型号来源”中选择，再面对型号与工程绝对路径表、多规则格式/正则/字段映射、CSV 编号表、工位文本互锁、两次分开的发布按钮，既无法知道自己当前生产哪种 ECU，也无法看到直接的“缺什么/下一步做什么”。设备连接、唯一编号解析、型号绑定、配置发布被混为一项任务；固定单型号工位承担了多型号配置的全部认知成本。

现有 `ProductionBarcodeRule.NewSerial()` 内置 `SN001234` / `SN|BAD` 示例，`InspectRules` 的静态正反样例通过可被误读为真实扫码枪已验证。已发布的工程记录当前仍指向原始项目路径而非自足安装包；不允许用 UI 文案声称完全独立安装。

## 2. 分离的唯一领域关系

- **工程**：ProjectDefinition、唯一正式 TEST 项目及固定调用顺序、DBC/波形、NativeFlashPublicationStore 的发布工艺；工程内部型号是唯一来源，用户不重复输入。
- **设备**：SerialScannerWorkbenchViewModel + StationScannerDeviceBinding 用真实 USB PnP / COM 连接；设备诊断不直接指定产品/工程；正式扫码来源必须是真实已绑定设备。
- **识别**：ProductionBarcodeRule 负责从原始输入得到唯一编号（固定工位缺省为整串）；模式 FixedStation/BarcodeModel/RegistryModel 负责确定型号及变型；同一编码的多规则歧义拒绝，不按首项猜测。
- **发布**：先完成工程/原生 FLASH 的版本冻结，再校验并发布产品规则/工位配置，严格核对 Manifest / TEST / Flash / firmware hash。UI 将两层操作整合成一次明确触发的“检查并发布”；后台绝不能用发布代替 START、夹具证明或正式 PASS。
- **运行**：生产扫码只识别本台 ECU，复检为同一编号下的新 InspectionAttempt；正式执行器仍需可信实体 START、机械反馈/互锁和正式 RECORD，当前不得绕开。

## 3. 交互方案（默认固定工位）

首次进入只显示**交付准备**主面板：A 当前工程（型号/工程名/是否已绑定）、B 真实扫码（设备/原始内容/解析编号/试扫与样例）、C 当前发布状态和真实阻断条件、D 明确的「核对并发布生产配置」动作。页面底部有到「扫码与工位设备」的直接入口。主路径不展示空的型号/路径 DataGrid、规则管理器、CSV 或正则。

二级「扫码与工位设备」复用真实 COM 设备工作台和机械安全字段；只显示实时连接、不可直接冒充机械到位。二级「高级识别」将既有型号绑定、编码规则、编号登记三编辑器合并到内层 TabControl，不复制数据模型。独立「发布详情」保留批量试扫、冲突原因和 SHA/TEST 明细用于追查，不作为第一次使用的主路径。

**简单配置显式选择当前工程**：模式固定单型号，工程型号由已打开的保存工程读取；相同绑定幂等，若当前规则/多个绑定不一致，不得静默清除旧配置，提示人工走高级配置。专业用户仍可使用多型号三种身份来源，不可反向迁移或放宽校验。

**样例策略**：新规则不再预置假的正/反条码。真实 COM 试扫提供可见的原始样本，用户明确点击后作为正例；错误样例可由现场工程师提供，或明确标明系统生成拒绝用例，不得把示例值标为实测。发布静态校验与实体设备来源验证分别显示，互不冒充。

## 4. 必须保留的负路径

没有工程、工程未保存或型号无效、工程与绑定不一致、FLASH 未发布、TEST/DBC/波形冻结失败、规则无有效样例、扫码冲突/格式非法、已发布快照与草稿不同、扫码设备未绑定、USB/CAN 码率不符、夹具到位/实体 START/正式 RECORD 未接入：均明确显示状态，不自动默认成功。对工程的选定不可悄悄替换多型号产品绑定。正式生产仍 NO-GO。

## 6. 实施验收要点

- 首屏默认主路径不出现五个编码选择/空白工程路径表；窄窗口不遮挡发布。
- 真实扫码输入后停留在当前工作流、显示原始码和解析结果，不自动跳到隐藏的规则/详情页。
- 工程发布的内部两层冻结仍顺序执行；取消、工程 SHA 改变、规则无样例、错误映射必须中止后续发布，不可报告“已发布”。
- 原始 `SN001234/SN|BAD` 历史占位不得通过规则样例验收。
- 多型号/CSV/正则旧配置可在高级配置无损读取和显式修改。
- Windows Build/启动、真实 COM、发布重新打开验证、设备拔插及机械安全检查待用户现场执行；生产 START/Inspection/夹具仍未完成时准出 BLOCKED。


## 7. 方案达标后已提交 R1 的实际源码变化

- \`ProductionPreparationWindow.Guided.cs\`：新增固定单型号的引导式首页，保留显示当前工程/型号、真实扫码设备和原始码、解析编号与项目冻结校验、当前发布状态及尚未满足的真实工位门禁。扫码实测不会跳出当前页面，也不发任何 CAN、FLASH 或机械命令。
- \`ProductionPreparationWindow.Navigation.cs\`：默认显示 1「交付准备」，2「扫码与工位设备」复用原实体串口组件，3「高级识别配置」完整保留原产品绑定/多规则/CSV 编号表，4「发布详情与批量核验」保留原发布细节。旧的“五阶段配置表即主流程”不再作为第一眼的操作路径。
- \`ProductionPreparationWindow.xaml\`：窗口标题更新、旧夹具/START/互锁自由字符串入口收起到硬件工程师高级配置；文字明确指出输入来源文本不等于机械实际到位/实体 START。
- \`ProductionPreparationWindow.xaml.cs\`：现有真实扫码事件连接引导页；最新扫码不因历史预览列表满而被丢弃；扫码同时验证已绑定 USB PnP 设备身份，并在连接改变时废止旧证据；工程发布反馈以真实 bool 成功/取消而非旧状态字符串判断。
- \`ProductionIdentityContracts.cs\`：新规则不预填 \`SN001234/SN|BAD\` 虚构正反例。
- \`StationProductionConfigurationStore.cs\`：旧草稿仅保留上述两条默认例子时明确阻断发布。原始严格字段/规则冲突、SHA、固定工程/原生 FLASH 校验不放宽。
- \`MainWindowViewModel.Production.cs\`：已有工程发布流程保留二次确认、FLOATING FLASH 草稿保存、真实冻结和工程指纹检查，对 UI 明确返回 true/false，取消时不可执行第二层发布。
- \`ProductionIdentityConfigTests.cs\`：追加无预置样例、历史虚构样例阻断、真实格式样例和明确人工构造反例的静态回归合同。测试源码提交，但未执行。

### 正式生产准出仍保持 BLOCKED

\`TrustedPhysicalStartConnected=false\`、\`VerifiedInspectionWriterConnected=false\` 属于实际未接线缺口。机械闭合反馈/互锁不因字段填写变为“真实到位”。生产准备发布本身无实体操作，不得生成正式生产 PASS 或把工程验证统计成已交付产品。

### 现场 Windows 验收（待进行）

1. 本地 Codex **仅**拉取现有 R1、按仓库 Release 脚本编译并启动；不修改源码，不创建分支，不执行 CI。
2. 首屏显示当前工程自动识别的型号，不要求先编辑规则表；「使用当前工程」重复点击不抬高版本。
3. 已绑定真实 COM/PnP 扫描后显示原始编码及唯一编号；若工程/FLASH 未发布，显示「已解析编号」与「资源尚未发布」的区别。
4. 明确采用实扫作为正例、软件构造非法拒绝例；默认虚构历史样例被拒绝；手工输入仅作离线预览。
5. 主控或扫码设备断线重连、COM 变动、PnP 重绑定、关闭工程/切换已发布项目、修改工位草稿、取消发布、FLASH 冻结失败、扫码与发布工程不符等场景不得出现假成功或错误型号放行。
6. 成功发布后重开软件检查工程指纹、正式已发布工位映射和实际测试项目顺序；工程外部文件修改必须使发布校验失效。
7. 高级多型号、登记表、复杂编码形制及原发布详情仍能正常读取编辑；正式 Inspection/START 始终阻断直至独立硬件+记录闭环验收。
