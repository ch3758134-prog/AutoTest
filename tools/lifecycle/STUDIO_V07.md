# Engineering Workbench V0.7｜能力追踪、人工变更评估和验证证据（候选）

> 这是 PR #28 中的候选增量，尚未发布，不代替 AutoTest 正式 main 或已批准工程基线。

## 实际使用

在 Windows 独立 Git 工作树中按照 `STUDIO_V06.md` 启动本地工程工作台（默认数据文件在用户本地目录；不要将真实个人/设备测试数据提交公开仓库）。

1. **项目驾驶舱 → 产品能力追踪**：查看已审查语义关系可达的需求、架构、接口、详细设计、工作包和测试规格。缺口提示是核查线索，不是完成百分比。关联层级不限于 ECU 项目。
2. **任意能力/需求/设计对象 → 记录发现 / 变更**：填写实际现象、详情、证据引用、记录人。服务端以一个 SQLite 事务生成 OPEN change 和指向当前目标修订的 `impacts:CANDIDATE`，不会预先批准影响。
3. **决策与变更 → 逐项审查影响**：确认每条 `impacts` 关系，再对每个直接目标写下 `REVISE`、`NO_CHANGE` 或 `INVESTIGATE`，附具体理由和评估者。评估同时固定当时的目标修订。
4. **变更关闭**：所有直接影响关系必须已审查、全部存在有效评估，而且评估中的目标修订仍匹配当前修订，否则后端拒绝关闭。间接影响仍由影响链提示人工复核；关闭是完成影响审查，不代表已修订设计、代码交付或物理验证完成。
5. **测试对象 → 执行记录与证据审查**：选择单测、集成、实体台架或用户验收，填写真实观察结论、环境、配置、原始证据引用、实际执行人；软件单测与集成测试必须固定完整 Git SHA，纯硬件台架和用户验收可以不提供软件 SHA，但仍需准确记录版本身份。没有执行的测试不得登记为 PASS。
6. **证据人工审查**：独立确认或驳回证据引用。执行记录不允许覆盖，证据审查不可重复覆盖；修订测试规格不会擦掉旧版本的执行记录。
7. **产品能力 → 查看全部验证证据**：查看沿已审查追踪关系关联的测试规格及每条执行记录的版本、结果和审查状态；没有证据时显示未知，而不是自动判定 PASS。

## 项目管理 AI 的证据上下文

管理事实简报的 `verification_runs` 使用本地登记的测试运行记录（与 GitHub 手动同步快照是不同来源）。未人工审查的执行记录进入 `EVIDENCE_REVIEW` 提醒；经审查确认的 FAIL 进入 `CONFIRMED_TEST_FAILURE` 提醒。它们都是管理线索，不自动批准需求、不自动转换实施状态，不覆盖历史版本或原始证据。

管理 AI 可以据此提出针对特定测试规格的复测、技术研究、设计复核或缺陷处理建议；每项提议仍需负责人审查，并遵循设计和编码门禁。

## 工程计划与工作包队列（新增）

AI 项目管理页显示本地登记的 milestone 和 work_package；通过已审查的 depends 关系展示直接工程输入，附 CODE_READY 结果以及最近保存的真实 GitHub 执行快照。已经派发但被设计修订失效的任务优先作为 `REVALIDATE` 提醒；候审依赖、缺失设计、GitHub 未绑定、尚待负责人派发和已派发待核对分别展示。所有可见任务均可打开原始工作包与实施准入。

该视图不构造虚假完成率、不预测工期、不将对象标为已交付、不自动触发派发。里程碑日期仅来自负责人输入的 `meta.due`。它不是基于资源与关键路径的正式排期引擎；后续仍需依赖调度、版本冲突与实际完成证据的严格模型。

## 结构化项目归档恢复：空工作区专用

恢复工具：`tools/lifecycle/studio_restore.py`。严格采用先预检再应用，不允许覆盖已有项目。举例：

```powershell
# 从现有工程工作台导出得到 JSON 后，先预检（无写入）
py -3 tools/lifecycle/studio_restore.py --archive D:\\Backups\\engineering-project.json --data D:\\Recovery\\workspace.sqlite3

# 仅在已核对预检内容、确定目标是空工作区时执行
py -3 tools/lifecycle/studio_restore.py --archive D:\\Backups\\engineering-project.json --data D:\\Recovery\\workspace.sqlite3 --apply
```

本工具执行结构化对象/修订/关系/来源检查，使用 SQLite 事务写入；出错回滚。能够恢复已有工程对象、关系、历史修订、审查事件、技术研究、GitHub 任务快照、管理建议和验证证据元数据。

**当前恢复功能的边界：** 没有恢复外部原始日志、波形、PDF 或 Git 仓库；没有验证历史审批签名或 Git SHA 真实性；不会重连 GitHub，也不会实际恢复设备。不能将 JSON 导入成功冒充恢复了整个工程运行环境。空工作区首页已提供“从备份恢复项目”向导，先文件预检再显式确认；服务端再次校验空工作区及确认短语，避免绕过 UI 覆盖现役项目。正式用户发布前仍需 Windows 实测、外部原始文件完整性清单、自动备份以及端到端恢复演练。

## 重要限制

- `PASS` 只表示执行人填写的本次运行结果，`CONFIRMED` 表示人员审查了该条证据，不自动代表系统、产品或实物通过验收。原始证据只存路径/标识；工具没有验证引用文件的真实性或内容。
- 单机 owner token 仍不构成针对同一 Windows 用户不受信进程的强安全隔离。不要开放无人审查的 AI 自动写入、审批或合并。
- UI 不在本轮自动创建工程设计修订、自动授权编码、自动关闭真实故障；已经批准的工作包仍必须通过 CODE_READY 以及准确源码基线检查。
- 目前只实现本地工作区和版本化导出；尚无完整的备份导入/恢复、多个 AI 可靠调度、Windows 浏览器人工验收。
- 项目导出 `verification.runs` 和 `verification.reviews`，保留执行证据元数据及其审查记录。**导出 JSON 不是完整可恢复的工作区备份**，原始证据文件也不包含在 JSON 内。
- 旧项目中的 `change.meta.assessments` 若只有结论而无目标修订、审查理由，则不能作为新式关闭依据；须通过新的逐项评估页面重新审核。
- `INVESTIGATE` 是影响评估结论；即使变更评审关闭，技术问题本身仍可能未解决，应建立独立研究/实验任务跟踪，不能认为故障已经关闭。

## 文件责任

- `studio_change.py`：发现登记、逐项影响评估、固定目标修订；
- `studio_store.py`：变更关闭有效性校验、工程导出包含验证记录；
- `studio_verification.py`：不可覆盖的执行记录及单次人工证据审查；
- `studio_change_ui.js`：人工变更审查；
- `studio_verification_ui.js`：执行记录与审查；
- `studio_capability_ui.js`：能力级线索、缺口和版本化验证历史；
- `studio_server.py`：仅 owner 可变更的接口及 localhost 读取；
- `tests/test_studio_change.py`、`tests/test_studio_verification.py`：跨项目、修订冲突、原子事务、旧评估失效、证据审查与导出。

## 验收进展

本轮 CI 仅覆盖 Python 标准库单元测试及 Node.js 静态语法检查。正式使用前还需要：Windows 端真实打开与逐页操作；使用真实项目数据检验追踪语义；导出和恢复演练；现场证据采集完整性与权限隔离审查。
