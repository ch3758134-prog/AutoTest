# P0-04｜AutoTest 配置管理计划

> SAEF v2.0 / `P0-04` · **M2 修订候审，尚未替换本地 ACCEPTED 版本**。以本地已接受文档为父版本，旧哈希、审批记录及差异表见本包。

## 一、配置项及源资产

本项目的配置管理对象包括：① SAEF 版本、治理文档、工作产品及审批 JSON；② HOST 源码、项目文件、构建依赖；③ 主控与按键两块 PCB 的原理图及实物配置；④ 两套固件源工程、构建设置与烧录映像；⑤ DBC、HEX、测试资源、波形/日志、工位与线束配置；⑥ 测试证据和发布清单。不同层次单独标识，不以 PDF 代表实装、不以源码代表现场已烧录映像。

**当前四份原始 HW/FW 资产以 SAEF `engineering/control/assets.json` 为唯一身份索引**。其哈希已由 P0-01 归档核对；本文件不复制完整哈希表，也不宣称这些文件与实物一一同版。当前现役 PCB 为固定设计输入，主控/按键固件暂时冻结；发现硬件重大能力缺口或确需修改固件时走正式变更，而非本阶段自主改动。

## 二、版本与身份规则

- `P0-01` 等是**工作产品 ID**；`CI-<域>-<编号>` 作为新增配置项唯一 ID；`ADR-xxxx`、`ISS-xxxx`、`CHG-xxxx` 记录重大决策、问题、变更。批准后不得复用编号。
- 文档版本由内容字节 SHA-256、工作产品登记状态、审批 JSON 和（形成正式项目基线后）本地 Git commit 共同定位；大二进制通过资产清单中的路径、SHA-256 和可恢复的原件定位。
- 采用**现已存在的独立本地 Git 仓库**：当前上传快照在 `SAEF_ROOT/WORKSPACE/AutoTest`。仅追踪 `engineering/work-products/`、`engineering/control/` 的正式文本与必要索引，及其他批准纳管的轻量工程文本；不将整个 SAEF 工具包、派生 `site/`、`_operations/` 操作缓存、备份 ZIP 和大型资产直接作为默认跟踪对象。原始四项资产继续保留在 `engineering/assets/`，由 `assets.json` 的哈希、独立副本和备份保护。**实际 Git 仓库已存在；禁止重新 `git init` 或并入 HOST Git。**
- HOST 工程如另有本地 Git 仓库，应以具体 HEAD 和外部配置引用管理；当前并无其确切仓库/HEAD 证据，不擅自迁移或初始化 HOST 仓库。SAEF 自身的框架发行 ZIP / `FRAMEWORK_VERSION.json`、脚本版本也作为项目外部配置依赖记录。

## 三、状态/变更/批准

- 工作产品经过 `NOT_STARTED → DRAFT → IN_REVIEW → ACCEPTED`；退回、废弃等按 SAEF 工具状态机处理。`ACCEPTED` 不等于 Gate `PASS`。
- ChatGPT 提交完整工作产品、内容自审报告与增量 ZIP；项目负责人决定批准/退回；Codex 在明确指令下登记真实批准 JSON、运行 `check` 并回传证据。任何已接受工作产品的修改须按变更控制评估并有新的批准，不直接覆盖。
- 正式 P0 Gate 批准之前，应形成可识别 Git commit、全部 P0 工作产品 `ACCEPTED`、完整原始资产清单与恢复证据。**是否批准 Gate 仍由项目负责人作决定**；任何工具输出不会自动批准。

## 四、存储/备份/恢复

- 项目文档以 `WORKSPACE/AutoTest/engineering/` 下的 Markdown/JSON 为权威源，HTML 由 `TOOLS/sitegen.py` 生成，不手工修改作为正式资料。
- 日常操作前按风险备份；形成阶段基线前，应做 **Git 版本 + 独立保存的 HW/FW 原件 + 独立介质完整备份** 三重保护。现有 `BACKUPS` 位于本地 SAEF 根目录，不等于另一物理介质；必须另外复制一份到独立磁盘/介质或受控独立存储，记录位置与清单。
- 恢复验证不能只看 ZIP 校验成功：在新的隔离目录解压、运行 `py -3 TOOLS/eng.py check`、重新生成 `site` 并比较原件哈希；软件工程可构建性在获得真实源码和工具版本后单独验证，当前不能填写“已通过”。
- 不把构建缓存、现场隐私记录、大波形及历史备份误纳入 Git。涉及记录保密或个人数据按最小访问与离线保管处理。
