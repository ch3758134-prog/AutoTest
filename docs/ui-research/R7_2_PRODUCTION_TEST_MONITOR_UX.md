# AutoTest R7.2｜生产检测 UI：纵向工位流程＋始终可见的测试用例

## 问题与纠正

原 R7.1 将六个生产阶段横向铺满中央主工作区，而 TEST 有序用例树仅折叠成“3 个已启用”的数字，操作者无法看到当前测试用例及步骤，故无法回答“检测到哪里、在哪里失败、还剩什么”。这不满足 ECU 出厂检测的主要信息需求。

R7.2 把信息结构改为：**左侧纵向工位状态｜中央有序 TEST 用例及步骤监控｜右侧 ECU、烧录和工位状态**。生产界面不是 TEST 编辑器，展示只读运行范围和实际执行结果；编辑仍在工程师工作区进行。

## 页面与交互规则

1. **左侧工位流程（窄栏）**：扫码识别→夹具准备→等待实体启动→ECU 烧录→自动测试→结果归档。阶段实际状态必须由原生工位事件驱动，浏览器无设备时只显示“等待扫码”和未进入状态，不自动播放。
2. **中央测试用例（主区域）**：工程中的**全部用例按项目树顺序可见**，默认显示名称、序号、步骤数量、是否禁用及运行状态。正式生产仅执行 Enabled 用例，完全不参考工程师本次调试勾选集合。
3. **步骤细节（中央下半区）**：点击用例查看准备/测试/清理步骤和逐步状态；仅切换查看对象，不允许改变实际执行范围与顺序。实际运行时应自动定位当前用例及步骤，但操作员仍可查看历史步骤。
4. **右侧状态**：当前 ECU 识别及唯一编号、烧录进度、测试通过/失败/未执行计数、当前步骤、设备连接与夹具反馈、上一台结果。当前 HTML 缺少原生执行事件，不能构造进度和 PASS/FAIL；当前显示真实离线状态。
5. **故障/停止**：正式 WPF 里失败时应保持失败用例和步骤的完整原因、相关报文/UDS/波形证据入口，直到下一台开始；停止后显示清理/释放的实际结果及异常，不允许仅闪过一条 toast。
6. **生产与研发分离**：生产只读，不提供编辑器中的禁用、拖动、插入步骤等指令；修改程序需进入工程师工作区并受冻结版本规则约束。

## 真实数据合同（正式 WPF 阶段）

- 生产范围：当前有效型号工程 TEST 树，按稳定顺序选所有 `Enabled=true` 用例；启动时冻结用例 ID、修订、资源内容指纹。
- 设备/烧录：Scanner Frame→Barcode Parsed→工程/型号匹配→夹具控制请求/实测条件→实体 START→FLASH 阶段及 CAN 证据。
- TEST 执行：RunId/CaseOccurrenceId/StepOccurrenceId/Phase/SequenceIndex/Status/Start/End/FailureReason/EvidenceRef；逐次实际事件驱动界面，并严格区分未执行、执行中、通过、失败、跳过与取消。
- 记录：已完成与未完成的步骤及证据统一进入 Record/Report，重复扫码不产生虚假新增检测。
- 若工位尚无真实 USB/COM/按键/夹具/FLASH/TEST 数据，状态必须停留在未就绪，不可通过前端演示按钮制造生产 PASS。

## 浏览器设计验证

在 1536×900 浏览器窗口实测：六阶段纵向列、五个 HydEPB 用例同步可见，其中三个启用；默认展开“静态驻车”（7 步），点击“静态释放”切换为其五个准备/测试/清理步骤；无脚本异常。验收 HTML 不连接现场设备。此研究不等于 WPF/实物验收通过。
