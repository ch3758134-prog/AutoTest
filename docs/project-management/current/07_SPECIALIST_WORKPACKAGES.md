# AutoTest｜专项研究和研发交接任务（按新确认的产品方向）
**2026-11-21｜这是管理任务范围；不自动授权修改 main、固件或正式生产写入。**

## 1. SCAN × REPORT 联合产品研究（业务优先）
**目标**：参考成熟工业 EOL/ECU 检测系统，找到**最少操作、可复核、可统计**的生产方式，不再从“每一个编号都映射一套配方”出发。

**SCAN 主责**：
- 真实条码规则：型号字段+唯一编号；原始字符串、可选 CRC/规则、非法/歧义处理，真实扫码枪 USB 枚举、输入帧、重复/误扫行为。
- 当前工程已同型号无需弹窗；异型号查询本机工程索引、弹窗确认后切换；未知不猜；编辑/测试/烧录进行中扫码拒绝且不排队。
- 生产站点与夹具、等待实体启动键、按键停止的事件关系，实际设备能力只做需求/证据接口，不替 HW 编造协议。
- 批次/复检的业务场景和最短操作路径：一台 PASS、一台功能 FAIL、一台烧录 FAIL、同号再测、跨型号切换。
- 不因扫码再配置 TestProject/DBC/FlashPolicy，生产始终直接用型号工程的有效配置；已实现复杂 Recipe 的迁移/兼容另给定点源码差异报告。

**REPORT/RECORD 主责**：
- 明确完整 CAN 底本、TEST 关键结果提取、测试日志、简明单台报告、批量报告四层结构；给可查看的**固定示例格式**而非报表设计器。
- 精确定义扫码次数、检测尝试次数、不同实体 ECU 数、PASS/FAIL/STOP、首次/最终合格、复检及出厂放行（后几项均属候审业务政策）。
- 设计每次必烧录对应的 FlashAttempt→TEST CaseAttempt→Inspection→报告证据关联，失败/数据不全也有记录。
- 用真实或可标注为“示意”的多次运行数据演算统计，并注明数据是否真实，提出负责人需要决定的少数政策问题。

**跨专业验收材料**：扫描枪真实输入/工程查找/屏幕状态，单台 PASS/失败/重复编号四类日志证据、单台报告样稿、批量报告草案、来源及 QA 缺口；研究中的数据政策保持 `PROPOSED`。

## 2. FLASH/UDS × PROJECT
- 从 CanTool **真实 XML 每一个实际使用的配置项**追踪到强类型原生编辑字段、限制、内存区域、APP/BOOT CAN ID、诊断会话、安全访问、超时及算法；哪些 ECU 私有行为不可通用，明确说明。
- 生产配置从当前型号工程固定保存的**一份** Profile 与**一份当前固件**得到，而不是每台扫码触发 XML/HEX 选择、或从外部目录扫描最新文件。固定物理路径/原生 Schema/历史项目迁移待工程师评审。
- 独立 Flash 工具无工程可用，可以使用临时参数和手动选择资源；如使用工程资源须显式清楚、不能静默修改生产正式配置。共享经过验证的 ISO-TP/UDS/CanTool 后端。
- 在**生产站点前置阶段**调度烧录，成功才交同一 TEST 后端；每次完整检测必烧、复检不免烧。迁移 TEST Flash 步骤代码时不丢已有成功参考日志、FlashJob SHA 和权限限制。
- 研究停止键/USB 断线/烧录擦除中的不确定状态如何恢复，避免无证据“马上释放夹具/安全停止”的虚假承诺。软件实际版本 DID 无依据不得猜。

## 3. PROJECT × TEST
- 工程唯一型号与有效资源模型；分类目录/实际可执行用例树；树的有序展开+Enabled；开发选中范围独立；公共流程继续共用 DSL。
- 默认模板复制给新工程且可编辑，模板管理入口低可见；工程自动保存全入口、可恢复非法草稿、工程切换/异常退出恢复，运行计划冻结。
- TEST 已有 Prepare/Test/Cleanup/IF/ELSE/When/Switch/Loop/异常/子程序/公共流程的真实 Capability 清单；不可运行的步骤不出现虚假承诺。
- 失败后是否继续、诊断、保留数据/可编辑清理，由 TEST 控制流决定；底层 STOP/Flash/设备未知态必须遵守不可绕过条件。
- TEST 在步骤中可配置哪些测量/信号/判据需要**提取为关键记录**；数据事实交 RECORD，日志/报告版式由产品固定实现。

## 4. UI / 工具 / DEVICE
- UI：白底 Fluent、一套统一控件/自动保存/窗口生命周期；工程师与独立生产工作区；正常批量生产无需鼠标，显示当前编号/工位/烧录/TEST/结果/失败和上一台结果。
- 工具：手动台架 CAN 原始数据为主、DBC 可选辅助、单次/多周期报文/KEY 按钮；DBC 连续编辑；UDS 序列工具；波形多曲线/参考采集；独立烧录阶段进度/CAN。各工具**无工程亦可打开**，是否使用工程资源逐工具判断。
- DEVICE/主控 FW：检查实体启动/停止键的原理图/实际 IO/USB 上报是否存在，夹具真实压紧与释放的可观测性、按键防抖、STOP 时实际响应；不能凭 UI 模拟实现当真机。
- 具体设备同时争用：允许不同窗口打开观察，但物理写入由真实单设备会话/所有权协调，不从资源概念推出工具必须关闭。
- 用户不应承担研发每个基础 UI BUG 的发现责任；代码审查、Windows 构建、全任务流回归先于集中真机验收。

## 5. WAVE × TEST × RECORD
- 单独波形工具多 DBC 信号真实采集/时间序列绘制，建立参考并审核其真实来源/质量；引用工程参考给 TEST 自动判定。
- 对离散 ECU 状态阶跃、自动时间平移掩盖超时、主机到达时间不代表 ECU 事件时间等问题建立负向测试。先查现有 WAVE 证据类型与 RECORD Validate 合同差异。
- 真实 PASS/FAIL/INCONCLUSIVE/ERROR、附件 SHA/采集 ID/StepOccurrence/报告有证据链，不能以模拟回放替代真实 ECU 验收。
- 高采样率示波器/额外 ADC 等物理能力不能凭用户要求臆造，先核对设备硬件。

## 6. 项目管理如何分配与接收
每一任务交接至少包含：**最新用户已确认产品合同→准确 R1/专业分支 SHA→待处理真实调用/文件→需保留资产→候审设计点→测试范围和证据→仍待负责人决定的问题**。专项输出研究不是自动批准整个接口；源码提交不等于可用；不可为了“全面”增加多套调度、配方或记录引擎。

**优先顺序**：稳定已有 TEST/Flash/RECORD 真运行与 Windows 构建，同时研究 SCAN+REPORT 产品政策、实体按键与夹具；待接口明确才将生产流程增量接入 R1。**这只是技术依赖安排，不擅自宣布 R1 版本必须完整生产闭环才能验收。**
