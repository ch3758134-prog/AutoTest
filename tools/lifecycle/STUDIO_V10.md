# Engineering Workbench V1.0｜语义优先的工程管理（待审查候选）

> 此版本在 `management/evolutionary-lifecycle-pilot-20261109` Draft PR 开发，**不是** AutoTest 正式产品定义或 main 的授权变更。没有直接改用户本地 Windows SQLite；先备份当前工作区、在副本验证，再考虑升级。

## 1. 为什么改变 V0.9 的设计

用户在真实 AutoTest 讨论中指出：产品定义不应机械附带“R1 出厂检测重点”“EPB 首个验证对象”等阶段性背景。V0.9 的字段名称竟主动要求将“用户、场景、系统边界与约束”全塞进“完整定义”，治理层又把 `summary/body/version/variant` 一起当作同一类产品身份，迫使 AI 过度融合工程层次。增加禁词、字数、固定十项研究任务无法解决理解问题。

**改法：概念说明先于表单和门禁；为 AI 提供语义依据、边界、反例、关系与判断问题。** 人类可以质疑 AI 的归属判断，相关事实要保留到适当工程对象而不是删除。只对版本、权限、具体证据修订和执行授权使用确定性后端规则。

## 2. 已新增的工程语义手册

- 文件：`engineering_semantics.json`；解释 13 类互相关联的工程信息：产品身份、目标与价值、使用场景、系统边界、能力、需求、架构、详细设计、版本范围、配置、验证证据、工程判断、实施授权。
- 每个概念均说明 **是什么、为什么有用、不代替什么、应当问什么问题、正确与易混淆案例、与哪些对象有关**。
- 真实案例围绕 AutoTest 软硬件本体、EPB 首例、R1 优先级、20 Key 五路模拟电压、CAN 原始帧与判定、物理验收范围等展开。**示例不是已批准的产品事实或禁词表。**
- `studio_semantics.py` 提供版本和内容 SHA、按工作焦点选择相关概念，避免把所有工程历史每次都塞给 AI。
- 服务端只读 API：`GET /api/studio/semantics?focus=product_identity,system_boundary` 或 `?focus=all`。
- 项目管理上下文 `GET /api/studio/management/context?project=...` 自动携带关键语义说明、legacy project 字段语义拆分提示以及关于如何分解事实的工作原则。
- HTML 的研发管理与产品定义界面均可打开“工程概念说明与语义判断”，对同一事实在不同工程场景中的位置给出可质疑的解释。

## 3. 用户不需要自己给数据库填产品定义

项目管理 AI 可以继续通过已有受限接口提交候选，但建议携带 `semantic_notes`，交代：

1. 用户原话实际更正了什么，来自哪里？
2. 哪些属于产品根本身份、哪些属于目的、系统边界、阶段范围、配置、需求或验证？
3. 为什么这样判断？若替换 R1/EPB/具体板卡，产品身份是否仍成立？
4. 未放入定义的细节准备保存到哪些工程对象？哪些属于未知或争议？

`semantic_notes` 是对 AI 解释的**可见记录**，不是填写越多就自动正确，也不是强行限制字数。人类通过建议审查页看到这个推理摘要与完整候选；仍须亲自复核来源。AI 不能因提交说明获得批准权限。

## 4. 旧项目数据不强行迁移

当前 V0.9 `projects` 表存储 `summary/body/version/variant` 四列并共同计算发布指纹。V1.0 先**以只读语义投影区分**：

| 现有列 | 在 AI 理解中的作用 |
|---|---|
| `summary` | 产品身份候选，不自动视为已批准 |
| `body` | 旧项目背景及讨论上下文，不自动等于产品身份 |
| `version` | 项目/交付版本元数据 |
| `variant` | 产品变体/配置元数据 |

实际底层版本事务**尚未彻底拆为四种独立类型**。此处保留兼容是为了不损坏已经导入的项目与审批历史。正式归一化数据模型需要另外设计、迁移验证及人类批准，不应悄悄将原有内容重新分配为“已确认事实”。

HTML 产品定义申请页已改变误导性字段名称：明确区分“产品身份简洁候选”“原有项目背景和上下文”“版本元数据”“变体元数据”，并可随时查看语义说明。只是语义提示，不按字数或关键字决定是否准入。

## 5. 研究范围不再由固定十项报告决定

- V0.9 创建的十项领域现在成为**默认研究视角**；对一份产品定义修订，只有“定位变化是什么”先作为 `OPEN` 的起点，其余默认 `SUGGESTED`，不会使整个项目平白出现九项阻塞。
- AI 可以针对某个视角提交候选材料，但仅提交不会把它变成必须完成的研究。负责人确认需要该方向时，`activate` 将它纳入真正的研究范围；也可以直接增加项目特定的问题 `add-topic`。
- 对被纳入实际范围的研究，候选、来源、局限、人类复核和研究修订继续受原有审计约束。负责人还可带理由/依据将某方向判为本次不适用；不能由 AI 自行改变范围。旧研究结果重新打开时，其影响审查会过期。
- `gate_rows` 不再将所有内置 `SUGGESTED` 当作“未完成研究”，正式影响评估只检查本次实际研究范围。仍需逐个审查现存实施包；旧编码授权、版本锁定、物理安全要求没有因为概念改进而放宽。
- V1.0 控制策略 `product-definition-control/3`。旧审批历史保留；不把旧策略尚未完成的产品定义候选自动认定通过新语义审查。

## 6. 如何检验 AI 的理解，而不是检验字数

- `semantic_evaluation_cases.json` 提供 14 个真实工程语义测试场景，尤其覆盖 AutoTest 历次误判和反例。
- `studio_semantic_evaluation.py --template` 输出人工评估记录模板。将实际 AI 回答、文本证据、逐维 0–3 评分和具体理由填入后，`--review <file.json>` 汇总结果。
- 维度：用户意图与事实、概念归属、内容保全与关联、适用范围与不确定性、执行/审批边界。
- 测试程序仅检查案例定义和人工评审数据结构，**不会用 R1、EPB、CAN 或字数决定 AI 是否正确**。当前 GitHub CI 也不包含真实调用大模型并评分；不能把测试用例结构通过说成“AI 语义理解能力已经通过”。
- 测试案例和评分应随实际项目讨论持续演进。对争议案例保留不同可成立的解释与依据，不要求模型输出唯一一句话。

## 7. 验证与风险

- 通过单元测试和本地 HTTP API 验证语义规范可读取、AI 建议仍不可越权、研究范围可以缩减/增加且保留历史、旧工程档案可恢复。
- 仍需在 Windows 上真实操作页面并以 AutoTest 当前工作区副本验证迁移和使用体验。
- Python 服务的本地令牌不是可信 AI 进程身份；若拥有相同 Windows 用户的数据库访问权，仍可能绕开 API。
- 语义说明不会保证 AI 正确；必须靠真实工程讨论、证据核实、回归评估和用户持续纠正来提升。
- 本轮不修改 AutoTest 的产品定义正式基线，不把刚形成的 AutoTest 产品认知直接当作已批准定义。
