# AutoTest｜R0 真实 UDS 只读诊断与 Flash 分层授权：代码级设计候选 v0.1

基于 GitHub `main@f701902325994802b896dafecffb5cfe81679875` 代码核对。本设计以**尽早实现真实可观察的 UDS 读取**为目标，同时保证 Flash 后续真实刷写不会绕过既有保护。未获审批前不修改通信源码或打开物理输出。

## A. 已证实的结构缺口

1. `HardwareBenchController.ConnectAsync()` 创建 `new CanFrameHub()`，注释明确“no physical Tx delegate”；所以 `ICanFrameHub.TransmitAsync()` 当前必定返回 `NO_TRANSMITTER`。仅把 UDS 页面 `Physical` 设为可选不能真正发送诊断请求。
2. `CanHubIsoTpLink.SendAsync()` 使用 `ICanFrameHub.TransmitAsync(new CanTxRequest(...),_lease,ct)`。接收 Pump 已按 `ResponseCanId`、`SessionGeneration`、`LostFrames` 过滤；底层能表达真实接收数据，但尚未拥有受限物理发送来源。
3. `UdsClient.RequestAsync()` 只允许非 Mock 通过 `UdsRiskLevel.ReadOnly` 服务；`UdsServiceCatalog` 将 SID 0x19/0x22/0x23/0x24 等归为 ReadOnly，将 0x10/0x3E 等归为 DiagnosticStateChange，将 0x27/0x34/0x36/0x37 等归为 Programming；该既有防线必须保留。
4. `CanHubIsoTpLink.SendAsync()` 当前每帧 `Guid.NewGuid()`，与外层 `UdsRequest.CorrelationId` 没有贯通；`UdsTrace` 记录 PDU，但没有直接联动 CAN 原始 FF/CF/FC 和 USB 事务。因此“能看到正响应”不等于“具备可追溯的现场诊断工具”。
5. `HardwareCanReceiveBridge` 把 USB 0x41 以 `HostArrivalOnly` 时间质量转换到 `CanObservation`，不能假称 ECU 自身采样时间。
6. `ProgrammingJobCoordinator` / `ProgrammingPreflight` / `FlashToolViewModel` 为 Mock-only，这是实体编程安全边界，必须通过单独实现/授权方案扩展，不能原地删除检查。

## B. R0-UDS-READ 的端到端调用链（目标）

`UdsToolView` → `UdsToolViewModel` → 受限物理只读会话入口 → 已有 `UdsClient` → 已有 `IsoTpConversation` → 已有 `CanHubIsoTpLink` → **DEVICE 专用受限 Tx/Rx 适配** → 主控板 USB/CAN → DUT ECU。

说明：图中“DEVICE 专用受限 Tx/Rx 适配”属于**待实现**。现有 `HardwareBenchController` 的接收 Hub 不得直接被改造成任意工具都能通过的物理 CAN Tx 通道。

### 首选接口设计原则

在 DEVICE/INTEGRATION 之间建立一个权限收敛的“Diagnostic ReadOnly Session”边界：打开时固定 DeviceIdentity、SessionGeneration、BusRole.DutCan、请求/响应 CAN ID、允许的 UDS SID 与最大 PDU 字节数；每次请求先通过 UDS 服务风险白名单，再进行 ISO-TP 分帧；单次请求对 CAN Tx 使用短租约和受控生命周期，取消/断开/丢帧立即失效。外部专业页面不得取得可以绕过 SID 风险校验的裸物理 Tx delegate。

**建议提交审查的 C# 接口（非现有接口、不作为未经批准的正式 Contracts）：**

~~~csharp
public sealed record ReadOnlyDiagnosticSessionSpec(
    string StationIdentity,
    long ExpectedSessionGeneration,
    UdsEndpointProfile Endpoint,
    IReadOnlySet<byte> AllowedReadOnlySids,
    TimeSpan MaxRequestDuration);

public interface IReadOnlyPhysicalUdsSession : IAsyncDisposable
{
    ValueTask<UdsExchangeResult> RequestAsync(
        UdsRequest request, CancellationToken cancellationToken);
    IAsyncEnumerable<DiagnosticEvent> ObserveAsync(
        CancellationToken cancellationToken);
}
~~~

`DiagnosticEvent` 应优先适配既有 `UdsTraceEntry`、`HardwareCanTrace` 和 OperationAudit，不允许未核对公共模型便扩成第三套全局 Evidence 类型。设计获批后由 INTEGRATION 确定对外合同；DEVICE 拥有实际物理 Tx 策略/设备传输实现；UDS 拥有请求合法性和服务语义；UI 只调用 Session，不接触 USB Tx。

### 最小放行条件

- 当前 ECU/Station 身份已确认、Generation 没变化、CAN Role 固定为 DUT、请求 ID/Rx ID 经过 Profile 校验；
- 限制起步 SID 到需要实测的非写入服务（首先 0x22，后续 0x19）；不能通过修改 `UdsServiceCatalog` 风险等级扩大权限；
- 原始物理 USB/CAN 发送所调用的命令、帧格式与固件现役源码一致，经 DEVICE 的受控软件/台架验证；
- Tx 权限不是永久开关；按请求/会话发放、到期失效；无日志/Trace 损失或连接变化即拒绝继续；
- 保存完整 Tx/Rx、PDU/ISO-TP 帧级、NRC/Timeout、错误与单调时间信息；连接丢失结果是 `Uncertain` 或明确失败，而非“成功”；
- 用户执行真实读取并获得足够原始记录之前，状态最多为 `READY_FOR_PHYSICAL_READONLY_LAB`，不能直接标“真实诊断通过”。

### 有效的逐层自动测试

1. SID 0x22/0x19 的批准请求通过 Mock guard；0x10/0x11/0x27/0x2E/0x31/0x34/0x36/0x37 被物理会话拒绝，且**没有实际 CAN 帧发送**。
2. 不匹配 Station/Generation/Bus Role/TxId/RxId 的请求被拒绝。
3. 单帧与多帧（FC/CF/序号/块间隔）在伪 CAN Tx/Rx 适配上回放可观察。
4. NRC 0x78 → P2*，有限待响应次数；错误 SID / 错 CF 序号 / FC Overflow / 无响应 / 断线 / 租约过期，结果与日志一致。
5. 取消请求后无后台重试和无隐式恢复写入；导出文件包含原始证据且不能被误认为 Mock。
6. UI 展示同一 CorrelationId 下的请求、PDU、原始帧及错误；页面关闭不会把旧设备事件投到新会话。

## C. UDS Console 真实测试所需的操作界面

保留 `UdsToolView` 既有布局能力，补齐：Target Profile（ECU ID、Tx/Rx ID、Normal 11/29-bit、P2/P2*）与当前 SessionGeneration；Service Catalog 与用户模板；Hex Request/Decode Response 双窗；按耗时组织的请求时间线；帧级 Trace（CAN ID、DLC、方向、数据、STmin/FC/CF 编号）；NRC/状态/超时可见；“复制全部”“导出诊断包”“错误定位”。

Mock、Replay、Physical 的工具状态不能混用。若物理入口尚未具备，Physical 操作明确呈现“发送通路未配置/未授权”，**不允许按钮点击后显示成功 Toast**。

用户进行真实单次读取后，提供 Trace 和屏幕反馈，UDS 专业对话据此优化服务参数、响应解码与 UI；共享 ISO-TP 只在独立复现证明有核心 Bug 后，由 UDS 核心维护角色受控修改。Flash 失败不能作为 UDS 核心修改的充分证据。

## D. Flash 真实刷写必须采用与通用诊断分开的写入能力

Flash 当前 Mock Job 与 Profile/Preflight/Evidence 是复用基础。物理编程应新增 **明确受控的 Programming Session**，不是“改写 UDS 只读会话白名单”或“把全局 `ICanFrameHub` 的所有请求都打开”。

建议单独设计并逐项审查：ECU/Bootloader 设备与版本识别；镜像哈希、地址范围与 ECU Profile 对应；供电及工装前提；明确的程序级操作授权；可审计的 Key/Seed 提供者（禁止硬编码或随意日志导出）；按真实 ECU 支持情况确定会话/下载/传输/校验/重启/回读；中断、断电、NRC、未确认写入的 `Uncertain` 和恢复指导。

**重要真实代码冲突**：`UdsClient` 非 Mock 的风险判断会拒绝所有 Programming 类 SID；物理烧录不能仅靠 Flash 分支新增 Workflow 就打通。需要建立单独的 UDS/DEVICE/FLASH 联合合同，或受授权的专门编程传输路径，批准后由**UDS 核心责任人**完成有测试覆盖的风险权限调整；FLASH 分支不得直接修改 `UdsClient.cs`、`IsoTpConversation.cs` 或 Device CAN 核心。

### Flash 实测研究的四类证据

- 成功路径：各阶段原始 ECU 响应、TransferData 字节/块数、校验/版本回读、写后状态；
- 兼容路径：镜像类型、地址映射、Bootloader/Session/Security 可用性与分段长度；
- 错误路径：NRC、超时、连接中断、请求取消、部分写入、恢复是否需要重新编程；
- 运行资料：JobId、Operation/CorrelationId、镜像 Hash、Profile Revision、来源、操作者明确确认（脱敏）。

真正的烧录成功必须由用户在目标 ECU 实测确认，不能通过模拟进度、作业结束状态或单个正响应推断。

## E. 责任人与首轮产出

**DEVICE：** 审核固件可用 CAN Tx 命令与物理白名单，完成受限请求传输的设计、拟修改文件列表、模拟 Tx/Rx 测试；不碰 UDS Console/Flash Job。
**UDS：** 补全 Console 的 Trace/响应/日志和只读请求合法性测试；要求设备实际 Tx 的问题只提 DEVICE/INTEGRATION 请求。
**FLASH：** 做完整 Mirror/Preflight/Mock Job/异常恢复 UI 与日志；真实写入单独提交证据和授权设计，不能先改 UDS 核心。
**INTEGRATION：** 将一次用户诊断操作贯通 UI→UDS→ISO-TP→DEVICE→日志；明确真实会话唯一所有者、生命周期和 DI 注册；冻结共享 Tx 风险边界。
**主对话：** 审查以上修改范围、批准代码级合同后统一分发精准修改指令和联合测试。
**Codex：** 只机械复制、Build/Test、回传完整错误和日志；不自主定位修复。
**用户：** 单独掌握现场试验、具体 ECU 行为判定和专业 UI 体验审批；其他软件开发不等待你的现场反馈。

## F. 此设计的未决项（不得伪装为事实）

现役固件对真实 CAN Tx 的 USB 命令、帧结构、时间边界和安全白名单尚未在本文件核对；目标 ECU 实际支持的服务、ECU/Bootloader 地址策略、Seed/Key 来源、供电/编程前提、重启后版本回读等，必须结合真实设备资料和专项试验形成确定设计。未关闭时不得把 Physical Flash 标记为 READY。
