# 01｜产品定义与决策模型（恢复候选）

## 产品是什么
AutoTest 是一套离线 Windows ECU 通用研发、集成测试与生产检测环境。现役系统是 PC、主控板、按键板、两套固件、夹具、外部电源、扫码枪、ECU DUT、工程资源和测试记录。首个样本 EPB 不是平台硬编码目标。当前单 PC 单 DUT。

核心目标：让工程师能配置工程/DBC、连接/观察 CAN、调试 UDS、配置并受控实测 Flash、操作真实台架、采集/比较波形、编辑/执行测试程序，并通过本地记录复现问题。生产用途在同一个核心上组合扫码身份、型号/版本匹配、必要烧录、自动测试、结果与报告。

## 什么是明确的，什么尚未明确
| 事项 | 当前地位 | 后续如何收敛 |
|---|---|---|
| 通用 ECU 与 Windows 离线 / 单工位 | 明确的系统边界 | 用不同 Profile 和工程验证 |
| USB/双 CAN/IGN/夹具/按键角色 | 已有设计/部分现场证据 | 按实际设备逐能力验收，不扩大 ACK 结论 |
| 同一套设备会话/工程/运行与记录核心 | 原 G2 架构约束，恢复时优先保留 | 与代码契约测试核对 |
| UI 信息架构与美术风格 | **待设计和操作验证** | 参考成熟 IDE + WPF 真实渲染/截图/交互验收 |
| 各页面最终布局/控件细节 | **待探索** | 组件/页面逐步批准，不以 Mock 页顶替 |
| 报告结构、字段、打印/导出样式 | **待使用和数据样例确定** | 先真实 Run 数据与报告样本，再定格式 |
| 扫码规则和生产步骤顺序 | 部分业务原则明确、细节待定 | 真实标签、异常和复测场景验证 |
| CAN Flash ECU 参数与 Bootloader | 必须依据实际 ECU/CanTool/安全条件 | 独立验证，禁止以模拟 Seed/Key 放行物理烧录 |
| R1 | **早期首次交付愿景/可调整范围**，不代表全功能已冻结 | 根据可用、实测和产品反馈选定最小可交付集合 |

## 决策等级
- `FACT`：有来源的硬件/源码/现场事实，含适用硬件版本和证据等级。
- `REQUIREMENT_CONFIRMED`：负责人明确提出的产品行为，含适用范围，不等于实现或用户验收。
- `DESIGN_BASELINE`：经过审查的公共架构/接口合同，可受控修订。
- `WORKING_HYPOTHESIS`：AI 方案、调研、Mock、HTML 参考、预计报告等，不可称“已定”。
- `EXPERIMENT`：具有输入、可操作环境、判据、证据的探索任务。
- `ACCEPTED_CAPABILITY`：在确切软件/设备配置上完成匹配的运行/实测验收。

新事实可以使旧决定失效；必须记录影响、替代方案与已验证事实，但不要求“整个 R1 设计完成后才能开发”。历史审批只证明当时批准的内容；不能把旧批准自动外推到新产品版本。

## 软件优先不动的基础
优先复核现有 main 的 Core、Contracts、Devices、Projects、Testing、Specialists、Records、Application 等核心代码；未经证据不要推翻稳定后端。UI 专项（尤其旧 R1 Shell）不列为已验收基线，不要求继承其实际布局。

## 完成的定义
每项能力分 `DEFINED / IMPLEMENTED / BUILD_PASS / LAB_READY / PHYSICAL_ACCEPTED / INTEGRATED / USER_ACCEPTED`，不存在“全部功能都计划好了，所以产品完成度高”的评分。未知和候选可以长期存在，只要有下一步探索方法。
