# 本地生命周期工作台｜首个可验收切片（候选设计 v0.1）

> 这是**管理工具的产品需求草案**，不是授权实现，不是另一轮 AutoTest 软件开发工作包。

## 1. 第一版为什么不做全功能

目标只验证一件事：**当代码/实测带来新事实时，能找到受影响的需求和架构，审查并形成新版本的实施依据**。如果这个闭环不成立，漂亮的主页、甘特图、任务树、AI 操作入口均没有实质价值。

## 2. 选择的最小架构（待批准）

- **Windows 本地优先**，浏览器访问 `localhost` 或本地桌面壳；单人使用，不需要多用户登录、云服务或 MySQL。
- 权威源仍是 Git 仓库中的 SAEF 工件、设计 Markdown、验证清单、Git SHA / PR；新工具先以**只读适配器**加载既有文件，输出索引和可视化报告。
- 候选变更、关系与新工作包可写到独立 `project-management/` 目录下的 JSON/YAML/Markdown。**不直接覆盖已批准的 SAEF 原始文件**，直到用显式受控修订流程完成。
- 元数据中记录 `source_path + git_commit + content_hash + object_id + revision`，避免跟随最新文件而失去版本一致性。
- 内存索引、简单关系图与按需生成的 HTML 报告即可满足首版；无需一开始选择复杂图数据库或全文搜索服务。
- 对象状态、关系解析、版本指纹、影响遍历与准入校验必须先有自动化测试，再接图形界面。

## 3. 核心画面（不是传统 Sprint）

1. **系统全貌**：按 L0～L6 和 HW/FW/HOST/工装分层浏览需求、架构、详细设计、代码/证据以及当前有效修订。
2. **变更闭环**：左侧显示 Finding/CR，中央显示受影响对象关系与审查结论，右侧显示决策、原始证据和批准版本；可做候选影响分析。
3. **实施准入**：按工作包展示设计依赖是否批准/仍有效、是否有悬而未决的阻断项、可改文件、源码 SHA、验证合同；一键生成 `implementation-context.md`。
4. **当前产品状态**：可以按功能查看 `需求状态 / 设计状态 / 实现状态 / 验证等级`，不能只用一个完成百分比。

## 4. 可检验功能测试（首版 Acceptance）

| ID | 场景 | 通过条件 |
|---|---|---|
| LM-01 | 读取现役 SAEF G1/G2/控制文件 | 识别已有历史批准与文件来源，不把正文“候审”覆盖结构化 Gate 状态 |
| LM-02 | 展示 `AT-SYS-011` | 显示需求原文、证据/阶段、相邻架构与当前审查缺口 |
| LM-03 | 登记 KEY_SIM 现场发现 | 创建新 Finding/CR，保留旧需求正文，不发生静默覆盖 |
| LM-04 | 变更影响传播 | 呈现潜在下游设计/工作包/验证，区分确有影响和待核实关系 |
| LM-05 | 负责人批准一个局部修订 | 新旧版本都可浏览，旧批准记录和审查证据不可丢失 |
| LM-06 | 检查工作包可编码性 | 未批准/依赖被替代的工作包标为 `NOT_READY / REVIEW_REQUIRED`，并给具体阻断原因 |
| LM-07 | 导出编码上下文 | 输出固定设计版本、约束、可改代码、风险、验证合同和未决项；没有“读最新设计并假定全部已验证”的行为 |
| LM-08 | Git pull 后刷新 | 只读索引识别本地 HEAD/内容修订变化，提示新对象或已变化的链接，不自动批准 |
| LM-09 | 与 AutoTest 正式库隔离 | 无覆盖 SAEF / main 产品源码 / 原始设备资产；可撤销试点生成数据 |

## 5. 分阶段完成方式

- **M0：模型验证**：使用 KEY_SIM 案例与现有需求/系统架构，确定对象、状态、关系及变更规则。成果是受审的本目录，不做新 UI。
- **M1：可运行的数据内核**：加载最小 SAEF 子集、关系校验、影响分析、版本辨别、工作包准入校验、命令行/HTML 报告；先为 LM-01～09 建测试。
- **M2：本地最小 UI**：系统全貌、变更闭环和实施准入三页，支持本地数据修改与 Git 同步，画面可被实际操作验证。
- **M3：并入 AutoTest 治理**：在 LM-01～09 真实通过后，选定当前应纳入的工作产品和变更，**明确批准受控迁移**；再扩展至版本计划、风险、真实测试追踪。

## 6. 什么情况下不应继续开发管理工具

- 如果只能画流程图，却无法确定当前有效的受控设计；
- 如果一轮变更不能准确识别需要复审的下游设计和工作包；
- 如果修改管理数据后破坏了 SAEF 既有批准历史；
- 如果生成的 AI 编码上下文仍混合旧设计、未批准建议与实际硬件已验收结论；
- 如果每次更新必须大量手工重复录入历史数据。

## 7. 本试点不接管的事

- 不改变现有 AutoTest 研发分支、PR、产品验证任务；
- 不要求重走全部 P0～G5，不重做已有效的批准工件；
- 不需要 ProjeQtOr、Jira、OpenPlan，也不追求完整替代它们的通用项目管理功能；
- 不自动让 AI 评审通过自己的产品/系统设计，也不执行实体硬件危险操作。

**下一次负责人需要批准的不是“选择哪个 AI 框架”，而是本试点的对象模型、变更控制原则与首个验收切片范围。**
