## 摘要

本报告刻意暂时脱离具体项目需求、旧版界面和现有代码，从一个更基础的问题出发：**一款现代化的、功能集成度高、专业复杂度高、需要长期使用的 PC 桌面软件，应怎样组织工作、信息与交互？**

对 ISO 人机交互系列、ISA-101 工业 HMI 体系、Microsoft Windows 设计指导、Nielsen Norman Group 复杂应用研究，以及 Siemens TIA Portal、Beckhoff TwinCAT 3、Autodesk Fusion、Adobe Photoshop、Microsoft Visual Studio、NI TestStand、ETAS INCA 等公开产品资料的对照研究显示：

> **现代化不是减少功能、增加留白或统一成卡片布局，而是在保留专业深度、准确性与操作安全性的前提下，让用户对当前工作拥有清楚认知、直接控制、连续上下文与可恢复的操作路径。**

进一步提出“六系统产品模型”：**工作空间、对象、命令、上下文、状态、恢复**。这些系统的组织应先于页面、面板、窗口和控件设计。工业工程软件不能简单套用传统 IDE、消费级仪表盘或过程控制 HMI 的一种形式；应允许不同类型的工作使用不同的呈现方式，但维持统一、可预期的交互语义。

本报告是**文献与产品公开资料研究**，尚不包含厂商软件的完整实机操作、现场用户观察、定量实验或具体项目验证。后续设计必须通过任务原型和真实用户操作验证，而不能把报告中的建议当作未经验证的结论直接冻结。

## 1. 研究目标、边界和方法

### 1.1 研究目标

1. 建立对“现代 PC 桌面软件”与“工业级专业软件”的可操作定义，而非仅按视觉风格定义。
2. 识别复杂软件在人机交互、对象组织、窗口管理、工作连续性和可信状态方面的共同规律。
3. 比较不同成熟产品的设计取舍，避免把产品功能清单直接翻译为导航菜单和页面。
4. 输出后续总体 UI 设计可使用的原则、反模式、评价维度与研究流程。

### 1.2 明确不包含

- 不对任何特定 AutoTest 页面、按钮位置、窗格比例或组件实施作出冻结决定。
- 不重新定义具体项目已有的领域模型、设备协议、执行器、工程文件格式或安全合同。
- 不宣称 ISO/ISA 对某一特定 Windows 工程软件的窗口数量、三栏布局、主题或控件类型作出了强制规定。
- 不把厂商文档中的产品功能介绍视为独立的效率实验或用户满意度实证。

### 1.3 证据分层

| 层次 | 资料类型 | 在本报告中的用途 | 限制 |
|---|---|---|---|
| A：规范/原则 | ISO 官方页面及公开摘要、ISA 官方介绍 | 建立人机交互及工业 HMI 的研究框架 | 部分标准全文受版权限制；不能臆测未公开条文 |
| B：厂商一手资料 | Microsoft、Siemens、NI、Autodesk、Adobe、ETAS、Beckhoff 官方文档 | 确认软件实际具有的视图、工作空间、窗口与功能机制 | 描述“是什么”，不证明“效果一定更好” |
| C：专业 UX 研究 | NN/g 复杂应用与启发式原则文章 | 辅助解释复杂度、用户控制、可见性与专家效率 | 属设计指导，不等同强制性标准 |
| D：本报告综合判断 | 跨产品的归纳与设计建议 | 形成原则、评价表与后续研究假设 | 需在目标产品中通过任务验证 |

## 2. 什么是“现代化”的 PC 桌面软件

### 2.1 它首先是持续工作的环境，而不只是页面集合

浏览器式页面导航适用于大量消费应用，但复杂桌面软件通常存在长期编辑、多个资源同时打开、工具与数据联动、持续观察、窗口并行、任务中断和恢复等需求。用户最关心的是能否**围绕正在处理的工作持续前进**，而不是每一步都导航至另一个页面。

因此评价软件总体结构，应首先询问：用户在处理什么工作？工作对象是什么？可执行什么命令？当前上下文怎样保持？操作结果从哪里来？异常之后如何恢复？之后才讨论究竟用一个页面、多个页签、独立窗口还是浮动面板。

### 2.2 “现代”不等于视觉极简

圆角、轻阴影、统一色彩、Fluent/WinUI 外观属于视觉表现。它们有助于辨识、层次和平台一致性，但**并不能代替操作模型**。对于专业软件，必要的数据密度、大表格、时间线、多轨图形、树结构和大量专业参数均可能是正确的设计。

正确目标不是“尽可能少显示东西”，而是**让当前任务最相关的信息和操作最容易使用，减少不相关内容对注意力的争夺**。[S04][S06]

### 2.3 现代化的可验证定义

本报告将现代专业 PC 软件定义为：

**在完整保留领域能力、数据正确性、安全与审计边界的条件下，以符合任务的工作空间、统一的对象/命令语义、连续的操作上下文、可信的状态反馈和稳定的错误恢复机制，支持用户高效而可控地完成复杂工作。**

这一表述是研究归纳，不是 ISO 或任何厂商的正式定义。

## 3. 标准、规范与研究原则对设计意味着什么

### 3.1 ISO 9241-110:2020：交互原则

ISO 9241-110:2020 讨论交互系统的设计原则。公开资料涉及任务适合性、自描述性、用户期望符合性、可控性、错误容忍/避免与恢复等方面。[S01] 它提醒设计者：**操作必须能支持任务，不应仅凭界面外观评价优劣**。

它没有要求复杂工业软件必须使用 IDE、固定三栏、属性面板或某种配色。因此“符合 ISO”不能作为任意具体布局的论据。

### 3.2 ISO 9241-210:2019：人本设计过程

ISO 9241-210:2019 关注交互系统生命周期中的人本设计活动。[S02] 对本研究尤其重要的是：理解真实使用环境、识别任务与用户需求、形成设计、持续评价与迭代。不能要求使用者先成为 UI 设计师，再通过答题来规定界面布局。

**注：** 截至编制日期，ISO 官方仍列示 ISO 9241-210:2019（第二版）；其他地区可能使用本地采用标准并带有不同年份。归档引用以 ISO 官方编号为准。

### 3.3 ISA-101：工业 HMI 的特殊价值及边界

ISA-101 系列聚焦制造业人机界面的生命周期、标准化和持续管理，强调减少操作错误、增强态势感知。[S03] 这对**真实过程状态、异常辨识、告警、操作反馈**具有参考价值。

但工业控制室 HMI 与工业工程编辑器不是同一种任务：前者更侧重监控、告警和受控操作，后者还需要高密度数据编辑、程序调试与复杂配置。**不能把面向过程监控的灰阶 HMI 画法或全部报警策略直接强加于每一个工程编辑页面。**

### 3.4 Windows 与复杂应用设计

Microsoft Windows 设计指导将导航、命令、布局、字体、窗口与响应式适配作为相关但不同的设计决策。它不提供“一种适用于全部桌面软件的导航”。[S04][S05]

NN/g 复杂应用研究强调逐步展示相关能力、支持专业用户、让错误能被识别和恢复、降低记忆负担，并避免将复杂能力藏得无法发现。[S06][S07]

**综合结论：** 要保持完整功能，但只在合适的对象和任务上下文中突出合适的操作；可发现性与专家效率必须同时考虑。

## 4. 成熟软件横向案例研究

以下内容基于厂商公开说明，判断侧重**设计机制与适用条件**，不把任何一种产品当作完美范本。

| 产品 | 已确认的产品机制 | 可以吸收的设计思想 | 不应照搬的部分 | 资料 |
|---|---|---|---|---|
| Siemens TIA Portal | Portal View 以任务导向组织，Project View 面向工程工作；工程视图可收展相邻区域 | 同一软件可兼具任务入口与工程深度 | 并非每个专业软件都需要庞大的双视图体系 | [S08][S09] |
| Beckhoff TwinCAT 3 | 工程环境与 Visual Studio 集成 | 复用成熟的编辑、文档、调试行为 | IDE 的整体形态未必适合操作员日常任务 | [S10] |
| Autodesk Fusion | 能力按工作目的划分 Workspaces，工作空间影响命令集合 | 任务不同则工作区组织不同 | CAD 画布并不是普遍中心 | [S11] |
| Adobe Photoshop | 文档、工具、面板、选区上下文命令共存；Contextual Task Bar 随内容变化 | 当前对象决定可用操作；减少长距离寻找命令 | 任意浮动面板过多会增加维护成本 | [S12][S13] |
| Microsoft Visual Studio | 文档窗口与工具窗口、浮动/停靠、保存/重置布局 | 保留专业用户的稳定工作环境 | 不应为每款小工具都建设完整的可停靠系统 | [S14] |
| NI TestStand | Sequence Editor 与 Operator Interface 面向不同工作目的，公用 TestStand API / 引擎 | 编辑与执行可以采用不同界面重点而不复制业务内核 | 不一定需要两个独立程序 | [S15] |
| ETAS INCA | Experiment Environment 集成测量、标定和各类仪表 | 高密度专业仪表与持续观察值得保留 | 不应将操作人员默认训练为熟悉全部测量术语 | [S16] |
| Vector CANoe（补充） | 同类工程测试软件提供环境配置与测试/分析能力 | 实时观察、配置、分析之间有信息联动需求 | 不能仅凭厂商功能清单推导最佳 UX | 本轮未单独核对官方具体操作页，留待后续补证 |

### 4.1 TIA Portal 的真正启示

它不是“工程树最好”，而是**任务导向与资源导向能够在同一产品内并存**。工程视图适合深入对象，任务视图适合了解和进入工作，二者不应互相阻碍。[S08][S09]

### 4.2 Fusion 与 Photoshop 的真正启示

工作空间会改变当前相关命令；上下文工具栏则跟随用户正在处理的内容。**不是所有功能都必须常驻，也不是所有命令都应躲进二级菜单**。[S11][S12]

### 4.3 TestStand 的真正启示

面向开发和面向执行的界面可以有不同的视觉与操作重心，但仍调用同一业务引擎与标准对象。**不同工作形态，不等于分裂业务模型**。[S15]

### 4.4 Visual Studio 与 INCA 的真正启示

面向长时间专业工作，应允许窗口/仪表布局适应任务、保存布局、恢复上下文，并容纳多个并行观察对象。过于强调单页干净、强制用户重复关闭/打开信息，也可能增加真实工作负担。[S14][S16]

## 5. 工业过程 HMI 与工业工程软件必须区别对待

| 维度 | 工业操作监控 / HMI | 工业工程开发、配置与测试软件 |
|---|---|---|
| 主要目的 | 监视过程、辨认异常、执行受控动作 | 设计、编辑、调试、执行、分析与维护 |
| 核心对象 | 当前工况、设备状态、告警、趋势 | 工程资源、程序、参数、测量、记录、工具 |
| 交互节奏 | 连续监控，异常时及时决策 | 长时间操作、反复修改、跨资源切换 |
| 正确性重点 | 态势感知、命令安全、真实反馈 | 编辑合法性、资源一致性、执行安全、结果追溯 |
| 视觉重点 | 重要异常辨识、工况清晰 | 操作密度、精确编辑、上下文与状态清晰 |

两者的共同底线是：**真实状态不可虚构，风险操作有明确边界，错误可以定位和恢复。** 但不应混淆用途，也不应强行让一个编辑器长得像控制室 HMI。[S03][S16]

## 6. 六系统产品模型：先于页面的设计结构

### 6.1 工作空间（Workspace System）

回答：“用户在哪里持续完成同类工作？”工作空间不一定是页面；它可以组合文档、工具栏、侧栏、图形、日志、结果与关联视图。首要原则是**为当前目标保留足够的工作面积**，而不是均分窗口。

### 6.2 对象体系（Object System）

回答：“用户正在处理什么实体？”每类对象的识别、选择、创建、编辑、删除、复制、引用与生命周期应清晰。用户不应被迫先理解软件内部的数据类、实现分层或协议对象。

### 6.3 命令体系（Command System）

回答：“对于当前对象，用户能做什么？”高频命令优先、危险命令分级、上下文命令贴近对象；菜单、工具栏、快捷键和右键都是同一命令的不同入口，不能含义冲突。

### 6.4 上下文体系（Context System）

回答：“切换任务时哪些内容必须保持？”包括当前文档、选择对象、筛选条件、编辑位置、视图布局、历史操作与后台任务。**避免切换就丢上下文、回头必须重新寻找。**

### 6.5 状态体系（State System）

回答：“系统实际发生了什么、目前能确认到哪一层？”把请求、处理中、成功/失败、未知与外部事实区分清楚。真正的运行/硬件结果须来自可信服务；界面层不得自行虚构 PASS、ACK 或测量结果。

### 6.6 恢复体系（Recovery System）

回答：“用户中断、输入错误、程序退出或设备异常后怎么办？”包括撤销重做、自动保存与持久化、关闭前处理、异常重启恢复、错误定位、取消、安全停机及可继续编辑。

六个系统不是一份具体的技术分层图；它们是**产品设计审查维度**，之后才映射到页面、窗口、组件和业务接口。

## 7. 十二条可归档的通用设计原则

| 编号 | 原则 | 具体含义 | 违反原则的典型表现 |
|---|---|---|---|
| P01 | 工作目标先于功能清单 | 围绕任务开始、进行和完成组织软件 | 将后端模块清单直接做成主导航 |
| P02 | 工作空间先于页面 | 优先支持持续工作和相关内容联动 | 每次处理一个字段都切新页面 |
| P03 | 当前对象优先 | 当前选中对象的主要动作就近可见 | 选中对象后还需寻找另一个隐藏编辑入口 |
| P04 | 完整专业能力与逐步呈现兼得 | 高级能力可发现、可操作，不干扰普通任务 | 要么满屏按钮，要么所有功能藏在深层菜单 |
| P05 | 一致的是规则，不是布局 | 相同操作语义跨工具一致，专业布局按任务区别 | 所有编辑器强制同一三栏模板 |
| P06 | 让操作可预测 | 左键、双击、右键、键盘行为一致并可解释 | 相同控件在不同窗口触发不同含义 |
| P07 | 直接编辑与即时反馈 | 高概率字段支持直达编辑；相关视图随对象更新 | 表格只读、需要反复打开“完整属性”才能修改 |
| P08 | 约束合法性而非限制自由 | 根据数据/物理规则阻止非法提交；不随意卡死浏览 | 未完成一个字段便禁止切换到其他对象 |
| P09 | 信息密度服从工作 | 高密度数据可以保留，但区分主次和状态 | 用巨型卡片占满空间或把字段挤成不可读 |
| P10 | 状态来自事实 | 区分界面状态、服务响应、设备动作与真实结果 | 点击按钮就显示物理动作成功或测试 PASS |
| P11 | 可恢复的长期工作 | 记住工程、文档、编辑位置、布局与可恢复的变更 | 退出、切换或错误后大量重复劳动 |
| P12 | 原型任务验证优先 | 原型必须允许实际完成任务，不只评审静态截图 | 仅凭“看着舒服”就宣布操作体验通过 |

以上是本报告提出的**产品设计建议**，不是标准条文的复制。每条应在特定项目下转换为可观察的验收行为。

## 8. 高风险反模式：以下现象应触发整体审查

1. **旧外观换新皮肤：** 改主题、圆角、间距，却保留强制跳转、复杂弹窗、只读表格等低效行为。
2. **数据结构驱动导航：** 用户必须顺着后端实体层级才能开始工作。
3. **强制先创建正式资源才能预览：** 把业务持久化前置条件错误地放到了功能探索入口。
4. **全产品共用三栏模具：** 不考虑波形画布、步骤编排、数据表和仪表监控需求。
5. **编辑入口碎片化：** 表格、属性、弹窗和右键分别拥有重叠且矛盾的编辑操作。
6. **过度确认：** 无风险局部编辑也要多次保存、应用、确认。
7. **过度自动化：** 用户不知道系统何时会修改资源、发送命令或覆盖选择。
8. **隐藏高级能力：** 为了界面“简洁”而导致专业用户无法快速找到主要操作。
9. **伪状态：** 缺少真实数据却填充假日志、假波形、假执行进度和假成功。
10. **任务切换破坏上下文：** 每次回到主窗口都需要重新选择当前对象。
11. **异常导致整体阻塞：** 单个非法字段或失效资源使无关工作不可继续。
12. **无法长时使用：** DPI、多屏、焦点、鼠标/键盘、窗口布局、性能和恢复没有系统测试。

这些反模式不是对某一产品代码的最终缺陷判定，而是指导后续问题发现的检查清单。

## 9. 不应教条化的设计选择

下述争论都不应以“现代化”作为唯一答案，应以任务观察和操作验证决定：

| 常见争论 | 研究结论 |
|---|---|
| IDE 还是仪表盘？ | 都只是形态。开发编辑可能借鉴 IDE，运行监控可能借鉴 HMI，不能整体一刀切 |
| 独立窗口还是主窗口页签？ | 看并行观察、任务切换、设备所有权和返回频率；两种都可能合理 |
| 表格直编还是右侧属性？ | 高频字段可就地编辑；全参数与复杂校验需可见但不必常驻所有空间 |
| 自动保存还是手动保存？ | 区分草稿、本地文档、正式工程资源及不可逆动作；需有确定保存状态 |
| 初学者界面还是专家界面？ | 不能简单二选一；在稳定结构上同时提供清晰发现与高效命令 |
| 统一所有模块还是个性化布局？ | 命令与状态语义统一，空间分配和专业控件因任务而异 |

## 10. 工业场景中的正确性、安全与交互边界

### 10.1 编辑正确性

字段输入类型、值域、跨字段约束、引用完整性与持久化完整性属于不同层次。可采用类型化输入、即时提示、整体校验和提交拦截，但不应为了保护正式数据，把用户锁在一个未完成字段中且无法浏览其他对象。

### 10.2 实体操作风险分级

本地可撤销编辑与真实设备写入、烧录、控制输出等操作的风险不同。后者的权限、所有权、准备状态、取消和失败恢复必须在业务合同中明确；UI 应忠实呈现，不得仅凭按钮禁用/启用自行决定安全性。

### 10.3 状态可信与证据链

设计上至少区分：用户发起、请求送达、设备 ACK、业务动作结束、外部物理事实、执行判定与报告归档。不是所有业务都需要逐层展示，但不得在视觉上合并成无法追溯的“已成功”。

### 10.4 长期与现场工作条件

需要核查分辨率与高 DPI、Windows 任务栏、单/多屏、鼠标键盘操作、断连恢复、较慢硬件响应、异步加载、日志大量增长及无障碍访问等；静态截图无法覆盖这些问题。[S04][S14]

## 11. 一套可以复用的 UI 设计与验证流程

### G-UX-0：研究立项与任务事实

确认用户类别、操作环境、工作目标、典型频率、主要对象、风险与长期工作条件。**不得直接拿现有模块列表作为 UX 需求**。

### G-UX-1：参考产品与设计原理

优先观察成熟产品完整操作过程而非宣传截图；建立“可迁移机制—适用条件—不能照搬项”的对照表。来源应有出版/版本信息。

### G-UX-2：概念模型与工作流

建立工作空间、对象、命令、上下文、状态、恢复模型。形成启动、创建、打开、选择、编辑、运行/操作、观察、保存、错误恢复等端到端典型任务路径。

### G-UX-3：可交互原型

必须可用真实鼠标和键盘执行有意义的操作；复杂工具至少有常用操作与错误状态。采用最小可验证任务，不能只在一张效果图上验收。

### G-UX-4：用户操作验证

观察首次使用、重复高频任务、误操作、切换任务、错误输入、窗口恢复、较小屏幕和连续使用。记录何处停顿、寻找、重复点击、上下文丢失或无法撤销。

### G-UX-5：设计基线及集成

用户批准后，版本化冻结视觉系统、交互规则、窗口组织、界面状态与专业接口边界。业务接线保持领域/设备合同，不得以旧版 UI 实现反向推翻已经认可的操作体验。

> **阶段间的原则：** 可以迭代和回退，但不能让后续 WPF 代码实现反过来决定之前未经审查的 UX 结构；任何偏差都应明确说明。

## 12. 提议采用的可用性验收评分表

**评分量表：** 0=不可完成，1=明显困难，2=可完成但成本高，3=顺畅，4=熟练操作高效。该量表为本报告建议，不是 ISO/ISA 官方评分。

| 维度 | 观察任务 | 评分 0–4 | 需要记录的证据 |
|---|---|---:|---|
| 入口可理解性 | 无先验培训识别首要任务入口 | 待测 | 是否犹豫、是否被强制完成无关步骤 |
| 任务连续性 | 从打开对象到完成主要操作 | 待测 | 中断次数、跳转次数、重找次数 |
| 编辑直达性 | 修改高频字段及复杂参数 | 待测 | 点击/窗口数、能否直接定位错误 |
| 状态可辨识性 | 判断当前操作是否完成及事实层级 | 待测 | 是否误判成功、UNKNOWN 是否清晰 |
| 错误恢复性 | 输入不完整、对象错误、程序关闭 | 待测 | 是否丢稿、是否阻塞无关操作 |
| 专家效率 | 重复执行常用任务 | 待测 | 快捷键、复制、批量和定位效率 |
| 窗口与焦点 | 多窗口切换、主从关闭 | 待测 | 错误焦点、遮挡、丢失工作窗口 |
| 长时舒适性 | 高密度使用、缩放与不同屏幕 | 待测 | 易读性、可调整性、视觉疲劳反馈 |
| 安全与可信 | 实体命令及异常观察 | 待测 | 命令/ACK/结果是否混淆 |
| 整体一致性 | 不同工作区执行相似操作 | 待测 | 相同操作语义是否可预期 |

**建议记录方式：** 每个任务要保存环境、前置状态、用户动作序列、关键截图、问题、严重程度、方案与复测结果。不要凭“UI 很漂亮”或“按钮都能点”代替体验验证。

## 13. 研究局限与后续补证任务

- **未实际完整操作** TIA Portal、TestStand、INCA、Photoshop、Fusion 等产品的最新版；案例来自公开手册/用户文档，因此不能推断它们在真实工位上的操作效率一定优于其他产品。
- **未开展目标用户现场观察**、长时间工业工程操作录像分析、眼动/绩效测量或 A/B 实验；不能将归纳观点标记为实测结论。
- **未覆盖完整的可访问性审查**，后续需结合 Windows Accessibility/Automation Peer、键盘焦点等专项扩展。
- **部分厂商产品具有特定行业复杂性**：只迁移机制，不移植模块数量、许可证设计、UI 历史遗留或不必要的复杂度。
- **未冻结任何具体产品 UI**。后续应用时仍需由专业领域负责人验证资源模型、安全约束及真实业务边界。

建议继续补证：工业工程软件真实操作录屏与官方交互手册、同任务跨产品对照、典型用户任务统计、原型可用性测试、错误/恢复流程与高 DPI 多窗口场景。此部分作为后续 UX 工作包，不应阻止本报告作为研究方法基准落档。

## 14. 研究结论与归档建议

### 14.1 核心结论

1. **首先设计工作，再设计页面。** 任务、对象和命令关系优先于导航树、按钮和面板。
2. **专业复杂性不能被简单删除，但能够被更好地组织。** 分层呈现与专家快捷操作应共存。
3. **统一设计语言不等于模板化布局。** 应统一行为与状态语义，允许不同工作区采用适合其目标的结构。
4. **工业级必须强调可信事实、正确性边界与恢复。** 普通可撤销编辑应高效，实体高风险命令应受正式业务约束。
5. **持续工作的上下文是桌面产品的重要价值。** 工程、文档、工具、布局、状态和历史应尽可能保留。
6. **真正的设计通过操作验证，而不只是视觉审查。** 静态截图和无业务交互的原型只能证明部分视觉效果。

### 14.2 归档口径

建议将本文归入 **“UI / UX 前置研究／全产品设计方法”**，而非 G4/G5 的具体实施规范。可作为后续设计审查时的原则和评分依据，但不能自动覆盖已批准的领域、安全、执行与工程文件合同。

**建议审批状态：** `RESEARCH_COMPLETED / METHOD_PROPOSED / PRODUCT_APPLICATION_PENDING / USER_APPROVAL_PENDING`。

若项目管理后续认可，可建立独立的“通用 UX 设计基准版本”，并派生针对具体项目的工作流、原型和正式设计；本文本身不代表这些工作已经完成。
