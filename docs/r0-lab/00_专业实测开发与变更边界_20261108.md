## 1. 立即采用的研发目标

R0 的首要结果不是完整 R1，也不是 Mock 单测计数，而是尽快交付 **可真实观察、可导出原始日志、可区分故障层级、可与用户共同迭代** 的专项 WPF 工具。软件设计、专项编码、自动测试、跨模块集成与用户实测可并行；不得要求全部模块或用户先完成一轮验收。

完整 R1 的 UI 总体目标已选定，专业页面细节先出可操作设计、按实测修订；不凭猜测将 ECU 特有响应、Bootloader 过程、波形物理质量参数写成最终事实。

研发版本分为：`R0-DIAG`（可测且可取证）、`R0-LAB`（真实验证和多轮反馈）、`R0-INT`（统一 HOST 联调），之后各能力独立收敛到 R1。它们是能力标签，不是整套软件串行 Gate。

## 5. 专业研发 UI 必须满足的诊断设计合同

每个工具必须具备：① 当前工程/DUT/Profile/Resource Revision；② Mock/Replay/Physical 显著来源标签；③ 连接/租约/会话/任务状态与有效性；④ 操作请求及真正接收/拒绝/执行的区分；⑤ Expected vs Actual 的分栏；⑥ 原始 Trace + 可读解码 + 时间序列；⑦ 错误码、NRC、失败阶段、超时与重试次数（实际发生才显示）；⑧ 数据完整性/掉帧/时钟质量；⑨ 复制、过滤、导出完整日志；⑩ 取消及不确定状态的明确反馈。

日志采用两层：**操作时间线**（人看得懂）与 **原始证据流**（能定位协议问题）。不能仅保存一段 Toast、只显示 PASS/FAIL 或只显示进度百分比。

推荐统一每条事件最小字段：`TimestampUtc`、`MonotonicOffset`（可用时）、`Source`、`StationId`、`SessionGeneration`、`BusRole`、`CorrelationId`、`JobId/RunId`（相关时）、`Layer`、`Direction`、`RawHex`（允许记录时）、`DecodedSummary`、`ErrorCode`、`TraceQuality`。先核对现有 `UdsTrace` / `ProgrammingEvidence` / `HardwareTraceRecorder` 的实际类型，**不许各专业重新定义正式全局日志模型**。

原始资料导出须标明版本、来源和脱敏策略；Seed/Key、个人身份信息及其他敏感凭据不得无条件明文导出或提交公开 Git。

### R0-UDS-READ-01：详细可操作 UI

页面按四块组织：左侧服务与用户模板（新建、复制、保存、版本），上部 ECU/Session/寻址/协议配置，中心请求 Builder 与响应解码（Byte Hex / DID / Positive/NRC / Timing），下部帧级 ISO-TP/CAN Trace + 过滤导出。
必须支持单次请求取消、排他锁冲突提示、会话过期、无响应/错 SID/NRC 0x78 等状态。先 Mock+Replay 软件验证；受控真实读取只在 DEVICE 提供明确安全 Tx 门禁、共享 CAN Link、连接世代检验和可导出 Trace 后联测。R0 读取候选不自动放开 0x10/0x27/0x2E/0x31/0x34/0x36/0x37 等改变状态的服务。

### R0-FLASH-DIAG-01：详细可操作 UI

页面包含镜像资产与分段表（范围/大小/校验），ECU 身份与匹配，Preflight 阻断项，作业生命周期（每阶段状态、字节、耗时），底部 UDS/Transport Trace 与失败恢复栏。进度必须来自 Job 实际阶段/已确认传输字节，不能用 UI 定时器伪造。取消/失败后的 ECU 状态用 `Uncertain` 等真实语义，不把 ACK 或块发送等同于刷写成功。与 UDS 核心的接口只读复用，绝不从 FLASH 分支调整核心 timeout/分帧以使作业表面通过。
真实 Flash 的独立设计审查应包含：ECU/Bootloader 真实支持列表、映像目标/地址合法性、供电与夹具前提、独立授权、Seed/Key 的受控密钥来源、逐阶段响应/验证、写后版本回读、失败恢复和安全停止；在用户提供可靠实测证据前保持待定，不伪称已完成。

### R0-WAVE-REPLAY-01：详细可操作 UI

信号树显示 DBC Revision 和单位，图区有可同步双游标/区域缩放/参考叠加，右区显示判定窗口、对齐策略、容差/缺样状态，下方保留原始 CAN/解码时间/错误。先验证真实磁盘 CAN 档案 + DBC + Wave，之后再接 Live 共享流；数据源质量不明时显示 `INCONCLUSIVE`，绝不画出看似真实但来自 Mock 的“物理曲线”。

### R0-BENCH-OBS-01：详细可操作 UI

控制器状态卡由工程资源生成，显示 Revision/Interaction/Mask/安全前提；操作历史拆分 Requested / TransportAccepted / PhysicalObserved / EcuFeedback。五路电压人工输入带仪表、时间、来源、工位状态；未实测则 `UNKNOWN`。控制器状态切换与夹具/IGN 这类物理副作用命令的授权不能由 UI 或 VM 自行放行。

## 6. 故障分类、升级和改代码条件

- P0 专业 UI/参数/显示/编辑：拥有该页面的分支直接修，配套 UI/VM 回归。
- P1 本专业业务流程或算法：该专业在自己代码范围修，配套单元/回放/故障注入测试。
- P2 共享 UDS / ISO-TP / CAN / Device：专业先提供可复现事件包：输入、目标、预期、实际、原始时间序列、错误位置/源码证据、最小回归测试。由主对话审查后分配 **唯一代码负责人** 修改共享层；其他专业不得抢改。
- P3 公共 Contracts / Prism / Repo 版本与资源：由 INTEGRATION 经主对话确认修改。
- P4 ECU/Bootloader/真实硬件行为未知：标记 `NEEDS_LAB_EVIDENCE`，不能凭猜测改核心、不能用加长超时或绕过校验“修复”。

用户与专业分支现场讨论后必须回传：`Specialist`、`FeatureId`、`BasedOnCommit`、`LabEvidence`、`Observed`、`DiagnosisConfidence`、`FilesProposed`、`SharedContractImpact`、`TestsRun`、`NeedsUserRetest`。主对话负责评估影响并接入总档案；不要求无关专业等待。

## 10. Git 与归档边界
