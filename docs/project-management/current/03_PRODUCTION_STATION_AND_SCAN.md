# AutoTest｜生产工位状态机、扫码与烧录前置业务合同
**2026-11-21｜业务目标已确认；硬件接口/现场安全状态待实测**

## 1. 用户目标：批量生产速度与少操作
出厂生产操作员面对**一个独立生产检测页面**。软件开机恢复上次工程；进入生产页面且设备/工位满足条件时立即待扫码，不要求点“创建工单”“开始批次”“开始扫码服务”“保存报告”。与工程师 TEST/工具工作区分离，但共用真实底层。

### 标准单台状态序列
```text
IDLE / WAIT_SCAN
  → 放置 ECU → SCAN_CAPTURED（输入原始完整编码）
  → MODEL_CHECK
       同型号 → 继续
       已知其它型号 → 提示确认切工程，自动载入其 DBC/TEST/固件/生产配置
       未知/冲突 → 显示原因，不做物理动作
  → CLAMP_REQUEST → CLAMP_READY（真实夹紧到位证明方式仍待研究）
  → WAIT_PHYSICAL_START（不执行 Flash）
  → 台架启动键有效输入 → STATION_PRECHECK → FLASH_RUNNING
  → FLASH_VERIFIED → TEST_RUNNING（按 TEST 树顺序全部已启用用例）
  → RECORD_FINALIZING → SAFE_FINISH/按工程配置收尾 → RELEASE_CLAMP
  → SHOW_RESULT + WAIT_SCAN（显示上一台结果直到下次有效扫描）
```
**当前主流程顺序是本轮较晚确认的“扫码后夹紧，等实体启动键，再烧录+测试”。** 更早“扫码后马上烧录”已被取代。按钮输入是否可通过主控固件安全上报、夹具能否确认真实到位尚无实物证据。

### 扫码行为
- 编码包含该 ECU 型号信息与唯一身份信息；格式/校验算法/USB 扫码枪类型/型号字段都在 SCAN 研究实测中，不能把可选 UT1 字符串形式写死为全部客户条码格式。
- 每次扫码校验完整输入与型号。当前工程匹配直接继续；另一已知型号查找工程、**仅跨型号切换时弹窗**；未知/歧义不得自动选择一份近似配置。
- 正式扫码是站点流程触发；合法后可进入夹具压紧阶段，**不是自动硬件安全授权**。完整烧录必须等物理启动键和必要预检条件成立。
- 检测进行中再扫：不接收新检测、不排队、不修改当前 ECU、不自动切工程。当前结果显示在下一有效扫码前保持。
- 同一实体编号可有多次 Run/Inspection；不覆盖历史、不重复统计为新 ECU。成功/失败后复检是否特殊提示，目前用户明确暂不细化。
- 无扫码/生产条件时**研发仍能**直接运行单步骤、用例、勾选范围。

## 2. 生产必烧录
每一次完整生产检测（含复检）**必须真实执行本次烧录**；无 NoFlash 生产模式，不因上一次成功、软件版本已匹配或重扫而跳过。FLASH 失败禁止 TEST 后续正式出厂运行；记录真实失败阶段和证据。本次 Flash 应视为生产状态机前置阶段，**不要求工程师把 Flash 插到 TEST 步骤树中**。

生产烧录配置集中于该 ECU 工程的生产配置工作区，与扫码型号配置在同一日常配置入口；当前固件唯一。原 CanTool XML 对应的参数在上位机**原生可视化编辑**、自动保存到工程固定位置；不强制导入 XML。固件 HEX/S19/BIN/必要安全算法是资源，不等于 XML 配置本身。

**独立烧录工具**拥有自己的操作参数，可无工程启动；它也可以主动使用工程的资源，但不强制复用生产配置或静默改变它。**真实 ISO-TP/UDS/CanTool 下载后端共用**。原生 Profile Schema、固定实际相对路径、原有数据迁移与设备独占合同，仍需 FLASH/PROJECT 技术审查。

## 3. 工位实体控制
| 现场控制 | 已确认方向 | 实际缺口 |
|---|---|---|
| 夹具 | 放 ECU 后扫码，核对成功自动发夹紧请求；完成检测按受控条件释放 | 目前主控 USB 可请求夹具1/2，但 GPIO 回读不证明机械到位；压紧传感器/安全条件未验证 |
| 启动键 | 压紧就绪后按实体键启动**整次烧录+TEST**，而非 UI 开始按钮 | 按键 IO/USB 上报、去抖、失联/重复触发、是否上电已按下、误触防范尚未确定 |
| 停止键 | 上位机必须能感知并终止后续操作，遵守 Flash 中断与设备收尾 | 输入通道、反应延迟、取消当前 UDS 命令、是否必须人为恢复待真机 |
| 断电键 | 实体硬件断电控制，HOST 不承担断电动作 | 真实供电与失联机械行为必须硬件明确，不能凭空假设 |
| 失败状态 | 在 TEST 中编辑失败后可继续/诊断/保持现场/清理动作，默认模板预填 | 是否保留 IGN/夹具等物理现场尚未确定，基本设备安全不受脚本配置取消 |

**不能为了满足“扫码就全自动”把未经审核的高风险 Flash 写入授权一律删去。** 需要 FLASH/DEVICE 专业提出可以在配置/设备就绪阶段完成的受控生产授权合同，避免每台 ECU 反复鼠标点击，同时保持每次真实目标/资源校验。R1 目前的单次 Consent 和 TEST Flash Step 迁移须明确测试，不能靠按钮 UI 冒充完成。

## 4. 检测结束与异常
- 结束后保留编号、PASS/FAIL/中止及失败原因，自动生成一次检测的记录/报告，回到待扫码状态；新有效扫码才覆盖当前结果画面。
- 扫码后夹具/按钮/烧录/TEST 中任何异常，都必须有可解释的阶段、实际证据及恢复操作；没有真实数据不发正式 PASS。
- TEST 普通失败时执行已编辑的 TEST 逻辑，底层只守住真实物理禁止条件；不能代码固定“FAIL 无条件释放夹具”或“FAIL 永远停工”。
- Flash 失败、操作员停止、设备断连时，如何中断/维持机械设备不能未经现场验证设定为立即释放。若系统无法证明处于安全待扫码状态，则不能假装已经清台。
- 自动保存不等于自动同意实体危险写入；执行开始时必须冻结当前实际运行配置和必要资源 SHA。

## 5. 生产配置的适度复杂度
生产配置集中扫码型号识别、原生 Flash 参数/当前固件、必要的工位参数与记录基础设置。**不叠加** ProductVariant→WorkOrder→BindingTable→ProductionRecipe→FlashPolicy→TestProject 的常规强制操作链；需求依据不充分时留为研究历史。工程内部可靠标识、SHA/修订、真正风险阻断可以保留，但不要变成每台 ECU 的人工配置步骤。

## 6. 生产实测和专项问题
真实扫码枪是 HID Keyboard、COM/CDC 还是 HID POS 未确定；原始输入与前后缀需实物捕获。型号唯一对应工程的索引/冲突防错需验证。实体按钮/夹紧真实到位/设备断线后的物理状态需 HW/FW/DEVICE 验证。复检、批次统计和批量报告的定义交 SCAN+REPORT 共同研究。完整生产阶段 **SOURCE_NOT_FIELD_VERIFIED**。
