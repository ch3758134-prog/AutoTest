## 3. 当前优先研究的业务链条

1. **真实链路**：WinUSB 主控→CAN0 按键板、CAN1 DUT→命令/回读/日志；供电、IGN、夹具、20 KeyMask 五路模拟电压需真实设备安全授权及验证。区分“USB 连接 PASS、CAN1 RX PASS”和其余输出/诊断未确认。
2. **产品工程与资源**：项目/控制器型号/DBC/信号/测试程序、版本和适用条件，以可回放的真实文件和实际设备配置审查。
3. **唯一自动测试程序**：扫码前置匹配→选择唯一测试方案→步骤编辑/调试→流程控制+专业工具动作→StepFact/Verdict；出厂执行是测试引擎的受控运行模式，不是另一种测试程序。
4. **专业工具与试验工作台**：独立 CAN/DBC、UDS、Flash、Wave、Bench 是试验和调试入口；不是在自动测试运行页面堆专业工具页签。真实设备基础能力先在 FieldStudio 验证，再按合同接入 R1。
5. **生产结果与报告**：真实运行与波形判定后处理身份匹配、复测规则、统计、不可篡改审计、报告；缺少实际执行证据不得标为交付。

## 4. 应形成的可判定工作卡（代替空泛模块百分比）

每卡固定：`用户价值/行为 → 当前冻结需求或问题 → 有效设计修订 → 当前候选 PR/HEAD → 证据层级（源码、CI、GUI、物理） → 当前阻塞 → 下一条可执行验收动作 → 责任角色 → 需要用户做的决策`。

首批核查卡（仅举具体节点，不自动创建或签发任务）：

- CAN1 真实 RX：用户基础观察记录已有；后续须查清该证据绑定的设备版本、当前可复现仓库 SHA、是否有 RAW 日志及工作台继承路径。
- 真实 CAN1 TX / UDS 只读：PR #26 与 Issue #17；当前最新 CI 只证明源码可构建，不证明 DUT 事务回应；明确受控只读服务、地址、响应与超时证据。
- 扫码枪：PR #26 采用 USB Serial COM，而旧输入定义强调键盘；查明实际扫码枪识别、COM 配置、成功读码原始 HEX；不要直接接受旧档案为现役设计。
- DBC→实时信号→Wave Verdict：区分文件解析通过、真实 CAN 时间戳、参考比较和实际判定。
- TEST 编辑/Debug：确认唯一引擎能否表达及运行全套动作，编辑操作与真实执行证据分开审查。
- Flash：先复核 CanTool 配置/ECU Profile/Bootloader/SeedKey 安全依赖，未批准不得将写入流程标为 ready。
- 正式 R1 UI：PR #27 编译候选；用户最新倾向浅色且自动测试为视觉主角。深色代码不能直接作为 UI 视觉最终基线。

## 5. 真正面向用户的 HTML 管理界面：信息架构建议

**视觉重心**应由左侧“对象类型目录”和右侧“大块对象元信息”转向：

1. **产品和决策概况（入口）**：顶部显示 R1 产品范围、实际生效版本、GitHub 最近核验时间及“待处理事实冲突”；中央优先显示产品业务链（从扫码/程序→实际测试→结果），其次是当前可执行研发线；第三层才是对象计数。
2. **研发推进（工作台）**：每条研发线横向清楚显示 main→候选 PR HEAD→CI→GUI→物理证据→集成审查；高优先阻塞及下一验收动作紧贴其所在行。历史 Closed PR 应折叠到“来源/继承”而非并排冒充进行中模块。
3. **评审与问题处理**：以“当前等待我决定什么”为中心，逐条打开有原始证据的争议与备选决策；审查通过后才可能生成设计修订，所有确认动作必须可撤销/留痕/按版本追踪。
4. **工程对象深钻（第二层）**：点击某个能力进入本能力的需求、设计、GitHub 版本、真实验证、受影响变更；元数据如 id/source_reference/import_mode 收到 Inspector，不在正文前占用半屏。
5. **操作与追踪**：真实使用必须包括搜索/过滤、当前版本对比、保存草稿、冲突提示、证据打开、按来源刷新、问题到任务的审核流程；“返回原处”保留筛选和定位，不要求用户每次从侧栏重新开始。
6. **浅色视觉结构**：以明亮中性背景、深色文本、有限强调色、清晰信息密度、固定上下文栏+列表/详情可调整宽度为起点。状态颜色仅表示明确的批准/警告/失败语义；不将文案重复成 10 个彩色徽章。关键操作常驻可见，次要历史/元数据折叠。
7. **AI 协作边界**：系统管理 AI 基于上述事实提出建议，人类可接受为规划但不会自动签发设计；受限编码 AI 只收到已经批准的软件详细设计、范围和验收条件；本地 Codex 只拉指定 SHA、Build/Test/启动收集日志。

### 目前 HTML 截图的具体使用问题

- 左侧单列菜单主要按数据类型分组，**不是用户的“盘查→判断→处理”自然路径**。
- 右侧需求对象占据最大视觉面积，已显示 `对象身份`、`当前状态`、`版本/修订` 和源属性，但用户最想先看的“为什么有问题/哪个 PR/是否实测/下一步”不在首屏。
- 面向单对象的按钮“编辑/增加关联/历史/发现/提交/批准”并列，很容易将批准动作放得与阅读动作同级。应区分阅读、提出修改和负责人裁决。
- “V0.6”版本显示与实际 V0.7 候选不一致（已有代码分支修正，但本地老工作树尚未同步）。
- 全部初始数据处于 DRAFT/CANDIDATE，导致默认能力追踪“已批准关系”视图可能显得空白；应在界面同时展示候选事实与已批准事实，但严禁混合展示为已确认。
