# Project Control V2｜项目研发管理工作台

这是**从项目管理目标重新设计的独立系统**。它不调用旧 Engineering Workbench 的 UI、对象存储、弹窗或业务路由。设计目标是让负责人在 **ChatGPT 网页端 + 专业对话 + GitHub + 本地 Codex** 的 Vibe Coding 工作方式下，有效管理项目目标、交付、计划、执行、风险、变更、工程阶段和审查。

## 功能

| 领域 | 实际功能 |
|---|---|
| 项目总览 | 当前研发状态、近期工作、计划来源、阶段信息及关键问题 |
| 目标与交付 | 锚定已批准 P0，维护交付目标、成功条件和范围候选 |
| 开发计划 | 工作分解结构、前后依赖、里程碑、进度层次、任务方向、优先级及计划日期依据；有日期才绘制甘特图 |
| 研发流程 | P0～G4 阶段要求与显式轮次、阶段审查决策，不从标题或对象数量推断 Gate |
| 进度及质量 | 实际进展与工作计划分开管理；报告完成必须引用证据，负责人独立核实 |
| 风险与变化 | 风险评估与处置、问题/变更、逐项影响判断、仅对受影响工作产生复核要求、计划新基线 |
| 审批与版本 | 计划送审、退回、批准不可覆盖的历史基线；修改批准计划另建修订 |
| AI 协作 | 人手动跨 ChatGPT 对话触发，通过准确 Git 仓库工作记录交接；无需 Agent 平台 |
| Codex 回执 | 本地命令真实执行的 Git HEAD、退出码、时长、原始日志 SHA-256 与人工核实 |
| GitHub 同步 | 标识本地未提交记录、当前 SHA；显式查询远端分支 HEAD，拒绝自动覆盖、合并和伪造同步 |

## 安装与启动

在**当前 GitHub 分支的完整仓库**中，使用 Python 3.11 或更高版本，无需安装第三方 Python 依赖：

```powershell
python tools/project-control-v2/server.py --port 8790
```

打开：`http://127.0.0.1:8790`。

本地启动终端会打印一次性负责人授权码。浏览与阅读不需要授权；首次修改计划、记录审批/问题/进度或核对远端时，页面要求输入本次运行授权码。该密钥不存 GitHub、不提供给其它 ChatGPT 对话。注意：它是本地 Web 请求的权限保护，**不是对同一个 Windows 用户下恶意进程的强操作系统隔离**。

该管理工作台使用仓库相对路径，不需要 ChatGPT 指定 Windows 盘符或新工作树。

## 数据与权威边界

- `tools/project-control-v2/sources/autotest_engineering.json`：从旧工程资料中明确摘取的**已批准 P0 和 G1 待审成果**，不自动导入旧系统几十个内部草稿。保留源头位置以便审计
- `tools/project-control-v2/process.json`：显示既定 P0～G4 研发流程及其要求；它不是私自更改的正式流程政策
- `tools/project-control-v2/workspace/autotest.json`：**Git 跟踪的项目管理记录**；包含当前候选计划、计划历史基线、任务执行状态、风险与变更、研发轮次、阶段决定、Codex 回执与审计记录
- 批准计划**不等于**批准 G1 需求、G2 设计、G4 编码或 Gate
- 本地写入**不等于** GitHub 已经收到；只有检查 Git diff、提交并推送后，其他 ChatGPT 对话才能读到这份共享事实
- GitHub `main` 是正式代码交付中心；本项目管理候选在 Draft PR 内试验，**不直接修改 main**，也不会覆盖既有 AutoTest 产品代码或审批档案

管理数据采用原子文件写入和乐观修订号。版本冲突直接拒绝，不能静默覆盖。活动历史与批准计划快照保留在管理记录中。

## 日常工作方式

1. 负责人在“目标与交付”检查当前版本范围；选择“开发计划”维护工作结构、日期依据、里程碑及风险。
2. 研究 AI 在 GitHub 中读取所需的正式依据、待审研究和具体工作，做实际分析；提交与任务相关的有效结论，不把每段聊天变成正式工程草稿。
3. 总协调 ChatGPT 分解并组织工作；根据当前项目记录与真实 GitHub 事实提出下一步建议。你在界面审查计划、阶段决定与重要变更。
4. 在“协作交接”复制明确工作说明到你选择的 ChatGPT 专业对话或本地 Codex；**你主动触发**，本系统不自动派发 Agent。
5. Codex 执行真实本地命令并形成回执；负责人可分别核实任务完成和工程交付/真实 ECU 验收。
6. 需要跨对话共享时，指示 Codex 核实 **Git 工作树差异和授权范围**，只把经你同意的管理记录与工程成果提交到 GitHub 候选分支，并创建或更新 Draft PR。**不自动 push、pull、reset、merge 或删除本地工作。**

### 本地 Codex 执行回执

在本地已核实的仓库运行实际测试等明确命令，例如：

```powershell
python tools/project-control-v2/run_task.py --work w-g1-review -- python -m unittest discover -s tools/project-control-v2/tests
```

此封装器**只负责记录一条你明确要求执行的命令**，不具有代码实施授权功能：

- 在 `tools/project-control-v2/local-logs/` 保存原始标准输出与错误输出；该目录受 `.gitignore` 排除
- 记录实际命令、退出码、起始/结束 Git HEAD、输出哈希、执行时间与回执编号到 Git 跟踪的管理记录
- 默认只发布原始日志哈希，不自动将完整本地日志、聊天、系统路径或秘密推送远端
- 回执状态始终先为 **UNVERIFIED**；经核对后才可标记已审查。**已审查回执不代表真实 ECU 物理验收**
- 对于需要提供完整错误日志的工作，可由你明确授权后人工挑选、脱敏、压缩和提交必要附件

若命令失败或超时，回执会记录对应退出状态，不会把任务自动标为通过。

### 管理计划、范围变化和螺旋迭代

- 工作按照交付目标组织，有研究、设计、编码、集成、验证与协调的不同性质
- 近期工作可以细化，未知远期任务可保留为规划包；没有日期依据则留空，不伪造甘特图
- 计划完成度、任务证据、正式工程文档批准、阶段 Gate 各自独立
- 事实纠正、需求变化、设计问题或代码缺陷首先经过范围判断；受影响的工作逐项评估，**不自动回滚全部项目**
- 新研发轮次可以明确触发原因和受影响范围，保留既有有效的正式基线
- 未经批准的 G1 可以作为研究参考，但不能冒充正式实施设计输入

## 验证

```powershell
python -m unittest discover -s tools/project-control-v2/tests -v
node --check tools/project-control-v2/app.js
node --check tools/project-control-v2/actions.js
```

本候选的自动测试覆盖真实 P0/G1 输入、项目范围锚点、计划修订/送审/批准、工作分解与依赖、证据充分性、审查授权、局部变更、风险、里程碑、研发轮次、Codex 回执及 HTTP 路由。它们不能代替 Windows 浏览器实际操作或真实 ECU 台架测试。

## 部署与同步限制

该版本为**单人本地可信环境**下工作的 Git-backed 管理系统：

- 不部署自动运行的多 Agent 编排、后台任务或远程托管管理服务
- 不擅自为你本地选择项目路径，不替你修改 Git 分支
- 不提供未经你授权的自动 Git 写入/推送
- 未获取 GitHub 最新证据时诚实标记远端状态未知
- 对话上下文与 Codex 全量日志不自动持久化；跨对话共享依靠受控的管理文件、真实任务和 PR
- 完整企业多用户 RBAC、分布式写入合并和正式合规认证不在当前单人工具适用范围，不能伪称已实现

这份边界是按 ChatGPT 网页端 + GitHub + 人主动触发 Codex 的真实工作方式确定的；以后扩展多用户时需重新审查存储及身份机制。
